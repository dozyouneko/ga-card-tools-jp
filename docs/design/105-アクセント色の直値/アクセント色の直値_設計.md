## 1. 症状（＝直す理由）

`--accent`（`#d9a441`）などのトークンと**同じ色を手で書いた `rgba(…)` リテラル**が、ページCSSに散っている。

⚠️ ⭐ **トークンを変えた日に、これらだけが古い色のまま残る**（色がちぐはぐになるが、どこにも警告は出ない）。
これは**過去に実際に起きた事故の再来**である——`2a057112` で `style.css` の `:root` だけが動き、
`--panel` / `--panel-2` / `--border` / `--radius` の4つがデッキ構築とズレ、**同じ `shared/css/filter-chips.css` が
2ページで違う色を出していた**（`shared/css/tokens.css` の冒頭コメントに記録がある）。
トークンを1本に集約してもなお、**リテラルで書かれた色は集約の外に居る**。

⚠️ ⭐ **既存の `npm run validate` はこれを検出できない**:

| 既存の検査 | 何を見るか | なぜ気づけないか |
|---|---|---|
| `shared css tokens in sync` | `shared/css/**.css` の `var(--…)` 参照が tokens.css に定義されているか | **参照と定義の突き合わせ**なので、**リテラルで書かれた色は視野に入らない** |
| `:root owners in sync` | `:root` を持つCSSファイルの集合 | 色の書き方は見ていない |

⭐ **同じ画面の中で「追従する箱」と「追従しない箱」が既に並んでいる**（裏取り済み・§2-3）。

## 4. なぜ `color-mix` か — ⭐ **ほかに手が無い**

`rgba(217,164,65,.08)` を「`--accent` に追従する形」で書き直す方法は3つ考えられるが、**2つは規約で塞がれている**:

| 案 | 書き方 | 可否 |
|---|---|---|
| A | `rgba(var(--accent-rgb), .08)` のようにRGB成分だけのトークンを新設 | ❌ **T4 の V21 で不合格**（トークンを増やさない） |
| B | ページCSSの `:root` に半透明の派生色を定義 | ❌ **`npm run validate` の `:root owners in sync` が exit 1** |
| C | **`color-mix(in srgb, var(--accent) 8%, transparent)`** | ⭕ **採用**。トークンを増やさず `:root` も増やさない |

⭐ **この結論は T4 が既に同じ理由で辿り着いている**（`tools/deck-builder/style.css` L354-357 のコメントに
「⭐ 2つの規約の隙間で成立する直し方が color-mix だけ」と書かれている）。本タスクはそれを残り全部へ広げる。

### 4-1. ⭐ 等価性は実測済み（2026-09-24・Chromium 149）

`color-mix(in srgb, C P%, transparent)` は `rgba(C, P/100)` と**完全に同じ色**になる。
**34箇所で実際に使われる (色, alpha) の全24組合せ**について、次の2通りで確認した:

- **算出値**を 0〜255 の整数へ正規化して比較 → **24/24 一致**
- **要素のスクリーンショットをバイト比較** → **24/24 完全一致**

⚠️ ⭐ **ただし `getComputedStyle()` の文字列は一致しない**:

```text
rgba(217,164,65,.08)                              → "rgba(217, 164, 65, 0.08)"
color-mix(in srgb, var(--accent) 8%, transparent) → "color(srgb 0.85098 0.643137 0.254902 / 0.08)"
```

⭐ **算出値の文字列をそのまま比較すると、色が同じでも「不一致」と出る。** 検証は必ず正規化してから行う（§7-V3）。

⚠️ ⭐ **正規化は小数の桁で比較してはいけない。** 同じ色でも実測で
`0.0823529` と `0.082353`、`0.658824` と `0.658823` の**両方の桁が出た**。
⭐ **0〜255 の整数に丸めてから比較する**（または画素で比較する）。

### 4-2. ⚠️ `color-mix` に対応していないブラウザでの落ち方（実測）

**実測（2026-09-24）**: `var()` を含む宣言が解決できない場合、CSS は
**IACVT（invalid at computed-value time）→ `unset`** になる。**「手前の宣言に戻る」のではない**:

| 書き方 | 解決できないときの算出値 |
|---|---|

- ⭐ **実害は「背景が透明になる／枠線が文字色になる」だけ**で、文字が読めなくなるような壊れ方はしない
- ⭐ ⭐ **そもそも新しい依存を作らない。** `color-mix` は**すでに全ページ族が必須にしている**（実測）:

## 6. 再発を止める検査（⭐ **足す**）

⭐ **足す。** 理由: この問題は **fail-open の典型**（画面は壊れず、警告も出ず、人の目では
「どの色が追従してどの色が追従しないか」を見分けられない）で、
**#93 / #97 / #101 と同じく「検査を足さないと必ず戻る」型**だから。
しかも**置き換え対象を0件にした直後**なので、**成功行が `0件` という一番強い形**にできる。

### 6-1. 仕様

`scripts/validate.mjs` の**既存のトークン検査ブロック（`shared css tokens in sync` / `:root owners in sync` と同じブロック）に
3本目 (iii) として足す**。⭐ **既存の `cssFiles` の走査・`stripComments`・`ROOT_OWNERS` をそのまま再利用する**
（新しい走査範囲リストも新しい許可リストも作らない＝**ドリフトする両辺を増やさない**）。

| 項目 | 内容 |
|---|---|
| **走査対象** | 既存の `cssFiles`（配信CSS 11枚。`docs/` `shared/vendor/` `node_modules` `tmp` `.wrangler` は既存の `CSS_SKIP_DIRS` で除外済み）＋ **生成元2枚**（下記） |
| **生成元** | ⚠️ ⭐ **1.1 で訂正: 2件ではなく3件**。`CSS_GENERATORS = { "scripts/build-tournament-pages.mjs": "tournaments/tournaments.css", "scripts/build-card-pages.mjs": "cards/cards.css", "scripts/gen-element-orbs-css.mjs": "shared/css/element-orbs.css" }`。値は「その生成元が書き出すCSS」＝**支配するトークン集合の出所** |
| **トークン集合** | ファイルが `ROOT_OWNERS` に含まれるなら**自分の `:root`**、そうでなければ `shared/css/tokens.css`。生成元は上の対応表が指すCSSの `:root` |
| **拾う形** | `rgb(` / `rgba(` の**整数3つ組**（空白・大文字小文字を許容）。三つ組が**そのトークン集合のいずれかの hex と一致**したら違反 |
| **成功行** | `no token-colored rgb() literals — 0件（11ファイル + 生成元3ファイル走査 / :root出所 4）`（⚠️ **1.1 で訂正: 2 → 3**） |
| **違反時** | `file:line` と、当たったトークン名・リテラルを列挙して **exit 1**。案内文に「`color-mix(in srgb, var(--トークン) N%, transparent)` に直してください」と書く |
| **⭐ 迷子検査** | ⚠️ ⭐ **`CSS_GENERATORS` は片側だけの手書き一覧なので、そのままでは「消せば黙る」。** `scripts/**/*.mjs` を走査し、**`writeFileSync(… ".css" …)` を含むファイルの集合が `CSS_GENERATORS` のキーと一致すること**を併せて見る（**増えても減っても exit 1**）。⭐ **両辺が別ファイルなので空回りしない**。⚠️ ⭐ **1.1 で訂正 — 実測は3件だった**: `scripts/build-card-pages.mjs`（cards.css）／`scripts/build-tournament-pages.mjs`（tournaments.css）／⭐ **`scripts/gen-element-orbs-css.mjs`（`shared/css/element-orbs.css`）**。⚠️ ⭐ **1.0 が3件目を落としたのは、書き出しが `writeFileSync(OUT, css)` で、パスが離れた行の `const OUT = …` にあるため**——**`writeFileSync(… ".css" …)` を「1行の中で」探すと落ちる**。⭐ **判定はファイル単位**（`writeFileSync` を呼び、かつ `".css"` の文字列リテラルを持つ `.mjs`）で行う |

### 6-2. ⭐ 検査 (iv): `var(--…)` の参照先が、そのページを支配する `:root` に在ること

⚠️ ⭐ **本タスクは自分で穴を1つ開ける。** §3-5 の ※ で `tournaments/tournaments.css` の `:root` に
`--accent-3` と `--yes` を足し、同ファイルから `var(--accent-3)` / `var(--yes)` を参照するようにするが、
⚠️ ⭐ **この2つが `:root` から消えても、いまは何も止めない**——
既存の検査 (i) は **`shared/css/**` しか走査しない**ので、`tournaments.css` は視野の外にある。

⭐ **消えたときに起きること**: `var()` が解決できず **IACVT → `unset`**（§4-2）。
**種別バッジの背景が透明になり、枠線が文字色になる**——⚠️ **エラーも警告も出ない fail-open**。

⭐ **だから同じブロックに (iv) を足す**（既存の `cssFiles` をそのまま使う。新しいリストは作らない）:

| 項目 | 内容 |
|---|---|
| **規則** | 配信CSS 11枚の **フォールバックを持たない `var(--X)`** は、**そのファイルを支配する `:root`**（§3 の表と同じ導出）に定義されていなければならない |
| **対象外** | ⭐ **`var(--X, 既定値)` の形は見ない**。⚠️ ⭐ **これは意図的**——`--printbar-h`（`style.css`）・`--editor-bar-h` / `--pane-top`（`tools/deck-builder/style.css`）の**3つは JS が実行時に書き込む変数**で、`:root` には**定義されないのが正しい**（CLAUDE.md の「FABの退避量は `--printbar-h` に印刷バーの実測高さを書く」）。フォールバック付きの参照を落とすと**この3つで必ず exit 1 になる** |
| **成功行** | `css var refs resolve — 未定義0（11ファイル走査 / フォールバック無し 605参照）` |
| **現状** | ⭐ **実測（2026-09-24）で違反0**。フォールバック無し **571参照** ＋ 本タスクで足す **34参照** = **605** |

⚠️ ⭐ **(i) と重なる部分がある**（`shared/css/**` は (i) のほうが厳しく、**フォールバック付きも落とす**）。
⭐ **重なっていてよい**——(i) は「共有CSSは tokens.css に集約されているか」、
(iv) は「どのページでも変数が解決するか」で、**見ている性質が違う**。

### 6-3. ⚠️ コメントの扱い（⭐ **#117 の罠を踏まないこと**）

| 対象 | コメント除去 | 理由 |
|---|---|---|
| **CSS 11枚** | ⭕ **`/* … */` だけを除去する**（既存の `stripComments` と同じ規則） | ⭐ **CSS に行コメントは無い**ので除去は厳密にできる。§3 の「触らない3箇所」はこれで除外される |
| **生成元 `.mjs` 2枚** | ❌ ⭐ **除去しない（生テキストを走査する）** | ⚠️ ⭐ **JS のコメント除去は #117 で実際に壊れている**（`scripts/validate.mjs` の `stripJs` が行コメント中の `/*` を後方の `*/` と誤対応させ、**計609行を検査から消していた**）。⭐ **同じ罠を踏まないために、そもそもパースしない** |

⚠️ ⭐ **その代わりに規約が1つ増える**: **生成元の `.mjs` には、トークン色のリテラルをコメントにも書かない。**
⭐ **「戻すな」という注意書きは、リテラルを書かずに書く**（例: 「直値に戻さないこと（色は `--accent`）」）。
⭐ 現時点で生成元2枚のコメントにトークン色のリテラルは**0件**なので、この規約はすぐ満たせる。

### 6-4. ⚠️ この検査の限界（⭐ **承知のうえ**）

| 限界 | 内容 |
|---|---|
| ① | ⚠️ ⭐ **トークンの hex を変えた**あと、**古い値のリテラルが残っている**ケースは**検出しない**（リテラルがどのトークンとも一致しなくなるため）。⭐ **ただし本タスクで0件にするので、以後現れるリテラルは「その時点のトークン色を書き写したもの」＝検査に当たる**。守れるのは**再発**であって**事後の腐り**ではない |
| ② | ⚠️ **hex の直書き（`color: #fca5a5`）は見ていない**（§9-1 の派生） |
| ③ | ⚠️ **生成元を直して再生成し忘れた**場合、生成物側は古いままだが**生成元側で exit 1 になる**ので気づける（⭐ こちらは塞がっている） |
| ④ | ⚠️ **cron は `validate` を実行しない**（#40 と同じ制約）。⭐ **CSSを編集するのは常に人**なので検出経路として成立する |
| ⑤ | ⚠️ **(iv) は「`:root` に在るか」しか見ない。** 値が正しいか・ページに実際に読み込まれるかは見ない（例: `shared/css/card-detail.css` が `tokens.css` を読まないページで使われても、(iv) は tokens.css を基準に緑のまま） |
| **⑥** | ⚠️ ⭐ **1.1 で追記（レビュー S3-1）— (iii) は「カンマ区切りの記法」しか見ていない。** 拾う正規表現が `rgba?\( 数 , 数 , 数 [,)]` の形なので、⭐ **CSS Color 4 のスペース区切り `rgb(217 164 65 / 14%)` と `rgb(217 164 65)`、および `color(srgb 0.85 0.64 0.25)` は素通りする**（**実測: 前者を配信CSSに書き足して `npm run validate` が exit 0**。大文字・空白ありの `RGBA(217, 164, 65, .14)` は exit 1 になる） |

⭐ **「緑だから全部トークン参照になっている」とは読まないこと**（②の穴があるため）。

### 6-5. ⭐ 限界⑥（スペース区切り記法）をどう扱うか — **承認時の判断（1.1）**

⭐ **いま漏れている実体は0件**（置き換えた34箇所も既存の残りも**すべてカンマ記法**）。
⚠️ ⭐ **しかし「放置してよい穴」ではない**——**スペース区切りは DevTools の色表示や新しく書くCSSで
自然に出てくる形**で、⭐ **この検査が本来いちばん止めたい「これから書かれる直値」の書き方そのもの**だから。

⭐ **判断（設計担当・2026-09-24）**: **塞ぐ。ただし #105 では塞がない。**

| | 内容 |
|---|---|
| **#105 では** | ⭐ **上の限界⑥として明記するにとどめる**（実装は1バイトも変えない）。⚠️ **実体が0件のいま、実装をもう1往復させる理由が無い** |
| **塞ぐ場所** | ⭐ **派生「hex直書きのトークン化」（#118）に scope として入れた**。⚠️ ⭐ **あの派生の設計の主題はもともと「(iii) の視野をどこまで広げるか」**（派生起票案 §3）なので、**記法のカバレッジと hex は同じ設計判断の中にある** |

### 9-1. ⚠️ hex の直書き（10箇所）— **別タスクにする**

トークンと**同じ色を hex で直書き**している箇所が、`:root` の定義以外に **10箇所**ある:

| ファイル | 箇所 | 中身 |
|---|---|---|
| `shared/css/card-detail.css` | 1 | `.gacd-modal … { color: #fca5a5 }`（= `--danger`） |
| `style.css` | 2 | `linear-gradient(180deg, #14171d, #0f1115)`（= `--bg`）／`.card { background: #1b1f28 }`（= `--panel`） |
| `tools/deck-builder/style.css` | 7 | `color: #fca5a5` ×7（= `--danger`） |

⭐ **分ける理由**（スコープを避けるためではなく、**別の問題だから**）:

1. ⭐ **原因が違う。** `rgba()` の直値は**「`var()` で書けない」という構造的な理由**でそうなった
   （`rgba(var(--accent), .08)` は成立しない）。hex の直書きは**単に `var(--danger)` と書けばよかっただけ**で、
   **`color-mix` は要らない**
2. ⚠️ **検査の作りが変わる。** `shared/css/card-detail.css` には `var(--muted, #9aa2b1)` のような
   **フォールバック付き参照が43箇所**あり、これは**正しく追従する**ので違反ではない。
   hex を検査するには「`var(…)` の中の hex は見逃す」判定が要り、**今回の検査より一段複雑になる**
   - ⚠️ ⭐ **さらに、そのフォールバックの hex 自体が腐っている**。⚠️ ⭐ **1.1 で訂正 — 1件ではなく
     3トークン / 15箇所**（承認時に数え直した）: **`var(--border, #2a2f3a)` ×10**（⭐ **現在値は
     `rgba(255,255,255,.11)` で、もう hex ですらない**）／**`var(--panel-2, #1f232c)` ×4**（現在値 `#232834`）／
     **`var(--panel, #171a21)` ×1**（現在値 `#1b1f28`）。⭐ **発火しないので実害は無いが、直すなら
     「フォールバックをどう保つか（消すのか・検査するのか）」を決める必要があり、判断が1つ増える**
     （⚠️ ⭐ **`--border` のように形が変わっているものがあるので、hex 同士の比較では足りない**）
3. ⭐ **`style.css:30` のグラデーションは判断が要る。** `#14171d` は**トークンではない中間色**なので、
   `#0f1115` だけを `var(--bg)` にすると**片側だけ追従する**という、この issue と同じ形になる。
   ⭐ **中間色をどう扱うかを先に決める必要がある**
