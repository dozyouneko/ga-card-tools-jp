## 4. 差分が設計書の想定と食い違った点

### 4-1. ⚠️ カードページが **475 → 実際は 495**（＋20）

**設計書 §1-2 / §4-3 / V2 は「475ファイル」と書いているが、コミットは 495 ファイルである。**
本セッションが独自に数え直した内訳:

|---|---:|---|

| **合計** | **495** | 475 |

⭐ **これはドリフトではなく、設計書自身の算術漏れである。** 根拠:

1. 20枚はすべて **`card.flavor` の末尾に空白・改行がある**カード（例: `reduce-to-ash` =
   `"Ashes to ashes. Dust to dust. "`）。差分は `<p class="cp-flavor">…dust. </p>` → `…dust.</p>` の
   **末尾空白1文字の除去のみ**で、文面は変わらない
2. 設計書 §4-1 の `flavorOf()` 仕様は **`pick = (v) => (typeof v === "string" && v.trim()) ? v.trim() : ""`**
   と**明示的に `v.trim()` を返す**と定めている。つまり **trim は設計どおりの挙動**であり、
   §1-2 が「出力が変わるカード」を数えるときに **trim だけが変わるケースを勘定に入れ忘れた**だけ
3. 20枚は**すべて `card.flavor` 側**（版側ではない）＝ §1-2 が対象にしていた「版側にしか無い474枚」の
   外側にあり、見落としやすい位置にある

→ **実装は設計に忠実で、逸脱ではない**と判断した。**設計書 §1-2・§4-3・V2 の「475」を「495」に改訂**した（§6 参照）。

### 4-2. ⚠️ V6 の期待値「バイト一致」は**成立しない**（実装の問題ではない）

`editions` を逆順にしたスナップショット（1,248枚が該当）で生成すると、**581ファイルが変化する**。
原因を追ったところ、**本タスクが触っていない `scripts/build-card-pages.mjs:153` の `newestFirst()`** だった:

```js
const eds = [...(card.editions || card.result_editions || [])].sort((a, b) =>
  day(b.set && b.set.release_date).localeCompare(day(a.set && a.set.release_date))
);
```

⚠️ **発売日だけで比較しており、同着時の第2キーが無い**ため、**同着の版は入力配列の順序をそのまま保つ**。
その結果、**収録セット表の行順・代表画像・`og:image`** が `editions` の配列順に依存する。
これは設計書 §2-3 が問題視した「配列順で拾うと非決定的になる」のと**同じ型の問題が隣の経路に残っている**もので、
**`a7125896` 以前から存在する**（本タスクの対象外）。

⭐ **`flavorOf()` 自体は無関係**である。`flavorOf()` は渡された配列を**自前で昇順ソートし直し、
同着は `edition.slug` で決着させる**ため、入力順に依存しない。実測で裏づけた:

| 測り方 | 正順 vs 逆順 |
|---|---|
| ページ全体のバイト比較（設計書の V6 の字面） | ❌ 581ファイルが不一致（原因は `newestFirst()`） |
| ⭐ **`<p class="cp-flavor">` の文面を2,495枚ぶん比較** | ✅ **完全一致** |

→ **V6 の設計意図（§2-3 の決定性＝cronがノイズコミットを作らないこと）は満たされている**と判定した。
なお **V5（同じキャッシュで2回）は2,560ファイルすべてバイト一致**しており、
**実運用（cronは配列順を勝手に逆順にはしない）でのノイズコミットは起きない**。
`newestFirst()` の順序非依存化は**別issueの候補**として §7 に挙げる。
