## 1. 目的

毎日1件、大会の入賞デッキをXに投稿する。1位のデッキを画像で添付し、本文に1〜3位のプレイヤー名とデッキ（チャンピオン）を書く。

- 日次で更新の実体がある発信を作り、サイトへの流入経路を増やす
- **#28 で「発見の問題」から「順位の問題」へ移行したことが確定**した（「グランドアーカイブ 日本語」で6表示・0クリック・平均掲載順位16.4）。外部からの流入と言及は順位に効く

## 2. 方針（2026-08-05・ユーザー判断）

1. **まず半自動（フェーズ1）で作り、後から自動（フェーズ2）へ切り替える** — 選定・画像・本文の生成をcronで自動化し、**投稿だけ手動**。投稿部分を差し替え可能な構造にする
2. **本文にサイトURLを入れる**
3. **未投稿プールから毎日1件**を選ぶ（「前日開催」に限定しない。本文に開催日を明記する）

## 3. 調査で確定した前提（すべて実測）

### 3.1 ⚠️ X APIに無料枠が無い（2026-02〜）

Xは2026年2月に従量課金をデフォルト化し、無料枠と新規のBasic/Pro契約を廃止した。
公式価格表 <https://docs.x.com/x-api/getting-started/pricing>（2026-08-05取得）:

| 課金対象 | 単価 | 毎日1投稿の月額 |
|---|---|---|
| 投稿の作成（通常） | $0.015 / 件 | 約 $0.45 |
| **投稿の作成（URLを含む）** | **$0.200 / 件** | 約 **$6.0** |
| Media Metadata | $0.005 / 件 | — |

- ⭐ **本文にURLを1つ入れるだけで月額が13倍**になる（2026-04にURL投稿の別料金が追加）
- ⚠️ **画像アップロード自体が別課金かは公式表に明記が無く未確定**。フェーズ2の実装前にDeveloper Consoleで実費を確認すること
- ⚠️ フェーズ2は**課金が発生する**。実装前にユーザーの明示的な合意を取る

### 3.2 ⚠️ 「前日の大会」は週の半分以上で0件

`data/tournaments/index.json` の実データ。**大会は土日に集中する**:

```
7/04(土) 13件  7/05(日)  7件   7/06〜7/09 0件
7/11(土) 15件  7/12(日) 10件   7/13〜7/16 0件
7/18(土) 14件  7/19(日)  5件   7/20〜7/22 0件
7/25(土) 10件  7/26(日)  9件   7/27〜7/28 0件
```

さらに**結果確定→API掲載に数日の遅れ**がある。直近16日の日次cronで新規収録があったのは**7日だけ**。2026-08-05時点で収録済みの最新大会は**8/01開催**。

→ 「前日開催」をそのまま実装すると投稿できるのは週2〜3日。かつ平日は参加者4名の大会になり内容が弱い。**§5の未投稿プール方式で解決する。**

### 3.3 素材はほぼ揃っている

| 必要なもの | 現状 |
|---|---|
| 1〜3位のプレイヤー名 | `events/<id>.json` の `standings[].player` → `players{}` |
| デッキの識別 | **デッキ名は存在しない**。チャンピオン名+属性で表す |
| チャンピオン名の日本語訳 | `data/tl-names.json`（2,262件） |
| デッキ画像の生成 | 仕様が確定済み（`tmp/X投稿用/デッキ画像機能/仕様.md`）。PIL参照実装あり |

⚠️ **参照実装 `compose.py` は `tmp/` 配下＝gitignore で、コンテナ再構築で消える。**
本機能で **`scripts/` へ移して恒久化する**（§7）。

### 3.4 Xの画像は4:5までクロップされない

単一画像は 16:9〜4:5 の範囲なら全体が表示される。既存のデッキ画像は 1200×約1750（≒4:5.8）で**タイムラインでクロップされる**。
→ **添付画像は 1200×1500（4:5）に収める**（§7）。

## 4. 全体構成

```
[日次cron 03:00 JST]  build-tournaments.yml（既存・変更なし）
        └→ data/tournaments/ が更新される
                    │
[日次cron 21:00 JST]  x-post.yml（新規）
        ├ ① 対象を選ぶ         scripts/pick-x-post.mjs       → 選定結果JSON
        ├ ② 本文を組む         scripts/build-x-post-text.mjs → 本文テキスト
        ├ ③ 画像を作る         scripts/gen-x-post-image.py   → PNG 1200×1500
        ├ ④【フェーズ1】成果物を artifact に上げ、issue #48 にコメント
        │  【フェーズ2】scripts/post-to-x.mjs で投稿（①〜③は共通のまま）
        └ ⑤ 台帳 data/tournaments/x-posts.json を更新してcommit・push
```

⭐ **①〜③はフェーズ1・2で完全に共通**。差し替えるのは④だけ。

⚠️ **既存の `build-tournaments.yml` には手を入れない。** 投稿の失敗が大会データの取り込みを巻き込まないようにするため（`build-tournaments.yml` の索引ステップが `continue-on-error` である理由と同根）。

## 5. 対象の選定（`scripts/pick-x-post.mjs`）

### 5.1 候補の条件（すべて満たすもの）

1. `data/tournaments/index.json` の `events` にある
2. **台帳 `x-posts.json` に未掲載**
3. `startAt` が **実行日から14日以内**（鮮度窓 `WINDOW_DAYS = 14`）
4. `playerCount >= 8`（`MIN_PLAYERS`）
5. 1位のデッキが実在する（`standings` の `rank:1` の `player` が `decklists` にある）

### 5.2 並べ替えと決定

`playerCount` 降順 → `startAt` 降順 → `id` 昇順 で並べ、**先頭1件**。
⚠️ **同点で揺れないよう第3キーに `id` を必ず入れる**（出力を決定的にするため）。

候補が0件の日は**何もせずに正常終了する**（exit 0）。

### 5.3 ⭐ 鮮度窓が「初回の大量バックログ」も同時に解決する

台帳が空の状態で起動すると候補は447件になるが、**鮮度窓14日が自動的に直近の十数件へ絞る**。
過去の大会を延々と流し続けることはない。**別途のバックログ処理は不要。**

### 5.4 実測: 毎日投稿できるか（供給シミュレーション）

2026-05-15〜08-04（82日）について「窓W日・下限F名・毎日1件消費・収録の遅れ+2日」で試算:

| 窓 | 下限 | 投稿できた日 | 空振り | 選ばれた大会の参加者数 |
|---|---|---|---|---|
| 10日 | 8名 | **100%（82/82）** | 0日 | 中央39名 / 最小16名 |
| **14日** | **8名** | **100%（82/82）** | **0日** | **中央40名 / 最小16名** |
| 21日 | 8名 | 100%（82/82） | 0日 | 中央42名 / 最小19名 |

- ⭐ **毎日投稿でき、しかも選ばれるのは中央値40名規模**。「参加者数が最大のものを選ぶ」規則が小規模大会を自然に排除するため、**下限8名は一度も効かなかった**
- ⚠️ この期間はRDOシーズンでStore Championshipが多い。**閑散期は候補が枯れうる**ので、下限8名は「枯れたときに4名大会を出さないための安全弁」として残す（コストはゼロ）

## 6. 投稿本文

### 6.1 確定した型（実データ・大会#59168）

```
🏆 Canyon RDO Store Championship
8/1 香港・Store Champs・20名

🥇 Zero0000000000　ロレイン（風/クラックス）
🥈 Mike0615　アリス（水/アンブラ）
🥉 Arthur　シエル（火/アンブラ）

優勝デッキの全カードはこちら👇
https://ga-card-tools-jp.pages.dev/tournaments/59168/#deck-4261
#GrandArchive #グランドアーカイブ
```

- 順位の絵文字は 🥇🥈🥉。プレイヤー名とデッキの間は**全角スペース**
- チャンピオン名は**日本語のみ**（英語名は画像のヘッダに出るので重複させない）。複数チャンピオンは `・` で連結し**2件まで**
- 属性は `（風/クラックス）`。順序は既存の `championElements()` と同じ規則（火→水→風→上級はアルファベット順、EXALTEDは出さない）
- カテゴリ表記は**サイトの短縮ラベルと同じ** `Store Champs` / `Regionals` / `Nationals` / `Ascent`（`CATEGORY_JP[].label`）
- ⚠️ **`startAt` はUTC。日付は既存ページと同じ扱いに揃えること**（`day()` を流用する）

### 6.2 ⚠️ 文字数が本当に足りない — 実測とその対策

Xの上限は**重み付き280字**（日本語・絵文字=2、ASCII=1、URL=一律23、改行=1）。
公式: <https://docs.x.com/resources/fundamentals/counting-characters>

#### ⚠️ 「上限は100字では?」との関係（2026-08-05・ユーザー確認）

**どちらも正しく、同じ制限の別の言い方**。混同しやすいので明記する。

| 固定で消える分 | 重み |
|---|---|
| URL（t.co換算） | 23 |
| `#GrandArchive #グランドアーカイブ` | 33 |
| 改行 9本 | 9 |
| **小計** | **65** |

残り 215 → **日本語だけで書くなら107字** ← ⭐ これが `promo-x-post-workflow` にある「本文は約100字」の出どころ。
リリース告知の投稿文は**ほぼ全部が日本語**なので実質100字だった。

⭐ **本機能は事情が違う。** プレイヤー名・大会名が**英数字（1字=1）**なので枠の消費が軽く、
同じ280の中に全角80字+英数字が収まる（モックの実測: 全角80字・合計277）。
**設計は280基準で計算する。100字基準にしてはいけない。**

**全447大会で試算したところ、素の型では26%が280字を超えた**（最大336字＝56字オーバー）。
原因の大半は**大会名**（最長90字相当。例: `Grand Archive Radiant Origin Store Championship - Saikou Cards, Figurines and Collectibles`）。

#### 対策A: 大会名の正規化（常時適用）

1. 先頭の `Grand Archive` + 区切り文字を除去
2. ` - ` ` – ` ` — ` ` @ ` ` ~ ` ` | ` のいずれかで分割し**先頭側だけ残す**（会場名・主催名はここ以降に来る）
3. 連続空白を1つに

#### 対策B: 段階的短縮ラダー（収まるまで順に適用）

**予算の計算**: 固定部（メタ行・順位3行・空行・誘導行・URL・タグ）を先に組み、
`大会名の予算 = 280 - 固定部 - 「🏆 」(3) - 改行(1)` とする。予算が **24未満**なら次の段へ進む。

| 段 | 内容 | 適用率（447件中） |
|---|---|---|
| 0 | 短縮なし | **443件（99%）** |
| 1 | ハッシュタグを `#グランドアーカイブ` のみに | 4件（1%） |
| 2 | 誘導文を `デッキ全文👇` に | 0件 |
| 3 | 属性の併記 `（風/クラックス）` を落とす | 0件 |

最後に大会名を予算まで `…` で切り詰める（**25件・6%** が該当）。
プレイヤー名は常に24字で切り詰める。

#### 実測結果（対策A+B適用後・全447大会）

```
最小214 / 中央256 / 平均256 / p90=276 / 最大280
⚠ 280超過: 0件
```

⭐ **カテゴリ表記を「ストアチャンピオンシップ」から「Store Champs」に変えるだけで、
短縮が要る大会が28件→4件、名前の切り詰めが80件→25件に減った**（24字→12字で12字浮く）。

### 6.3 ⚠️ 実装時の注意

- **重み付き文字数は自前で数える。** `String.length` でも `[...s].length` でもない。
- ⚠️ **`east_asian_width` で近似してはいけない。** 公式（twitter-text v3）の規則は
  **「既定=2、下記の範囲だけ=1」**で、東アジア幅とは一致しない:

  ```
  重み1 = U+0000–U+10FF (0–4351) / U+2000–U+200D / U+2010–U+201F / U+2032–U+2037
  それ以外はすべて重み2。URLは23、改行は1。
  ```

  | 文字 | 公式 | `east_asian_width` 近似 | |
  |---|---|---|---|
  | `ｱ` 半角カナ (U+FF71) | 2 | **1** | ⚠️ **過小評価＝280を超える投稿を通してしまう** |
  | `é` `А` `Ω` `—` `’` | 1 | 2 | 過大評価（安全側だが無駄に切り詰める） |

  ⭐ **過小評価が1文字でもあると投稿がAPIに弾かれる**（フェーズ2では課金だけ発生して投稿が失敗しうる）。
  近似ではなく**上の範囲をそのまま実装する**こと。
  （設計時に両方で全447大会を測り、**現データでは結果が同一**であることを確認済み。
  つまり**この欠陥はテストデータでは顕在化しない**——だから規則を明文化する）
- **数え方の検証は「280に収まること」だけでは不足**。`npm run validate` 相当の検査で
  **全447大会を通して0件超過**であることを確認する（設計時の実測値を回帰の基準にする）

## 7. 添付画像（`scripts/gen-x-post-image.py`）

モック: `モック_添付画像_1200x1500.jpg`（実データ・大会#59168の優勝デッキ）

### 7.1 確定仕様

- **サイズ 1200×1500（4:5）固定**。⚠️ これを超えるとXでクロップされる（§3.4）
- 意匠は既存のデッキ画像仕様を踏襲: BG `#0f1115` / PANEL `#1a1d23` / GOLD `#d9a441` / TEXT `#e7e9ee` / MUTED `#969eac`
- **ヘッダ（206px）**: 大会名（Bold 36・はみ出しは `…`）/ メタ行（Regular 23・`2026/08/01 · 香港 · Store Championship · 参加20名`）/ 優勝行（`優勝` をGOLDで + `<名前> — <チャンピオン英語名（日本語名）>`）+ **右端に属性玉**（`scripts/lib/element-orbs.json` の32px WebPを30pxで貼る）
- **本体**: `Materials` / `Main Deck` / `Sideboard` の3節。節見出し（Bold 28・GOLD）+ `12枚 / 12種`（Regular 21・MUTED）+ 区切り線
- **枚数バッジ**: 2枚以上のカードのみ、**カード画像の左下**に黒地ゴールド枠
- **フッタ（70px）**: 上端に2pxのゴールド線 + `ga-card-tools-jp.pages.dev` を中央にMUTEDで

### 7.2 ⭐ 列数は自動で決める（4:5に必ず収める）

デッキの**種類数は可変**（実測 11,026デッキ: 中央39種 / p99 47種 / **最大69種**）。
固定7列では収まらないため、**7列から順に増やし、最初に収まった列数を採用する**:

```
avail = 1500 - 206(ヘッダ) - 70(フッタ) - 50×3(節見出し) - 40(余白)
COLS を 7,8,…,15 と試し、rows*ch + gaps <= avail になった最初の値を使う
cw = (1200 - 80 - (COLS-1)*12) / COLS,  ch = cw / 0.714
```

実測（#59168・44種）で **9列・カード113×158px・余裕50px**。

### 7.3 ⚠️ 実装時の落とし穴

- ⚠️ **画像に絵文字を使わない。** `NotoSansCJK` に絵文字が無く**豆腐（□）になる**（本モック生成時に実測）。
  🏆🥇 は**本文だけ**に使い、画像では `優勝` などの文字で表す
- ⚠️ **`tmp/api-cache/cards-snapshot.json` は gitignore。** cronでは既存スクリプトと同じく
  未取得なら公式APIから取り直す経路を使う
- カード画像の取得は `https://api.gatcg.com` + `editions[0].image`。**失敗したカードは
  PANEL色のプレースホルダで続行する**（1枚の失敗で投稿全体を落とさない＝fail-open）
- 出力は**PNG**。⚠️ Xの画像上限は5MB。実測1.5MB（PNG）で収まるが、**5MBを超えたらJPEG q85で再出力**する保険を入れる

### 7.4 タイムラインでの見え方

モック: `モック_タイムライン_375px.jpg`（375px幅＝スマホ相当を2倍で描画）

- スマホ幅では**1枚のカードが約35pt**になり、個々のカードは読めない。**「デッキの全体像」+タップで拡大**という位置づけで割り切る（デッキの中身はリンク先で読める）
- 検討したが**採らなかった案**: Sideboardを省いて8列にする（カードが113→131pxで+16%）。
  ⭐ **16%のために情報を1節まるごと落とす価値は無い**と判断

## 9. ワークフロー `.github/workflows/x-post.yml`（新規）

```yaml
on:
  schedule:
    - cron: "0 12 * * *"   # 21:00 JST（03:00 JSTの大会取り込みの後・日本の閲覧が多い時間帯）
  workflow_dispatch: {}
```

- ⚠️ **既存の `build-tournaments.yml` とは別ジョブにする**（§4）
- ⚠️ **この workflow は `data/tournaments/x-posts.json` を main に push する。**
  日次cronに続く**2本目の自動push経路**になる（公開サイトの表示は変わらないが、
  mainへのpushはCloudflare Pagesのデプロイを起こす）。
  → ✅ **2026-08-05 にユーザー承認済み。**
  ⚠️ コミット対象は **`data/tournaments/x-posts.json` だけ**を明示的にステージする
  （`git add -A` は使わない。日次cronの生成物と競合するため）
- 候補0件の日は**コミットもコメントもせず正常終了**する

### フェーズ1の受け渡し

- 画像とテキストを **artifact**（`actions/upload-artifact`・retention 7日）に上げる
- **issue #48 に本文をコメント**する（`gh issue comment`）。コメントには artifact へのリンクを添える
- ⭐ **リポジトリに毎日PNGをコミットしない。** 1枚あたり約1.5MB（JPEGでも約360KB）で、
  1年で数十MB〜数百MBの履歴になる。artifactなら7日で消える

### フェーズ2への切替（別途ユーザー合意が必要）

- `scripts/post-to-x.mjs` を④に差し込む。①〜③は変更しない
- 必要な Secrets: `X_API_KEY` / `X_API_SECRET` / `X_ACCESS_TOKEN` / `X_ACCESS_SECRET`
  （⚠️ 画像アップロードは OAuth 1.0a ユーザーコンテキストが要る見込み。実装時に要確認）
- ⚠️ **課金の安全装置を必ず入れる**:
  - リポジトリ変数 `X_AUTOPOST_ENABLED` が `true` のときだけ投稿する（**キルスイッチ**）
  - 台帳の当月 `posted` 件数が **31件**を超えたら投稿しない（暴走時の上限）
  - 投稿APIが失敗したら `state` を `draft` のままにする（**二重投稿を避けるため、成功時だけ `posted` にする**）

## 10. 検証項目

期待値は**画面に出る最終形**で書く。

| # | 項目 | 期待値 |
|---|---|---|
| V1 | 選定の決定性 | 同じ入力・同じ台帳で2回実行し、選ばれる `eventId` が一致する |
| V2 | 鮮度窓 | 台帳を空にして実行したとき、選ばれるのは**実行日から14日以内**に開催された大会。**447件の最古（2026-04）は選ばれない** |
| V3 | 候補0件 | 候補が無い日は**exit 0** で終わり、**コミットもissueコメントも発生しない** |
| V4 | 文字数 | 全447大会で本文を生成し、**重み付き280字を超えるものが0件**。かつ**最大値が280以下**であること |
| V4b | 数え方の規則 | `ｱ`(U+FF71・半角カナ)=**2**、`é`(U+00E9)=**1**、`—`(U+2014)=**1**、`🏆`=**2**、`あ`=**2** を単体で数えて一致すること。⚠️ **実データでは差が出ないので、この単体テストが唯一の検出経路**（§6.3） |
| V5 | 短縮ラダーの分布 | 段0=443件 / 段1=4件 / 段2=0件 / 段3=0件、大会名の切り詰め=25件（**設計時の実測値と一致**。ズレたら正規化規則が変わった疑い） |
| V6 | 画像サイズ | 出力が**必ず1200×1500**。種類数が最大の69種のデッキでも**はみ出さず・欠けず**に収まる |
| V7 | 画像の文字 | 画像内に**豆腐（□）が出ない**。大会名が長い場合は `…` で切れて**枠内に収まる** |
| V8 | カード画像の失敗 | 1枚を取得失敗させても**画像生成が完走**し、該当枠がプレースホルダになる |
| V9 | 台帳 | 2日続けて実行すると**別の大会**が選ばれ、台帳に2件並ぶ |
| V10 | 逃げ道 | 台帳から1件消して再実行すると、**その大会が再び選ばれる** |
| V11 | 実物確認 | 生成した画像を**実際にXの下書きに貼り**、①タイムラインでクロップされない ②本文が「さらに表示」で折りたたまれない ことを目視する |

⚠️ **V11 は自動化できない。** フェーズ1の初回は必ずユーザーの目で確認する。
