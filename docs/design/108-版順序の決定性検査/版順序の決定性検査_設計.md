## 2. 何を守るのか（守備範囲の定義）

⚠️ **「版順序」には性質が2つあり、混ぜると設計を誤る。**

| 性質 | 内容 | 壊れると |
|---|---|---|
| **P-決定性** | 比較器に**同値のペアが存在しない**（＝全順序）。`Array.prototype.sort` は安定なので、同値ペアがあると**入力配列の順が出力に漏れる** | ⚠️ **公式APIが `editions` を並べ替えた日に、中身が変わらないのに生成物が変わる**（#71 の「無関係な差分」の正体） |
| **P-順序** | 5つのキーが**どういう順で・どちら向きに**効くか | 生成物の `og:image`・収録セット表の行順・イラスト切替の並びが変わる（⚠️ **決定性は壊れない**） |

⭐ **本タスクの主目的は P-決定性。** ただし §3 の実測で分かったとおり、
**P-決定性だけを実データで測っても、キーを4本まで削れてしまう**（残った1本で実データは決着するため）。
⭐ **したがって検査は「比較器が宣言どおり5段であること」＝ P-順序の骨格まで見る**。

## 3. 案A / 案B / 案C の決着（⭐ 実測で決めた）

### 3-1. 破壊試験の実測（2026-09-23・スナップショット 2,495枚 / 4,941版）

**比較器のキーを1本ずつ潰して、各案が落ちるかを測った。**

| 潰したもの | 案A（合成フィクスチャ） | 案B（実データの同値ペア） | 実データの非決定カード数 | 実データで出力が変わるカード数 |
|---|---|---|---|---|
| **K1** 発売日 | ⭕ **落ちる** | ❌ **0組（素通り）** | **0** | 101 |
| **K2** `meta.sets` の並び | ⭕ **落ちる** | ❌ **0組（素通り）** | **0** | 335 |
| **K3** レアリティ | ⭕ **落ちる** | ❌ **0組（素通り）** | **0** | 1 |
| **K4** カード番号 | ⭕ **落ちる** | ❌ **0組（素通り）** | **0** | 3 |
| **K5** 版slug | ⭕ **落ちる** | ⭕ **5組（検出）** | **5** | 3 |
| `numeric: true` の除去 | ⭕ **落ちる**（F6） | ❌ 0組 | 0 | **0** |
| `day()` の 1970 特例の除去 | （フィクスチャを置かない＝§3-3） | ❌ 0組 | 0 | **0** |
| **（無傷）** | ⭕ 違反0 | ⭕ **0組** | **0** | — |

⭐ **読み取れること（起票案の想定と違う点）**:

1. ⚠️ **案B の検出力は 5キー中 1キーだけ。** K1〜K4 を削っても**実データには同値ペアが1組もできない**
   （前のキーで既に差がついているため）。⭐ **起票案が「実物で効いていることを直接見る＝強い」と
   書いたのは誤り**で、**実物は4本のキーが無くても決着してしまう**
2. ⚠️ **K1〜K4 を削っても実データの非決定カードは 0。** 壊れるのは**出力の内容**（101件・335件…）であって
   決定性ではない。⭐ **つまり「決定性だけを実データで測る検査」は、比較器が4段削られても永久に緑のまま**
3. ⭐ **案A は 5/5 で落ちる。** しかも**実データの現状に依存しない**ので、データが変わっても検出力が落ちない
4. ⭐ **案B にも案A に無い検出力が1つある**: **実データが最終決着キー（版slug）の一意性を破った日**
   （同一カード内に同じ slug の版が2つ来る等）。これは比較器を一切触らなくても起きる**データ側の事故**で、
   **合成フィクスチャでは原理的に見えない**（現状のカード内 slug 重複は **0件**）

### 3-2. 決定（⭐ 両方採る。ただし役割が違う）

| 案 | 採否 | 役割 | fail する条件 |
|---|---|---|---|
| **A** 合成フィクスチャで比較器の全順序性を突く | ⭕ **採る（本体・必須・スキップ不可）** | **人が比較器を簡略化したこと**を捕まえる | 常に走る。**落ちたら exit 1** |
| **B** スナップショットの実データで同値ペアを数える | ⭕ **採る（上乗せ・別目的）** | **データが最終決着キーの一意性を破ったこと**を捕まえる | スナップショットがあるときだけ走る |
| **C** フルビルド2回でバイト一致 | ❌ **採らない** | — | — |

- ❌ **案C を採らない根拠（⭐ 実測で理由が入れ替わった）**: 起票案は「重すぎる（2,495ページ×2回）」を理由に
  していたが、**実測ではフルビルド1回は約6秒**（`GA_SNAPSHOT_MAX_AGE_MIN=0`・スナップショット再利用）で、
  2回でも約12秒＝`validate` の約35秒に対して**致命的な重さではない**。⚠️ **却下の本当の理由は別に2つある**:
  ① ⭐ **案C の検出力は案B と同じで 5キー中1キーだけ**（§3-1 の「実データの非決定カード数」列＝K1〜K4 はすべて **0**）。
  **12秒払って案B と同じものしか見えない**
  ② ⚠️ **`build-card-pages.mjs` は出力先をモジュールの位置から決めるので、走らせると
  作業ツリーの `cards/**` `sets/**` `sitemap.xml` `index.html` を実際に上書きする**。
  ⭐ **`npm run validate` が生成物を書き換えるのは論外**（ほかのセッションと作業ツリーを共有している）
- ⚠️ **案B を「本体」にしない根拠は §3-1 の 1・2**。⭐ **これは起票案に対する設計上の変更点なので、
  レビューはここを見ること。**

### 3-3. フィクスチャに**入れない**と決めたもの（⭐ 実測で潰した候補）

| 候補 | 実測 | 判断 |
|---|---|---|
| `day()` の **1970-01-01 → 空文字** 特例を守るフィクスチャ | 特例を外しても**実データの出力は1ファイルも変わらない**。`release_date` が `1970-01-01` のセットは **3件**（PRDEVP / SP4 / P26）だが、**日付が未設定（空）のセットは 0件**なので、特例の有無で順序が変わる組が実在しない | ❌ **入れない**（守る対象が実在しない。⚠️ 将来 `release_date` を持たないセットが現れたら再検討） |
| **キーの入れ替え**（例: レアリティとカード番号を交換）を検出するフィクスチャ | 入れ替えても**全順序のまま**なので P-決定性は壊れない。検出するには「5キーの適用順そのもの」を宣言する必要があり、**検査が比較器の写しになって同源化する**（＝空回りの原因） | ❌ **入れない**（§7 の「証明しないこと」に明記する） |
| **推移律**のフィクスチャ | 比較器は全順序の辞書式合成なので構造的に推移的。合成データで突いても**構成上必ず通る**＝検出力が無い | ❌ **入れない** |

## 4. 構造 — 比較器をどこに置くか

⚠️ **`scripts/validate.mjs` から `scripts/build-card-pages.mjs` を import してはいけない**
（§1-3 で実走確認。**`npm run validate` のたびにカード2,495ページが生成される**）。

| 案 | 内容 | 判断 |
|---|---|---|
| **a** | `build-card-pages.mjs` の末尾の `main()` 呼び出しをエントリポイント判定で囲い、`editionOrder` を export する | ❌ **却下。** ⚠️ **判定が false に転ぶと `npm run build:cards` が「正常終了して何も生成しない」**——⭐ **週1の大会データ更新がこの経路を使う**ので、無言の空振りを本番側に作ることになる。⚠️ しかも `deploy:prod` は `git archive HEAD` から作るため、**空振りに気づかないまま公開まで進む** |
| **b** | 比較器一式を **`scripts/lib/edition-order.mjs`** に切り出し、`build-card-pages.mjs` と `validate.mjs` の**両方が import** する | ⭕ **採用。** `build-card-pages.mjs` の**起動経路には一切触れない**（定義を import に置き換えるだけ）。切り出したモジュールは**副作用ゼロ**（読み書きもネットワークも無い） |
| **c** | `validate.mjs` に比較器を**書き写して**突き合わせる | ❌ **却下。** ⚠️ **二重定義**になり、片方だけ直しても何も止まらない（CLAUDE.md が用語ハイライトで踏んだ型） |

### 4-1. ⚠️ 切り出す範囲は「比較器だけ」では足りない

`editionOrder()` は `day()` と `setOrder()` に依存し、`setOrder()` は `SET_LABELS`（`meta.sets` から作る）に依存する。

⚠️ ⭐ **`SET_LABELS` の構築を `validate.mjs` 側に書き写すと、そこが新しい二重定義になる**
（`build-card-pages.mjs` 側だけ壊れても検査は気づかない）。⭐ **`day()` / `SET_LABELS` / `setLabel()` /
`setOrder()` / `editionOrder()` の5つをまとめて lib へ移し、`build-card-pages.mjs` は import して使う。**

- ⭐ **`day()` が `edition-order.mjs` に居るのは意図的**（キー1が依存するので分離できない）。
  `build-card-pages.mjs` は `sitemap.xml` の `lastmod` や公式裁定の日付表示にも `day()` を使っているので、
  ⚠️ **「版順序と関係ないから」と別ファイルへ移し直さないこと**（移すと `day()` が2本になる）
- ⭐ **`setLabel()` も一緒に移す**（`SET_LABELS` を持つ側に置かないと、`SET_LABELS` だけが lib に残って
  参照が分断される）

- ⚠️ **`main()` の呼び出しには手を触れない**（§4 案a を却下した理由がここ）

### 5-3. `scripts/validate.mjs` に検査を1本追加

⭐ **置き場所は「UI規約の自動検査3本」の後・「カードページの用語ハイライト」の前**
（用語ハイライトの検査は非同期で最後にあるため、その前に入れる）。

処理は3段:

**(1) 準備（fail-closed）**

- `makeSetOrder(loaded.meta.sets)` → `makeEditionOrder(setOrder)` で**本物の比較器**を組み立てる
- ⚠️ **import や組み立てに失敗したら exit 1**（メッセージ: `比較器を読み込めません: <理由>`）。
  ⚠️ **素の例外でクラッシュさせない**——原因が分かる1行を出してから `problems++` する
- ⚠️ **`meta.sets` から「`order` の異なる prefix」が2つ取れなければ exit 1**
  （メッセージ: `meta.sets から order の異なる prefix が2つ取れません（K2 のフィクスチャを作れません）`）。
  ⭐ **取れないまま黙って K2 を飛ばすと、そこだけ無検査になる**

**(2) 案A: 合成フィクスチャ 6組（必須・常に走る）**

基準の版オブジェクト（`BASE`）を1つ作り、**1フィールドだけ変えた相手**と組にする。

| # | 組 | 変えるフィールド | 期待 |
|---|---|---|---|
| **F1** | `BASE` vs 発売日を古くしたもの | `set.release_date`（`"2025-01-01"` → `"2024-01-01"`） | **負**（新しい版が先） |
| **F2** | `BASE` vs `meta.sets` の並びが後ろの prefix | `set.prefix`（order が小さい方 → 大きい方） | **負** |
| **F3** | `BASE` vs レアリティが大きいもの | `rarity`（`1` → `2`） | **負** |
| **F4** | `BASE` vs 番号が大きいもの | `collector_number`（`"001"` → `"002"`） | **負** |
| **F5** | `BASE` vs slug が後ろのもの | `slug`（`"base-slug"` → `"zzz-slug"`） | **負** |
| **F6** | 番号 `"9"` vs 番号 `"10"`（どちらも `BASE` 由来） | `collector_number` | **負**（⭐ `numeric: true` が生きていれば 9 < 10） |

各組について**3つ**を見る:

1. ⭐ **フィクスチャの自己検査**: 2つの版が、宣言した観測フィールド
   （`set.release_date` / `set.prefix` / `rarity` / `collector_number` / `slug` の5つ）のうち
   **ちょうど1つだけ**で違うこと。⚠️ **違えば exit 1**
   （⭐ **フィクスチャの作り間違いで「2つ違う」になると、キーを1本潰しても差がついてしまい検査が空回りする**。
   これを構造で塞ぐ）
2. **比較結果が 0 でないこと**、かつ**符号が表のとおり**であること
3. **反対称性**: `sign(cmp(a,b)) === -sign(cmp(b,a))`

⚠️ **フィクスチャの BASE と変種は、観測フィールド5つを明示的に書いて作ること**
（スナップショットから借りてこない＝案B と独立させる）。

**(3) 案B: スナップショットの同値ペア走査（スナップショットがあるときだけ）**

- `tmp/api-cache/cards-snapshot.json` が無ければ**走らせず、スキップした旨を成功行に書く**（§6）
- あれば、**同一カード内の全ペア**について `editionOrder(a, b) === 0` の組を数える。**0組が期待値**
- ⚠️ **版が1件も取り出せなかったら「一致」へ倒さない**（メッセージ: `スナップショットから版を1件も取り出せません（破損か形式変更の疑い）`）。
  ⭐ `meta.rarities` の検査と同じ流儀
- ⚠️ **ペアは同一カード内だけでよい**（並べ替えが起きるのはカード単位のため）。
  実測 5,764ペアで**比較は約6ms**。⚠️ **カード横断の全ペア（約1,200万組）を回さないこと**
- ⭐ **スナップショットの読み込みは `meta.rarities` の検査と共有しない**（既存の検査に手を入れて
  回帰面を増やさないため）。⚠️ **コストは実測 +0.55秒**（18MBのJSONを2回パースする。
  `validate` 全体が約35秒なので 1.5%）＝**許容する**

## 6. 成功時に出す1行・失敗時の出力（✅ 実装済み）

### 6-1. 成功行（⭐ 数えた件数を出す）

**スナップショットがあるとき**（`N` `M` は実行時の実測値。2026-09-23 時点では `4941` / `5764`）:

```text
edition order is a total order — 合成6組 / 実データ N版・Mペア・同値0
```

**スナップショットが無いとき**:

```text
edition order is a total order — 合成6組 / 実データはスキップ（tmp/api-cache/cards-snapshot.json がありません）
```

- ⚠️ **「合成6組」は固定値**（フィクスチャを増減したらこの数字も直す）
- ⚠️ **「同値0」も固定値**（0 でなければ失敗側に落ちるため、成功行に 0 以外は出ない）
- ⚠️ **版・ペアの数は実データ由来なので日によって動く。判定基準にしない**

### 6-2. 失敗時

```text
NON-DETERMINISTIC EDITION ORDER (scripts/lib/edition-order.mjs):
  - F2（meta.sets の並び）で差がつきません（比較結果 0）
  - F5（版slug）が反対称ではありません（cmp(a,b)=-1 / cmp(b,a)=-1）
  - 実データに同値ペアがあります: 5組
    例: arisanna-astral-zenith（…-rdopd / …-rdopd-ext）
  → editionOrder() は5段すべてが必要です。1段でも削ると公式APIの editions 配列順が
    生成物に漏れ、中身が変わらない日に差分が出ます（#108 / 親タスク: 版順序の非決定性）
```

- ⚠️ **「実データに同値ペア」のときだけ、最後の誘導文を変える**:
  `→ 同一カード内で版slug が重複している可能性があります（比較器ではなくデータ側の事故）`
  ⭐ **案A の失敗（人がコードを削った）と案B の失敗（データが変わった）は原因も対処も違う**ので、
  同じ誘導文を出さないこと

## 7. ⭐ 緑が何を証明するか / しないか

⚠️ **これを書かないと、緑が「版順序は大丈夫」という無制限の保証として読まれる。**

### 7-1. 緑が**常に**証明すること（案A・スキップ不可）

- `editionOrder()` が **5つのキーそれぞれで差をつける**こと（1つでも削れば exit 1）
- 5つのキーの**向き**（発売日は降順・他は昇順）が保たれていること
- カード番号の比較が **`numeric: true`** であること
- 比較器が**反対称**であること（`Array.prototype.sort` の結果が実装依存にならない）

### 7-2. 緑が**スナップショットがあるときだけ**追加で証明すること（案B）

- **その時点の実データ**に、同一カード内の同値ペアが **0組**であること
  （＝最終決着キーの一意性が実データで保たれている）

### 7-3. ⚠️ 緑が**証明しないこと**

| 証明しないもの | なぜ | どうなるか |
|---|---|---|
| **キーの適用順**（例: レアリティとカード番号の入れ替え） | 入れ替えても全順序のままで、検出するには検査が比較器の写しになる（§3-3） | ⚠️ **生成物の内容は変わるが緑のまま**。⭐ ただし**フルビルドの差分として必ず見える**（無言ではない） |
| **ブラウザ側の代表画像**（`shared/js/card-i18n.js` の `firstEdition()` 等） | 別実装で、いまも直っていない（487枚が食い違う） | 別issue（起票案「ブラウザ側の代表画像」）。⚠️ **本検査は一切触れない** |
| **スナップショットに入っていないカード**の版 | スナップショットは取得時点のコピー | 案B の網羅は「その時点」まで |
| **`build-card-pages.mjs` のほかの並び**（セット一覧の `setsSorted` 等） | 既に `localeCompare` の第2キーを持つ（親タスクで確認済み） | 対象外 |
| **スナップショットが無い環境での実データの健全性** | 走らないため | ⭐ **だから成功行にスキップを明記する**（黙って通らない） |
| ⚠️ ⭐ **`build-card-pages.mjs` が lib の比較器を使い続けていること**（1.1 で追記） | 検査は `scripts/lib/edition-order.mjs` を直接 import して測るだけで、**ビルド側が何を使っているかを一切見ていない**（`scripts/validate.mjs` に `build-card-pages.mjs` を参照する経路が無いことを確認済み） | ⚠️ ⭐ **再インライン化しても緑のまま、生成物は86ファイル変わる**（レビュー R-2 の実測）。⭐ **守っているのは `makeSetOrder` 呼び出しの上のコメント1行だけ**＝#108 の出発点と同じ型が1段上に移った。**派生issue #113 で別途塞ぐ** |

### 7-4. 検出経路の整理（CLAUDE.md の書き方に合わせる）

- ⭐ **`npm run validate` が exit 1 で人を止める**（案A は常時・案B はスナップショットがあるとき）
- ⚠️ **cron は `validate` を実行しない**（しかも 2026-09-18 から停止中）。⭐ **比較器を触るのは常に人**なので、
  #70（cron列挙のドリフト防止）と同じ理屈で**検出経路として成立する**
- ⚠️ **`tmp/api-cache/cards-snapshot.json` は gitignore なので、コンテナ再構築直後は案B が走らない。**
  ⭐ **その状態でも案A は走る**ので、**緑の意味が空洞化しない**（＝起票案が懸念した fail-open を、
  「本体をスキップ不可にする」ことで回避した）
