⚠️ **開発担当は「検査を足す」ではなく「重複を消す」を選んだ**（設計 §8-4-3 の第1案）。
⚠️ ⭐ **その場合、報告に書ける破壊試験が無い**（検査が無いので「わざと壊すと exit 1」が出せない）。
⭐ **そこでレビュー側で「片方だけ動かせないこと」を直接測った**——`tools/deck-builder/app.js` の応答を配信時に差し替え、
**`COND_FOLD_SHOW` だけを変えて CSS 側（隠れる行）と文言（`ほか N`）が一緒に動くか**を見る:

| `COND_FOLD_SHOW` | 見えている行 | `display:none` の要素 | `.cond-extra` の印 | ボタンの文言 |
|---|---|---|---|---|
| **3（そのまま）** | 3 | 10 | 10 | `▾ すべて表示（ほか 5 項目）` |
| **2（差し替え）** | **2** | **12** | **12** | **`▾ すべて表示（ほか 6 項目）`** |
| **5（差し替え）** | **5** | **6** | **6** | **`▾ すべて表示（ほか 3 項目）`** |

（いずれも条件8項目）

⭐ **3つの数がすべて `COND_FOLD_SHOW` 1つから動いている**＝**CSS に行数が残っていないので、片方だけずらすことが構造的にできない**。
⭐ **これは「検査が通ること」より強い**（検査は片方を直し忘れてから初めて鳴るが、こちらは間違いを作れない）。

## 5. 推奨基準の指摘（⚠️ **合格を妨げない**）

### S-1（S1 コード品質）⚠️ **`app.js` に、消したはずの `:nth-child(n+7)` を指すコメントが2行残っている**

- **該当**: `tools/deck-builder/app.js` の `COND_FOLD_SHOW` 宣言まわり（`condRows()` の直前のブロック）

  ```js
  //    押し下がった＝モック説明 §4-2 の実測）。畳みの閾値は style.css の :nth-child(n+7) と対。
  const COND_FOLD_AT = 4;   // ⭐ これを「超えたら」畳む（＝4項目までは畳まない・設計 §6）
  const COND_FOLD_SHOW = 3; // 畳んだときに見せる項目数。⚠️ style.css の n+7 は 3*2+1（dt+dd で1項目）
  ```

- **なぜ気になるか**: ⭐ **T4 が消したのはまさにこの「対」で、`style.css` にはもう `n+7` が無い**（V17-c で0件）。
  ⚠️ ⭐ **設計 §8-4-3 は「数値の指定へ戻さないこと」を明示的に禁じている**のに、**このコメントは「CSS 側に `n+7` がある」と読者に教えている**——
  **次に読む人が「CSS が追随していない」と勘違いして `nth-child` を書き戻す**経路になる（⭐ **開発担当は `style.css` 側のコメントからは `nth-child` の語を外している**ので、**`app.js` 側だけ取り残されている**）。
- **重大度**: **軽微**（動作には影響しない。`grep -n 'nth-child' tools/deck-builder/style.css` の期待値0件は満たしている）
- ⭐ **対応要否は設計担当の判断待ち**（T5 のコミットにまとめて入れるのが自然と思われる）

### S-2（S1）⭐ **「面は常に1つ」（実装報告 §1-2 / §5 の逸脱1）は設計と矛盾しない**

- ⭐ **矛盾しないと判断した根拠**: ① 設計 §2-1 ③ が「PC・スマホとも**タブ**」を採っており、**帯は `role="tablist"`・面は `role="tabpanel"`**（§4-1・§8-4-1）。
  **WAI-ARIA の tabs パターンでは、選ばれていない tabpanel は表示しない**のが前提なので、**「固定タブ表示中はパネルを `hidden`」の逆向きも同じ規則から出る**。
  ② §8-4-1 の4が `hidden` を要求する理由（「見えていない tabpanel を支援技術に露出させない」）は**そのまま逆向きにも当てはまる**。
  ③ 実測でも**副作用が見つからなかった**（R-1: 統計の鮮度は保たれる・デッキ面は元の面に戻る）。
- ⚠️ ⭐ **ただし「追認」はレビュー担当の仕事ではない**。**実装報告 §6 の確認事項3 として設計担当へ回す**（⚠️ **私は追認していない**）。
  ⭐ **追認するなら設計書 §8-4-1 に5項目目として明文化されるべき**（⚠️ **書かれていないと、T5 で「整理のつもりで」戻される**＝1.1 §11-6 と同じ型）。

### S-3（S2 応答性）⭐ **並び替えを変えたときも「タブ帯まで送る」が走る**

- **実測**: 375px で `scrollY 0` からソートを `名前順 → レベル順` に変えると **`scrollY 0 → 677`（bandTop 0）**。1200px以上で帯が上半分にあるときは動かない。
- **経路**: `updateActiveSearchTab()` → `tab.ctl.run(true)` → `onStart(reset=true)` → `sendPageToTabs()`。
- ⭐ **設計違反ではない**——§2-3 で並び替えは「表示中のタブをその場で更新する＝検索が走る」と決まっており、§8-7 の「検索のたびに送る」に素直に当てはまる。
- ⚠️ ただし**ユーザーから見ると「並び替えを触っただけでページが飛ぶ」**とも読める。⭐ **§10-5 の実物確認（3）で感触を見てもらう候補**として挙げておく
  （⚠️ **実装報告 §6 の確認事項2（`behavior: "smooth"` にするか）と同じ場所の話**）。

### S-4（S1）**左ペインの「選択中の条件」の背景は直値のまま**

- 実装報告 §6 の確認事項1のとおり。⭐ **本件（T4）の範囲外という判断に同意する**（V21 が `shared/` を禁じており、`#s-selected-filters` はデッキ構築のページCSS側だが、**S-4 の裁定は「箱の背景」に限定されていた**）。

### S-5（S1・⭐ **参考。指摘というより記録**）**条件の箱の見出しだけは前のタブの文字列が残る**
