## 4. 指摘（不合格の理由）

### ❌ **M1-1 / M5-1（V7）: 別タブで投入したカードが、裏のタブでは「デッキに入っていない」ままになる**

- **該当**: `tools/deck-builder/app.js` の `selectSearchTab()`（`restoreTiles(tab)` の直後に、
  タイルの「n枚」バッジと追加行を描き直す処理が無い）。
  関連するのは `stashTiles()` / `restoreTiles()` / `updateResultBadge()` / `renderAddRow()`。
- **再現**（レビューが実行した手順・`tmp/review/未採番-検索結果のタブ化/v6-v7.mjs`）:
  1. デッキ（カード0枚）を開く。
  2. 左ペインで `sword` → 🔍検索（**検索1**・24枚）。Escape。
  3. もう一度 `sword` → 🔍検索（**検索2**・同じ24枚）。
  4. **検索2** の「熟達の剣豪（`adept-swordmaster`）」で **＋メイン** を押す
     → 検索2 のタイルは「**1枚**」・追加行が `− 1 ＋`・メインデッキ `1 / 60以上`。
  5. Escape → タブ **検索1** を押す。
- **期待**（設計書 §10-2 **V7**）:
  > 別タブに同じカードがある状態で投入 → ⭐ **そのタブを開いたときに「n枚」が反映されている**（タブを表示するたびに描き直す）

  ＝ 検索1 の「熟達の剣豪」も「**1枚**」バッジと `− 1 ＋` ステッパーになる。
- **実測**: 検索1 のタイルは **`badge="0枚" / hidden=true`**、追加行は **`＋マテリアル ＋メイン ＋サイド ＋検討中`** のまま。
  ⚠️ **同じ画面の裏側（メインデッキゾーン）には確かに1枚入っている**のに、タイルだけが「入っていない」と言い続ける
  （スクリーンショット `tmp/review/未採番-検索結果のタブ化/v7-tab1-stale-badge.png` — 左に「メインデッキ 1 / 60以上」、
  モーダル内の同じカードは「＋メイン」）。
- **重大度**: **重大**
  - ⭐ **本件の目的（「過去の検索結果が残る」）そのものを損なう**。残った結果が**嘘のデッキ状態**を表示するなら、
    残っていることが利点ではなく罠になる。
  - ⚠️ **副作用として、意図しない2枚目が入る**。ユーザーは「入っていない」と見えているタイルの `＋メイン` を押すが、
    実際には2枚目が追加される（`deckData` は正しいので `renderAddRow()` の直後に `− 2 ＋` に変わる）。
  - ⚠️ **完全に無言**。`npm run validate` は緑、例外も出ない。**人が2つのタブに同じカードを出さない限り気づけない**。
- **根拠（⚠️ なぜ「今周の欠落」なのか）**:
  1. ⭐ **原因を作ったのは T2 である。** 設計書 **§5-1** が「`tiles`＝取得済みの結果タイル（DOM）」をタブに持たせ、
     「**同じページを開いている間は、タブを切り替えても再検索しない（取得済みのタイルを出し入れする）**」と決めている。
     §5 は **T2 の設計**（§9 の単位表・設計完了 §2）。**再検索しない＝描き直されない**ので、V7 はこの決定の直接の帰結。
  2. ⭐ **後続のどの単位にも割り当てられていない。** §9 の単位表では
     **T3 = 条件の箱**／**T4 = 結果モーダルの撤去・パネル移設・`min-height`・スクロール送り**／
     **T5 = §8-1〜8-3・8-5・8-6** であり、**「タブを表示するたびに描き直す」はどこにも入っていない**。
     ⚠️ **V22（絵柄）のように「T5 でやる」と書かれている項目とは扱いが違う**（§5 参照）。
  3. ⭐ **M1-b に当たる。** 「既存では効いている副作用（結果タイルの『n枚』と追加ボタンがデッキの中身に追従する）が、
     新しく足した条件（裏のタブ）では効かない」型そのもの。`.claude/agents/review.md` の M1-b は
     **「設計書に書かれていなくても M1 の欠落＝不合格」**と定めており、**本件は設計書に書かれている（V7）**ので二重に該当する。
  4. ⚠️ **「デッキの中身に依存するのでヘッドレスでは担保できない（§10-4）」は理由にならない。**
     §10-4 自身が「⭐ **srcdoc 方式で見るか、実物確認に委ねる**」と代替手段を示しており、
     実際に**レビュー側は `/api/decks/<id>/cards` を stub するだけで再現できた**（V6 も同じ手順で ✅ にできた）。
     `.claude/agents/review.md` の「**未検証は不合格**」に照らしても、ここは検証可能な項目である。

## 6. 推奨基準の指摘（合格を妨げないもの・対応要否は設計担当の判断待ち）

### **S1（コード品質・設計との解釈差）: 固定タブを見ている間に裏の検索タブを×すると、結果ダイアログが勝手に開く**

- **実測**（`extra.mjs` / `close-bg-tab-from-deck.png`）: 検索を2回して 🃏デッキ タブへ戻す
  （`aria-selected`: デッキ=true、検索1・検索2 とも false、結果ダイアログ hidden=true）
  → **検索2 の × を押す** → **🃏デッキ が false になり、検索1 が選択され、結果ダイアログが開く**
  （デッキ面は hidden にならないので、モーダルの裏に残る）。
- 設計書 §4-2 は「**表示中のタブを ×** → 右隣 → 左隣 → デッキタブ」としか書いておらず、
  実装は「表示中」を **`activeSearchTab`（結果パネルを持っているタブ）** と解釈している。
  ⭐ 帯の選択（`selectedSearchTab`）で見ると、このとき**表示中の検索タブは無い**。
- ⚠️ **T4 で結果パネルが右列へ移ると、この分岐は「デッキを見ていたのに検索結果の面に飛ばされる」になる**ので、
  **T4 の前に解釈を決めておくほうが安い**（→ §7 の確認事項1）。
- ⭐ **S止まりにした理由**: 設計書がこの場合を書いていないため、どちらが正かをレビューが決められない。

### **S2（コード品質）: `aria-controls` が暫定で `result-grid` を指している**

- 検索タブ・固定タブの `aria-controls` がすべて別々の対象を指すべきところ、検索タブは全部 `result-grid`。
  実装報告 §4-1 が「パネルが移ったら `#view-editor` 側の tabpanel を指す」と申告済み。**T4 で必ず直すこと**。
- ⚠️ 併せて **`#result-grid` 側に `role="tabpanel"` / `aria-labelledby` が無い**（固定2つの `ed-pane-deck`/`ed-pane-stats` にはある）。

### **S3（fail-open）: 良好**

- `localStorage` が例外を投げる環境で **pageerror 0件・タブは その場限りで動作**（§3-1）。
- 保存の読み直しも `JSON.parse` を try/catch し、`n` が壊れた行は捨てて続行する作りになっている。
- 壊れた保存（`tabs` が配列でない・`cond` が未知のパラメータだらけ）でも `applyCondToForm()` が
  「選択肢に無い値・未知のパラメータは黙って無視」で落ちない。⭐ **設計 §5-2 の fail-open 要件を満たしている。**

### **S4（良かった点・記録として残す）**

- ⭐ **`filterGroups` を `condGroups()`（名前つきの1つの表）から導出した**のは良い判断（実装報告 §4-3）。
  「絞り込めるのに条件が保存されない」ずれを**構造で防いでいる**。
- ⭐ **`setSearchOrder()` の切り出し**も同様（「▲昇順と出ているのに DESC で検索する」を構造で防ぐ）。
- ⭐ **`mine()` による「結果を描いてよいのは結果パネルを持っているタブだけ」**は、
  §8-2・§8-3 を T5 に残したまま件数・警告の食い違いを防げており、切り分けとして妥当。
