## 2. いまのコード（⭐ 経路の棚卸し）

### 2-1. 絵柄を決めている2系統

| 面 | 絵柄の出所 |
|---|---|
| デッキゾーンのタイル `.gtile`（`renderZones()`） | `rowImageUrl(row, card)` = **`row.art_image` があれば `API + art_image` ／ 無ければ `imageUrl(card)`** |
| 共有画面 `#v-zones .cardph`（`renderViewZones()`） | 同上 |
| イラスト選択ダイアログ（`openArtPicker()`） | 同上（`cardImages(card)` と突き合わせて「使用中」を出す） |
| ⚠️ **その詳細モーダル** | `openDetail(slug)` → 第2引数なし → `detailArtCond = null` → `preferredArtIndex(imgs, null)` → **`imgs[0]`** |
| 検索結果タイル `.result` とそのモーダル | `preferredArtIndex(imgs, artCond)`（#97 の D-3。⚠️ **本件では触らない**） |

### 2-2. ⭐ 決定的な発見 — **タイルは、自分が表示しているURLをすでに持っている**

`.gtile` も `#v-zones .cardph` も、描画時に **`const url = rowImageUrl(row, card);`** を1回だけ計算し、
その `url` を `<img src>` に差し込んでいる。⭐ **つまり「モーダルに渡すべきURL」は、タイルの中に既に在る。**

- ⭐ だから本件は「モーダル側で絵柄を**もう一度導き直す**」必要がない。**タイルが見せている値をそのまま運べばよい**
- ⚠️ ⭐ **再導出しないことが設計の肝**。再導出すると「タイルの規則」と「モーダルの規則」の2本になり、
  **本件そのもの（片方だけが `art_image` を見る）と同じ構造を作り直す**ことになる

### 2-3. `.gtile` の画像は描画後に書き換わらない（⭐ 確認済み）

`gtile` が作られるのは `renderZones()` の1箇所だけ。以後 `img` を触るのは**無い**
（`flashTile()` はクラスの付け外しのみ・`refreshResultTiles()` は `.result` だけが対象）。
イラスト変更（`openArtPicker` → PATCH）も **`renderZones()` による全再描画**で反映される。
`#v-zones` も毎回 `innerHTML = ""` から作り直す。
⭐ **よって「タイルが持つURL」と「タイルが表示している画像」がずれる経路は無い。**

## 4. 論点1 — 「絞り込み条件」と「決め打ちのURL」をどう渡すか（⭐ issue が明示した唯一の未決点）

### 4-1. いまの形

```js
let detailArtCond = null;
function openDetail(slug, artCond) { detailArtCond = artCond || null; GA_CARD_DETAIL.openBySlug(slug); }
// init: preferredArtIndex: (imgs) => GA_CARD_SEARCH.preferredArtIndex(imgs, detailArtCond),
```

第2引数は `artCondOf(els)` が返す **`{prefixes: [...], rarities: [...]}`**（版レベルの絞り込み条件）。

### 4-2. 案の比較

| 案 | 形 | 評価 |
|---|---|---|
| **案1** 同じ引数に混ぜ、**値の形で見分ける** | `openDetail(slug, cond)` のまま。受け側で `cond.prefixes` の有無などを見て分岐 | ❌ **却下**。⚠️ **「条件」と「URL」が同じ名前の変数に同居する**ので、読み手が呼び出し元を全部見ないと意味が決まらない。⚠️ `artCondOf()` がキーを増やした日（#93 の `MULTI` に2つ目が来た日）に**判別が静かに壊れる** |
| ⭐ **案2 推奨** 第2引数を**「版の選び方（pick）」1オブジェクト**に広げ、**`{cond}` と `{url}` の排他**にする | `openDetail(slug, {cond})` / `openDetail(slug, {url})` / `openDetail(slug, null)` | ⭐ **採用**。§4-3 |
| **案3** 引数を増やす | `openDetail(slug, cond, url)` | ❌ **却下**。⚠️ **位置引数3つは呼び出し側で読めない**（`openDetail(slug, null, u)` が何を意味するか字面から分からない）。⚠️ 「両方渡す」が書けてしまい、優先順位の規則が新たに要る |
| **案4** 別関数を足す | `openDetailAt(slug, url)` を新設 | △。⭐ 呼び出し側は読みやすいが、⚠️ **`detailArtCond` を消し忘れる経路**ができる（前回モーダルの条件が残る）。⚠️ **入口が2つ**になり「どちらを使うか」の規則が増える |
| **案5** 解決そのものを `shared/js/card-search.js` に移す | `artIndexFor(imgs, pick)` を新設し `preferredArtIndex()` を包む | △ **対案**。⭐ 「どの絵柄で開くか」の決定が1ファイルに集まるのは #97 の趣旨に合う。⚠️ だが **`art_image`（デッキ構築だけの概念）を共有モジュールに持ち込む**。⚠️ `ART_COND` に `url` を足すのは**絶対に不可**（`validate` の `条件キー 2項目` の双方向照合と `els` の読み方が壊れる） |

### 4-3. ⭐ 採用する形（案2）

```js
// 詳細モーダルを「どの版で開くか」の指定。⚠ 次の3つのいずれかで、2つを同時に渡さない。
//   null        … 先頭の版（imgs[0]）で開く
//   { cond }    … 版レベルの絞り込み条件。⚠ 検索結果タイルから開いたときだけ（#97・D-3）
//   { url }     … そのタイルが表示している絵柄のURL。デッキゾーン・共有画面はこちら（#124）
let detailArtPick = null;

function openDetail(slug, pick) { detailArtPick = pick || null; GA_CARD_DETAIL.openBySlug(slug); }
```

解決は **`GA_CARD_DETAIL.init()` のクロージャ1箇所**だけ:

```js
preferredArtIndex: (imgs) => {
  const pick = detailArtPick || {};
  // ⚠ url を指定された経路は cond を見ない。落ちる先は imgs[0] だけ（#124 §5）
  if (pick.url) { const i = (imgs || []).findIndex((im) => im.url === pick.url); return i >= 0 ? i : 0; }
  return GA_CARD_SEARCH.preferredArtIndex(imgs, pick.cond);
},
```

⭐ **なぜ「排他」と書けるのか**: 呼び出し元が構造的に分かれているため。
**検索結果タイルは `cond` しか持たず、デッキゾーン・共有画面は左ペインの条件を一切見ない**（それが #97 V4 の要求そのもの）。

⭐ **`{url}` を指定したら `cond` に落ちない**のが要点。これで
**「保存版が解決できなかったデッキのカードが、左ペインの検索条件で別の絵柄になる」という #97 V4 の再発を、
フォールバックの向きで構造的に塞ぐ**（⚠️ 現にデッキゾーンでは `cond` が常に空なので実害は同じだが、**規則として書き下しておく**）。

### 4-4. ⭐ URLの運び方 — `data-art-url` をタイルに持たせる

3つの呼び出し元で**同じ読み方**にするため、タイルに属性を1つ持たせ、1本のヘルパで読む。

```js
// タイルが表示している絵柄で詳細モーダルを開くための pick。
// ⚠ ここで rowImageUrl() を呼び直さない——タイルを描いたときの値をそのまま読み戻す（§2-2）。
function tileArtPick(tile) {
  const url = tile && tile.dataset ? tile.dataset.artUrl : "";
  return url ? { url } : null;
}
```

- ⭐ **属性名は `data-art-url`**。**検索結果タイル `.result` が既に同じ名前で同じ意味（そのタイルが見せている版のURL）に使っている**ので、新しい語彙を増やさない
- ⚠️ ⭐ **`data-art-url` は `<img src>` と同じ `url` 変数から、同じ描画文の中で書く**。
  ⭐ **別途 `rowImageUrl()` を呼び直さないこと**——呼び直した瞬間に「2本の規則」が復活する
- ⚠️ **画像が無い行（`.noimg`）では属性を付けない** → `tileArtPick()` が `null` を返し、`imgs[0]` で開く（＝現状どおり）

#### ⭐ 対案: `tile.querySelector("img").src` を読む（⚠️ **採らない**）

実測では **`img.src` は `rowImageUrl()` の戻り値と文字列として完全一致する**（`https://api.gatcg.com/cards/images/Io93lyvSyg.jpg`。
⭐ 属性を増やさずに済む）。それでも採らない理由:

- ⚠️ **`img.src` はブラウザが解決した絶対URLで、テンプレートの書き方（相対パス・エスケープ）次第で `imgs[].url` と形が変わりうる**。いまたまたま一致しているだけ
- ⚠️ ⭐ **検索結果タイルでは成立しない**。あちらは**裏面一致（#46）のとき `img.src` が裏面URL**で、`data-art-url` は表面URL。
  ⭐ **後から経路を揃えるときに `img.src` 方式だと必ず破綻する**

### 4-5. ⚠️ ⭐ 範囲外だが同型の食い違いを2件見つけた（**実測済み** → ⭐ **#126 として起票した**）

タイルの **🎨（イラスト切替）で版を変えてから、そのタイルの画像を押してモーダルを開くと、切り替え**前**の版で開く**。

| 画面 | タイル初期 | 🎨 切替後のタイル | `data-art-url` | モーダル |
|---|---|---|---|---|
| トップ（`/?q=Advent+of+the+Stormcaller`） | `4ymOAWOC49` | **`o8jwanjcy4`** | — | ⚠️ **`4ymOAWOC49`** |
| デッキ構築の検索結果 | `4ymOAWOC49` | **`o8jwanjcy4`** | ⭐ **`o8jwanjcy4`（正しい）** | ⚠️ **`4ymOAWOC49`** |

- ⭐ **デッキ構築側は `data-art-url` が既に正しい値を持っている**ので、本設計の `{url}` 方式に乗せれば**呼び出し1箇所の差し替えで直る**
- ⚠️ ⭐ **ただし U1 が「検索結果経路は触らない」と決めている**ので、**本設計では直さない**。⭐ **派生issueにした** → **#126**（→ §14 N2）。⚠️ ⭐ **②の U4' でユーザーが実際に踏んだ経路でもある**（§12-3）

## 5. 論点2 — 保存版の URL が `card.editions` のどれにも一致しないとき

### 5-1. ⭐ 決定: **`imgs[0]` に倒す（fail-open）。⚠️ `cond` へは落ちない**

| 候補 | 評価 |
|---|---|
| ⭐ **`imgs[0]`（＝ `preferredArtIndex(imgs, null)` と同じ）** | ⭐ **採用**。①`preferredArtIndex()` の既存の fail-open と**同じ方向に倒れる**（規則が2つに割れない）②`currentImgs` の添字として必ず妥当（`card-detail.js` が `Math.min/max` で丸めるが、丸めに頼らない）③**いまの挙動そのもの**なので悪化しない |
| モーダルを開かない／エラーを出す | ❌ 却下。⚠️ 「カードの詳細が読めない」という**より重い劣化**に変える |
| `imgs[]` に無いURLを `#d-img` に直接入れる | ❌ 却下。⚠️ **サムネイル列（`#d-arts`）と選択状態が対応しなくなり、`currentAi` / `selection()`（#42）の前提が壊れる** |
| 注記を出す（「この版は見つかりません」） | ❌ 却下。⚠️ **U2 が「モーダル内に表示を足さない」と決めている** |

### 5-2. ⭐ 「保存版が無い行は1ピクセルも変わらない」ことの根拠（⚠️ 実測＋構造）

本設計では **保存版の有無で分岐しない**（タイルのURLを常に渡す）ので、
⚠️ **「`art_image` が null の 6,264行で `imgs[0]` 以外が選ばれない」ことを示す必要がある**。

### 10-1. ⚠️ ⭐ B-2 が no-op である理由（**1.1 で確定・「V4-a の作り方」の問題ではない**）

⭐ **1.0 の §10 は「B-2 で落ちなければ V4-a の作り方が甘い」と書いていたが、これは誤りだった。**
**開発担当とレビュー担当が独立に実測し、どちらも「B-2 はこの設計では原理的に no-op」と裁定した**ので取り消す。

| # | 根拠 |
|---|---|
| ① **構造** | 採用した案2では、デッキゾーン・共有画面が渡す pick は **`tileArtPick()` が作る `{url}` だけで `cond` を持たない**。したがってフォールバックを `cond` 側に向けても `pick.cond` は `undefined` ＝ `preferredArtIndex(imgs, undefined)` ＝ **先頭の版**で、結果が1ビットも変わらない |
| ② **V4-a の検出能力を破壊で直接示した（B-R）** | ⭐ **デッキゾーンが実際に `{cond}` を渡すように壊すと V4-a はちゃんと落ちる**。⭐ **つまり V4-a は cond 漏れを検出できる**——B-2 で落ちないのは**測り方ではなく壊し方が no-op だから** |
| ③ **絞り込み状態が作れていることを同じ測定内で示せる** | V4-a の直後に同じタブで検索結果タイルを開くと**タイルもモーダルも絞り込みの版になる**（V4-c）。⭐ **絞り込みが効いていなければ V4-c も先頭の版のままになるはず**で、そうなっていない |

⭐ **結論**: §4-3 の「フォールバックの向きで #97 V4 の再発を構造的に塞ぐ」という主張は**正しいが、効くのは排他も同時に破られたときだけ**。
⭐ **それを測れる唯一の組み合わせが B-2b で、落ちる唯一の検証項目が V4-a'**。
⚠️ ⭐ **だから V4-a' を §9 の正式な検証項目にした**（1.0 のままでは**設計の肝が未検証で合格してしまう**）。
