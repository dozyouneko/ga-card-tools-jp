# 派生issueの起票案 — GitHub復旧後、起票案と工程記録の検査をどう畳むか

⚠️ **これは設計書ではなく「issueの下書き」。** GitHubアカウント停止中で `gh issue create` が打てないため、本文をここに用意する。

- 出所: [`索引の転記ドリフト防止_設計.md`](索引の転記ドリフト防止_設計.md) §12（検査で防げないもの・この設計の寿命）
- ⭐ **起票時**: ラベル `enhancement` `検討中`（⚠️ **いま着手しない**＝復旧まで症状が出ない）

## 何が起きるか（予告）

「索引の転記ドリフト防止」の検査は、**モードB（ファイル運用）の約束事**を前提にしている:

- 工程記録を探す範囲は **`docs/design/未採番-*/` と `docs/design/待ち行列/` だけ**
- **`完了` の起票案には、`（→ 完了）` を宣言した工程記録が範囲内に1件必要**

⚠️ **復旧後の手順（索引 §2 ④）でフォルダを `<issue番号>-<タスク名>` にリネームすると、
そのフォルダの工程記録は範囲から外れ、`完了の根拠がありません` で `npm run validate` が exit 1 になる。**
⭐ **これは設計どおり**（黙って緑になるより、決め直す合図として赤くなるほうがよい）。

### ⚠️ ⭐ ただし赤くなるのは全部ではない（2026-09-13 実測・レビュー S-3）

**記録が範囲外へ出たとき、そのタスクの状態によって「赤」と「無言の緑」に分かれる**
（`matchRecords()` を記録0件で呼んで実測）:

| 状態 | 記録が範囲外へ出ると | 効く判定 |
|---|---|---|
| `完了` | **赤**（`完了の根拠がありません`） | T5 |
| `取り下げ` | **赤**（`取り下げの根拠がありません`） | T6 |
| `実装中` | **赤**（`実装中の根拠がありません`） | T8 |
| `生きている` | ⚠️ **無言で緑** | （無し） |
| `設計中` | ⚠️ **無言で緑** | （無し） |

⚠️ ⭐ **だから「完了済みフォルダから順にリネームする」と赤で気づけるが、
`生きている`・`設計中` のタスクのフォルダを先に畳むと、何も言われないまま検査の対象が減る。**
⭐ **どの案を採るにせよ、「移したフォルダの数だけ工程記録の総数が減ること」を
`task records in sync — 工程記録N件` の N で確かめる**手順を決めておく（N は成功行に出る）。

### ⚠️ ⭐ `--posting-plan`（索引 §2-③）も同じ範囲に縛られている（2026-09-13 実測・単位3の実装報告 §6-2）

⚠️ **検査（`validate`）だけでなく、復旧当日に打つ投稿計画も範囲外へ出ると壊れる**。
⭐ **索引 §2 の「③投稿 → ④リネーム」の順を守れば起きない**が、⚠️ **順を崩したときの症状が2つとも分かりにくい**:

| 崩し方 | `node scripts/gen-queue-index.mjs --posting-plan` の挙動 |
|---|---|
| フォルダを `<番号>-` に**リネームした後**に打つ | ⚠️ ⭐ **exit 0 のまま、そのタスクの記録が計画から消える**（**無言**）＝ **投函漏れになる** |
| 記録ファイルを**範囲内で**リネームして打つ | **exit 1**（`未コミットの工程記録があります（投稿順が決まらない）: <path>`）。fail-closed で安全だが、⚠️ **文面は「未コミット」で実態（リネーム）と違う** |

⭐ **どの案を採るにせよ、この2つの扱いも同時に決める**（とくに前者は「赤くならない」＝ §4-3 の
`生きている`・`設計中` が無言で緑になるのと**同じ型**）。⭐ **投函の前に一度 `--posting-plan` を通して exit 0 と件数を確かめる**（索引 §2-③ に手順として入れた）。
