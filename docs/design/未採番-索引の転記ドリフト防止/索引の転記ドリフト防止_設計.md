1. **タスクの状態は1か所だけに書く**（起票案の1行目）

## 3. 仕様 — 起票案（1行目）

### 3-1. 対象

`docs/design/**` を再帰的に走査し、**基名が `/^(派生)?起票案/` に一致する `.md`**（前方一致・既存と同じ）。

### 3-2. 1行目の書式

```text
**状態: <状態>**（最終確認 YYYY-MM-DD）— 呼び名「<呼び名>」<以降は自由記述>
```

```js
const DRAFT_RE = /^\*\*状態: ([^*]+)\*\*（最終確認 (\d{4}-\d{2}-\d{2})）— 呼び名「([^「」|`*\s]+)」/;
const STATES = ["実装中", "設計中", "生きている", "完了", "取り下げ"]; // ⚠ この順＝生成部の並び順
```

- **BOM は除去してから**、`split(/\r?\n/)[0]` を1行目とする（既存と同じ）
- 呼び名に使えない文字: `「` `」` `|` `` ` `` `*` と空白（表と正規表現を壊すため）
- 日付は形式だけ見る（値・鮮度は見ない＝既存 D4/D5 と同じ）

### 3-3. 起票案ごとの問題（**1ファイルにつき高々1行**・上から順に判定）

| 順 | 条件 | 出す行（`<path>` はリポジトリ相対） |
|---|---|---|
| 1 | 読めない | `起票案の読み込みに失敗: <path>（<message>）` |
| 2 | パスに空白・`(`・`)`・`\|`・`#` を含む | `起票案のパスに使えない文字があります: <path>` |
| 3 | 1行目が `**状態: ` で始まらない | `起票案の1行目に状態行がありません: <path>` |
| 4 | `DRAFT_RE` に一致しない（呼び名が無い等） | `起票案の1行目の書式が違います: <path>` |
| 5 | 状態が `STATES` に無い | `起票案の状態が不明です: <path>（「<語>」）` |

- 読めた起票案の間で**呼び名が重複**したら、重複した呼び名ごとに1行:
  `呼び名が重複しています: 「<呼び名>」（<path1> / <path2>）`（パスは昇順・行の順は各呼び名の先頭パスの昇順）
- **起票案が0件**なら `起票案が1件も見つかりません: docs/design`（既存 D8）
- ⭐ **走査するディレクトリが読めない**なら `起票案の走査に失敗: <dir>（<message>）` を1行（**1.1 版で明文化**。
  D10 の fail-closed を引き継ぐ＝**黙って飛ばすと起票案が静かに漏れる**）

- ⚠️ 番号付きフォルダ（`73-PRD新カード和訳/` 等）は**範囲外**（GitHubの issue に属する記録）。⚠️ 復旧後の扱いは派生起票案「**復旧後の起票案と検査の扱い**」

### 4-2. 1行目の書式

```text
**対象: 「<呼び名>」**[（→ 完了）|（→ 継続）|（→ 取り下げ）][ — <自由記述>]
```

```js
const REC_RE = /^\*\*対象: 「([^「」|`*\s]+)」\*\*(?:（→ (完了|継続|取り下げ)）)?(?: — .*)?$/;
```

| 種類 | `（→ …）` |
|---|---|
| `承認` / `実物確認結果` | ⭐ **`完了` か `継続` のどちらかが必須**。`完了`＝**そのタスクを完了とする記録**（⚠️ **軽微な残作業を後に回す承認も `完了`**——実例: 版レベルの意味統一・起票案の整合検査。残作業の `実装報告_` は完了の後に来てよい）。`継続`＝**単位の承認**や、**続きの `追加指示_` を出す承認** |
| `取り下げ` | **`取り下げ` が必須** |
| それ以外の6種類（`モック説明` `設計完了` `追加指示` `実装報告` `レビュー判定` `再判定`） | **付けない** |

### 4-3. 記録ごとの問題（**1ファイルにつき高々1行**・上から順に判定）

| 順 | 条件 | 出す行 |
|---|---|---|
| 1 | 読めない | `工程記録の読み込みに失敗: <path>（<message>）` |
| 2 | 1行目が `**対象: ` で始まらない | `工程記録の1行目に対象の宣言がありません: <path>` |
| 3 | `REC_RE` に一致しない | `工程記録の1行目の書式が違います: <path>` |
| 4 | 呼び名に一致する起票案が無い | `工程記録の対象に一致する起票案がありません: <path>（「<呼び名>」）` |
| 5 | 承認・実物確認結果が `完了`/`継続` でない | `承認_ と 実物確認結果_ の記録は（→ 完了）か（→ 継続）を宣言してください: <path>` |
| 6 | 取り下げが `取り下げ` でない | `取り下げ_ の記録は（→ 取り下げ）を宣言してください: <path>` |
| 7 | それ以外の種類が `（→ …）` を持つ | `（→ <語>）を宣言できない種類の記録です: <path>（<種類>）` |

- ⭐ **走査するディレクトリが読めない**なら `工程記録の走査に失敗: <dir>（<message>）` を1行（**1.1 版で明文化**・§3-3 と同じ fail-closed）
- ⭐ **工程記録が0件**なら `工程記録が1件も見つかりません: docs/design/未採番-* と docs/design/待ち行列`
  （**1.2 版・レビュー S-1**。⚠️ **実装は単位3のコミット**）。位置は**走査の失敗の行の直後**（1行目の読み取りより前）
  - ⭐ **入れる理由**: 単位2の時点では、走査範囲が全滅しても赤くなるのは「**完了済みの起票案が実在するから T5 が出る**」という偶然によっている
    （レビューの破壊試験 X1 で `isRecordDir` を常に false にすると16行の赤）。⚠️ **全タスクが `生きている`・`設計中` だけになった日に走査が壊れると、黙って緑になる**
    （1.2 版の実測: 記録0件のとき赤くなるのは `完了`・`取り下げ`・`実装中` の状態だけ＝T5・T6・T8）。起票案側の D8（`起票案が1件も見つかりません`）と**対称**にする
  - ⚠️ **これも「記録の問題」なので §6-1 の省略が働く**＝T5〜T8 の行は出ず、**原因を名指しする1行 ＋ 省略の1行**になる（**V45**）

## 5. 仕様 — 生成部と検査（**単位1**）

### 5-1. 新しいファイル `scripts/gen-queue-index.mjs`

- ⚠️ **Node の標準モジュール以外を import しない**（V1 で設計コミットのツリーへ単体コピーして動かすため）

- ⚠️ **コメントに `<file>.js:<行番号>` の形を書かない**（既存の検査で exit 1）

| 起動 | 動作 | 出力と exit |
|---|---|---|
| `node scripts/gen-queue-index.mjs` | 生成部を作り直して書く | 変わったら `索引の生成部を更新しました（起票案N件）`／同じなら**書かずに** `索引の生成部は最新です（起票案N件）`・exit 0 |
| `… --check` | 書かずに比べる | 同じなら `索引の生成部は最新です（起票案N件）`・exit 0／違えば標準エラーに `索引の生成部が起票案と一致しません（最初の差: 生成部のK行目）`・exit 1 |
| `… --posting-plan` | 〔単位3〕§7 | §7 |

- ⚠️ **起票案の問題（§3-3）・マーカーの問題（§5-2）があれば、どの起動でも書かない**。問題を1行ずつ標準エラーに出し、

### 5-2. マーカー

```text

<!-- QUEUE-INDEX:END -->
```

- ⭐ **行全体がこの文字列と完全一致する行だけ**をマーカーと数える（前後に空白や文字があれば数えない）。

### 5-3. 生成部の中身（⭐ **設計コミットの索引に入っているものが正解**）

## 6. 仕様 — 突き合わせ（**単位2**）

### 6-1. 実行の条件

- 起票案の問題（§3-3）が1件でもあれば、**突き合わせはせず** `起票案との照合を省略しました（起票案を読めないため。先に QUEUE INDEX DRIFT を直してください）` の1行だけを出す
- 記録ごとの問題（§4-3）が1件でもあれば、それらの行の後に `起票案との照合を省略しました（工程記録の問題が <件数>件 あるため）` を出し、**タスクごとの判定（6-2）はしない**
  （⚠️ 1つの原因で2種類のエラーを出さない＝旧設計 D6 と同じ）

### 6-2. タスクごとの判定（起票案のパスの昇順・**1タスクにつき高々1行**・上から順）

段階: `生きている`(0) < `設計中`(1) < `実装中`(2) < `完了`(3)。記録の種類ごとの**最低段階**:
`モック説明`→`設計中`、`設計完了` `追加指示` `実装報告` `レビュー判定` `再判定` `承認` `実物確認結果`→`実装中`。

| 順 | 条件 | 出す行 |
|---|---|---|
| T1 | `（→ 完了）` と `（→ 取り下げ）` の両方がある | `完了と取り下げの両方が宣言されています: 「<呼び名>」（<記録> / …）` |
| T2 | `（→ 完了）` が2件以上 | `完了の宣言が複数あります: 「<呼び名>」（<記録1> / <記録2> …）` |
| T3 | `（→ 取り下げ）` が2件以上 | `取り下げの宣言が複数あります: 「<呼び名>」（…）` |
| ⭐ **T4** | 終端の宣言が1件あり、状態がそれと違う | ⭐ `状態行が工程記録と食い違っています: 「<呼び名>」は <記録> で<完了\|取り下げ>したのに、起票案の状態が「<状態>」です（<起票案>）` |
| — | 終端の宣言が1件あり、状態と一致 | （問題なし。以下を見ない） |
| T5 | 状態が `完了` なのに `（→ 完了）` が無い | `完了の根拠がありません: 「<呼び名>」の状態は完了ですが、（→ 完了）を宣言した記録がありません（<起票案>）` |
| T6 | 状態が `取り下げ` なのに `（→ 取り下げ）` が無い | `取り下げの根拠がありません: 「<呼び名>」の状態は取り下げですが、（→ 取り下げ）を宣言した記録がありません（<起票案>）` |
| T7 | 状態がそのタスクの記録の最低段階より低い | `状態が工程記録より遅れています: 「<呼び名>」の状態は「<状態>」ですが、<記録>（<種類>）があります（<最低段階> 以上にしてください）`（記録は**最も高い最低段階を要求するもの**・同じなら**パス昇順で先**） |
| T8 | 状態が `実装中` なのに `設計完了_` も `追加指示_` も無い | `実装中の根拠がありません: 「<呼び名>」は実装中ですが、設計完了_ か 追加指示_ の記録がありません（<起票案>）` |

- 記録の列挙（T1〜T3 の括弧内）は**パスの昇順**。⭐ **T1 では完了と取り下げをまとめて1つの昇順に並べる**（種類で分けない＝**1.2 版で E-4 を追認**）
  - ⚠️ **宣言語を書き添えない**。⭐ **どちらの宣言かは接頭辞から一意に決まる**ためで、`（→ 完了）` は `承認_` と `実物確認結果_` からしか、
    `（→ 取り下げ）` は `取り下げ_` からしか来ない（§4-3 の 5・6 が他の組み合わせを**記録の問題として先に落とす**＝V31・V32 と 1.2 版の実測）

### 6-3. 出力

- 成功: `task records in sync — 工程記録N件（完了の根拠a / 継続b / 取り下げの根拠c）`（N は §4-1 の範囲で見つけたファイル数）
- 失敗: 空行 → `TASK RECORD DRIFT:` → 問題を `  - ` 付きで1行ずつ → 次の2行:

  ```text
    → 工程記録の1行目は **対象: 「呼び名」** です（承認_・実物確認結果_ は（→ 完了）か（→ 継続）、取り下げ_ は（→ 取り下げ）を付ける）
    → 状態を進める記録（設計完了_・（→ 完了））を書いたら、同じコミットで起票案の1行目を直し、node scripts/gen-queue-index.mjs を打ってください
  ```

- 置き場所: **単位1のブロックの直後**

### 6-4. ⭐ `（→ 継続）` を必須にした理由（設計中の実測）

「最後の承認で `（→ 完了）` を**付け忘れ**、状態も直し忘れる」と、`（→ 継続）` が任意の設計では**タスクは `実装中` のまま整合して緑**になる
（プロトタイプで再現・V33 の前段）。⚠️ **これまでのずれは7回とも「直し忘れ」**なので、**承認のたびに `完了` か `継続` を選ばせる**。
残る穴は「**選び間違える**」だけになる（§12）。

#### 8-4-b. レビュー **S-1** — `PLAN_KIND_ORDER` を `KINDS` から導く（⭐ **転記をやめる**）

**症状**（レビューが合成データで実測）: `KINDS`（9種）と `PLAN_KIND_ORDER`（9種）は**別々に書かれた配列で、一致を保証するものが無い**。
10種目を `KINDS` にだけ足すと `PLAN_KIND_ORDER.indexOf()` が **-1** を返し、**同時刻の並びでその種類が `承認` より前**に出る（**無言**）。

**直し方**（`scripts/gen-queue-index.mjs`・現在の `PLAN_KIND_ORDER` のリテラルを次で置き換える）:

```js
/** 締めの記録（同時刻ならこの順で先に出す・設計書 M9） */
const PLAN_CLOSING_KINDS = ["承認", "実物確認結果", "取り下げ"];
// ⚠ 3語は KINDS からの転記なので、綴りが合わなくなったら落とす（fail-closed）。
for (const k of PLAN_CLOSING_KINDS) {
  if (!KINDS.includes(k)) throw new Error(`PLAN_CLOSING_KINDS に KINDS に無い種類があります: ${k}`);
}
/** 同時刻のときの種類の順。⭐ 残りは KINDS の並びのまま後ろに続く＝10種目を足しても -1 にならない */
const PLAN_KIND_ORDER = [...PLAN_CLOSING_KINDS, ...KINDS.filter((k) => !PLAN_CLOSING_KINDS.includes(k))];
```

- ⭐ **導出結果は現在のリテラルと同じ並び**（設計担当が確認済み）＝ **`--posting-plan` の出力は是正前後でバイト一致する**（**V53**）。⚠️ **変わったら疑うのは実装**
- ⚠️ **`PLAN_KIND_ORDER` を検証のために `export` しない**（公開面を増やさない）。確かめ方は **V53・V54** の**出力側**
- ⚠️ ガードは**モジュール読み込み時**に落ちる＝ `npm run validate` も道連れで落ちる（**意図どおり**。コードを編集したときしか起きない）
