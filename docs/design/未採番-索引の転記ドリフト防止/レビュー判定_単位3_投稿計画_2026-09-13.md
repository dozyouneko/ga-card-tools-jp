### 4-3. §7-2 の「未コミットの記録」の対象範囲（報告 §6-3）

## 5. 推奨基準（S）の指摘 — **合格を妨げません**

| # | 基準 | 指摘 | 重さ |
|---|---|---|---|
| **S-1** | S1（コード品質） | ⚠️ **`KINDS`（9種）と `PLAN_KIND_ORDER`（9種）が別の配列で、一致を保証するものが無い。** 10種目を `KINDS` にだけ足すと、`PLAN_KIND_ORDER.indexOf()` が **-1** を返し、**その種類が同時刻の並びで `承認` より前に来る**（合成データで実測: `検証メモ` が `承認` の前に出た＝`u3/36-kindorder-drift.txt`）。⭐ **影響は「同じコミットで追加された記録どうしの順」だけ**なので軽微だが、**無言**。`PLAN_KIND_ORDER` を `KINDS` から導く／長さの不一致で落とす、のどちらかで塞げる | 軽微 |
| **S-2** | S3（fail-open） | ⚠️ **git 管理外で `--posting-plan` を打つと、Node のスタックトレースがそのまま出る**（`git archive` した複製で実測。exit 1・`Error: Command failed: git -c core.quotepath=false log …`＝`u3/23-nogit.txt`）。**fail-closed で安全**だが、読み手には原因が分かりにくい。`execFileSync` を try/catch して1行（例: `git を実行できませんでした（投稿順は git の追加時刻から作ります）: <message>`）にすると親切 | 軽微 |
| **S-3** | S1（コード品質） | `--posting-plan` は **`validate` から呼ばれない**ため、**壊れても誰も気づかない**（索引を読まない・ファイルを書かないので副作用は無い）。⭐ **今回のように復旧の直前にしか使わない道具としては妥当**だが、⚠️ **復旧後に初めて動かす道具でもある**。索引 §2 の手順に「**投函の前に一度 `--posting-plan` を通して exit 0 を確認する**」を1行入れておくと、当日に慌てない | 参考 |
