## 3. ⭐ (2) の判断 — **解禁（2026-10-16）はバッチの外で、公開の直前に1本だけ**

### 3-1. 結論

⭐ **訳とは独立した「解禁コミット」を、公開の直前に1本だけ立てる**（**J13**）。

| 案 | 採否 |
|---|---|
| ① 最後のバッチ（バッチ3）で取り直す | ❌ ⚠️ **バッチ3 に「訳13枚」「解禁40枚」「その日のAPIドリフト」が同居し、V5 の集合一致が破れる**（＝ #140 / #141 を混ぜないのと同じ理屈） |
| ② 解禁コミットを先に（バッチ1 の前に）作る | ❌ **10-16 以降でないと意味が無いので、バッチの着手が 10-16 まで止まる** |
| ③ ⭐ **公開直前に独立コミットを1本** | ✅ ⭐ **採用。1回公開ならコミットを増やしても公開回数は増えない＝以前は払えなかったコストがタダになった** |

⭐ **効き目**:

- ⭐ **バッチ1〜3 の手順と検証項目（V1〜V13）が1文字も変わらない**
- ⚠️ ⭐ **§0 (1) の「日付の引き金」というバッチ側の罠が消える**（**壊れうる部品を直すのではなく無くした**＝ CLAUDE.md の流儀）
- ⭐ **1.2 の §6-1 が書いていた「D1 で先に解禁ぶんを確定させてから訳を入れる」は不要になった**——
  ⚠️ ⭐ **あれは「訳と解禁が同じコミットに同居する」前提の分離手順で、1回公開では前提ごと消える**
  （**訳はもう前のコミットに入っているので、解禁コミットの差分はAPIが動いたぶんだけ**）

### 3-2. ⚠️ ⭐ 判定はカレンダーではなくライブAPIで（**J14**）

**`release_date` は `2026-10-16T00:00:00` でタイムゾーンの表記が無く、何時に反転するか保証が無い。**
⭐ **作業ツリーに触れずに1コマンドで測れる**:

## 4. ⭐ (3) の確認 — **V5 と 手順0 は未pushが積み上がっても成立する**

⭐ **成立する。基準が `origin/main` ではなく HEAD だから。** → **V5-c として設計書に明記した**。

| 検証 | 基準 | 未pushの影響 |
|---|---|---|
| **手順0（基準取り）** | `git status --short`＝**作業ツリー ↔ HEAD** | ⭐ **無し**（`origin/main` を一切参照しない） |
| **V5**（変更カードページの集合） | 同上 | ⭐ **無し** |
| **§6-0 の強い測り方**（`git archive` で親ツリーと HEAD ツリー） | **親＝直前のバッチのコミット** | ⭐ **無し**（`git archive <sha>` はローカルのコミットで動く） |
| **V1 の累計件数**（2,517 → 2,531 → 2,544 → 2,557） | HEAD からの累計 | ⭐ **無し** |

- ⚠️ ⭐ **「本番と比べる」形に書き換えないこと。** **バッチ2・3 の時点で本番にはバッチ1 が入っていないので、必ず食い違う**
- ⭐ **バッチ2 の 手順0 は「バッチ1 のコミット済み生成物」を基準にする**——
  **同じ凍結スナップショットで回せば 0件になるのが正**

### 4-1. ⚠️ ⭐ 1回公開で新しく効くようになること（#139 の外側）

- ⚠️ ⭐ **#139 のバッチが未pushで積まれているあいだ、別タスクの実装をコミットすると、
  そのタスクだけを公開する手段が無くなる**（**push はブランチ全体を送る**）。
  → ⭐ **#139 が公開されるまで、他タスクの実装コミットを挟まないのが安全**（⚠️ **#140 / #141 も同じ**）
- ⚠️ ⭐ **週1更新（次回 ≒ 2026-10-20）がこの期間に来たら、その公開に #139 のバッチが同乗する。**
  ⭐ **「大会データの更新だけです」と説明してはいけない**——`git fetch origin && git diff --stat origin/main..HEAD -- . ':(exclude)docs/*'` で**一緒に出るものを提示する**
