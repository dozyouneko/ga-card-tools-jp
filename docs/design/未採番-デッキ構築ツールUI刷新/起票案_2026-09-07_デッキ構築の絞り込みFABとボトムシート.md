# 起票案 — デッキ構築ツールの絞り込みにも FAB ＋ ボトムシートを入れる

⭐ **由来**: [`左ペイン化_設計.md`](左ペイン化_設計.md) §14-4（**2026-09-07・ユーザー判断で本タスクの範囲外と決めた分**）。

---

## 1. 何が起きているか

**2026-09-07 のユーザー決定で、1199px以下は「スマホ表示」に統一された**（設計書 §14）。
その中身がページで違う:

| ページ | 1199px以下の絞り込み導線 |
|---|---|
| **トップ（`/`）** | ⭐ **折りたたみトグル ＋ FAB ＋ ボトムシート ＋ ベール ＋ フォーカストラップ** |
| **デッキ構築** | **折りたたみトグルだけ**（`.search-top .filter-toggle`） |

⚠️ **これは劣化ではない**——デッキ構築にはもともと FAB が無く、
**本タスク（G-3b）は「既にある折りたたみ導線の帯を 860px → 1199px へ広げるだけ」**にとどめた。

⭐ **ただし「同じサイトの同じ検索条件なのに、戻り導線がページで違う」状態が残る。**

## 2. なぜ本タスクでやらなかったか（⚠️ 蒸し返さないための記録）

**2026-09-07・ユーザー判断**（設計書 §14-7 の2）。理由は実装量:

- FAB は**単体のボタンではない**。トップでは次が一式で必要だった:
  **`IntersectionObserver`（条件バーが画面外に出たら出す）／ベール（`#filter-veil`）／
  シートのダイアログ意味論（`role="dialog"` / `aria-modal` / `body.no-scroll`）／
  Tab のフォーカストラップ／Esc で閉じる／`--printbar-h` 相当の退避量**
- ⚠️ **デッキ構築には「印刷バー」が無い代わりに `.editor-bar`（sticky）と結果モーダルがある**ので、
  **退避量と z-index の設計はトップの流用ではなく作り直しになる**
- ⭐ **トップで実装したときも独立した1タスクだった**（`docs/design/未採番-UI刷新の検討/スマホ絞り込み導線_設計.md`）

## 3. やること（設計工程で決めること）

1. ⭐ **そもそも要るか**——デッキ構築の 1199px以下では、
   **`.search-top` はページと一緒に流れる**（`position: static`）ので、
   **トップのように「条件バーが画面外に出たまま戻れない」問題が起きるか**を先に実測する
   （⚠️ **トップは `.controls` が sticky だったのを static にしたために FAB が必要になった**——
   デッキ構築は元から static なので、**同じ動機が成立するとは限らない**）
2. FAB の**退避量**（`.editor-bar` は上端・結果モーダルとトーストは下端／中央）
3. **z-index の並び**（`.editor-bar` sticky ／ 結果モーダル ／ カード詳細 ／ `#tile-menu` ／ トースト）
4. **ベールとフォーカストラップをトップと共有するか**（⚠️ **現状はトップの `app.js` にしかない**＝
   移すなら `shared/js/` へ寄せる話になり、**0件文言・`preferredArtIndex()` と同じ二重定義の論点**）

## 4. ⚠️ 前提（着手前に確認する）

- ⚠️ **本タスク（デッキ構築の左ペイン化）の G-3b が入っていること**。
  入る前に着手すると、**帯が 860px のまま FAB を足すことになり、641〜1199px で導線が二重になる**
- ⚠️ **「検索結果のタブ化」と衝突しうる**——タブ化で結果モーダルが消えると、
  **FAB の退避量と z-index の前提が変わる**。⭐ **タブ化の後に回すのが手戻りが少ない**

## 5. ユーザーに確認したいこと

1. ⭐ **そもそも必要か**（§3 の1で実測してから聞く。**要らないなら取り下げる**）
2. トップと**同じ見た目・同じ操作**にするか（⭐ 揃えるなら共有モジュール化が前提）
