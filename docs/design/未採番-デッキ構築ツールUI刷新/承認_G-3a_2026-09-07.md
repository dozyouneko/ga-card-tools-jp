## 1. 承認の理由

- **M1〜M7 が全部 ✅**、⭐ **M1-b も適用して通過**。**必須条件2点**（`MOBILE_MQ` の5使用箇所を1つずつ実駆動／
  900px と 1199px の2点）も**充足**。
- ⭐ **破壊試験を「別の方法で」独立に再実施している**——`.controls` を使わず、
  **自前の sticky プローブを body 直下に挿す方式**で3本を測り直した。
  ⚠️ ⭐ **同じ手順をなぞるだけの再実施は「実装が仕込んだ前提」ごと引き継ぐ**ので、
  **手段を変えて同じ結論に着く**のは、この3つの対策（`overflow-x: clip` / `position: static` /
  `backdrop-filter: none`）のように**外すと静かに壊れる**ものを見るときに最も効く当て方。
  ⭐ **3つとも新しい帯（900 / 1199px）で load-bearing であることが確認された**——
  ⚠️ **これは「640px以下で効いていた対策が、広げた帯でも本当に効いているか」という
  G-3a 固有の問いに正面から答えている**。
- ⭐ **2ブロックの重複を静的に全数照合している**（並び順に依存しない形で）。
  ⚠️ **§14-3 の分割（導線は 1199 / 寸法は 640）は「同じ宣言が2か所に無いこと」で初めて意味を持つ**ので、
  目視ではなく全数照合で見たのは的確。
- ⭐ **`404.html` への波及を見ている**——`style.css` は `404.html` も読む。
  ⚠️ **設計書が名指ししていなかった経路**で、レビューが自分で気づいて足した分。
- **報告に無い検証6本**（重なり順・印刷バーと FAB の退避 ほか）も含め、**すべて期待どおり**。

## 2. 設計判断

### S-1 ⭐ **検査③を入れる。`E-add-1` に3本目として足す**（＝実装は1回で済む）

⚠️ **CSS の `@media (max-width: 1199px)`（絞り込み導線）と `app.js` の
`MOBILE_MQ = matchMedia("(max-width: 1199px)")` を結ぶのは、依然コメント2か所だけ。**

⭐ **裁定: 入れる。** ⚠️ **E の S1・G-2 の S-1 と同じ型なので、ここだけ入れないなら理由が要る。理由は無い。**
むしろ**この対がいちばん危ない**——**CSS を読むかぎり「直っている」ように見える**（§14-3 の警告そのもの）。

#### ⚠️ ⭐ 素朴な形は「通ってしまう」ので採らない（**実測で確認した**）

**「`MOBILE_MQ` の値が、ページCSSの `max-width` の集合に含まれること」では不足。**
理由: ⭐ **トップには `@media (max-width: 1199px)` が2ブロックある**（2026-09-07 実測）:

| ブロック | 何のためか | 結びつく相手 |
|---|---|---|
| **①絞り込み導線**（G-3a が作った） | スマホ表示への統一 | ⭐ **`MOBILE_MQ`** |
| **②`#results { display: contents }`** | 左ペイン化の裏返し | ⭐ **`PANE_MIN_WIDTH`（1200）の裏側** |

⚠️ ⭐ **①だけを 640 に戻しても、②が 1199 のまま残るので素朴な検査は通る**＝**穴が開いたまま緑になる**。

#### ⭐ 採る形：**マーカーで①を名指しする**（リポジトリに前例がある形）

- `style.css` の**①のブロックの直前**に、**マーカーのコメントを1組だけ**置く
  （⭐ `.github/workflows` の `git add` 行を `<!-- CRON-ADD:START -->` で囲っているのと同じ手口）。
- 検査は **マーカーの直後に現れる `@media` の `max-width` の値**を読み、
  **その値が `MOBILE_MQ` の値と一致すること**を見る。
- ⚠️ ⭐ **fail-closed にする**——**マーカーが無い／2組ある／直後が `@media` でない**は、いずれも **exit 1**。
- ⭐ **両辺は別ファイル（`style.css` と `app.js`）＝「同源で常に通る」形ではない。**
  ⚠️ vendor除外コメントで「入れない」と決めたのは**両辺が同じ変数から来ていた**ためで、今回は当たらない。
- ⭐ **自動で対象が広がる形にする**——**`matchMedia("(max-width: …)")` を持つページを探し、
  見つかったページにはマーカー付きの帯を要求する**。
  ⚠️ ⭐ **これで「デッキ構築に将来 JS 側の帯を足したらマーカーも要る」が、覚えておかなくても効く**
  （＝いまデッキ構築に `MOBILE_MQ` 相当が無いことを、検査の前提に埋め込まない）。

### 逸脱1 ⭐ **`.filter-rest { margin-top: 10px }` の 1199 側への移設を追認し、§14-3 の表に足す**

レビューが CSSOM で実測（**無いと 900 / 1199px で直前の `.fgroup` に密着する／640px以下への影響ゼロ**）。
⭐ **§14-3 の分割表は「開閉のグリッド」しか書いていなかった**＝**設計書の列挙漏れ**。
⚠️ **移設が正しく、設計書が不足していた**型なので、**表に1行足す**（→ 1.9）。

### 確認事項1 ⭐ **`.filter-toggle` の16px予告は外れていた。記述を実測に直す。揃えない**

⚠️ §14-3 は「移すとトグルが 641〜1199px でも 16px になる」と予告したが、
**実際は `.controls button` の詳細度が勝って 14px のまま**だった。⭐ **予告が外れた＝設計書を実測に直す。**

⭐ **結果として残る「640px 境界でトグルだけ 14→16px に変わる」既存挙動は、揃えない。** 理由:

1. ⚠️ ⭐ **G-3a が持ち込んだものではない**——`.controls button { font-size: 16px }` は**元から ≤640 にある**。
   **本タスクのスコープ外**（M7）。
2. ⭐ **揃える方向が2つあり、どちらも §14-3 の区分（寸法系は 640 に残す）を崩す最初の1件になる。**
   崩すには根拠が要るが、**いま手元にあるのは「気になる」だけ**。
3. ⭐ **判断材料は実機のタップしやすさ**なので、**ユーザーの実物確認で見てもらうほうが安い**（→ §12-9）。

### 確認事項2 ⭐ **iPad のフォーカス時ズームは「広げない」。⚠️ ユーザーに実機で見てもらう**

⚠️ **641〜1199px の入力欄は 14px のまま**なので、iOS Safari のフォーカス時ズームが起きうる
（⭐ `≤640` の `font-size: 16px` は**まさにこれを防ぐため**にあり、コードのコメントもそう書いている）。
⚠️ ⭐ **「タブレット幅でスマホ表示にする」という決定により、iPad が主な対象になり得る**のは指摘のとおり
（iPad の CSS 幅は縦 820 / 1024・横 1180 など＝**新しい帯のど真ん中**）。

⭐ **裁定: 本タスクでは広げない（現状の 14px のまま）。** 理由:

1. ⚠️ ⭐ **G-3a が持ち込んだ劣化ではない**——**1199px以下の入力欄はもともと 14px** で、
   ズームするなら G-3a の前から同じ。**帯の広げ方とは独立**。
2. ⚠️ ⭐ **実機が無いので、広げても「直った」ことを誰も確認できない。**
   **確認できない変更を本番配信物に入れない**（＝「未検証」を作らない・レビューの必須基準の趣旨）。
3. ⭐ **§14-3 の区分を崩す最初の1件になる**（上と同じ）。
4. ⭐ **ユーザーが iPad を持っているなら1分で判明する。** → **§12-9 の実物確認に足す。**
   **実際にズームするなら、そのとき別単位で広げる**（`font-size: 16px` の帯を 1199 まで広げるだけ）。
