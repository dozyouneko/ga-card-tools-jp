### 3-5. `validate` に足す検査2本

⭐ **このリポジトリで生き残っているルールは、例外なく `validate` が見張っているもの。**

| # | 検査 | 落ち方 |
|---|---|---|
| **(i)** | `shared/css/**.css` が参照する `var(--…)` が、**すべて `shared/css/tokens.css` に定義されている** | 未定義が1つでもあれば **exit 1**（名前を全部列挙する） |
| **(ii)** | **`:root {` を持つCSSファイルの集合**が、許可リスト（`shared/css/tokens.css` / `cards/cards.css` / `tournaments/tournaments.css` / `tools/print/style.css`）と**一致する** | 増えても減っても **exit 1** |

- 成功時のログ（1行ずつ）:
  `shared css tokens in sync — N トークン参照 / 未定義 0`
  `:root owners in sync — 4ファイル`
- ⚠️ **(ii) は「減った」でも落とす**（許可リスト側の消し忘れを検出するため）。
- ⚠️ ⭐ **走査するのは配信されるCSSだけ**——`docs/` は**対象外**にする
  （設計モックの `モック_PC左ペイン_2026-09-02.css` と `モック_左ペイン化_2026-09-05.css` が
  `:root` を持っており、含めると**モックを増やすたびに `validate` が落ちる**）。
- ⚠️ ⭐ **`:root` は「コメントの中」にも現れる。** 実測（2026-09-06）: `shared/css/card-detail.css` と
  `shared/css/filter-chips.css` は、**どちらも本文に `:root` ルールを持たないのに、注意書きの文中に `:root` と書いてある**。
  ⭐ **素の文字列一致で数えると、この2枚が「持っている」側に混ざって (ii) が常に落ちる**。
  → **`:root` の直後に `{` が続く形だけを数える**か、**`/* … */` を除去してから走査する**。
  ⚠️ **同じ理由で (i) の `var(--…)` 収集もコメントを含めない**（説明文に書いた変数名を「参照」と数えない）。
- ⚠️ ⭐ **検査(ii)には限界がある**（2026-09-06・レビューが実測して発見）。**`:root` ではなく `body { --panel: red }` のようにページCSSでトークンを再定義すると、`validate` は緑のまま画面だけが変わる**（`html { … }` なら詳細度で `:root` が勝つので起きない）。⭐ **これは承知のうえで許容する**——任意セレクタでのトークン再定義まで見にいくと、**ページ固有のローカル変数を誤検出する**ため。⚠️ **緑を「トークンが1本化されている証明」と読まないこと**。
- ⚠️ **cron は `validate` を実行しない**。この2本が守るのは**人が編集するとき**だけ（#40 と同じ制約）。

## 11. E：「選択中の条件」の✕・すべて解除でも再検索する（2026-09-07・ユーザー決定）

### 11-1. 決めたこと

[`承認_D_統一_2026-09-06.md`](承認_D_統一_2026-09-06.md) §2 の論点3（3通りの選択肢）について、
ユーザーが実物を触って **「①✕でも再検索する」** を選んだ。

- **症状**（変更前）: 結果モーダルを開いたまま「選択中の条件」の✕を押すと、
  **条件のチップは消えるのに結果は前のまま**。一方で**並び替えだけはその場で更新される**（C の成果）。
- ⭐ これは**承認済みの2つの決定の合成**であって基準違反ではない（Q5「チップ変更で再検索しない」＋ Q4「並び替えは常に再検索」）。
  ユーザー判断で**✕側を再検索する方に寄せる**。

### 11-2. ⚠️ ⭐ まず実測する（2026-09-07・コードを読んで確認）

| ページ | チップ本体を押す | **✕（個別解除）** | **すべて解除** |
|---|---|---|---|
| **トップ（`/`）** | 再検索する | ⭐ **既に再検索する（1回）** | ⭐ **既に再検索する（1回）** |
| **デッキ構築** | 再検索しない（Q5・意図どおり） | **再検索しない** | **再検索しない** |

仕組み（⭐ **ここを取り違えると実装を間違える**）:

- **個別✕**は `createSelectedFilters` の `chipFor()` が `item.input.click()` を呼ぶ
  → チェックボックスの `change` → **群（`fillChips` が作った `<details>`）側の `onChange`** が走る。
  トップは `updateFilterBadge(); runSearch(true)`、デッキ構築は `updateFilterBadge()` だけ。
  ⚠️ **widget に渡した `onChange` はこの経路を通らない**（コード内のコメントもそう書いてある）。
- **すべて解除**は `g.setValues([])`（⭐ `change` を発火しない）→ **widget の `onChange` を1回**。
  ⭐ **だから「すべて解除は選択件数によらず検索1回」が成立している**（V15）。

⭐ **結論: トップは既にユーザーの望む形。据え置く。変えるのはデッキ構築だけ。**

### 11-3. ⚠️ トップは1行も触らない

`index.html` / `style.css` / `app.js`（トップ）は **E では変更しない**。
⚠️ **V15（トップの回帰）は E でも生きている**——`shared/js/card-search.js` は両ページが読むので、
**共有モジュールの変更がトップの✕を2回検索にしていないこと**を数えて確認する（→ V24）。

### 11-4. 実装：`createSelectedFilters` にオプションを1つ足す

```js
// shared/js/card-search.js
GA_CARD_SEARCH.createSelectedFilters({
  container, list, groups,
  onChange,      // 「すべて解除」で全群を空にしたあとに1回だけ呼ぶ（既存）
  onRemoveOne,   // ⭐ 追加: 個別の✕を押した「後」に1回だけ呼ぶ
```

- `chipFor()` の click ハンドラを `item.input.click(); if (onRemoveOne) onRemoveOne();` にする。
- ⚠️ ⭐ **トップには渡さない。** 個別✕はもともと群側の `onChange` が再検索するので、
  **渡すと1回の✕で2回検索する**（＝APIリクエストが倍になる）。
  **この注意書きをコードのコメントに必ず残すこと**（次に触る人が「対称にしよう」として踏む形）。

| ページ | `onChange`（すべて解除） | `onRemoveOne`（個別✕） |
|---|---|---|

### 11-5. ⚠️ 却下した2案（⭐ 蒸し返さないための記録）

| 案 | ⚠️ 却下の理由 |
|---|---|

### 11-6. ⭐ 判断1：**結果モーダルが開いているときだけ再検索する**

```js
// tools/deck-builder/app.js
// ⚠️ 結果ダイアログが閉じているときに runSearch(true) を呼ぶと、searchCtl の onStart が
//    openModal(el.resultModal) を呼ぶ＝「✕を押すたびに結果モーダルが開く」。
```

  並び替えは**触っても画面が何も変わらない＝無言**なので、ガードが劣化だった。

### 11-7. ⭐ 判断2：**✕1回につき1リクエスト。デバウンスしない**

理由は3つ:

1. ⭐ **トップが既にそうなっており、揃うのが自然**（✕1回＝検索1回）。
2. ⭐ **連打しても取り違えは起きない。** `shared/js/card-search.js` の `create()` は `seq`
   （`mySeq !== seq` で早期 return する世代カウンタ）を持ち、**最後の1回だけが描画される**。
