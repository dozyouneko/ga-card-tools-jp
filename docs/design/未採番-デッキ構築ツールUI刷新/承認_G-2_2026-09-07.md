## 1. 承認の理由

- **M1〜M7 が全部 ✅**、⭐ **M1-b も適用して通過**。
- ⭐ **設計 §14-2 の実測表（＝ユーザーが「8列→6列を受け入れる」と判断した根拠）を、出荷コードで
  数値まで再現している**（1200/1240/1279 とも6列・タイル 128.66 / 135.33 / 141.83px・`.stats-pane` あふれ0）。
  ⚠️ ⭐ **承認の根拠が「設計時のモック上の数字」から「実装後の実測」へ更新された**のが本周の最大の成果。
- ⭐ **破壊試験で「無言の劣化帯」の実在を示している**——1240px で **CSS 閾値だけ 1280 に戻すと、
  `#s-selected-filters` が `display:none` に落ちる一方でアコーディオン（JS＝1200）は活性のまま**になり、
  **選んだ条件が画面のどこにも見えなくなる**。⭐ **出荷コードにその帯が無いことを同じ測定で対照**している＝
  **V51 / V53 が空回りしていないことの直接の証拠**。
- ⭐ **M1-b の当て方が的確**——**「新しく左ペインになった帯（1240px）」と「従来から左ペインの帯（1280px）」で
  レアリティ絞り込みの副作用3つを突き合わせ、全項目がバイト一致**。
  ⚠️ **G-2 は新しい絞り込み条件を足す変更ではない**ので、M1-b は
  **「帯が変わっても既存の副作用が同じか」**として当てるのが正しい。
- ⭐ **挙動を変える差分が2行しかないことを、コメントを機械的に除去して確認している**
  （`@media (min-width: 1280px)` → `1200px` ／ `PANE_MIN_WIDTH = 1280` → `1200`）。
  ⚠️ **`index.html` はコメント除去後に完全一致・`app.js`（トップ）と `shared/js/card-search.js` は非コメント差分0**
  ＝ **§14-3 のチェックリストが「コメントも直す」まで含んでいたことが、スコープの証明に使えている**。
- **V43 を合否に含めなかった判断も正しい**（G-3a / G-3b の担当）。

## 2. 設計判断（レビューが上げた2件への回答）

### S-1 ⭐ **検査を入れる。`E-add-1` の範囲を広げ、着手順を前倒しする**

⚠️ **CSS 閾値（`@media (min-width: 1200px)`）と JS の `PANE_MIN_WIDTH` のずれを止める自動検査が無い。**

⭐ **裁定: 入れる。** 根拠は3つ:

1. ⚠️ ⭐ **症状の実在がレビューの破壊試験で示されている**（推測ではない）。
   しかも**踏んだときに出るのは「選んだ条件が見えない」「E が効かない」だけで、エラーは出ない**。
2. ⭐ **E の S1 とまったく同じ構図**（守っているのはコメントだけ）で、**そちらは検査を入れる裁定をした**。
   ⚠️ **同じ型に別の判断を下すと、次に迷ったときの基準が消える。**
3. ⭐ **今回は「両辺が同源」ではない**——**CSS ファイルと JS ファイルという別々の出所**なので、
   検査は空回りしない（⚠️ vendor除外コメントで「入れない」と決めたのは両辺が同源だったため）。

#### ⭐ どこに入れるか: **`E-add-1` の範囲を広げる**（別単位にしない）

- どちらも **`scripts/validate.mjs` に検査を足すだけ**で、実行時の挙動を変えない。
  **レビューを2周に割る利得が無い。**
- ⭐ **`E-add-1` の題を「UI規約の自動検査（2本）」に改める**（→ 設計 §8-1・§11-9）。

#### ⭐ 着手順を **単位5（F-a の前）へ前倒しする**

⚠️ **F-a / F-b は、両ページに `@media (min-width: 1200px)` のブロックを新しく1本ずつ足す単位**である。
⭐ **閾値の検査が先に入っていれば、F でうっかり別の数字（1280 など）を書いた瞬間に `validate` が止まる。**
（⚠️ **後ろに置くと、F を書き終えてから気づくことになる**）

### S-2 ⭐ **§14-5 の表を直す。⚠️ ただし承認の根拠は無傷**

⚠️ 表の「1200〜1279px 現状＝8列」は不正確だった。⭐ **設計担当も独立に実測して確認した**（2026-09-07）:

| 画面幅 | G-2 前（境界1280） | G-2 後（境界1200） |
|---|---|---|
| 1200 | **8列** / タイル 133.5px | 6列 / 128.66px |
| 1240 | **8列** / タイル 138.5px | 6列 / 135.33px |
| 1279 | ⭐ **9列** / タイル **126.11px** | 6列 / **141.83px** |
| 1280 | 6列 / 142px | 6列 / 142px（＝変化なし） |

- ⭐ **1279px では列が 9→6 と大きく減るが、タイルは 126.11 → 141.83px と「大きくなる」。**
  ⚠️ **「8列→6列」という書き方は、精度が甘いだけでなく、変化の向きの一部を隠していた。**
- ⭐ **ユーザーの承認（§14-7 の1）の根拠は §14-2 の表**（＝**列が落ちないこと**と
  **`.stats-pane` が横あふれしないこと**）で、**そちらは無傷**。**承認は有効。**
- ⚠️ ⭐ **腐った数値を残さない**——**§14-5 と §14-2 の該当行を実測値に差し替える**（→ 設計 1.8）。
  ⭐ **併せて §12-9 の実物確認に 1279px を明記する**（**帯の端でいちばん変化が大きい**ため）。
