## 1. このタスクで何をするか

**トップページ（`app.js`）で、検索のやり直し（`reset`）中に `#grid` を空にしたときにページが縮み、
ブラウザがスクロール位置を上限（0）へクランプしてしまうのを止める。**

- ⭐ **方針は案1（ユーザー承認済み・2026-09-02）＝「再描画中だけ `#grid` の高さを維持する（`min-height` を退避する）」。**
  **位置を復元するのではなく、クランプ自体を起こさない。**
- ⭐ **対象はトップだけ**（ユーザー決定・2026-09-28）。デッキ構築（`tools/deck-builder/app.js`）は触らない（→ §9）
- ⭐ **`style.css` は触らない**（→ §4-4。触らないことで `validate` の検査②③の罠を丸ごと避ける）
- ⭐ **`shared/js/card-search.js` も触らない**（→ §5-2。0件文言の一本化を壊さない）

### 1-1. なぜ「位置を復元する」方式（案2・案3）を採らないか（2026-09-02 のユーザー承認の理由）

1. ⭐ **原因を直接断つ**ので、操作の種類（並び替えだけ／絞り込みを広げた／狭めた）で場合分けしなくてよい
2. ⭐ **取得が長い経路でも破綻しない。** 実測（§3-4）で **レベル順（数値ソート・絞り込みなし）は 24.2 秒**
   グリッドが空のままだった。「取得完了後に復元する」設計だと**その 24 秒間ずっと 0** になる
3. ⚠️ **既存の正しい挙動（何も変えずにシートを閉じたら位置が保たれる）を壊しにくい**

### 1-2. ⭐ 残る論点（ユーザーが許容したうえで案1を選んでいる）

⚠️ **案1でも「並び替えだけ変えたとき、同じ位置に別のカードが来る」状態は残る。**
⭐ **ユーザーはこれを承知のうえで案1を選んでいる**（2026-09-02）。

## 4. 実装（P1〜P4）

⚠️ **変更するのは `app.js` の1ファイルだけ。** ⭐ **`style.css` / `index.html` / `shared/` は触らない。**

### 4-1. P1 — 退避（`onStart` の中）

`onStart(reset)` の `if (reset) { … }` の中で、**`el.grid.innerHTML = ""` の直前**に高さを退避する。

- 測る値: **`el.grid.getBoundingClientRect().height` を `Math.ceil` した整数 px**
  - ⭐ `* { box-sizing: border-box }` なので**矩形高さ＝`min-height` の基準（ボーダーボックス）と一致する**
  - ⭐ `Math.ceil` にするのは**縮まない側へ丸める**ため（`Math.round` だと最大1px縮みうる）
- 書き方: ⭐ **CSSOM で書く**（`el.grid.style.setProperty("min-height", h + "px")`）
  - ⚠️ ⭐ **`setAttribute("style", …)` は使わない**——CSPが `style-src 'self'` なので
    **HTMLのstyle属性は使えない**（CLAUDE.md「環境の注意」）。⭐ **CSSOM は阻まれない**
    （前例: `app.js` が `--printbar-h` を `documentElement.style.setProperty()` で書いている。
    ⭐ **実測で min-height の適用を確認済み**＝§3-2）
- ⚠️ ⭐ **すでに退避中なら上書きしない**（`el.grid.style.minHeight` が空でないときは何もしない）。
  **絞り込みを連続で変えると `onStart` が2回続く**ことがあり、そのとき2回目は
  **空のグリッド（＝高さ 0 相当）を測ってしまう**ので、**1回目の退避を守る**

### 4-2. P2 — 解放（`onResults` の末尾）

`onResults` の**末尾**（`appendGrid` / `updateSearchStatus` / `el.loadMore.disabled = false` の**後**）で
`el.grid.style.removeProperty("min-height")` する。

- ⚠️ ⭐ **`appendGrid` より前に解放しない。** 先に解放すると**一瞬縮んでからまた伸びる**ので、
  その瞬間にクランプが起きて案1が丸ごと無意味になる（同一タスク内で「埋める → 解放」の順にする）
- ⚠️ ⭐ **件数に関わらず必ず解放する。** `appendGrid()` は `if (!cards.length) return;` で
  **0件のとき何もしない**ので、**`appendGrid` の中に解放を書くと 0件で永久に残る**（→ §5-1・§4-5）
- ⭐ `reset` が false（もっと見る）のときに呼ばれても**無害**（退避されていないので何も起きない）
- ⚠️ ⭐ **1.1 追記: この「同一タスクで埋めてから解放」には副作用がある**——
  **`min-height` を同じレイアウトの中で消すと、ブラウザのスクロールアンカリングが抑止される**。
  ⭐ **P2 は変えない**（変える案 (b) の代償のほうが大きい）が、**検証項目の期待値はこの副作用を織り込んで書く**（→ **§4-6**・**§5-5**・**§6-1**）

### 4-3. P3 — 解放（`onError` の末尾）

`onError` の**末尾**で同じく解放する（⚠️ **`el.grid.innerHTML = ""` の後**）。

- ⭐ **ここでは「クランプさせるのが正しい」。** エラー文は `#status`（グリッドより上）に出るので、
  **退避したまま位置を保つと、ユーザーには空白しか見えず失敗に気づけない**。
  **解放してページを縮め、0 へクランプさせることでエラー文が読める**（実測: 解放した瞬間 `y` 1524 → 0）
- ⚠️ ⭐ **`onError` では退避しない**（`onStart` が既に退避しているので、測り直すと**退避後の高さ**を測る）

### 4-4. P4 — コメント（⚠️ `validate` の生テキスト走査に当たらない書き方で）

P1〜P3 のそれぞれに、**なぜ必要か**と**外したときの症状**を1〜3行で書く。⭐ **必須の内容**:

- 「`#grid` を空にするとページが縮み、ブラウザがスクロール位置を上限へ丸める（#94）」
- ⭐ 「**PC幅ではページではなく `#results` が縮む**ので、両方に効くよう `#grid` に置く」
- ⚠️ 「**解放を落とすと、空のグリッドのぶん縦に長い空白が残り続ける**（0件検索の直後がいちばん起きやすい）」

⚠️ ⭐ **コメントに書いてはいけない字面**（`npm run validate` が **exit 1** になる）:

| 禁じ手 | 当たる検査 |
|---|---|
| `onRemoveOne` に続くコロン | ① `onRemoveOne wiring in sync` |
| `PANE_MIN_WIDTH` への代入 | ② `pane threshold in sync` |
| `matchMedia` / `max-width:` の字面 | ③ `mobile band marker in sync` |
| `<ファイル名>.js:<行番号>` の形 | `no line-number refs in code comments` |

⭐ **参照は関数名で書く**（例: `card-search.js の run()`）。
⭐ **`style.css` を触らないので、`MOBILE-BAND:START` マーカーの罠（`*/` と `@media` の間にコメントを置けない）には当たらない。**

### 4-5. ⚠️ ⭐ 「戻し忘れ」が起きたときどう見えるか（＝失敗の見え方）

⭐ **実測した**（0件検索で解放を止めた場合・390x844）:

| | 解放あり（正） | ⚠️ 解放なし（戻し忘れ） |
|---|---:|---:|
| `#grid` の高さ | **24px**（padding のみ） | ⚠️ **10,139px** |
| `scrollHeight` | **844px** | ⚠️ **10,714px** |
| `scrollY` | **0**（0件文言が読める） | ⚠️ **1500**（⭐ **画面は真っ白。下端まで送っても何も無い**） |

- ⚠️ ⭐ **「空白の海」になる。** 0件文言は画面外の `#status` にあるので、
  **ユーザーには「真っ白で何も出ない壊れたページ」に見える**（エラーも警告も出ない＝無言）
- ⭐ **ただし次の検索で自己回復する**（`onStart` が退避を上書きせず保持し、その検索の
  `onResults` / `onError` が解放するため）。**恒久化はしない**
- ⭐ **`onStart` の後に `onResults` / `onError` のどちらも来ない経路は、いまは無い**
  （設計担当が `shared/js/card-search.js` の `run()` を全部読んで確認した）:
  - `elementAndBlocked()` の早期 return は **`onResults([], { blocked: "element-and" })` を呼ぶ**
  - `mySeq !== seq` の早期 return（3箇所）は**新しい `run()` が既に `onStart` を呼んで退避の持ち主になっている**ので、
    その新しい `run()` の `onResults` / `onError` が解放する
  - ⚠️ ⭐ **`await loadEffects()` だけは `try` の外にある**が、`card-i18n.js` の `fetchJson()` が
    **`.catch(() => null)` を持つので reject しない**（＝いまは漏れない）。
    ⚠️ **`fetchJson()` の catch を外す変更が入ると、この経路が「空白の海」の恒久化に化ける**

### 4-6. ⚠️ ⭐ P2 の副作用 — `min-height` を消すとスクロールアンカリングが抑止される（1.1 で新設）

⭐ **CSS Scroll Anchoring**（ブラウザが「見ているものが動かないように」スクロール量を自動で補正する仕組み）には
**suppression trigger**（＝補正をやめる条件）がある。**仕様（CSS Scroll Anchoring Level 1 §2.2.2）の一覧には
`min-height` と `padding` が入っている**——正確には *アンカー要素からスクロールコンテナまでの経路上の要素*の
`top` / `left` / `right` / `bottom` / `margin`（と longhand）/ `padding`（と longhand）/
`width` / `height` / `min-width` / `max-width` / **`min-height`** / `max-height` の**計算値の変化**。

⭐ **`#grid` はアンカー要素（画面に見えているカード）の祖先**なので、
**その `min-height` を同じレイアウトの中で消すと、そのレイアウトでは補正が入らない。**

#### 4-6-1. ⭐ Chromium で単独再現させた（アプリと無関係な最小ページ）

⭐ **`#above`（100px）＋ `#grid`（80px × 100行）だけのページで、`scrollY=1500` から
「1タスクの中で `#above` を +23px 伸ばす」ときに何が起きるかを測った**（390x844・Chromium 1228）:

| # | 同じタスクでやったこと | `ΔscrollY` | `ΔgridTop` | 補正 |
|---|---|---:|---:|---|
| **A** | `#above` を +23px だけ（`min-height` に触らない） | **+23** | **0** | ⭐ **入る** |
| **B** | ＋ `#grid` の `min-height` を **`removeProperty`** | **0** | **23** | ⚠️ **入らない** |
| **C** | ＋ `#grid` の `min-height` を **`0px` に `setProperty`** | **0** | **23** | ⚠️ **入らない** |
| **D** | ＋ `#grid` の **`padding-bottom`** を変える（`min-height` ではない） | **0** | **23** | ⚠️ **入らない** |
| **E** | ＋ `min-height` の解放を **2フレーム後**に遅延 | **+23** | **0** | ⭐ **入る** |
| **F** | ＋ **`#grid` の「弟」のスペーサー要素**の高さを 0 に戻す | **+23** | **0** | ⭐ **入る** |

- ⚠️ ⭐ **D が重要**: **`padding` に逃げても同じ**。⭐ **「`min-height` を使うのが悪い」わけではない**
- ⭐ **F が重要**: **アンカー要素の祖先ではない要素**（弟のスペーサー）なら trigger にならない＝**案 (c) は技術的には成立する**（→ §5-5 で採らない理由）
- ⭐ **配信中の実装（`28beef4a`）は B の形**なので、**JPモードで `ΔgridTop` = 23 / `Δoff` = 0 になるのが正しい姿**

#### 4-6-2. ⚠️ ⭐ 23px はどこかが必ず吸収する（消せない量）

**JPモードでは `#status` が 33px → 56px に折り返す**（`50 件を表示 / 全 934 件` →
`40 件を表示 / 全 624 件（日本語テキスト一致・翻訳済みのみ）`）。
⭐ **この 23px は、アンカリングが入れば「スクロール量」が、入らなければ「グリッドの画面上の位置」が吸収する。**
⚠️ **どちらにしても消えない**（3通りの解放タイミングすべてで `ΔstatusH` = 23 を実測）。

| 解放のしかた | `ΔgridTop` | `Δoff` | `ΔstatusH` |
|---|---:|---:|---:|
| ⭐ **同一タスク（＝P2・配信中の実装）** | **23** | **0** | **23** |
| 2フレーム後に遅延（案 (b)） | **0** | **+23** | **23** |
| 解放しない（＝バグ） | **0** | **+23** | **23** |

⭐ **dev の実装報告の3行表を設計担当が独立に再現した**（`tmp/design/94/v5.mjs` の `MODE=real|delay|never`）。

## 5. 設計判断

### 5-1. 0件のとき・取得が失敗したとき（⭐ 0件文言との関係）

⭐ **結論: どちらも「解放してクランプさせる」＝現状と同じ見え方にする。**

| 場合 | 案1での見え方 | 根拠 |
|---|---|---|
| **0件** | ⭐ **先頭へ戻り、0件文言が読める**（`ΔgridTop` は現状と同じ 1500） | 文言は `#status`（グリッドより上）にあるので、**位置を保つと読めない**。⭐ **高さを維持したまま0件だと「空白の海」**（§4-5）になる |
| **取得失敗（経路②）** | ⭐ **先頭へ戻り、エラー文が読める** | 同じ理由（§4-3） |

- ⭐ **`shared/js/card-search.js` の `searchStatus()` は触らない。**
  0件文言は**いまの文言のまま・いまの場所（`#status`）のまま**で、**文言を1文字も増やさない**
  → ⭐ **`validate` の `search status text is single-sourced` は現状のまま緑**（断片5個・下限も動かない）
- ⚠️ ⭐ **「0件のときだけ位置を保つ」は採らない。** 保つと空白しか見えないので、
  **0件は先頭へ戻すのが情報量が多い**（＝クランプが偶然そうなっている現状が、この1点では正しい）

### 5-2. 触らないもの

| 対象 | 理由 |
|---|---|
| `style.css` | ⭐ **`min-height` を JS から直接書けば足りる**。触らないことで検査②③・`MOBILE-BAND` マーカーの罠を丸ごと避ける |
| `shared/js/card-search.js` | ⭐ 0件文言の一本化（#101/#114）と、`onStart`/`onResults`/`onError` の契約を変えない |
| `tools/deck-builder/app.js` | ⭐ **スコープ外**（ユーザー決定）。かつ**同型ではない**（→ §9） |
| スマホ帯の3つの対策 | ⚠️ **1行も触らない**（→ §5-4） |

### 5-3. ⭐ V4 の判断 — PC とスマホで挙動を分けない

⭐ **分けない。**

- 根拠: **1440x900 でも同じ欠陥が起きている**（クランプされるのが `#results.scrollTop` に変わるだけ）。
  **`#grid` に `min-height` を置けば両方に効く**ことを実測した（§3-1 の `ΔgridTop` が 375 / 390 / 768 / 1440 の4幅で 0）
- ⚠️ **幅で分岐を書くと、`validate` の検査②③（`PANE_MIN_WIDTH` / `MOBILE_MQ`）と新しい暗黙の依存を作る**。
  ⭐ **案1は幅に依存しない対策なので、そもそも分岐を書かないのが正しい**

### 5-4. ⚠️ ⭐ スマホ帯の3つの対策と干渉しないこと（実測済み）

⚠️ トップの `@media (max-width: 1199px)` には**外すと静かに壊れる対策が3つ**ある（CLAUDE.md「環境の注意」）。
⭐ **`min-height` を `#grid` に置く案1は、3つとどれも干渉しない**ことを**破壊試験で確認した**（390x844）:

| 壊した対策 | documented な症状が出るか | ⭐ 案1は動くか |
|---|---|---|
| `html, body { overflow-x: clip }` → `hidden` | ✅ **出る**（`#grid` の直前に差し込んだ sticky プローブの `top` が **0 → -1688px**＝sticky が死ぬ） | ⭐ **動く**（`y` 1501 を維持） |
| `.controls { position: static }` → `sticky` | ✅ **出る**（FAB が `is-hidden` のまま＝**永久に出ない**） | ⭐ **動く**（`y` 1501 を維持） |
| `.controls { backdrop-filter: none }` → `blur(8px)` | ✅ **出る**（シートの `bottom` が **844 → 249px**＝画面下端に来ない） | ⭐ **動く**（`min-height` の設定・解放は正常） |

⭐ **つまり「3つの対策 × 案1」はどちらも独立に効く**。⚠️ **それでも V9〜V11 で再確認する**（→ §6-3）。

### 5-5. ⭐ Q1 の裁定（1.1・2026-09-28）— **案 (a)。実装は変えず、検証項目の期待値を直す**

⚠️ **P2（同一タスクで解放）と 1.0 の V5（`ΔgridTop` = 0 ± 2px）は同時に満たせない**（→ §4-6）。
⭐ **設計担当が3通りの解放タイミングと最小ページの A〜F を自分で測り直したうえで、dev の推奨どおり (a) を採る。**

| 案 | 採否 | 理由 |
|---|---|---|
| **(a)** 実装は今のまま・**V5 の期待値を直す** | ⭐ **採用** | 下の3点 |
| **(b)** 解放を `requestAnimationFrame` 2回後へ遅延 | ❌ 却下 | 下の「(b) を採らない理由」 |
| **(c)** `#grid` の**弟**にスペーサー要素を置く | ❌ 却下 | 下の「(c) を採らない理由」 |

#### (a) を採る理由

1. ⭐ **ズレの量が「グリッドより上が伸びた量」と 1px も違わない。** 実測で
   **`ΔgridTop` 23 ＝ `ΔaboveH` 23 ＝ `ΔstatusH` 23**（33px → 56px）。
   ⭐ **`#status` はグリッドより上にあるので、そこが伸びた分グリッドが下がるのは「レイアウトとして正しい」**
2. ⭐ **#94 の症状は消えている。** 同じ操作の `ΔgridTop` は **1523 → 23**（**98.5% 減**）で、
   ⭐ **`Δoff`（スクロール量）は 1500 → 0 の飛びが完全に無くなった**（`Δoff` = 0）。
   ⚠️ **このissueが直そうとしたのは「スクロール量が上限へ丸められること」**であって、
   **「グリッドが 23px 下がること」ではない**
3. ⭐ **23px を消す方法は (b)/(c) しかなく、どちらも代償が 23px より大きい**（次項）。
   ⚠️ **`padding` に逃げても消えない**（§4-6 の D）

#### ⚠️ (b)（遅延）を採らない理由 — 3つ

1. ⚠️ ⭐ **競合が入る。** 遅延中に次の検索が始まると、**新しい `onStart` は「既に退避中」なので付け直さない**
   （＝J1 の「上書きしない」ガード）一方、**古い遅延解放が新しい検索の退避を外す**。
   ⭐ **結果は「案1が効かない検索が混ざる」＝再現しにくい取りこぼし**になる。
   直すには**世代カウンタ**が要り、**`onStart` のガードと真正面からぶつかる**
2. ⚠️ **数フレームぶん、余分な空白が下に残る**（`min-height` が2フレーム長く生きる）
3. ⚠️ ⭐ **買えるものが 23px しかない。** ⭐ **(b) にしても 23px は消えず、`Δoff` が +23 に移るだけ**（§4-6-2 の表）

#### ⚠️ (c)（弟のスペーサー）を採らない理由 — 2つ

1. ⭐ **技術的には成立する**（§4-6-1 の F で実測: `ΔgridTop` = 0・`ΔscrollY` = +23）。
   ⚠️ **だが `index.html` と `style.css` に手が入る**＝ **§5-2 の「触らない」と正面から矛盾**し、
   **`validate` の検査②③・`MOBILE-BAND` マーカーの罠を丸ごと引き受ける**
2. ⚠️ ⭐ **これも 23px は消えない**（`Δoff` が +23 に移るだけ）。**払う額に対して買うものが無い**

#### ⭐ 1.0 が誤った原因（次の人が同じ誤りを繰り返さないために）

⚠️ ⭐ **1.0 の「0 ± 2」は、設計担当の模擬実装が「解放を後のタスクでやっていた」ことの副作用だった。**

- 模擬は `innerHTML` の setter で退避し、**解放は Playwright 側から `await page.waitForTimeout(…)` の後に
  `window.__release()` を呼んでいた**（`tmp/design/94/m6.mjs` 等）＝ **§4-6 の E の形**
- ⚠️ ⭐ **つまり「設計が指示した実装（P2）」と「設計が数値を測った実装（模擬）」が別物だった。**
  ⭐ **教訓: 模擬で期待値を作るときは、模擬が指示どおりのタイミングで動いているかを必ず確かめる**
  （**「同一タスクか/別タスクか」は数値に 23px の差として出るのに、模擬の側では見えなかった**）
- ⚠️ ⭐ **これは「動いたかしか測らない検証項目」の変種**（2026-09-17 の教訓）——
  **1.0 は数値で書いていたが、その数値の出どころが実装と違っていた**

### 5-6. ⭐ Q2 の裁定（1.1）— **V11 は「`sheet-open` 以降の `gridTop` が不動」で判定する**

⚠️ ⭐ **V11（`backdrop-filter: blur(8px)` を戻す破壊試験）の素の `ΔgridTop` は 1501 になる。
これは案1の失敗ではないので、そのまま「不合格」と読んではいけない。**

⭐ **設計担当が両方を並べて測り直した**（390x844・`scrollY=1500` → FAB → チップ1つ → ✕）:

| 時点 | ⭐ 壊していない（V3 相当） | ⚠️ `backdrop-filter` を戻した（V11） |
|---|---|---|
| `before`（シートは閉じている） | `gridTop` −1188 / `y` 1500 / シート `bottom` **1012** | `gridTop` −1188 / `y` 1500 / シート `bottom` **−1083**（⭐ 閉じた位置も違う＝包含ブロックが `#controls` に変わっている） |
| **`sheet-open`** | `gridTop` **−1188** / `y` **1500** / シート `bottom` **844** | ⚠️ **`gridTop` 312 / `y` 0** / シート `bottom` ⚠️ **249** |
| `minh-set` → `grid-empty` → `minh-release` → `sheet-closed` | `gridTop` **−1188 のまま**（`y` 1501） | ⭐ **`gridTop` 312 → 313 で不動**（`y` 0） |
| **判定に使う差** | `ΔgridTop`(before→末尾) = **0** | ⚠️ `ΔgridTop`(before→末尾) = **1501** / ⭐ **`ΔgridTop`(sheet-open→末尾) = 1** |

- ⭐ **飛ぶのは `sheet-open` の時点**＝**絞り込みを変える前・グリッドを空にする前**なので、
  **壊した `backdrop-filter` 自身の症状**（シートが画面下端に来ない＝`bottom` 844 → **249**）。
  ⭐ **裏取りは「壊していない側は `sheet-open` で 1500 / −1188 を維持する」こと**（上の表の左列）
- ⭐ **だから V11 の期待値は2本立てにする**（→ §6-3 で書き換えた）:
  **① シートの `bottom` が 844 → 300px 未満（実測 249px）＝ 対策が効いていた確認** ／
  **② `sheet-open` の直後を基準にした `ΔgridTop` が 0 ± 2px（実測 1）＝ 案1が独立に動く確認**
- ⚠️ ⭐ **V9 / V10 は `sheet-open` で飛ばないので、基準を分ける必要は無い**（V9 は sticky が死ぬだけ・V10 は FAB が出ないだけ）。
  ⭐ **V11 だけが「シートの位置そのもの」を壊す試験なので、V11 だけ基準が違う**

## 6. 検証項目（⚠️ 期待値は「一致する相手」と許容差で書く）

### 6-1. ⭐ 位置の判定（1.1 で書き換えた。⚠️ **V1〜V7 は1つの式で判定する**）

⭐ **4つの量を操作の前後で測り、下の3つの判定に通す。** ⚠️ **1.0 は `ΔgridTop` 単独で判定していたが、
それだと「23px のズレが正しいのか壊れているのか」を区別できない**（→ §4-6-2・§5-5）。

| 量 | 測り方 | 何を表すか |
|---|---|---|
| `gridTop` | `#grid.getBoundingClientRect().top` を `Math.round` | **グリッドの上端が画面のどこにあるか** |
| `off` | ⚠️ ⭐ **PC幅（`#results` が `overflow-y: auto`）なら `#results.scrollTop`、それ以外は `window.scrollY`** | **スクロール量**（＝#94 が壊していたもの） |
| `aboveH` | `#grid` から `offsetParent` を辿った `offsetTop` の合計（⭐ **スクロール量に依存しない**） | **グリッドより上の高さ** |
| `statusH` | `#status.getBoundingClientRect().height` | **ステータス行の高さ**（`aboveH` が変わる唯一の出どころ） |

#### ⭐ 判定1（本体）— スクロール量は、新しい内容で届く上限で切られる以外は動かない

```text
Δoff == −max(0, off(前) − (scrollHeight(後) − clientHeight(後)))   ± 2px
```

- ⭐ **`off`・`scrollHeight`・`clientHeight` は「判定に使うコンテナ」から取る**（PC は `#results`・スマホは `document.scrollingElement`）
- ⭐ **この1本で V1〜V7 が全部説明できる**（実測値は §6-3 の各行）。
  ⭐ **0件（V7）も同じ式で通る**——上限が 0 になるので `Δoff` = **−1500** が期待値（＝先頭へ戻して文言を読ませる設計＝§5-1）
- ⚠️ ⭐ **P1（退避）を無効化すると `chip` / `jp` / `1440` のすべてで `Δoff` = **−1500** になり、この判定は NG になる**
  （実測済み）＝ **空回りしない**
- ⚠️ ⭐ **PC幅で `window.scrollY` を見てはいけない**（常に 0 なので**壊れていても合格する**＝偽陰性）。
  ⭐ **`usesResults` の判定結果が幅の予想と食い違ったら、そこで測定を止める**（→ §6-5 のひな形）

#### ⭐ 判定2（測定側の自己点検）— 3つの量のつじつまが合うこと

```text
ΔgridTop == ΔaboveH − Δoff   ± 2px
```

⭐ **これは恒等式なので「合格して当たり前」**。⚠️ **合わないときは実装ではなく測り方が壊れている**
（コンテナの取り違え・別の要素を測っている・測定のタイミングがずれている）。**先に測定を直す。**

#### ⭐ 判定3（ズレの出どころの特定）— 動いた分はステータス行の分だけ

```text
ΔaboveH == ΔstatusH   ± 2px
```

- ⭐ **`ΔgridTop` が 0 でないとき、その量が「ステータス行が伸びた量」であることを裏取りする**のがこの判定。
  ⭐ **JPモード（V5）は `ΔaboveH` = `ΔstatusH` = **23**（33px → 56px の折り返し）**
- ⚠️ ⭐ **`ΔgridTop` を単独で「0 かどうか」で見ない。** ⭐ **見るのは「`ΔgridTop` が `ΔaboveH − Δoff` と一致するか」**
  ＝ **`ΔgridTop` が 1500 前後になるのは `Δoff` が −1500 のときだけ**（＝#94 の症状そのもの）
- ⚠️ ⭐ **px の絶対値を判定基準にしない。** 判定するのは**差**だけ

### 6-2. ⚠️ ⭐ `ΔgridTop = 0` にならない正しい場合（但し書き）

**新しい結果が短くて、操作前のスクロール量まで送れないとき**は、**足りないぶんだけずれるのが正しい**。
⭐ **判定1 の `−max(0, …)` の項がこれ**。

```js
// 1) ⚠ 幅で「どちらのスクロールコンテナか」を判定する（PC は #results・それ以外はページ）
const g = document.getElementById("grid"), r = document.getElementById("results");
const usesResults = getComputedStyle(r).overflowY === "auto";
// ⚠ ここが幅の予想と食い違ったら測定を止める。取り違えると「壊れていても合格」になる
console.assert(usesResults === (window.innerWidth >= 1200), "スクロールコンテナの取り違え");
const sc = usesResults ? r : document.scrollingElement;
// 2) 4つの量（aboveH は offsetTop の連鎖＝スクロール量に依存しない）
const aboveH = () => { let n = g, y = 0; while (n && n !== document.body) { y += n.offsetTop; n = n.offsetParent; } return Math.round(y); };
const m = () => ({
  gridTop: Math.round(g.getBoundingClientRect().top),
  off: Math.round(usesResults ? r.scrollTop : window.scrollY),
  aboveH: aboveH(),
  statusH: Math.round(document.getElementById("status").getBoundingClientRect().height),
  maxOff: sc.scrollHeight - sc.clientHeight,
});
// 3) 判定（§6-1）
// 判定1: Δoff       == -Math.max(0, before.off - after.maxOff)  ±2
// 判定2: ΔgridTop   == ΔaboveH - Δoff                          ±2   （恒等式＝測定側の自己点検）
// 判定3: ΔaboveH    == ΔstatusH                                ±2
// 4) 退避中の様子は MutationObserver で拾う（グリッドが空になる瞬間は一瞬）
new MutationObserver(() => console.log(g.childElementCount, getComputedStyle(g).minHeight, JSON.stringify(m())))
  .observe(g, { childList: true });
```

`removeProperty` を包んで `this === g.style && p === "min-height"` でログを足す**
（⚠️ **ブラウザの中だけを触るので、ファイルは1つも書き換えない**）。
