## 1. 背景と目的

### 1-1. 何がドリフトするか

`.github/workflows/build-tournaments.yml` の **`git add` の対象**（＝日次cronが自動publishする範囲）は、
**3箇所に同じ列挙が書かれている**:

| # | 場所 | 役割 |
|---|---|---|
| **正** | `.github/workflows/build-tournaments.yml` の `git add` 行 | **実際の挙動** |
| 写し1 | `README.md`「大会データの自動更新」節 | 外部の読者向け |
| 写し2 | `CLAUDE.md`「cronがコミットする範囲」 | セッション向け（**判断に直結**） |

⚠️ **写しを直す係がいない。** ワークフローを変えても写しは黙って古いままになる。

### 1-2. すでに2回起きている

| 時期 | 何が起きたか |
|---|---|
| `#30`（2026-07-27） | cronのコミット範囲を7パスに拡大したが、README・CLAUDE.md を更新しなかった |
| `#69`（2026-08-15） | 上記が発覚。README は「**カードページは含めません**」と**事実と正反対の断定**のまま約3週間放置。さらに CLAUDE.md 側は **`index.html` が抜けていた**（＝トップページも自動publishされる事実が読み取れなかった） |

### 1-3. なぜ厄介か

- **失敗が無言**。ワークフローは正常に動き続け、cronは緑のまま、誰も気づかない
- ⚠️ **間違ったドキュメントは無いより悪い**。`#69` の「カードページは含めません」は、
  **「新セットの日に数百〜数千ファイルがレビューなしで自動publishされる」という #30 の要点を打ち消していた**
- 3度目が起きる条件は「ワークフローの `git add` を1つ足す」だけ

### 1-4. 目的

**列挙が食い違ったまま気づかれない状態を無くす。** ドキュメントの列挙自体は**残す**
（`CLAUDE.md` は「読めば分かる」ことに価値があり、毎回ワークフローを開かせるのは後退のため）。

## 2. 案の比較と採否

### 2-1. 前提: ドリフトを起こすのは誰か

⭐ **`git add` 行を書き換えるのは常に人（＝作業ツリーで動くセッション）であり、cronではない。**
cronはワークフローを読むだけで、書き換えない。

→ この前提が案の評価を決める。**検出は「作業ツリーで人が変更した直後」に効けばよく、
cronの実行時に効く必要はない**。issue本文が案Aの短所に挙げていた
「⚠️ cronは `validate` を実行しない」は、**本件には当たらない**（#40 は「新セットが公式APIに増える」＝
人の操作と無関係に起きるので当たっていた。本件は起点が人の編集なので事情が違う）。

さらに、この作業ツリーで `scripts/` や `.github/` を変更する経路は
**設計 → 実装 → レビュー**の3工程を通り、**レビューの必須基準 M3 が `npm run validate` の exit 0 を要求する**
（`.claude/agents/review.md`）。**`validate` に載せれば、レビューを通る限り必ず踏む。**

### 2-2. 案の比較

| 案 | 内容 | 判定 |
|---|---|---|
| **A** | `npm run validate` に**3箇所の集合一致検査**を足し、食い違えば **exit 1** | ⭕ **採用**（§3-2） |
| **B** | ワークフローの `git add` 行の**直上コメント**に追従先2箇所を明記 | ⭕ **採用**（§3-3。Aと併用） |
| C | ドキュメントの列挙をやめ、「正はワークフロー」への参照だけにする | ❌ **不採用**。列挙が読めること自体に価値がある（§1-4）。⭐ **Aを入れれば二重管理のコストは機械が払う** |
| **D** | **hook**（`build-tournaments.yml` を編集した瞬間にハーネスが警告を出す） | ❌ **不採用**（§2-3・実測の末に却下） |
| E | GitHub Actions で push 時に `validate` を走らせる | ❌ **不採用**。この運用は**mainへ直接push**するので、赤が出た時点で**既に本番公開済み＝手遅れ**。cronの自動コミットで毎日走るノイズも増える |

### 2-3. 案D（hook）を却下する根拠

⚠️ **推測ではなく実測で潰した。** 4セッションにわたる実測の全記録は
[`実測メモ_hook.md`](実測メモ_hook.md)（撤去も完了済み）。結論だけ:

| 実測結果 | 案Dへの意味 |
|---|---|
| ⭕ `if:` はツール名＋パスで正確に絞れる／**exit 2 + stderr**・`additionalContext` はモデルに届く | **配管は全通した**（＝技術的には作れる） |
| ⚠️ **同じ定義でも発火しない起動が実在した**（第3段は全滅、第4段は成立） | ⛔ **決定的**。⭐ **失敗が無言**という、本件で潰したい失敗そのものを持ち込むことになる |
| ⚠️ Bash（`sed -i` 等）経由の編集は捕まらない | 取りこぼしが構造的に残る |
| ⚠️ 設定変更は**セッション再起動まで効かない**／**変えたセッションでは以後止まる**（R6） | 導入当日は効かない・入れた本人が効きを確認できない |
| ⚠️ 効くのは**このコンテナの Claude セッションだけ** | GitHub Web UI での直接編集・他マシンからの変更には無力 |
| ❌ `systemMessage` はモデルに届かない | 警告経路が exit 2 + stderr に限られる |

⭐ **「無言で効かないことがある保険」より、「必ず踏む場所で必ず落ちる検査」を採る**、というのが判断。
（`validate` は同期実行で結果が exit code に出るため、効かなかったことが**隠れない**。）

⚠️ ただし**実測の資産は捨てない**。`実測メモ_hook.md` は
「このリポジトリで hook が使えるか」の一次資料として残す（`#63` skill 検討の材料でもある）。

### 2-4. 案Aの短所「検査自体が脆い／陳腐化する」への対処

issue本文が案Aに付けた最大の懸念は**「ドキュメントの節の範囲指定・表記ゆれに依存して脆い」**だった。
⭐ **脆いこと自体は避けられない。避けるべきは「脆くて、壊れたときに黙って通る」ことである。**

→ **抽出に失敗したら「一致」とみなさず、問題として報告して exit 1 する**設計にする（§3-2④）。
具体的には次の4つを**すべて loud に落とす**:

1. ワークフローの `git add` 行が**1行でない**（0行＝行が消えた／2行以上＝分割された）
2. ドキュメントのマーカーが**片方でも無い**
3. マーカー間に**列挙が0個**
4. 集合が**食い違う**

#### 設計時の実測（2026-08-16）

抽出規則が**今日の実データで成立する**ことを確認済み。

```text
$ grep -cE '^[[:space:]]*git add ' .github/workflows/build-tournaments.yml
1
$ grep -E '^[[:space:]]*git add ' .github/workflows/build-tournaments.yml | sed -E 's/^[[:space:]]*git add //' | tr ' ' '\n' | wc -l
8
```

⚠️ **`grep -c "git add "`（行頭指定なし）だと 2 になる**（コメント行 36 が「下の git add 対象(#30)」と書いている）。
⭐ **抽出規則は「行頭＝インデントを除いて `git add ` で始まる行」でなければならない。**

ドキュメント側も、現在の README（170〜171行目）・CLAUDE.md（546〜547行目）の
インラインコードを抽出したところ **3箇所とも 8パスで完全一致**することを確認した（順不同・末尾スラッシュ除去）。

#### マーカーがGitHubの描画に出ないことの実測

HTMLコメントのマーカーを箇条書きの途中に入れても**描画に一切現れない**ことを、
GitHub の Markdown API（`POST /markdown`・`mode=gfm`）で実測した:

```text
入力: - コミット対象は <!-- CRON-ADD:START -->`data/tournaments` / … `index.html`<!-- CRON-ADD:END -->
出力: <li>コミット対象は <code>data/tournaments</code> / … <code>index.html</code><br>…</li>
      （マーカー文字列の出現数 = 0・箇条書きの構造も維持）
```

## 3. 変更内容

### 3-1. ドキュメントの列挙をマーカーで囲む

**マーカー**: `<!-- CRON-ADD:START -->` … `<!-- CRON-ADD:END -->`

⚠️ **マーカーは列挙そのものだけを囲む**（注釈・前後の文は外に出す）。
中に別のインラインコード（例: `` `build:cards` ``）が入ると、それがパスとして拾われるため。

#### ① `README.md`「大会データの自動更新」節（現 170〜173行目）

変更前:

```markdown
- コミット対象は `data/tournaments` / `tournaments` / `sitemap.xml` / `cards` / `sets` /
  `data/card-meta-index.json` / `data/featured-sets.json` / `index.html`
  （⚠️ #30 以降、**カードページ・セットページ・トップページも含みます**。新セットが出た日は
  数百〜数千ファイルがレビューなしで自動publishされます）
```

変更後（⚠️ **マーカーを足し、末尾に注記の子箇条書きを1つ追加するだけ**。列挙の中身は変えない）:

```markdown
- コミット対象は <!-- CRON-ADD:START -->`data/tournaments` / `tournaments` / `sitemap.xml` / `cards` / `sets` /
  `data/card-meta-index.json` / `data/featured-sets.json` / `index.html`<!-- CRON-ADD:END -->
  （⚠️ #30 以降、**カードページ・セットページ・トップページも含みます**。新セットが出た日は
  数百〜数千ファイルがレビューなしで自動publishされます）
  - 正は [build-tournaments.yml](.github/workflows/build-tournaments.yml) の `git add` 行です。
    ⚠️ 変更したらこの列挙も直してください（`npm run validate` が一致を検査し、食い違うと exit 1 します）
```

#### ② `CLAUDE.md`「cronがコミットする範囲」（現 545〜552行目）

変更前:

```markdown
  - **cronがコミットする範囲**(#30・2026-07-27〜):
    `data/tournaments` `tournaments` `sitemap.xml` `cards` `sets` `data/card-meta-index.json`
    `data/featured-sets.json` **`index.html`**
```

変更後:

```markdown
  - **cronがコミットする範囲**(#30・2026-07-27〜):
    <!-- CRON-ADD:START -->`data/tournaments` `tournaments` `sitemap.xml` `cards` `sets` `data/card-meta-index.json`
    `data/featured-sets.json` **`index.html`**<!-- CRON-ADD:END -->
```

さらに、同じ節の「⭐ 正は**ワークフローの `git add` 行**…」の箇条書き（現 551〜552行目）の**直後に**、
子箇条書きを2つ追加する（既存の2行は**変えない**）:

```markdown
      - ✅ **2026-08-16〜、`npm run validate` が3箇所(ワークフロー・README・CLAUDE.md)の集合一致を検査する**(#70)。
        食い違うと **exit 1**。⚠️ **cronは `validate` を実行しない**が、`git add` 行を変えるのは**常に人**なので
        検出経路として成立する(レビューの必須基準 M3 が `validate` の exit 0 を要求する)
      - ⚠️ 上の列挙は**HTMLコメントのマーカーで囲ってある**(GitHubの描画では見えない)。
        **節を書き換えるときもマーカーを消さない**(消すと検査が exit 1 で落ちる＝安全側だが手を止める)
```

⚠️ **この2行の本文にマーカー文字列そのものを書かないこと**（書くと V2 の期待値が変わる）。

### 3-2. `scripts/validate.mjs` に一致検査を追加する

**配置**: 既存の「メタ索引の並び替えキーの内部整合チェック（#43）」ブロックの**直後**、
`if (problems > 0)` の**直前**。既存様式（`{ … }` ブロック / `bad[]` に積む / `problems++` /
大文字ラベルの `console.error` / 最後に `→` の手順案内）に合わせる。

#### ① 抽出規則

| 出所 | 規則 | 今日の値 |
|---|---|---|
| ワークフロー | `.github/workflows/build-tournaments.yml` を読み、**`/^\s*git add /` に一致する行**を集める。**ちょうど1行**であること。その行から先頭の `git add ` を除いた残りを**空白で分割** | 1行 / **8パス** |
| `README.md` / `CLAUDE.md` | `<!-- CRON-ADD:START -->` と `<!-- CRON-ADD:END -->` の**間の文字列**（複数行にまたがる）を取り、その中の**インラインコード `` `…` `` をすべて**抽出 | 各 **8パス** |

#### ② 比較方法

**末尾スラッシュだけ落として集合比較**（順序・重複は問わない）。

- 順序を検査しない理由: 順序が違っても**情報は欠けない**。ノイズになる検査は入れない
- 末尾スラッシュを落とす理由: `cards` と `cards/` の違いは**パスの増減を隠さない**ので、
  正規化しても検査は嘘をつかない

#### ③ 出力（文言はこのとおり）

成功時（`console.log`・1行）:

```text
cron git add paths in sync — 8パス（README.md / CLAUDE.md）
```

（`8` は抽出したパス数。将来増減する）

失敗時（`console.error`）:

```text
CRON PATH DRIFT (.github/workflows/build-tournaments.yml):
  - README.md に無い: index.html
  - CLAUDE.md にだけある: foo
  → 正はワークフローの git add 行です。README.md「大会データの自動更新」節と
    CLAUDE.md「cronがコミットする範囲」のマーカー間の列挙を合わせてください
```

#### ④ 報告する異常（**すべて `problems++` → exit 1**）

| # | 条件 | メッセージ |
|---|---|---|
| 1 | `git add` 行が1行でない | `git add 行が1行ではありません（N行）— 抽出規則が陳腐化しています` |
| 2 | マーカーが片方でも無い | `<ファイル名> にマーカーがありません` |
| 3 | マーカー間にインラインコードが0個 | `<ファイル名> のマーカー間に列挙がありません` |
| 4 | 集合が食い違う | `<ファイル名> に無い: …` / `<ファイル名> にだけある: …` |
| 5 | ファイルが読めない | `読み込みに失敗: <メッセージ>` |

⚠️ **1〜3・5 を「一致」に倒してはいけない**（§2-4）。**検査が壊れたときに黙って通る**のが最悪。

⭐ **両辺は同源にならない**（ワークフローを読む側とドキュメントを読む側が別ファイル）ので、
レビュー基準 M5「検査の両辺が同源だと常に通る」には該当しない。

### 3-3. ワークフローに追従先コメントを足す（案B）

`.github/workflows/build-tournaments.yml` の **`git add` 行（現62行目）の直上**に、
既存の `index.html` に関するコメントに続けて次を追加する:

```yaml
          # ⚠ この git add の対象を増減したら、README.md「大会データの自動更新」節と
          #   CLAUDE.md「cronがコミットする範囲」の列挙も直すこと(#70)。npm run validate が
          #   3箇所を集合比較しており、食い違うと exit 1 する。
```

⚠️ **`git add` 行そのものは1文字も変えない**（＝cronの挙動は不変）。
⚠️ **`git add` を複数行に分割しない**（§3-2④-1 で落ちる）。

### 3-4. 変更しないもの

| 対象 | 理由 |
|---|---|
| `docs/design/30-cron生成物の同期/` の列挙 | **日付つきのスナップショット**（当時の設計判断の記録）。現況に追従させるものではない。⚠️ **検査対象にもしない** |
| `.claude/agents/*.md` | 列挙を持っていない |
| cronの挙動（`git add` の対象そのもの） | 本件は**ドリフト防止**であって、範囲の見直しではない |

## 5. 保証の範囲と、残るリスク

⭐ **保証できるのは「作業ツリーで `npm run validate` を打った時点で食い違いが見つかる」ことだけ。**

| 経路 | 検出できるか |
|---|---|
| このリポジトリで**セッションがワークフローを編集** → 実装 → レビュー（M3 で `validate`） | ⭕ **止まる** |
| 人が手元で編集して `validate` を打たずに push | ❌ **すり抜ける**（→ 案Bのコメントが最後の砦） |
| **GitHub Web UI** から直接ワークフローを編集 | ❌ **すり抜ける**（この運用では通常起きない） |
| cronの自動コミット | ⭕ **そもそもドリフトを起こさない**（cronはワークフローを書き換えない） |

⚠️ **「検査があるから安心」と書かない。** 案Bのコメント（§3-3）は、`validate` を打たない経路への
唯一の保険として**必ず併せて入れる**。

## 6. ロールバック

| 状況 | 手順 |
|---|---|
| 検査が誤検出して作業を止める | `scripts/validate.mjs` の追加ブロックを丸ごと削除して再実行（**ほかの検査に影響しない独立ブロック**） |
| マーカーが邪魔 | マーカーを消すと検査が exit 1 で落ちる。**検査ブロックとマーカーは同時に外す** |
| 本番影響 | **無い**。cronの `git add` 行を変えないため、公開物は1バイトも変わらない（`scripts/` `README.md` は配信されるが、サイトの表示・生成物は不変） |
