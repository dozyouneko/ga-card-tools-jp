## 1. 背景と目的

### 1-1. 「新セットが来たら手で足す辞書」が `meta.sets` 以外にもあった

#40 で判明した落とし穴 — **ページ・sitemap・絞り込みの選択肢は日次cronがAPIから自動生成するが、
`data/translations.js` の一部だけは手書きで、更新の号令が無い** — は `meta.sets` に限らなかった。

#73(PRD 254枚の和訳)で、同じ型の抜けが**3種類**見つかった:

| # | 抜けている辞書 | 症状 | fail-open か |
|---|---|---|---|
| A | `meta.subtypes` | カードページ・詳細モーダルの**サブタイプ行が素の英字**(`VELTECH` 等) | ✅ 英字のまま出るだけ |
| B | `terms` | 効果文中の用語に**ハイライトも用語解説も出ない** | ✅ 素の文字のまま出るだけ |
| C | `TRANSLATION.md` の表記表 | **表記ルールの原本が実データと食い違う**(`Retort`) | ⚠️ 人が誤訳を書く原因になる |

⚠️ **いずれも `npm run validate` が緑のまま通る。** 破綻しないので画面を見ても気づけない
(#40 の SP4 が約1か月放置されたのと同じ構造)。

### 1-2. この設計書の目的

1. **今ある抜けを埋める**(§3-1〜§3-4)
2. ⭐ **次に同じ抜けが起きたとき、人を止める/痕跡を残す経路を作る**(§3-5・§3-6)

⚠️ 1 だけやると**同じことがPRDの次のセットで再発する**。#40 の教訓は「埋めた」ではなく
「**検出経路を2つ作った**」ことだったので、ここでも同じ形に倒す。

### 3-1. `data/translations.js` の `meta.subtypes` に10種を追加

⚠️ **既存エントリはアルファベット順に並んでいるので、その位置に挿入する**(末尾に足さない)。

⚠️ **`meta.subtypes` は日本語検索(JPモード)の索引には影響しない。**
`data/card-meta-index.json` が持つのは**英字コード**なので、**索引の再生成は不要**。
影響するのは**表示だけ**(サブタイプ行・`highlightSubtypes()` によるハイライト)。

### 3-2. `data/translations.js` の `terms` に15種を追加

形は既存エントリと同じ `{ jp, desc }`。**`jp` は §2-2 の既訳表記をそのまま使う**
(⚠️ `highlightTerms()` は `jp` の「（」より前を日本語文から探すため、**既訳と字面が違うとハイライトが効かない**)。

- **複数枚で使われる3種**(`training` / `blood` / `lash`)は、効果文から読み取れる範囲で `desc` を書く
- **1枚だけの12種**は `aim counter` / `age counter` と同じ**スタブ説明**にする:
  `「◯◯」でのみ使用されるカウンター。詳細は元カードを参照。`
- ⚠️ **カウンターの挙動を推測で書かない**(CLAUDE.md: 公式APIに用語定義のエンドポイントは無く、
  裏が取れるのは効果文とリマインダー文だけ)。**上限・範囲・タイミングを断定しない**

### 3-3. `training counter` の表記を統一する

**推奨: 「修練カウンター」に寄せる**(⚠️ §8-1 で承認を得てから実施)。

- 多数派(7枚・14回)であり、既存の `frost`→霜 / `debt`→負債 / `divination`→占術 と同じ
  **「意味のある語は和語、固有名詞・造語はカタカナ」**の慣行に合う
- 直す対象は **2枚**(`greater-boon-of-dux` / `where-futures-stir`)。トレーニング→修練
- ⚠️ **`where-futures-stir` は #73 で入れたばかりの訳**。#73 の設計判断を上書きする形になるため、
  実装担当ではなく**設計担当(＝この設計書)の判断として明記**しておく

### 3-4. `TRANSLATION.md:77` を `Retort → リトルト` に修正

⚠️ **ルート直下＝本番配信対象**(`/TRANSLATION.md` は 200 で配信される)。**pushはユーザー判断**(§7)。

### 3-5. ⭐ `scripts/validate.mjs` に「サブタイプ辞書の網羅性」検査を追加する(#40 と同型)

**正は `data/card-meta-index.json`**(コミット済み・日次cronが毎日再生成する)。

```js
// data/card-meta-index.json の m[slug][3] がサブタイプのトークンID列(#27の形式)
const used = new Set();
for (const e of Object.values(idx.m)) for (const i of e[3]) used.add(idx.d[i]);
const missing = [...used].filter((code) => !(loaded.meta.subtypes || {})[code]);
```

- ⭐ **ネットワーク不要**。`validate` は現在まったく fetch しない作りなので、**その性質を壊さない**
- ⭐ **#40 と同じ「コミット済みの生成物を正とする」形**。生成スクリプトを呼んで突き合わせない
  (両辺が同源になり常に通ってしまう)
- ⚠️ **片方向にする**(辞書にあるが実データに無い＝`SHENJU` は**報告しない**)。
  先回りで訳を入れておくのは正当なので、ここで落とすと**正しい運用が止まる**
- 落ちたときのメッセージは `data/translations.js` の `meta.subtypes` への追記を促す形にする(#40 の文面に倣う)
- **プロトタイプ実測済み**: この方法で §2-1 の10種を**過不足なく**検出できることを確認した
  (API スナップショット由来の集計と**完全一致**)

⚠️ **cron は `validate` を実行しない**ので、これは**人を止める経路**。
cron ログ側の痕跡は既存の `gen-card-meta-index.mjs` の完走サマリで足りる(サブタイプは索引に入るため、
**索引が生成できていれば新サブタイプは必ず索引に載る**)。

### 3-6. `scripts/check-terminology.mjs` に「カウンター語の未登録」スキャンを追加する

⚠️ **これは `validate` には置けない。** 判定に**効果文の英語原文**が要るが、原文は
`tmp/api-cache/`(gitignore)にしか無く、コミット済みの生成物には含まれないため
**オフラインでは判定できない**。`check-terminology.mjs` は**すでにAPIを叩く手動ツール**で、
「表記ゆれの疑い一覧」を出す役なので、ここが正しい置き場になる。

- 規則: 効果文(`*` 除去済み)から `([a-z]+) counters?\b` を拾い、
  **`"<語> counter"` も `"<語>"` も `terms` に無いもの**だけを報告する
- ストップワード(`of` / `each` / `more` / `those` / `four` …)を除く
  (⚠️ 除かないと `2 or more counters` 等が候補に紛れる。**実測で確認済み**)
- ⭐ **§2-2 の15種を過不足なく出せることを実測済み**(誤検出0)
- ⚠️ **exit code は変えない**(既存どおり「疑い一覧」として出すだけ)。
  誤検出があり得る性質のツールなので、赤くすると使われなくなる

## 5. 保証の範囲と、残るリスク

| 守れること | 守れないこと |
|---|---|
| **サブタイプ**の抜けは `validate` が**人を止める**(#40 と同じ強さ) | ⚠️ **cron は `validate` を実行しない**ので、**新セット当日の自動publishは止められない**(#40 と同じ) |
| **カウンター語**の抜けは手動ツールが一覧で出す | ⚠️ **カウンター以外の新キーワード**は機械的に検出できない(公式APIに用語定義のエンドポイントが無い＝#73 実測) |
| 既訳の表記に合わせるのでハイライトが効く | ⚠️ **今後の表記ゆれ**は防げない(`check-terminology.mjs` の既存機能が疑い一覧として出すのみ) |

⭐ **フレーバー未訳の検査は、この設計書では見送る。**
**原文フレーバーを持つ1,200枚のうち、和訳が入っているのは117枚だけ**(2026-08-20実測・**未訳90%**)。
全体を対象にすると**常時赤**になり、検査として機能しない。
対象セット限定にする案もあるが、「どのセットを完訳扱いにするか」の管理が新たに手書きで増え、
**同じ型の落とし穴を1つ作る**ことになるため、費用対効果が合わない。

⚠️ **フレーバーの「表示されない」不具合は別issue**(`docs/design/未採番-フレーバー表示経路/`)。
本設計書と**変更ファイルが重なる**(どちらも `data/translations.js` 以外に `scripts/` を触る)ため、
⭐ **同時に走らせず、片方を完了させてから着手する**(WIP=1)。

### 8-1. ⚠️ `training counter` をどちらに寄せるか

### 8-2. `SETTLEMENT` / `VEHICLE` の訳語

和語(集落 / 車両)を推奨したが、カタカナ(セトルメント / ビークル)も既存の慣行に反しない
(辞書は**両方の流儀が混在**している: `CASTLE`→城 と `CHESSMAN`→チェスの駒)。
**各1枚しか無いので影響は小さい**。承認時に決めてよい。

### 8-3. 1枚だけのカウンター12種を本当に全部登録するか

`aim counter` / `age counter` の前例に倣う方針にしたが、**登録しない**選択もある
(その場合 §3-6 のスキャンが毎回12件を報告し続けるので、**除外リストが必要になる**)。
⭐ **登録するほうが安い**と判断した。
