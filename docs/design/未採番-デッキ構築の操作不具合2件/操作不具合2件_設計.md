## 3. 不具合1：デッキ側の＋でページが上へ飛ぶ（単位1・設計確定）

### 3-1. 再現（実測）

**手順**: デッキを開く → ページを下へ送り、メインデッキの11枚目のタイルを画面の上から約300pxの位置に置く →
タイルにホバーして **＋** を押す → 1.2秒待って `scrollY` を読む。

| 画面 | 押したゾーン | scrollY（前 → 後） | Δ |
|---|---|---|---|
| 1440×900 | メイン | 669 → 195 | ⚠️ **−474** |
| 1440×900 | サイド | 1143 → 0 | ⚠️ **−1143**（0で頭打ち） |
| 1440×900 | 検討中 | 1419 → 0 | ⚠️ **−1419**（0で頭打ち） |
| 1200×900 | メイン | 609 → 174 | ⚠️ **−435** |
| 1920×1080 | サイド | 862 → 0 | ⚠️ **−862**（0で頭打ち） |
| 1199×900（スマホ表示） | メイン | 878 → 430 | ⚠️ **−448** |
| 375×812（スマホ表示） | メイン | 3078 → 1638 | ⚠️ **−1440** |

- ⭐ **Δ は「押したゾーンより上にあるゾーンの高さの合計」に一致する**。1440×900 ではマテリアルゾーンの上端 245・メインゾーンの上端 719 で、**719 − 245 = 474**
- ⭐ **同じ症状が出る操作**: ＋（上表）／**−**（メイン Δ−474）／**枚数の直接入力**（メイン Δ−474）／**キーボード（Tabで＋にフォーカスして Enter）**（メイン Δ−474）
- ⭐ **出ない操作**: ⋯メニューの「サイドへ移動」（Δ0）／**検索結果ダイアログの「＋マテリアル」**（Δ0）
- ⚠️ **1199px以下（スマホ表示）でも起きる**。ユーザーの報告は PC だが、**直せば全幅で直る**（§3-3 の変更は幅に依存しない）

### 3-2. 原因（実測で特定）

**`renderZones()`（`tools/deck-builder/app.js`）が、枚数が1枚変わるだけでも全ゾーンを DOM から抜いて差し直している**ことと、
**Chrome のスクロールアンカリングが「フォーカス中の要素」を優先的な基準にする**ことの組み合わせ。

```js
order.forEach((zone) => {
  const zoneEl = pane.querySelector(`.zone[data-zone="${zone}"]`);
  pane.insertBefore(zoneEl, memoBlock); // 上から order の順に並べ直す(メモは常に最後)
  ...
  grid.innerHTML = "";   // ← 押した＋ボタンはここで捨てられる
```

⚠️ **下の1〜4は Chrome 内部の順序についての推定**（内部の実装は読んでいない）。**確かなのは次の表の実験結果**で、
**「並べ直しを止めれば直る」「フォーカスが無ければ起きない」「Δ が上のゾーンの高さの合計に一致する」の3点**。

1. ＋を押すと、そのボタンにフォーカスがある
2. `renderZones()` の最初の周で **マテリアルゾーンが `memoBlock` の直前（＝一番下）へ移される**。
   この瞬間、**メインゾーン以下が一時的にマテリアルの高さぶん上へ詰まる**
3. メインゾーンの `grid.innerHTML = ""` で**フォーカス中のボタンが捨てられる**。ブラウザはフォーカスを外すためにレイアウトを確定させ、
   **フォーカス中だったボタンを基準にスクロールを補正する**（＝上へ詰まったぶんだけページを上へ送る）
4. その後マテリアルは元の位置（最上段）に戻るが、**補正されたスクロールは戻らない**

**裏付け（どれも 1440×900・メイン・実測）**:

| 実験 | Δ | 読み取れること |
|---|---|---|
| そのまま | **−474** | 再現 |
| ⭐ **`.zone` の `insertBefore` だけを握りつぶす**（並べ直しをしない） | **0** | ⭐ **原因は並べ直し**（サイド・検討中・1920×1080・1199・375 でも **0**） |
| `#ed-pane-deck { overflow-anchor: none }` | 0 | スクロールアンカリングが補正の主体 |
| クリックの捕獲フェーズで `activeElement.blur()` | 0 | **フォーカス中の要素**が基準になっている |
| クリックせず `dispatchEvent("click")`（フォーカスが移らない） | 0 | 同上 |
| `#ed-pane-deck` 直下の `childList` を MutationObserver で数える | ＋1回で **8件**（4ゾーン × 抜く/差す） | ⭐ **標準デッキでは並び順は最初から正しい**のに、毎回8件動いている |

⭐ **標準デッキの DOM は、1回目の描画のあと `pantheon(hidden), material, main, side, maybe, memo-block` で安定している**（実測）。
つまり**2回目以降の並べ直しは常に空振り**で、**不具合を起こすためだけに走っている**。

### 3-3. 変更（単位1）

**`tools/deck-builder/app.js` の `renderZones()` だけ。⭐ 並び順が既に正しいときは、ゾーンを動かさない。**

```js
// ⚠️ ゾーンの並べ直しは「表示するゾーンの並びが order と違うとき」だけ行う（操作不具合2件_設計 §3）。
//    ＋/−で毎回全ゾーンを抜き差しすると、Chrome のスクロールアンカリングが
//    フォーカス中の＋ボタンを基準にページを上へ送ってしまう（メインで −474px を実測）。
//    ⚠️ hidden のゾーン（標準デッキの pantheon 等）は比較から外す。混ぜると毎回「違う」と判定して元に戻る。
const shown = [...pane.querySelectorAll(":scope > .zone")].map((z) => z.dataset.zone).filter((z) => order.includes(z));
if (shown.join() !== order.join()) {
  order.forEach((zone) => pane.insertBefore(pane.querySelector(`.zone[data-zone="${zone}"]`), memoBlock));
}
```

- ⚠️ **並べ直しのループを、描画のループ（`order.forEach((zone) => { … grid.innerHTML = ""; … })`）から分けること。**
  既存のループ内の `pane.insertBefore(zoneEl, memoBlock)` の1行は**削除**し、上のブロックを**描画ループの直前**に置く
  （`ZONES.forEach(... zoneEl.hidden = ...)` の直後）
- ⚠️ **比較は「表示するゾーンだけ」で行う**（`filter((z) => order.includes(z))`）。
  標準デッキでは hidden の `pantheon` が DOM 上に残っているので、**全 `.zone` で比べると毎回不一致になり、不具合がそのまま残る**
- ⭐ **フォーマット切替（スタンダード ↔ パンテオン）では並びが実際に変わるので、従来どおり並べ直す**。
  そのときフォーカスは editor-bar のフォーマット切替にあり、ゾーンの中には無い
- ⚠️ **`#ed-pane-deck { overflow-anchor: none }` は採らない**（上表で効くことは確認済み）。
  **原因（空振りの抜き差し）を残したまま症状だけ消す**ことになり、ブラウザ既定の補正も一律に失うため。
  ⚠️ **両方入れることもしない**——片方を外しても症状が戻らず、**破壊試験で効き目を示せなくなる**
- ⚠️ **スコープ外（手を付けない）**: ＋を押したあと**フォーカスが `BODY` に落ちる**のは変更前からの挙動（ボタンが作り直されるため）。
  キーボードで続けて押せない点は**別の課題**（§7 の申し送り）。⚠️ **もし将来フォーカスを戻すなら `focus({ preventScroll: true })`**
  （既定の `focus()` は要素を画面内へスクロールさせる）

## 4. 不具合2：左ペインの🔍検索が押せない（単位2・⚠️ ユーザー判断待ち）

### 4-1. 何が起きているか（仕組み）

1200px以上の左ペイン（`#search-top`）は **`position: sticky; top: var(--editor-bar-h)`** で、高さの上限が

```css
max-height: calc(100vh - var(--editor-bar-h, 57px));
```

になっている（`tools/deck-builder/style.css` の `@media (min-width: 1200px)`）。
⚠️ **この式は「ペインが上端に貼り付いている（＝上端が `--editor-bar-h`）」ことを前提にしている。**
**ページ最上部ではペインの上にサイトヘッダ（約121px）がある**ので、**ペインの下端がそのぶん画面の下へはみ出し**、
**下端に貼ってある リセット／🔍検索 の行（F-a）も一緒に画面外に出る**。

- ⭐ **ここまでは既知**（`左ペイン化_設計.md` §12-9 の **1-2**。2026-09-10 の実物確認でユーザーが **(A) このまま**を選んだ）。
  ⚠️ **ただしその判断の前提は「少しでも下へスクロールすれば以後は常に見えます」だった。**
- ⚠️ ⭐ **新しく分かったこと：検索結果ダイアログが開いていると、ページを下へ送れない。**
  `openModal()` が **`document.body.style.overflow = "hidden"`** にするため、**ホイールがページに伝わらない**
  （ペイン上でホイール → ペインだけが最下端まで動いて止まる。結果ダイアログ上でホイール → ダイアログの中だけが動く）。
  ⭐ **ユーザーの「カードを検索してから」がこの状態**で、**1-2 の前提が崩れて、ボタンに届く手段が無くなる**

### 4-2. 再現（実測・1440×900）

**手順**: デッキを開いた直後（ページ最上部・scrollY=0）→ カード名に `fire` → **🔍検索**（結果ダイアログが開く）→ 左ペインの **エレメント** を開く

| 時点 | ペイン（表示／中身） | 🔍検索の位置（上〜下） | 画面の高さ | `elementFromPoint(ボタン中心)` |
|---|---|---|---|---|
| 検索の直前 | 714 / 714（スクロール無し） | 838〜880 | 900 | ⭐ `#s-search`（押せる） |
| 検索後（ダイアログ開） | 714 / 714 | 838〜880 | 900 | `#s-search`（押せる） |
| ⚠️ **エレメントを開いた後** | **843 / 914（ペインにスクロールが出る）** | ⚠️ **967〜1009** | 900 | ⚠️ **`null`（画面外）** |
| そのままペイン上・ダイアログ上でホイール | 843 / 914（ペインは 71px 動く） | ⚠️ **967〜1009（scrollY は 0 のまま）** | 900 | ⚠️ `null` |

⭐ **ユーザーの報告（検索 → エレメントを開く → ペインにスクロールが出る → 押せない）と手順・現象が一致する。**

**画面サイズ・ページ位置ごと（エレメントを開いた状態・結果ダイアログ開）**:

| 画面 | scrollY=0 | 60 | 121 | 400 |
|---|---|---|---|---|
| 1200×800 | ⚠️ 画面外（867〜909） | ⚠️ 画面外（807〜849） | 押せる（746〜788） | 押せる |
| 1280×720 | ⚠️ 画面外（787〜829） | ⚠️ 画面外 | 押せる（666〜708） | 押せる |
| 1536×730（Windows 125% 相当） | ⚠️ 画面外（797〜839） | ⚠️ 画面外 | 押せる（676〜718） | 押せる |
| 1920×950 | ⚠️ 画面外（1017〜1059） | ⚠️ 画面外 | 押せる（896〜938） | 押せる |

- ⭐ **はみ出す量は常に「121 − scrollY」px**（サイトヘッダの高さ。デッキ名が長く `.editor-bar` が2行でも同じ）
- ⭐ **ダイアログが閉じていても同じ位置に出る**（違いは「ページを送れるかどうか」だけ）
- ⭐ **トップページ（`/`）には起きない**——トップの 1200px以上は `body.page-top { height: 100vh; overflow: hidden }` のアプリシェルで、
  **ペインが常に画面の高さちょうど**に収まる（構造が違う）。⭐ **不具合2はデッキ構築だけの問題**

### 4-3. ⚠️ 再現できなかった部分 — 「下の方の何も表示されていないところを押すと検索される」

ユーザーは「**描画がおかしい**（見えている位置と押せる位置がずれている）」と推測している。

- ⚠️ **ヘッドレス Chromium では、描画位置と当たり判定のずれは再現しなかった。**
  **1200/1280/1440/1536/1920 × scrollY 0/30/60/90/121/400 × エレメント／サブタイプ × ダイアログ開閉 × ペインのスクロール位置**で、
  `getBoundingClientRect()` ・スクリーンショット上の金色の画素・`elementFromPoint` の3つが**すべて一致**した
- ⚠️ ⭐ **ヘッドレスで見られないもの**: **実機の GPU 合成**（スクロール中にスレッド側で貼り付き位置を更新する経路）。
  **「sticky の中の sticky」**（sticky なペインの中に sticky なボタン行）なので、**実機でだけずれる可能性は否定できない**
- ⭐ **最も近い再現**: **scrollY が 67〜120 のあいだ**（1440×900）は、**🔍検索のボタンの上端だけが画面の最下端に数px〜33px 残る**
  （例: scrollY=90 で 877〜919、画面内に見えるのは上から 23px）。
  **この細い帯を押すと検索が走る**（実測）。**ボタンの大部分が画面外なので「何も表示されていないところ」に見えうる**

### 4-7. 案1を選んだ場合の変更（⚠️ **Q2 の回答で案1が選ばれるまで実装しない**）

**`tools/deck-builder/style.css`**（`@media (min-width: 1200px)` の `#view-editor #search-top` の1宣言だけ）:

/* ⚠️ 上端はペインの「実際の」上端（--pane-top）。ページ最上部ではサイトヘッダの下にあるので、

**`tools/deck-builder/app.js`**（`updateEditorBarH()` の近くに関数を1つ）:

```js
// 左ペインの実際の上端を --pane-top に入れる（操作不具合2件_設計 §4-7）。
// ⚠️ 値は「sticky の top（--editor-bar-h）」と「実際の上端」の大きい方。ページ最上部ではヘッダの下にある。
// ⚠️ 1200px未満（スマホ表示）とエディタ非表示のときは何もしない（CSS 側も min-width の中でしか読まない）。
// ⚠️ Math.ceil で切り上げる。四捨五入だとペインの下端が画面から 1px 未満はみ出すことがある。
function updatePaneTop() {
  const pane = el.searchTop;  // #search-top
  if (!pane || !pane.getClientRects().length) return;
  if (!matchMedia(`(min-width: ${PANE_MIN_WIDTH}px)`).matches) return;
  const barH = Math.round(document.querySelector("#view-editor .editor-bar").getBoundingClientRect().height);
  const top = Math.max(barH, Math.ceil(pane.getBoundingClientRect().top));
  document.documentElement.style.setProperty("--pane-top", `${top}px`);
}
```

- **呼ぶ場所**: ①`window` の **`scroll`**（`passive: true`・**rAF で1フレーム1回に間引く**）②既存の **`resize` の rAF**（`updateEditorBarH()` の直後）③**`renderEditorBar()` の末尾**（`updateEditorBarH()` の直後。バーの高さが変わると sticky の上端が変わるため）
- ⚠️ **`PANE_MIN_WIDTH` を使う**（1200 を直書きしない）。⚠️ **`@media` を足さない**（既存ブロックの1宣言を書き換えるだけ）——
  `validate` の検査②（`min-width` の集合 ＝ `PANE_MIN_WIDTH`）・検査③（マーカー直後の `max-width`）に触れない
- ⚠️ **コメントに `<file>.js:<行番号>` を書かない**（`validate` が exit 1。関数名で参照する）
- ⚠️ **`body.style.overflow` のロック（`openModal()`）は変えない**（案2 は採らない）
- ⚠️ **F-a の `#search-top > .row-actions`（sticky bottom）には触れない**
