# 数値ソートのページング根治 — 設計書（issue #44）

## 改版履歴

| 版 | 日付 | 内容 | 状態 |
|---|---|---|---|
| 1.0 | 2026-08-05 | 初版。案F（安定キーで全件取得→ローカル整列）を確定 | **実装待ち** |

---

## 1. 直す症状

数値項目（`level` / `power` / `life` / `cost_memory`）で並び替えると、**同点行がページ境界に当たったときに
1枚が2ページに重複し、代わりに別の1枚が一度も返ってこない**。

利用者から見える形: 「全 124 件」と表示しながら**120枚しか出ない**。**4枚のカードが検索から永久に見えない**。

⚠️ **#39 が持ち込んだ不具合ではない**（素の昇順ページングの性質）。詳細は issue #44 本文。

---

## 2. 調査で確定した事実（すべて 2026-08-05 の実測）

### 2.1 バグは今も再現する

`sort=level&order=ASC` で `page_size=50` → 重複4種、`page_size=24` → 重複2種。**起票時と同じslug**。

### 2.2 ⭐ 安定した全順序のページングキーが存在する

| クエリ | `sort=collector_number` | `sort=level` |
|---|---|---|
| 絞り込みなし（2,240件） | ✅ **2240/2240**（45リクエストで捲り切り） | ⚠️ 重複4種 |
| `element=WIND`（294件） | ✅ 294/294 | ✅ 294/294（境界に当たらず） |
| `type=champion`（125件） | ✅ 125/125 | ⚠️ **125取得/123ユニーク＝2枚欠落** |
| `class=warrior`（299件） | ✅ 299/299 | ✅ 299/299 |

→ **崩れるのは数値項目でソートしたときだけ。** 安定キーで捲れば完全な候補集合が取れる。

### 2.3 ⭐⭐ 現行の実装は「すでに」非常に遅い

`probeNonNullCount()`（非nullの境界を二分探索する仕掛け）は**逐次14リクエスト**で、**実測22.7秒**かかる。

```
単発の応答時間        1.79秒（page_size=50）/ 1.59秒（page_size=1）
現行の二分探索        14リクエスト逐次 = 22.7秒   ← 数値ソートの初回はここで待たされている
全件取得（並列6）     45リクエスト     = 20.7秒
全件取得（並列12）    45リクエスト     = 16.6秒   ← 並列12以上は頭打ち（API側で律速）
```

⭐ **つまり「全件取得」は現行より遅くない。むしろ速い。**

### 2.4 応答は軽い / ただしメモリは重い

- 50件で **32KB(gzip)** ・全2,240件で **1.4MB(gzip)**
- ⚠️ ただし**展開後は50件で496KB＝全件で21.7MB**。内訳は **`editions` 43% + `result_editions` 43%**
- ✅ `result_editions` は `card.editions || card.result_editions` という**フォールバック専用**で、
  検索応答には `editions` が必ず入るため**使われない**（`card-i18n.js` / `card-detail.js` / `card-search.js` の5箇所すべてこの形）
  → **取得時に捨てて良い。これだけで43%減る**
- ⚠️ **`editions` は捨てられない**。`cardImages()` が全版を回し、`flipEdition()` が
  `configuration === "flip"` を全版から探し、エキスパンション絞り込みが全版の `set.prefix` を見る

## 3. 対処: 案F — 安定キーで全件取得 → ローカルで整列

### 3.1 やること

数値ソートのときだけ、取得と並び替えを次に置き換える:

1. `sort=collector_number&order=ASC&page_size=50` で、**絞り込み結果の全ページ**を取得する
   （1ページ目の `total_cards` からページ数を決め、2ページ目以降は**並列6**で取る）
2. 取得時に各カードから **`result_editions` を捨てる**（§2.4）
3. `isNullish(field, card)` で**その項目を持たないカードを除外**する（#39 の既存規則をそのまま使う）
4. **全順序**で整列する（キー比較 → 同点は `slug`。昇順・降順とも）
5. ページングは**ローカルの `slice`**

### 3.2 ⭐ メタ索引は使わない

当初は `data/card-meta-index.json` の `m[slug][6]` を使う案だったが、**不要**と判明した。
**取得したカードオブジェクト自身が `level` / `power` / `life` / `cost_memory` を持っている**ため。

これにより:

- ✅ **索引の消費側が増えない**（CLAUDE.md の「壊れたときの症状」の表を**更新しなくてよい**）
- ✅ 索引の鮮度に依存しない。**自分が取ったデータだけで完結する**
- ✅ 検算が同じ応答の中で閉じる（ユニーク数 vs `total_cards`）

### 3.3 ⭐ 絞り込みキーでキャッシュする → 並び替えの変更が無料になる

取得した集合は **`filterParams()` の文字列をキーに保持**する（現行の `nCache` と同じキー）。
並び替えの項目・方向を変えても**再取得は起きない**（ローカルで並べ直すだけ）。

現行は並び替えを変えるたびに `countNonNull()` のキャッシュミスで**22.7秒の二分探索が再発**しうる。

### 3.4 消えるコード

| 消すもの | 行数の目安 | 理由 |
|---|---|---|
| `probeNonNullCount()` | 約30行 | 件数Nは取得した集合を数えれば分かる |
| `countNonNull()` / `nCache` | 約15行 | 同上 |
| `fetchNumericPage()` | 約35行 | **降順の位置演算（ASCページを逆から読む）がまるごと不要**。降順はローカルの比較で済む |

差し引き **約80行減って約40行増える**。

## 4. リクエスト数と体感（実測ベース）

| 場面 | 現行 | 案F |
|---|---|---|
| 初回・絞り込みなし | probe 14逐次 **22.7秒** + 1ページ | 45並列 **16.6秒** / 1.4MB |
| 初回・`element=WIND`（294件） | probe 14逐次 22.7秒 + 1ページ | 6リクエスト **約3秒** / 0.19MB |
| 2ページ目以降（もっと見る） | 毎回1リクエスト 約1.8秒 | **0リクエスト（即時）** |
| 並び替えの項目・方向の変更 | 最悪 22.7秒（キャッシュミス時） | **0リクエスト（即時）** |
| 正しさ | ⚠️ 欠落あり | ✅ 完全 |

⭐ **絞り込みを併用するほど速くなる。** 絞り込みなしの初回だけが最も重く、それでも現行より速い。

### ⚠️ 16.6秒は「速くなった」だけで「速い」わけではない

**進捗表示を必ず入れる**（現行の `onStart` の「検索中…」だけでは無言で16秒待つことになる）。
`読み込み中 12/45` のように**取得済みページ数を出す**こと。

## 5. 自衛（fail-open）

⚠️ **`collector_number` の安定性は実測であって、APIが保証しているものではない。**

- 全件取得後に**ユニーク数と `total_cards` を突き合わせる**。食い違ったら
  **注記を出して続行する**（黙って落とさない・エラーにもしない）
- 取得したページ数が想定より多い場合の**暴走止め**を入れる（`MAX_PAGES = 60`。2,240件÷50=45が上限のため）
- 途中のリクエストが失敗したら**その検索全体を失敗させる**（部分的な集合で並べると
  「順位は正しいが歯抜け」という**最も気づきにくい壊れ方**になるため。⚠️ ここだけは fail-fast）

## 6. 副作用として直るもの・変わる表示

- ✅ 「全 124 件（レベルを持つカードのみ）」が**実際に124枚出る**ようになる（現在は120枚）
- ✅ **AND絞り込みの総件数が正確になる。** 現行はページ内で `matchesAndFilters` を後から
  間引くため件数が概数（`approxTotal`）だが、案Fは全件に対して間引ける
  → **数値ソート時は `approxTotal: false` にしてよい**
  ⚠️ 非数値ソートの挙動は**変えない**（本issueの範囲外）
- ⚠️ 「もっと見る」で**ページごとの表示件数が揃う**ようになる（現行はAND間引きで不揃い）
