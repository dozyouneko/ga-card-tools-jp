## 3. 決めたこと（実測にもとづく設計判断）

### 3-1. L8: DOM を動かさず CSS だけで組む — ⭐ **採用**

`body` を2カラムの Grid にし、**左列にペイン（`.controls`）・右列にそれ以外**を置く。

```css
@media (min-width: 1200px) {
  body { display: grid; grid-template-columns: 320px minmax(0, 1fr); align-content: start; }
  /* ⭐ body直下に要素が増えても壊れないよう、既定を右列にする */
  body > * { grid-column: 2; }
  .site-header { grid-column: 1 / -1; }
  .controls {
    grid-column: 1;
    grid-row: 2 / span 50;      /* ⚠️ 下記の注意を参照 */
    align-self: start;
    position: sticky; top: 0;
    max-height: 100vh; overflow-y: auto;
    border-bottom: none; border-right: 1px solid var(--border);
  }
}
```

- ⭐ **`body > * { grid-column: 2 }` にしたのが要点。** 各要素を個別に列指定すると
  **body直下に要素が増えた日に、その要素だけ左列へ落ちる**（無言で壊れる型）
- ⚠️ **`grid-row: 2 / -1` は使えない。** `-1` は**明示グリッドの最終ラインを指す**ため、
  `grid-template-rows` を持たない本レイアウトでは意図どおりに解決しない。
  `span 50` は「最後の行まで」の代用で、**余った暗黙行は高さ0**（`row-gap` を持たないため増分なし）
- ⭐ **`display: contents`（R4）にも `#filter-row` の中身にも触らない**ので R4・R5 は自動的に守られる

⚠️ ⭐ **1.1 で訂正: 「DOM 変更ゼロ」は成り立たなくなった。**
**ヘッダ固定（§11）にはラッパ要素 `#results` が1つ要る**ため、案1でも DOM 変更が1件発生する。
⚠️ 案2 を採るなら、さらに検索入力の1行を `.controls` の外へ出す変更が加わる。
⭐ **どちらも `#filter-row` の中身ではない**ので **R5 には抵触しない**。

### 3-2. L2: ペイン幅は **320px**、列数は 1〜2列減る

ペイン幅を変えて実測した（再現: `tmp/design/measure-pane.mjs`）:

| ペイン幅 | 2560 | 1920 | 1440 | 1280 | 1024 |
|---|---|---|---|---|---|
| （現状） | 12列 | 9列 | 7列 | 6列 | 5列 |
| 280px | 11 | 8 | 5 | 4 | 3 |
| **320px** | **11** | **8** | **5** | **4** | **3** |
| 360px | 11 | **7** | 5 | 4 | 3 |

- ⭐ **280 と 320 で列数は変わらない**（`auto-fill` の丸めに吸収される）。
  **同じ列数ならチップが窮屈でないほうがよい**ので **320px** を採る
- ⚠️ **360px にすると 1920 で1列余分に減る**ので上限は 320px
- ⚠️ **列の減りは 1〜2列で、幅によって揺れる**（1200:-1 / 1280:-2 / 1366:-1 / 1440:-2）。
  `auto-fill` の丸めによるもので、**単調ではない**。「常に1列減」と書かないこと

### 3-3. L4/L5: ブレークポイントは **1200px**、それ未満は**現状のまま**

| 幅 | 左ペイン時の列数 | 判断 |
|---|---|---|
| 1024px | 3列（現状5列） | ❌ **5列中2列＝40%を失う。割に合わない** |
| 1100px | 3列（現状5列） | ❌ 同上 |
| **1200px** | **4列**（現状5列） | ✅ **右側に4列を保てる下限**（計算上の限界は約1140px。余裕を見て1200px） |
| 1280px 以上 | 4〜11列 | ✅ |

⭐ **判断の規則は「結果側に最低4列を保てること」。** 1200px 未満では現状の上部バーのままにする。

- ⭐ **L5（タブレット帯の未設計）は発生しない。** 641〜1199px は**今と同じ挙動**が続くので、
  「どちらの導線も出ない幅」は生まれない。⚠️ **新しいメディアクエリは `min-width: 1200px` の1本だけ**
- ⚠️ 既存の `max-width: 640px`（スマホのFAB＋シート）とは**重ならない**ので相互作用しない

### 3-4. L3: ペインは sticky・**チップ領域に丈の上限を掛ける**

実測（1440x900・ペイン320px）:

| 状態 | ペインの中身の高さ | 表示枠 |
|---|---|---|
| 全グループ閉 | 614px | 900px ✅ 収まる |
| エレメントのみ開 | +453px | |
| サブタイプのみ開 | **+761px**（チップ160個） | |
| **4グループ全開** | **2,577px** | ⚠️ **1,678px あふれる** |

- ✅ **sticky は効く**（scrollY=2000 でペイン `top=0` を実測）
- ⚠️ ⭐ **ペイン内スクロールは原理的に避けられない。** チップ領域に上限を掛けても
  4グループ全開なら 1,484px（200px上限時）で、**なお 900px に収まらない**
- ⭐ **そこで「よくある使い方では二重スクロールにしない」ことを狙う**:
  **`.controls .fgroup .chips { max-height: 200px; overflow-y: auto }`** を掛けると、
  **1グループ開いた状態（＝実際の主な使い方）はペインに収まる**（614 − 見出し + 約256 ≒ 870px < 900px）
- ⚠️ **セレクタは `.controls` で限定して `style.css` に書く**。
  ⭐ **`shared/css/filter-chips.css` には触らない**＝デッキ構築ツールに波及しない（**R6・S1 を守る**）

### 3-5. ペイン内のレイアウト

```css
@media (min-width: 1200px) {
  .filter-row   { grid-template-columns: minmax(0, 1fr); }   /* 4列タイル → 1列 */
  .controls-row { flex-direction: column; align-items: stretch; }
  #q, #qtext    { flex: 0 0 auto; width: 100%; min-width: 0; }
  .filter-rest  { display: grid; grid-template-columns: 1fr 1fr; gap: 8px; }
  .filter-rest select { grid-column: 1 / -1; }
}
```

⭐ **これで `#q` は 271px 固定になり、G1 を満たす**（実測）。

## 5. HeroUI 案A の技術評価（L6）

⭐ **結論: 「案A＝デザイントークンの移植」で実際に借りる価値があるのは、ごく一部だった。**

HeroUI v3 の実トークン（`packages/core/theme/src/` を確認）と現状の突き合わせ:

| トークン | HeroUI | 現状のサイト | 評価 |
|---|---|---|---|
| **角丸** | sm 8 / md 12 / lg 14 px | 8px（入力）・10px（グループ）・12px（`--radius`）・999px（チップ） | ⭐ **ほぼ同値。移植しても見た目は変わらない** |
| **フォーカスリング** | 2px ＋ offset | `outline: 2px solid var(--accent-2); offset 1px` | ⭐ **既に同等**。offset を 2px にする程度 |
| **影（elevation）** | `0 0 5px rgba(0,0,0,.02)` ほか3段 | ほぼ無し | ⚠️ ⭐ **そのままでは使えない**（下記） |
| **配色** | 暗色は **純黒 `#000` ＋ zinc ＋ blue-500** | `#0f1115` ＋ 青みのある暗色 ＋ **金 `#d9a441`** | ❌ **採らない**（下記） |
| **文字サイズ / 行高** | .75 / .875 / 1 / 1.125rem ／ 1 / 1.25 / 1.5 / 1.75rem | 個別指定でスケール無し | ⭕ **借りる価値がある**（案A-しっかり） |

### ⚠️ ⭐ 影スケールは暗色地では効かない

HeroUI の影は **黒・不透明度 0.02〜0.08** で、**明るい地の上で機能する設計**。
本サイトの地は `#0f1115` なので、**黒い影を重ねてもほぼ知覚できない**。

⭐ **翻案**: 暗色テーマの立体感は**面の明度差**で作るのが定石なので、
影の代わりに **面の明度を一段上げる ＋ 内側の 1px ハイライト**（`inset 0 1px 0 rgba(255,255,255,.045)`）
と、**区切り線の半透明化**（`--border: rgba(255,255,255,.11)`）で置き換える。

### ❌ 配色パレットは置き換えない

- ⭐ **金（`--accent: #d9a441`）はサイトの識別子**。ブランドマーク・選択チップ・バッジ・
  未翻訳ラベルまで全部これで、HeroUI の blue-500 に替えるのは**近代化ではなく別サイト化**
- ⚠️ **`:root` の12変数を置き換えると `404.html` にも同時に出る**（R8）。
  影響範囲が「トップだけ」ではなくなる

### 採否の提案

| 段階 | 内容 | 影響範囲 |
|---|---|---|
| **案A-最小**（⭐ 推奨） | 区切り線を半透明に・面の明度差で階層化・角丸を8/12/14に統一・フォーカスリングの offset を2pxに | `:root` の3変数＋数ルール。⚠️ **`404.html` にも出る**（R8・意図的） |
| **案A-しっかり** | 最小 ＋ 余白/行高/文字サイズをHeroUIのスケールに統一・ヘッダ/ペイン/カードの面をはっきり分ける | 同上＋トップの主要要素 |
| 現状のまま | 左ペイン化だけ行う | — |

⚠️ **どの段階でも React・Tailwind・ビルド工程は導入しない**（調査メモ §3 の結論どおり。
**CSS の値と考え方だけを借りる**）。

## 10. ⚠️ ⭐ ユーザーに実物を見せるサーバーは **3000番で上げる**（2026-09-02 に実際に踏んだ）

⚠️ **`.devcontainer/devcontainer.json` の `forwardPorts` は `[3000]` の1つだけ。**
それ以外のポートで上げたサーバーは**コンテナ外（ユーザーのブラウザ）から届かない**。

- 実例: 設計工程でモックを **3400番**で上げてURLを渡したところ、**ユーザーの環境から開けなかった**。
  ⚠️ ⭐ **コンテナ内からは `curl` も Playwright も 200 を返す**ので、
  **渡す側だけを見ていると正常に見える**（＝無言で失敗する型）
- ⭐ **対処: ユーザーに渡すときだけ `PORT=3000 npm run dev` にする。**
  測定・検証はどのポートでもよい（コンテナ内で完結するため）

### ⚠️ CLAUDE.md の「ポートを役割で分ける」表との衝突

CLAUDE.md は 開発3000 / レビュー3100 / 広報3300 / ダッシュボード3200 と割り当てているが、
⚠️ **3100・3200・3300 はいずれも `forwardPorts` に無い**。

- ⭐ **役割分離は「セッション同士の `EADDRINUSE` を避ける」ためのもので、
  ユーザーに見せる用途は想定されていなかった**（2026-09-02 に本タスクの受け入れ条件として初めて発生した）
- ⭐ **本タスクの §8-4（レビュー合格後にユーザーが実物を触る工程）では、
  レビュー担当も 3000番で上げてURLを渡す**こと。⚠️ **3100 で渡すと同じ失敗を繰り返す**

## 11. ヘッダ固定（アプリシェル化）

### 11-1. 何が変わるか

**ページ全体がスクロールする**形から、**ヘッダとペインは動かず、結果側だけがスクロールする**形へ変える。

```css
@media (min-width: 1200px) {
  html, body { height: 100%; }
  body {
    display: grid;
    grid-template-columns: 320px minmax(0, 1fr);
    grid-template-rows: auto minmax(0, 1fr);   /* 1行目=ヘッダ / 2行目=残り全部 */
    overflow: hidden;                          /* ⚠️ ページ自体はスクロールしない */
  }
  .site-header { grid-column: 1 / -1; grid-row: 1; }
  .controls    { grid-column: 1; grid-row: 2; position: static; overflow-y: auto; }
  #results     { grid-column: 2; grid-row: 2; overflow-y: auto; }
}
```

⚠️ ⭐ **`position: sticky` が不要になる。** 2行目のトラックが `minmax(0, 1fr)` で
ビューポート高に固定されるため、ペインは**そもそも動かない**。§3-1 の `grid-row: 2 / span 50` も要らなくなる。

### 11-2. ⚠️ DOM 変更が1件要る — 右列をまとめるラッパ

**右列は現在5要素**（`#status` / `#grid` / `.load-more-wrap` / `.setlinks` / `.site-footer`）で、
**これらを「ひとまとまりでスクロールする1つの領域」にするには共通の親が要る**。

```html
<div id="results">   <!-- ⚠️ 新設。#status 〜 </footer> を包む -->
  <p id="status" …>
  <main id="grid" …>
  …
</div>
```

- ⭐ **`#filter-row` の中身には触らない**ので **R5 に抵触しない**
- ⚠️ ⭐ **1200px 未満では箱を作ってはいけない**（スマホ・タブレットの現状を1pxも変えないため）:

  ```css
  @media (max-width: 1199px) { #results { display: contents; } }
  ```

  ⭐ **`#filter-sheet` と同じ手口**（R4 の実績ある手法）。⚠️ **これを忘れるとブロック整形文脈が1段増え、
  余白の詰まり方が変わりうる**

### 11-3. ⭐ 実測（モックで確認済み）

| 確認 | 結果 |
|---|---|
| 結果側を 1500px スクロール | ⭐ **ヘッダの `top` は 0 のまま**・**ペインも動かない**・`#results.scrollTop = 1500` |
| `body` の `overflow`（1200px以上） | `hidden`（＝ページ自体はスクロールしない） |
| **375px 幅** | ⭐ **`overflow-x: clip` のまま**（`overflow: clip visible`）＝ **R1 は無傷** |

### 11-4. ⚠️ 気をつけること

| # | 内容 |
|---|---|
| **H1** | ⭐ **`window` のスクロールに依存したコードが無いことを確認済み。** 唯一の候補だった FAB の `IntersectionObserver`（`app.js:750`）は **`MOBILE_MQ.matches` でガードされており**、アプリシェルが効く1200px以上では動かない。無限スクロールも無い（`#load-more` は手動ボタン） |

## 12. 絞り込みのアコーディオン化 ＋ 選択中の表示

### 12-1. アコーディオン（1つ開いたら他は閉じる）

- ⭐ **`<details>` の `toggle` イベントを拾って他を閉じるだけ**で実現できる（実測済み）
- ⚠️ ⭐ **実装は `app.js`（トップ専用）に置く。`shared/js/card-search.js` には書かない**
  — 書くと**デッキ構築ツールの絞り込みも勝手にアコーディオンになる**（S1 違反）
- ⭐ **副次効果: §3-4 の「ペイン内スクロール」がほぼ起きなくなる。**
  同時に開くのが1つだけなら、最大でも 614 + 761 = 約1,375px … ⚠️ **サブタイプを開いたときは
  なお 900px を超える**ので、**チップ領域の `max-height: 200px`（§3-4）は引き続き必要**

### 12-2. ⚠️ 「何を選んだか見えなくなる」への対処 — 4案

⚠️ **アコーディオンにすると、閉じたグループの選択内容が数字バッジだけになる。**
⭐ **4案をモックに実装したので、実際に操作して選んでください。**

| 案 | 置き場所 | ⭕ 良い点 | ⚠️ 弱い点 |
|---|---|---|---|
| **案A** | **左ペインの最上部**に「選択中の条件」ブロック | ⭐ **全条件が1か所に集まる**。✕で個別解除・「すべて解除」も置ける | ペインの上を常に少し使う |
| **案B** | **件数表示（`50 件を表示 / 全 N 件`）の横** | ⭐ **結果を見ながら外せる**（視線移動が少ない） | ⚠️ 条件が多いと件数行が伸びる。⭐ **ペインから離れた場所に条件がある**ことになる |
| **案C** | **閉じたグループの見出しに項目名** | ⭐ **場所を増やさない**。どのグループの条件かが自明 | ⚠️ **長いと省略される**。一覧性が低い |
| **案D** | **案A ＋ 案C の併用** | ⭐ 全体（ペイン上部）と内訳（見出し）の両方が見える | 表示が2か所に重複する |

⭐ **設計担当の推奨は 案D**。理由は、**案Aだけだと「どのグループの条件か」が分からず**、
**案Cだけだと「全体でいくつ絞っているか」が一望できない**ため。

### 12-3. ⚠️ 案C・案D を作って分かったこと（実測）

⚠️ ⭐ **項目名を見出しの「同じ行」に置くと、320px のペインでは AND/OR トグルが押し出されて切れる**
（モック初版で実際に発生）。

⭐ **対処: 項目名は見出しの2行目に回す**（`summary` を `flex-wrap: wrap` にして項目名に全幅を与える）。
⚠️ **この1行を省くと、レビューで「AND/OR が押せない」として差し戻される。**

### 13-5. ⚠️ 2つの落とし穴

| # | 内容 |

再現条件の分かりにくい不具合になる**（CLAUDE.md の #27 と同型）。
