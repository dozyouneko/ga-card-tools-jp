## 1. 背景と目的

### 1-1. ユーザーの申告（2026-08-28）

> スマホ表示はスクロールすると検索条件まで戻るのがめんどくさい

スマホ幅でカード一覧をスクロールすると検索条件バーが画面外へ流れ、
**絞り込みを変えるたびにページ最上部まで戻る必要がある**。

出所と一次調査は `UI刷新_調査メモ_2026-08-28.md` §4-2。
⭐ **「UI刷新（HeroUI）」の議論とは独立した単体の不具合＋導線改善**であり、
ライブラリ選定（同メモ §2・§3）とは切り離して先に片付ける。

### 1-2. この設計書の目的

1. **スクロール位置を失わずに絞り込みへ戻れるようにする**（判断1 = FAB＋ボトムシート）
2. **`position: sticky` がスマホ幅で全部死んでいる原因そのものを潰す**（判断2 = `clip` 置換）

⚠️ **2 は「今回のFAB案では使わないから不要」ではない。** `overflow-x: hidden` は
**スマホ幅の sticky を無差別に無効化している**状態で、今後どこかで追従UIを使うたびに同じ罠を踏む。

## 2. 原因と実測

### 2-1. sticky が効かない原因（一次調査で特定済み）

`.controls` には**既に** `position: sticky; top: 0` が付いている（`style.css:85`）。
効かない原因は `@media (max-width: 640px)` の中にある次の1行:

```css
/* style.css:314 */
html, body { overflow-x: hidden; }
```

`overflow-x: hidden` は要素を**スクロールコンテナ化**するため、**子孫の `position: sticky` を無効化する**。
このルールがメディアクエリの中にあるので、**スマホ幅でだけ sticky が死ぬ**。

| 条件 | `.controls` の `top`（scrollY=1500） | 追従 |
|---|---|---|
| PC 1440x900（`overflow-x: visible`） | **0px** | ✅ |
| スマホ 390x844（現状 `hidden`） | **-1427px** | ❌ |
| スマホ 390x844（`visible`） | **0px** | ✅ |
| スマホ 390x844（**`clip`**） | **0px** | ✅ |

⭐ `clip` は**スクロールコンテナを作らない**ので、横はみ出し防止の目的を保ったまま sticky が復活する。

### 2-2. ⚠️ 単純に sticky を復活させてはいけない

`.controls` の縦の高さ（390x844・設計時に再実測して追認）:

| 状態 | 高さ | 画面占有 |
|---|---|---|
| 絞り込み **閉** | **179px** | 21% |
| 絞り込み **開** | **642px** | **76%** |
| 開＋4グループ全展開 | **1861.6px** | **221%** |

そのまま追従させると、絞り込みを開いた状態で画面の76%が貼り付いて**カードが見えなくなる**。
→ **採用したのは sticky の復活ではなく FAB（フローティングボタン）案**（§3）。

### 2-3. ⚠️ 設計時の実測で判明した5点（F1〜F5）

⭐ **ここが本設計書の中核。** 起票案・モックの記述のうち **2点は前提が誤っており（F1・F2）**、
残り3点（F3〜F5）は**知らずに実装すると必ず動かない** CSS の性質。

再現スクリプト: `tmp/design/probe-fab.mjs` 〜 `probe-fab5.mjs`（⚠️ `tmp/` はgitignore）。
測定は `PORT=3400 npm run dev` ＋ Playwright（`--ignore-certificate-errors` / `ignoreHTTPSErrors`）。

#### F1. ⚠️ 対象は「5ページ共通」ではなく **2ページ**（判断3の前提が誤り）

モックの判断3の欄は「`style.css` を読む5ページ（トップ・404・デッキ構築・キーワード解説・印刷PDF）共通」
と書いているが、**実測では誤り**。`href` が相対パスなので、**ツール3ページはそれぞれ自分のディレクトリの
別ファイルを読んでいる**:

| ページ | `<link rel="stylesheet">` の解決先 | ルート `style.css` を読むか |
|---|---|---|
| `index.html` | `style.css` → **`/style.css`** | ✅ **読む** |
| `404.html` | `/style.css`（絶対パス） | ✅ **読む** |
| `tools/deck-builder/index.html` | `style.css` → `tools/deck-builder/style.css`（34,637バイト・別物） | ❌ 読まない |
| `tools/glossary/index.html` | `style.css` → `tools/glossary/style.css`（2,059バイト・別物） | ❌ 読まない |
| `tools/print/index.html` | `style.css` → `tools/print/style.css`（3,772バイト・別物） | ❌ 読まない |

- ⭐ **`overflow-x: hidden` はルート `style.css` にしか無い**（`grep -n 'overflow-x' tools/*/style.css`
  でヒットするのは deck-builder の `overflow-x: auto` 1件だけで、無関係）
- **回帰確認が要るのは `404.html` だけ。** 他3ページは**そもそも影響を受けない**
  （§7 V21 で「読んでいないこと」自体を確認項目にする）
- ⚠️ **承認された判断3の中身（＝「`style.css` の1箇所を直す」）は変わらない。** 変わるのは
  影響範囲の見積もりだけなので、**実装は止めずに進めてよい**（ユーザーへの通知事項は §8-1）

#### F2. ⚠️⭐ `clip` を入れると **FAB が永久に出なくなる**（判断1と判断2が衝突する）

判断1の確定要件は「**検索条件バーが画面外に出たら FAB を表示**」。
ところが判断2（`clip`）を入れると `.controls` の sticky が**復活する**ため、
**バーは画面上端に貼り付いたまま永久に画面外へ出ない** → **FAB の出現条件が一度も成立しない**。

→ ⭐ **スマホ幅では `.controls` を明示的に `position: static` にする**（§4-1 の変更③）。

- これは `clip` 化の副作用を打ち消す**意図的な指定**である。`hidden` のままなら「たまたま static と
  同じ挙動」だったものを、**原因を潰したうえで明示的に選び直す**形にする
- ⚠️ **この1行を落とすと、実装は一見完成しているのに FAB が絶対に出ない。**
  しかも `hidden`→`clip` の置換とセットでしか再現しないため、**原因が最も見つけにくい失敗**になる
- ⭐ 副産物として **21%の常時占有も起きない**（§2-2 の懸念がそのまま解消する）

#### F3. ⚠️ `.controls` の `backdrop-filter` が `position: fixed` の**包含ブロック**を作る

`.controls` には `backdrop-filter: blur(6px)` がある（`style.css:92`）。
`backdrop-filter` は `filter` と同じく **`position: fixed` の子孫の包含ブロックを作る**ため、
`.controls` の中にボトムシートを `position: fixed; bottom: 0` で置いても**画面下端に来ない**。

実測（390x844・`#filter-row` を `position: fixed; bottom: 0` にして `getBoundingClientRect().bottom`）:

| 条件 | `bottom` | 画面下端(844)に一致 |
|---|---|---|
| 現状（`.controls` に `backdrop-filter: blur(6px)`） | **251px** | ❌ **`.controls` に張り付く** |
| `.controls` の `backdrop-filter` を `none` にする | **844px** | ✅ |
| `<body>` 直下の要素で試す（参考） | **844px** | ✅ |

→ ⭐ **スマホ幅では `.controls` の `backdrop-filter` を `none` にする**（§4-1 の変更④）。
背景は `rgba(15,17,21,.92)` ＝**すでに92%不透明**なので、ぼかしを外しても見た目の差はほぼ無い（§8-2）。

#### F4. ⚠️ `.controls` の**スタッキングコンテキスト**がシートを印刷バーの下に閉じ込める

`.controls` は `position: sticky` ＋ `z-index: 5` ＝ **スタッキングコンテキストを作る**。
その中に置いたシートは**どんな `z-index` を振っても `.print-bar`（`z-index: 15`）より前に出られない**
＝ **シートとベールが印刷リストバーの下に潜る**。

- ⭐ **F2（`position: static` 化）と F3（`backdrop-filter: none`）を両方入れると、
  `.controls` はスタッキングコンテキストを作らなくなる**（`z-index` は static 要素では無効）。
  結果、シートは**ルートのスタッキングコンテキストで素直に重なる**
- 実測（最終構成・`document.elementFromPoint()` で印刷バーの中心を叩く）:

  | 確認 | 結果 |
  |---|---|
  | シートが画面下端に接する | ✅ `bottom === innerHeight`（844） |
  | 印刷バーの上の点で最前面にあるのは | ✅ **シートの中の要素**（`.controls-row.filter-rest`） |
  | 印刷トレイ（`#tray`・`z-index: 20`）を開くと最前面は | ✅ **トレイ**（シートより前のまま＝順序が壊れていない） |

- **重なり順の決定**（既存値を壊さない）:

  | 要素 | `z-index` | 備考 |
  |---|---|---|
  | `.controls`（PC幅のみ sticky） | 5 | 既存・変更しない |
  | `.print-bar` | 15 | 既存・変更しない |
  | **FAB** | **16** | 印刷バーより前・ベールより後ろ |
  | **ベール** | **17** | 新規 |
  | **シート** | **18** | 新規 |
  | `#tray`（印刷トレイ） | 20 | 既存・変更しない（**シートより前のまま**） |

#### F5. ⚠️ 印刷リストバーの高さは固定ではない（モックの「56px 退避」は**不足**）

`.print-bar` は中の文言が折り返すため高さが変わる。実測:

| 条件 | `.print-bar` の高さ |
|---|---|
| 390px幅・短文（`印刷リスト: 3種 / 9枚（A4 1ページ）`） | **60px** |
| 390px幅・長文（`印刷リスト: 12種 / 48枚（A4 6ページ）`） | **79px** |
| 375px幅・長文（同上） | **79px** |

⚠️ **モックの `bottom: 78px`（＝56px 退避）は 79px のバーに対して足りない。**
→ ⭐ **退避量はハードコードせず、`.print-bar` の実測高さから求める**（§4-3 の④）。

## 5. FAB とボトムシートをどこに実装するかの方針

### 5-1. ⚠️ DOM の移動（ポータル）は**しない**

「スマホ幅のときだけ `#filter-row` を `<body>` 直下のシートへ移す」という実装は**採らない**。理由:

- 幅の行き来（端末の回転・ウィンドウのリサイズ）のたびに**戻す処理**が要り、失敗が無言になる
- `<details open>` の開閉状態・`fillChips()` が握る参照・イベントリスナの生存を**そのつど確かめる**必要が出る
- ⭐ **F2＋F3 を入れれば、DOMを動かさなくても目的は達成できる**（F4 で実測して確認済み）

### 5-2. 採用する構造

```text
<body>
  <header class="site-header">…</header>

  <section class="controls" id="controls">        ← スマホ幅では static ＋ backdrop-filter:none（F2・F3）
    <div class="controls-row">…検索入力2つ…</div>
    <button id="filter-toggle">…</button>          ← 既存。スマホのみ表示。これもシートを開く
    <div id="filter-sheet">                        ← ★新規のラッパ
        …つまみ・見出し・×（★新規）…
        <div class="filter-row" id="filter-row">…既存のまま・中身も順序も不変…</div>
        …フッタ「この条件で見る」（★新規）…
    </div>
  </section>

  <main id="grid">…</main>

  <button id="filter-fab">…</button>               ← ★新規（body直下・z-index 16）
  <div id="filter-veil"></div>                     ← ★新規（body直下・z-index 17）
  <div id="print-bar">…</div>                      ← 既存（z-index 15）
  <div id="tray">…</div>                           ← 既存（z-index 20）
</body>
```

- **`#filter-sheet` は PC幅で `display: contents`**（箱を作らない）＝ **PCのレイアウトは1pxも変わらない**。
  実測で確認済み（`.filter-row` の矩形 `top:140 left:24 w:1392 h:101` と
  `grid-template-columns: 342px 342px 342px 342px`、`.controls` の高さ 184px が**ラップ前後で完全一致**）
- **FAB とベールだけが `<body>` 直下**。⚠️ **`.controls` の中に置くと F3・F4 で必ず壊れる**
- シート本体（`#filter-sheet`）は `.controls` の中に残るが、**F2＋F3 で `.controls` が
  包含ブロックもスタッキングコンテキストも作らなくなる**ため、`position: fixed` と `z-index: 18` が素直に効く

### 5-3. 状態の持ち方

- **状態は `.controls` の `filters-open` クラス1つだけ**（既存）。FAB からでもインラインのトグルからでも
  同じ関数を通す。⚠️ **FAB専用の状態を別に持たない**（2つの入口で開閉状態が食い違う）
- 既存の `.controls.filters-open .filter-row { display: block }`（`style.css:359`）と
  `.controls.filters-open .filter-rest { … }`（`:361`）は**そのまま活かす**
