## 4. 推奨基準の指摘（**合格を妨げない**）

### S1-A ⚠️ ⭐ 新しいコメントの括弧内「**赤くなる**」は、現時点では成立しない

- **該当**: `scripts/validate.mjs` の `shared/vendor` 除外の説明（`LINEREF_EXCLUDE` の直前）
- **書かれている文**: 「ルートが shared/ なのでこの除外は実際に効いている（**外すと shared/vendor/ の配布物を拾って赤くなる**）。整理目的で消さないこと。」
- **レビュー担当の実測**: ⭐ **除外を外しても exit 0**（`0件（47ファイル走査）`＝R1）。
  `shared/vendor/jspdf.umd.min.js` の `<file>.js:<行番号>` の**実ヒットは 0件**なので、
  ⚠️ **今日この除外を外しても赤くはならない**（**走査対象に入る＝「拾う」までは真**）
- **なぜ S 止まりにしたか**（＝**不合格にしない**理由）:
  1. ⭐ **指示 §1 が求めた趣旨は「除外が実際に効いている（外すと `shared/vendor/` を拾う）」で、そこは満たしている**。
     「拾う」は R1 で実測ずみ（46→47）。⚠️ **`赤くなる` は指示に無い1語の上乗せ**
  2. ⭐ **直前の文が「配布物にソースマップ由来の記述が入りうる」と将来形で書いており**、
     承認記録 §4-1-4 も同じ条件形（「将来 …増えたら赤くなる」）を使っている＝**文脈上は将来の帰結として読める**
  3. ⭐ **害の向きが fail-open ではない**。この一文の役目は「消すな」という警告で、
     帰結を強めに書いても**検査が緩む方向には働かない**（実際に外した人が見るのは緑＝害は「警告が信用を落とす」に留まる）
- ⚠️ ⭐ **ただし本タスクは「コメントに書いた事実は腐る」を実証したタスクである。**
  その検査自身のコメントに、**測れば今日すぐ反証できる一文**が残るのは据わりが悪い。
  ⭐ **修正案（1語）**: 「外すと `shared/vendor/` も走査対象に入る（**現在の配布物にヒットは無いが、ソースマップ由来の記述が入れば赤くなる**）」
- **対応要否は設計担当の判断待ち**（⚠️ **レビュー担当はコードを直さない**）
