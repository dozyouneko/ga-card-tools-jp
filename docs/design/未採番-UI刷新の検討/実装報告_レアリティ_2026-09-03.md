### 1-2. ⭐ `urlGroups()` に足したことの意味（設計書 §4-1 の「足し忘れ」対策）

設計書は「`filterGroups()` 相当（バッジ集計・リセット）にも足す」と書いているが、
実装を読むと **`filterGroups()` は `urlGroups()` から作られている**（`app.js`）ので、
**`urlGroups()` に1行足すと次の5経路が同時に対応する**：

1. スマホのバッジ集計（`updateFilterBadge()` — インラインのトグルと FAB の両方）
2. `#reset` によるリセット（`resetControls()`）
3. PC左ペインの「選択中の条件」（`renderSelectedFilters()` / `✕` / 「すべて解除」）
4. PC左ペインのアコーディオン（`initAccordion()`）
5. 共有URL（`queryString()` / `applyUrlQuery()`）

⚠️ **逆に言えば、ここを足し忘れると5つ同時に壊れる。** R-V6・R-V7・R-V11d でそれぞれ実測した。

### 1-3. 落とし穴 P1〜P3 への対応

| # | 対応 | 実測での裏取り |
|---|---|---|
| **P1** | `MULTI` の第3要素を `null` にし、`haveOf(card, field, key)` が `editions[].rarity` から重複を潰して組み立てる。`matchesMulti()` の `card[field]` を `haveOf(...)` に差し替え | ⭐ **スナップショット2,495枚での「いずれかの版がそのレアリティ」の集計が、公式APIの `total_cards` と9値すべて一致**（749/678/645/493/123/476/227/19/80） |
| **P2** | `metaMatches()` に `if (field === null) continue;` を追加（索引に列挙値が無い項目では候補を落とさない） | ⭐ **R-V3d の破壊試験**：この1行を route で抜いて配信すると、正解5件の検索が **0件**になる |
| **P3** | ⭐ **`fillChips()` の `.sort()` は触っていない**（設計書の指示どおり）。代わりに `validate` に「`meta.rarities` が10種以上なら exit 1」のガードを置いた | ⭐ 破壊試験で確認（§3 の R-V9） |

## 6. ⚠️ 設計担当への確認事項（判断が要るのでここで止まる）

### 6-1. ⭐ 【要判断】日本語モードの「全N件」が実際の件数より多く出る（R-V3c）

**症状**（実測・`tmp/dev/rarity/jpcount.json`）：

```
日本語「イン」× レアリティ CUR/CPR
  #status = "5 件を表示 / 全 22 件（日本語テキスト一致・翻訳済みのみ）
             （うち17件は取得後の判定で除いたため表示されていません）"
  行数 = 5   ←  「全 22 件」と一致しない
```

**対照実験**（同じ日本語語句で、既存の絞り込みを使った場合）：

```
日本語「イン」× タイプ CHAMPION
  #status = "7 件を表示（日本語テキスト一致・翻訳済みのみ）"
  行数 = 7   ←  一致する（総数と表示数が同じなので「全N件」自体が出ない）
```

**原因**：JPモードの `total` は **`jpCand.length`＝索引で絞ったあとの候補数**である。
**P2 の対応でレアリティだけは索引で絞らない**ことにしたので、
**レアリティで落ちる分が `total` に残ったまま**になる。

⚠️ **副作用がもう1つある**。落ちた件数は `jpDropped` に数えられ
「うち17件は取得後の判定で除いたため表示されていません」と出るが、
**CLAUDE.md はこの注記を「出たら異常の信号」（索引の腐り・取得失敗・畳み漏れ）と位置づけている**。
⭐ **レアリティ絞り込みでは正常時に必ず点灯するので、異常信号としての価値が失われる。**

**⚠️ これは実装の不備ではなく、設計書 §5 P2 が「代償は取得件数が増えること」とだけ書いて
「件数表示をどうするか」を決めていないことによる。** 実装側では決めない。**選択肢は3つ**：

| 案 | 内容 | 影響 |
|---|---|---|
| **案1** | **`jpApprox = true` にする**（レアリティのように索引で判定できない絞り込みが有効なとき） | ⭐ **既存の仕組みをそのまま使う**（`jpApprox` は元々「索引で判定しきれない候補が混じる」ための旗）。表示は `5 件を表示（…）（一部のカードは取得後に判定するため総件数は概算です）` になり、**誤った「全22件」が消える**。⚠️ **`jpDropped` の注記は残る**（＝異常信号の価値は戻らない） |
| **案2** | **案1 ＋ 「索引で判定できない絞り込みによる除外」を `jpDropped` に数えない** | ⭐ **異常信号としての価値が戻る**。⚠️ `matchesActiveFilters()` を「索引が担当する条件」と「担当しない条件」に分ける改造が要る（`shared/` の共有ファイル） |
| **案3** | **現状のまま（何もしない）** | ⚠️ **日本語モードで件数が多めに出続ける**。⭐ ただし**表示される集合そのものは正しい**（R-V3b で実証済み）ので、実害は件数表示だけ |

⭐ **開発担当としての推奨は案1**（設計書に書かれていない意味を足さず、既存の
`jpApprox` の定義そのままで説明が付くため）。⚠️ **ただし判断は設計担当に委ねる。**
⭐ 案1なら `shared/js/card-search.js` の1〜2行で済む。
