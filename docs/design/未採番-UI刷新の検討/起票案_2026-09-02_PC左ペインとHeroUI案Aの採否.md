## 5. 検討すべき論点（設計工程で決めること）

| # | 論点 | メモ |
|---|---|---|
| **L1** | **左ペインに何を入れるか**（検索入力も入れるのか、絞り込み4グループだけか、並び替え・件数表示・印刷導線はどちらか） | ユーザーの言葉は「検索条件の部分を持っていく」。⚠️ **`#q` の入力欄が上に残るのか左に入るのかで見た目が大きく変わる**ので、モックで両案を見せて選んでもらう |
| **L2** | **ペインの幅と、結果グリッドの列数の落としどころ** | 実測のとおり結果側は 1440px で7列・1920px で9列。⭐ **左ペインを 280〜320px 取ると1〜2列減る**。減った列数が許容できるかは見た目の判断＝モックで確認する |
| **L3** | **ペインは追従（sticky）するのか、スクロールするのか** | サブタイプ157チップを開くとペイン自身が長くなる。⚠️ **ペイン内スクロール＋ページスクロールの二重スクロールは操作性を損ねやすい** |
| **L4** | ⚠️ **中間幅のブレークポイントをどこに置くか**（現状は `max-width: 640px` の1本のみ） | 実測で **1024px 以下は4列タイルが3列/2列に折り返し `.controls` が 295px に膨らむ**。**左ペインを出す下限**と**スマホのFAB＋シートに切り替える上限**の2境界を決める必要がある |
| **L5** | ⚠️ **641px〜左ペイン下限の帯（タブレット幅）をどう見せるか** | ⭐ **今は「スマホでもPCでもない帯」が実質未設計**。左ペインを入れると、この帯の扱いを決めないと**どちらの導線も出ない幅**が生まれうる |
| **L6** | ⭐ **HeroUI 案A の採否と、採るなら何をどこまで移植するか** | 対象候補はOKLCH色・角丸・余白・影・**フォーカスリング**。⚠️ **`:root` の12変数を置き換えると `404.html` の見た目にも同時に出る**（同じ `style.css` を読むため）。⚠️ ライブラリは入れない（React/Tailwind不要）＝**CSSの値だけを借りる**案であることを設計書で明示する |
| **L7** | **「古臭い」への対処を、トークン以外でも行うか** | 例: 入力欄の高さ・チップの密度・区切り線の使い方。⚠️ ⭐ **判断基準が主観なので、必ずモックで並べて選んでもらう**（設計担当が独断で決めない） |
| **L8** | **DOM を動かすか、CSS だけで組むか** | ⚠️ `#filter-sheet { display: contents }` と `.fgroup[open] { grid-column: 1/-1 }` を前提に、**スマホのシート構造を壊さずに** PC だけ2カラムにできるか。⭐ CSS Grid の領域指定で足りるなら DOM を動かさないほうが安全（下記 §6） |

## 6. ⚠️ 壊してはいけないもの（回帰の要注意点）

⚠️ ⭐ **ここが本タスクの最大のリスク。** 同じ `.controls` に、**外すと静かに壊れる対策が既に入っている**。

| # | 守るもの | 外す／壊すとどうなるか | 出所 |
|---|---|---|---|
| **R1** | `html, body { overflow-x: **clip** }`（スマホ幅。❌ `hidden` に戻さない） | スクロールコンテナ化で**子孫の `position: sticky` が全部死ぬ** | 設計書 `スマホ絞り込み導線_設計.md` §2-3・`style.css:322`〜 |
| **R2** | `.controls { position: **static** }`（スマホ幅のみ） | 条件バーが画面外に出ず、**FABが永久に出ない**（⭐ 実装は完成して見えるのに動かない） | 同 F2・`style.css:357` |
| **R3** | `.controls { backdrop-filter: **none** }`（スマホ幅のみ） | `fixed` の**包含ブロック**ができ、**シートが画面下端に来ない** | 同 F3・`style.css:363` |
| **R4** | `#filter-sheet { display: contents }` | ⚠️ **やめるとPCのレイアウトが変わる**（`style.css:122` のコメントに明記） | `style.css:122` |
| **R5** | `#filter-row` の中身の参照 | ⚠️ **`shared/js/card-search.js` の `fillChips()` が参照を握っている**（`index.html:61` のコメント）。**動かすと絞り込みが動かなくなる** | `index.html:61` |
| **R6** | `shared/css/filter-chips.css` の共有 | ⚠️ **デッキ構築にも出る**。⭐ 片方だけ直すと**画面によってチップの見た目が違う**という分かりにくい不具合になる | CLAUDE.md「環境の注意」 |
| **R7** | CSP `style-src 'self'` | HTMLの `style` 属性・`<style>` 注入は使えない。動的スタイルは **`data-*` 属性＋CSSOM** | CLAUDE.md「環境の注意」 |
| **R8** | `404.html` の見た目 | ⭐ **同じ `style.css` を読む**。`:root` のトークンを変えると**404ページにも同時に出る**（⚠️ `404.html` はJSを読まない） | 実測（§3） |

⭐ **検証は「動いたか」ではなく、CSSOM で対策を実行時に外して壊れることを見る（破壊試験）。**
「動いたから合格」では、対策が効いているのか偶然動いているのか区別できない
（スマホ導線タスクで確立した手法）。

## 7. 規模の目安（`小タスク` を付けない理由）

⚠️ **`小タスク` は付けない。** 根拠:

1. **レイアウト構造の変更**（縦1本のスタック → 2カラム）と、**中間ブレークポイントの新設**（L4・L5）が同居する。
   現状メディアクエリは1本しかなく、**新しい幅帯の設計そのものが発生する**
2. **HeroUI 案A の採否評価**（L6）が同じタスクに入る（S2）
3. **回帰の対象が広い**。§6 の R1〜R8 に加え、スマホ導線タスクの検証項目は **V0〜V32 の33件**あり、
   `.controls` を触る以上その相当部分を再確認する必要がある
4. ⚠️ **見た目の判断が主観**なので、モック提示 → ユーザー選択の往復が最低1回は入る

⭐ **設計工程で分割の余地はある**（例: 「左ペイン化」と「トークン移植」を別コミットにする）。
ただし **S2 のとおり採否の判断は同じ設計書で行う**。
