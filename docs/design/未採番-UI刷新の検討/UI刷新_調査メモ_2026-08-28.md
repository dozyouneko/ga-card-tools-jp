## 2. HeroUI の調査（2026-08-28時点）

旧 NextUI。**2026年3月に v3 として全面書き直し**された。

| 項目 | 内容 |
| --- | --- |
| 土台 | **React Aria Components**（アクセシビリティ）＋ **Tailwind CSS v4**（スタイル） |
| 規模 | Web 75+ コンポーネント（うち21が新規）＋ React Native 37 |
| ライセンス | **Apache-2.0**（完全無料・有料ティアなし） |
| 前提 | **React 19** / Next.js。v3から Provider ラッパー不要 |
| 採用規模 | コアパッケージ 週間約34万DL |

### メリット

- **アクセシビリティが土台から入っている**（Adobe の React Aria）。キーボード操作・スクリーンリーダー・
  フォーカス管理は自前実装で最も手を抜きやすい部分で、ここは明確に強い
- **v3でアニメーションが全部CSSに移った**（JSランタイムなし）。CSS変数・OKLCH色・BEM修飾子で
  外に開いており、テーマ調整にライブラリ内部への介入が要らない
- 無料・Apache-2.0。非商用ファンサイトという性格と衝突しない
- ⭐ **見た目のルールを構造で担保できる。** 現在は `style.css` / `shared/css/card-badges.css` /
  `shared/css/filter-chips.css` / `tools/deck-builder/style.css` に分散しており、
  CLAUDE.md にはバッジ配置の同種の失敗を **#25・#26・#35 と3回繰り返した**記録がある。
  本来ライブラリが解く種類の問題

### デメリット・リスク

- ⚠️ **v3はまだ若い。** v2と**共存できず**、`Image` のように削除されたコンポーネントがある。
  **Navbar など不足**がGitHubで指摘され、ロードマップの不透明さも批判されている。
  2026年3月の書き直し直後は採用側にとって最もリスクが高い時期
- **React必須。** 非Reactでの利用経路は無い
- **Tailwind v4必須 → ビルド工程が必須**
- v2からの移行で「入力ラベルのアニメーション・プリセット単位・オートコンプリートが消えた」という
  機能後退の報告がある

## 3. 現状スタックとの距離（実測・2026-08-28）

| 項目 | 実測値 |
| --- | --- |
| フロントの依存 | **ゼロ**。`package.json` の devDependencies は `wrangler` のみ |
| React / Tailwind / バンドラ | **いずれも無し** |
| 生成HTML | **3,467ページ**（カード2,495・セット63・大会909）＋手書き5ページ |
| 生成方法 | Nodeスクリプトが**生のHTML文字列**を組み立て（`scripts/build-card-pages.mjs` 他） |
| フロントJS | 素のJS。`shared/js/card-search.js` 48KB、`tools/deck-builder/app.js` 2,766行 |
| CSS | `style.css` 419行 ほか。メディアクエリは **`max-width: 640px` の1本だけ** |
| ビルド工程 | **無し**。`wrangler.toml` は `pages_build_output_dir = "."` |

⭐ **結論: HeroUI固有の障壁ではなく、「React・Tailwind・バンドラ・ビルド工程」を先に4つ導入する必要がある。**
HeroUI自体の学習コストより、こちらが桁違いに大きい。

### 副次的に効く3点

1. **SEO用の静的3,467ページが最大の論点。** 各ページに `og:image` と `ld+json` を焼き込んだ完全な
   静的HTMLで、Reactに寄せるならSSGが要る。翻訳の埋め込み・シーズン禁止の日付依存・sitemap生成が
   すべてこの生成器に乗っているため、**移行対象はUIではなくビルドチェーン全体**になる
2. **デプロイ経路②との相性。** `npm run deploy:prod` は `git archive HEAD` から作るため、
   **ビルド成果物をコミットしないと本番に出せない**。毎回コミットする運用は日次cronの自動コミットと
   混ざって差分ノイズの温床になる
3. **CSP は思ったほど問題にならない。** `style-src 'self'` が禁じるのはHTMLの `style` 属性と
   `<style>` タグ注入であって、**Reactの `style` prop は CSSOM 経由なのでブロックされない**。
   Tailwind v4 も静的CSSを吐くだけ。
   ⚠️ ただし Headless UI が `<style>` 注入でCSP違反になった実例（tailwindlabs/headlessui#2615）が
   あるため、**HeroUIについては実測が要る**（⚠️ `npm run dev` は `_headers` を解釈しないので
   `wrangler pages dev` で測る）
   - ⭐ 本調査中に**この性質を実地で踏んだ**: Playwright の `addStyleTag` は meta CSP に
     ブロックされたが、`element.style.setProperty()` は通った（§4-2 の切り分けで使用）

### 選択肢

| 案 | 内容 | コスト | 評価 |
| --- | --- | --- | --- |
| **A. 見た目だけ借りる** | HeroUIのデザイントークン（OKLCH色・角丸・余白・影・フォーカスリング）を既存CSSへ移植。ライブラリは入れない | 小 | ⭐ **第一候補。** アーキテクチャを変えずに §1 の「古臭い」と §4-1 に効く |
| **B. デッキ構築ツールだけReact島に** | `tools/deck-builder/` のみ Vite + React + HeroUI。他は現状維持 | 中〜大 | ⚠️ `card-search.js` をトップと共有しているため、二重管理か先行リファクタが必要 |
| **C. 全面移行** | Next.js等へ移し3,467ページをSSG | 特大 | 現体制（1件ずつ回す運用）では過大。非推奨 |

⚠️ **BもCも「v3の若さ」を抱え込む。** 採るなら Navbar 等が揃うのを待つ判断もありうる。

## 4. HeroUIとは独立した不満（2件）

⚠️ **どちらもHeroUIを入れなくても直せる。** ライブラリ選定と混ぜて議論しないこと。

### 4-1. PC表示：検索条件の置き方（未調査・要設計）

> 左ペインにメニューを置いて右に検索結果を表示したらきれいになるのでは

現状は `<section class="controls">` が**画面上部に横並び**で、
`.filter-row` が `grid-template-columns: repeat(auto-fit, minmax(max(240px, (100% - 24px) / 4), 1fr))`
で絞り込み4グループをタイル状に並べている（`style.css:130`）。
sticky なので追従はするが、**開くと縦を大きく占有し、カード一覧を下へ押し出す**。
CSSのコメントにも「全幅で縦に積むとカード一覧が下へ押し出される」ため現在の形にした経緯が残っている。

- **左ペイン案の見立て**: 縦長の余白は左ペインのほうが素直に使える。
  ⚠️ ただし**同じ絞り込みUIをデッキ構築ツールも使っている**（`shared/css/filter-chips.css` は
  トップとデッキ構築の両方が読む）ので、**片方だけ変えると乖離する**
- ⚠️ **メディアクエリが `max-width: 640px` の1本しかない**ため、左ペイン導入には
  中間幅（タブレット）のブレークポイント追加も伴う
- **未着手。** レイアウト案は設計工程で起こす

### 4-2. スマホ表示：検索条件まで戻るのが面倒 → ⭐ **原因を特定した（バグ）**

> スマホ表示はスクロールすると検索条件まで戻るのがめんどくさい

**`.controls` には既に `position: sticky; top: 0` が付いている**（`style.css:85`）。
つまり**設計上は追従するはずなのに、スマホでだけ効いていない**。

⭐ **原因: `style.css:314` の `html, body { overflow-x: hidden }`。**
`overflow-x: hidden` は祖先をスクロールコンテナ化するため、**子孫の `position: sticky` を無効化する**。
このルールは `@media (max-width: 640px)` の中にあるので、**スマホ幅でだけ発症する**。

#### 実測（Playwright・`http://localhost:3400/`・scrollY=1500 時点の `.controls` の top）

| 条件 | `.controls` top | 追従 |
| --- | --- | --- |
| PC 1440x900（`overflow-x: visible`） | **0px** | ✅ する |
| スマホ 390x844（現状 `overflow-x: hidden`） | **-1427px** | ❌ しない（画面外へ流れる） |
| スマホ 390x844（`overflow-x: visible` に変更） | **0px** | ✅ する |
| スマホ 390x844（**`overflow-x: clip`** に変更） | **0px** | ✅ する |

- ⭐ **`overflow-x: clip` なら、横はみ出し防止という当初の目的を保ったまま sticky が復活する**
  （`clip` はスクロールコンテナを作らないため）。
  - ⚠️ ⭐ **「1語の変更で直る」という当初の見立ては誤りだった**（2026-08-28の設計時に判明）。`clip` を入れると sticky が**復活してしまう**ため、**検索条件バーが画面外に出なくなり**、採用した FAB（画面外に出たら表示）が**永久に出ない**。→ スマホ幅では `.controls` を `position: static` にする必要がある（設計書 §2-3 F2）
- ⚠️ 3条件とも横はみ出しは検出されなかった（`scrollWidth === clientWidth`）が、
  **`overflow-x: hidden` は #21 等で横はみ出し対策として入った経緯があるため、単純削除ではなく
  `clip` への置換を検討する**。⚠️ ページ状態（長いカード名・チップ多数）によっては
  はみ出しが再現しうるので、**削除案を採るなら再現条件を潰してから**
- ⚠️ **実測は `npm run dev`（`_headers` 非適用）で行った。** sticky の挙動はヘッダに依存しないため
  問題ないが、**CSP絡みを測るときは `wrangler pages dev` を使うこと**
- 再現スクリプト: `tmp/design/sticky-check.mjs` / `tmp/design/sticky-cause.mjs`（⚠️ `tmp/` はgitignore）

⭐ **これは「UI刷新」ではなく単体のバグ。** 刷新の議論と切り離して先に直せる。
→ 起票案を `起票案_スマホの検索条件が追従しない_2026-08-28.md` に用意した。
