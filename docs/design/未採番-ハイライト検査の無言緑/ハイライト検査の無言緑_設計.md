#### ⚠️ ⭐ 訂正 — 「合計版は相殺で緑になる」は成立しない（2026-09-02・レビュー §6-1）

`SECTION` は

```js
/<h2>効果（日本語）<\/h2><p class="cp-effect">([\s\S]*?)<\/p>/g
```

で、**各マッチは先頭に `<h2>効果（日本語）</h2>` を1つ必ず消費する**。`matchAll` のマッチは
重ならないので、**どのページでも必ず 節数 ≤ 見出し数**が成り立つ。
⭐ **各ページの差（見出し − 節）が非負**である以上、**総和が0であることと各項が0であることは同値**であり、
**「合計は一致しているのに、あるページでは食い違っている」状態は作れない**。

- ⚠️ **見出しを壊すと節も同時に壊れる**（節のマッチが見出しを含むため）。
  ＝ **「見出しだけが1つ減るページ」を作れない**のが、相殺が成立しない直接の理由
- **設計担当の再実測（2026-09-02・承認時）**: 無傷の 2,495 ページで
  **節 2517 / 見出し 2517・`節数 > 見出し数` のページは 0件**（レビューの実測と一致）
- **レビューの実測**: 相殺を狙って2ページ同時に壊しても（A: 2つ目の `<p>` に属性 / B: 節ごと削除）、
  合計は **節2515 / 見出し2516** と食い違ったままで、**合計版でも検出できた**

⭐ **それでもページ単位を採る理由は「診断性」**。合計版は **「2516 ≠ 2517」としか言えず
どのページか分からない**が、ページ版は **slug を名指しできる**（V5 の `beseeched-fatestone（節1 / 見出し2）`）。
**同じ走査の中で数えるだけなのでコストは同じ**——⭐ **決定（D2）は変えない。**

- 実測: 現在の 2,495ページすべてで **ページごとの一致が成立**（不一致 **0ページ**）＝ false red は起きない

### 3-1. ① 見出しの計数

```js
// ⚠ (b) の右辺。SECTION と「同じHTMLを別の数え方で数える」ことが要点。
//   同じ正規表現から導いた値どうしを比べても、破れは検出できない。
const JP_H2 = /<h2>効果（日本語）<\/h2>/g;
```

⚠️ **`SECTION` から見出し部分を切り出して使い回さないこと。** 両辺が同源になると常に一致し、
**この検査が新しい無言の緑になる**（元タスク設計書 §5-1 の「両辺が同源になり常に通る」と同じ罠）。

### 3-2. ② `scan()` の戻り値

`scan()` は**節の数も返す**。ハイライト判定のロジック（`visibleText` / `cores` の突き合わせ）は**一切変えない**。

```js
const scan = (html) => {
  const hits = new Set();
  let sections = 0;
  for (const m of html.matchAll(SECTION)) {
    sections++;
    const text = visibleText(m[1]);
    for (const c of cores) if (text.includes(c)) hits.add(c);
  }
  return { hits: [...hits], sections };
};
```

### 3-3. ③ ページごとの判定

ワーカー内、`pages++` の直後で:

- `const h = [...html.matchAll(JP_H2)].length;`（見出しの数）
- `const { hits, sections } = scan(html);`
- **(a)** `sections === 0` なら `noSection.push(slug)`
- **(b)** ⭐ **`else if (sections !== h)`** なら `partial.push(`${slug}（節${sections} / 見出し${h}）`)`
  - ⚠️ **`else if` にする**（D5）。`sections === 0` のページで (b) も積むと、
    **1つの原因で2種類のエラーが出る**
- 既存どおり `hits.length` があれば `missed.push(…)`
- 集計用に `sections` の総和も持つ（成功行に出すため）

⚠️ **`noSection` / `partial` も `missed` と同じく `sort()` する**（並列8で読むので順序が不定。
既存の `missed.sort()` と同じ理由）。⚠️ **`total += …` を `await` の左辺に書かない**（既存コメントの注意がそのまま効く）。

`if (!pages)` の既存分岐はそのまま。`else` の中で、**この順に**積む:

   - ⚠️ **片方だけ直すと `npm run validate` が exit 1 になる**（前タスクで入れた `issue drafts in sync` 検査）。
     ⭐ **これは正しい動作**——直してから `validate` を通してコミットする
3. ⚠️ **その結果、V1 の期待行が `issue drafts in sync — 起票案11件（生きている5 / 完了5 / 取り下げ1）` に変わる**。
   §5 の表は**書き換えず**、検証済みの記録として残す（レビュー判定と食い違わせないため）

### 6-3. ⚠️ ⭐ 順序の申し送り（**起票案 §6 の位置づけをそのまま引き継ぐ**）

> **カードページのテンプレート（効果節のマークアップ）を変えるタスクより前に、本タスクを入れる。**

順序が逆になると、テンプレート変更のレビューで `npm run validate` が緑を返し、
⚠️ **「回帰していない」根拠として使われてしまう**（実際には節を1つも走査していない）。

- ⚠️ 具体的に競合しうるのは **`docs/design/未採番-UI刷新の検討/`**（カードページの見た目に手を入れる可能性がある）
- ⭐ 本タスクを先に入れておけば、テンプレート変更の側は **`validate` が赤くなることで
  「検査も直せ」と機械的に知らされる**（§1-2・§4-1）

### 6-4. push について
