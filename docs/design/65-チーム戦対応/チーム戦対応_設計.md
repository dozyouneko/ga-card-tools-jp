## 1. 背景と目的

⚠️ **時限性がある。** 2026-08-15 10:00 JST 開催の **Ascent Worlds Singapore Team Standard 3v3**（`#59730`）は、
当サイトが取り込む4カテゴリ（`store-championships`/`regionals`/`nationals`/`ascent`）で**初のチーム戦**。
現行コードはチーム戦の応答形を想定しておらず、**大会完了の翌朝のcronがレビューなしで自動publishする**。

現行のまま公開された場合の実際の見え方（§2-2 の実データで再現・モック §1）:

| 症状 | 原因 |
|---|---|
| 順位表の**全行が `Player #undefined`** | チーム戦の `standings` 行に `id` が無く、`playerName()`（L427）が `Player #${undefined}` に落ちる |
| **全行が「デッキ未提出」**＝デッキが1件も開けない | 同じ行に `hasSubmittedDecklist` が無く `hasDeck` が常に false（L220） |
| 見出しが「順位表（**6名**）」と実人数（18名）で食い違う | `standings.length` は**チーム数** |
| `<meta name="description">` が `上位: Player #undefined・…` | L683 |
| 一覧のフォーマット列が生の英字 `team-standard-3v3` | `formatJp()` にラベルが無い（L406） |

**目的**: チーム戦を**チーム単位の順位表＋メンバーごとのデッキ**として正しく掲載する。
あわせて、**未知の形のイベントを黙って壊れた形で公開しない**フェイルセーフを入れる。

### 1-1. この設計書がやらないこと

- **チーム戦の勝敗をメンバー単位に分解しない**（APIはチーム単位でしか持たない）
- **`category: regular` の取り込み対象化はしない**（チーム戦68件のうち67件が `regular`。対象拡大は別issue）
- **決勝トーナメント（single-elimination）の対戦表は扱わない**（既存の個人戦と同じく「スイス終了時点」の注記を維持）

## 2. 調査結果（2026-08-14・すべて実測）

### 2-1. チーム戦の見つけ方と分布

`/omnidex/events/<id>/teams` は **チーム戦=200 / 個人戦=400 `{"error":"Not a team event."}` / 不在=404** を返す。
これを判別子に **id 46500〜60529（14,030件・cronのスキャン範囲と同一）を全件走査**した:

| 区分 | 件数 |
|---|---|
| チーム戦 | **68** |
| 個人戦 | 13,962 |
| 取得エラー | 0 |

- チーム戦68件のうち **`category` が取り込み対象なのは `#59730`（ascent）の1件だけ**。残り67件は全て `regular`
- **`format` は68件すべて `team-standard-3v3`・`teamSize` は全て 3**
- 完了済み（`status: complete`）は48件

### 2-2. ⭐ 参照データセット: `#50528 Atelier Alliance 3v3 Blend`

完了済みチーム戦19件を調べたところ、**デッキリストを持つのは `#50528` だけ**（6チーム・18名・**デッキ18件**）。
他18件は `decklists` が0件で、現行の `collectEvent` でも**pendingのまま公開されない**（＝既存仕様のままで無害）。

→ **本件の実装・検証は `#50528` を唯一の実データとして行う**（§7・§8）。

### 2-3. 応答形の違い（個人戦 `#60363` ↔ チーム戦 `#50528`/`#59730`）

| 項目 | 個人戦 | チーム戦 |
|---|---|---|
| イベント本体の追加キー | （なし） | **`teamSize: 3`** / **`teams`** |
| `/teams` | **400** `Not a team event.` | **200** `[{name, finalPlacement, players:[{id, slot}]}]` |
| `/standings` の行 | `id` / `hasSubmittedDecklist` / `isDecklistPublic` / `finalPlacement` / `stats*` / `status` / `tiebreaker` | ⚠️ **`name`（チーム名）** / `finalPlacement` / `stats*` / `status` / `tiebreaker`（**`id` と `hasSubmittedDecklist` が無い**） |
| `/players` | `{id, username, country, cp, emblem, rank, finalPlacement}` | **同じ**（`finalPlacement` はチームの順位が入る） |
| `/decklists` | `{decklist:{material,main,sideboard}, player, visible}` | **完全に同じ**（`#50528` の18件で確認） |

⭐ **デッキはチーム戦でも「プレイヤーid単位」**。チームとの対応は `/teams[].players[].id` で解決できる。

### 2-4. `#50528` で確認した不変条件

| 確認項目 | 結果 |
|---|---|
| `teams.length` と `standings.length` | **6 = 6**（完了済み19件すべてで一致） |
| `standings[].name` が `/teams` に存在するか | **全6件が一致**（19件すべてで不一致0） |
| チーム名の重複 | **0件**（19件すべて） |
| 配列順と `finalPlacement` | **完全一致**（1,2,3,4,5,6） |
| デッキの `player` が全員どこかのチームに所属 | **YES**（所属不明0件） |
| メンバー数 | **全チーム3名**（完了済み19件すべて） |

### 2-5. ⚠️ ただしRSVP段階（`#59730` 現在）は様相が違う

| 項目 | `#59730`（2026-08-14 時点・`status: rsvp`） |

| メンバー数の分布 | **0名=76・1名=63・2名=45・3名=31** |

## 4. データ構造

### 4-1. `data/tournaments/events/<id>.json`（チーム戦のときだけキーが増える）

```jsonc
{
  "id": 50528, "name": "…", "category": "…", "format": "team-standard-3v3",
  "startAt": "…", "season": "…", "host": {…},
  "playerCount": 18,          // = /players の件数（従来どおり「人数」）
  "teamSize": 3,              // ★新規（チーム戦のみ）
  "teamCount": 6,             // ★新規（チーム戦のみ）
  "swissRounds": …, "cutSize": …, "url": "…",
  "players": { "278": "snackz", … },        // 従来どおり id → username
  "teams": [                                 // ★新規（チーム戦のみ）
    { "name": "Two Sight", "placement": 1,
      "players": [ { "id": 278, "slot": "1" }, { "id": 5390, "slot": "2" }, { "id": 390, "slot": "3" } ] }
  ],
  "standings": [                             // ★チーム戦では行の中身が変わる
    { "rank": 1, "team": "Two Sight", "members": [278, 5390, 390],
      "score": 9, "wins": 3, "losses": 0, "ties": 0, "byes": 0,
      "gwPercent": 100, "mwPercent": 100, "status": "winner" }
  ],
  "decklists": [ { "player": 278, "material": […], "main": […], "sideboard": […] } ]  // 従来と同一
}
```

- ⚠️ **チーム戦の `standings` 行に `player` を出さない**。個人戦の行は従来どおり `player` を持つ。
  **`ev.teamSize` の有無が個人戦／チーム戦の唯一の判別子**（既存451件には無いキーなので後方互換）
- ⚠️ **チーム名は `trim()` 済みの値を保存する**（先頭・末尾の空白は §2-5 のとおり実在する）。
  `standings[].team` と `teams[].name` は**必ず同じ文字列**にする（画面の突き合わせに使うため）
- `members` は `teams` から解決した**プレイヤーidの配列**（解決できなければ `[]`）。
  ⭐ これを持たせることで、**生成側は `teams` を再突き合わせしなくてよい**（描画が決定的になる）

### 4-2. `data/tournaments/index.json` の `events[]`

既存キーはそのまま、チーム戦のみ **`teamCount`** を追加する（`playerCount` は人数のまま）。

## 5. 取り込みロジック（`collectEvent`）

### 5-1. 判別と取得

```
isTeam = Number.isFinite(ev.teamSize) && ev.teamSize > 0
```

- ⚠️ **`/teams` は「チーム戦のときだけ」呼ぶ。** 個人戦で呼ぶと **400** が返り、`fetchJson()` は
  404以外を3回リトライしたうえで**例外を投げる**（L108-119）。13,962件の個人戦で毎回3回叩くことになる
- 取得は個人戦が3本（players/standings/decklists）、チーム戦は **4本**（＋teams）

### 5-2. 判定（収録する / pending にする）

既存の判定は**そのまま維持**したうえで、チーム戦の条件を足す:

| # | 条件 | 扱い |
|---|---|---|
| 1 | カテゴリ許可リスト外 / `canceled` / 開催日が `INCLUDE_FROM_DATE` より前 | **収録しない**（従来どおり） |
| 2 | `status !== "complete"` または `!ev.decklists` | **pending**（従来どおり） |
| 3 | `standings` が0行 または `decklists` が0件 | **pending**（従来どおり）。⭐ 完了済みチーム戦19件中18件がここで止まる |
| 4 | **チーム戦なのに `/teams` が空・取得失敗** | ⚠️ **pending**（推測で描かない） |
| 5 | **チーム戦なのに `standings` 行に `name` が無い** | ⚠️ **pending**＋`log()` に警告1行（未知の形＝公開しない） |

⭐ **4・5 が「`Player #undefined` を本番に出さない」ためのフェイルセーフ。**
pending は60日で破棄されるため、恒久的にゴミが残ることはない。

### 5-3. チーム名の突き合わせ（決定的であること）

1. `/teams` を配列順に走査し、`Map<trim済みname, team[]>` を作る（**同名は配列に積む**）
2. `standings` を配列順に走査し、行の `trim` 済み `name` でMapを引き、**先頭から1つ取り出して消費する**
3. 引けなければ `members: []`（画面には「メンバー情報なし」と出す）

- ⚠️ **実測では重複0だが、重複しても順序で決まる**ようにする（同じ入力から常に同じ出力＝cronのノイズコミット防止）
- `rank` は**配列順**（既存の個人戦と同じ規則）。`finalPlacement` は使わない
  （`#50528` では両者が完全一致。既存の「順位はスイス終了時点」の注記もそのまま活きる）

### 5-4. `playerCount` / `teamCount`

- `playerCount` = `/players` の件数（`#50528` で **18**）。⚠️ **既存の `Array.isArray(ev.players) ? ev.players.length : standings.length` は
  チーム戦だと `standings.length`（=チーム数）に落ちる可能性があるため、チーム戦では `/players` の件数を使う**
- `teamCount` = `teams.length`（`#50528` で **6**）

## 6. 画面仕様

⭐ **すべて `docs/design/65-チーム戦対応/モック_順位表.html` の「2. 変更後 案A」と一致させる。**

### 6-1. 順位表（大会詳細ページ）

**列は個人戦と同じ8列のまま**（順位／チーム・メンバー／デッキ／勝ち点／成績／GW%／MW%／リンク）。
1チーム = 1つの `<tbody class="team-block">`。

| 行 | 各セルの内容 |
|---|---|
| **チーム行**（`<tr class="team-row">`） | 順位（1〜3位は 🥇🥈🥉）／**チーム名**＋`3名` の小さな添字／デッキ列は空／勝ち点／成績／GW%／MW%／末尾セルは空 |
| **メンバー行**（`<tr class="member-row" data-player="<id>">`） | 順位セルは空／**slot番号＋プレイヤー名**（インデント）／属性玉＋チャンピオン名／勝ち点・成績・GW%・MW%は空／`📄 デッキを見る` |

- ⚠️ **`data-player` はメンバー行に必ず残す。** `tournaments/deck.js` の `openRankBlockOf()`（L1321）が
  `tr[data-player="…"]` で行を探し、共有リンク `#deck-<playerId>` の復元に使っている
- メンバーが0名のチームは `メンバー情報なし` の1行を出す（**チーム行は消さない**）
- デッキが無いメンバーは既存と同じ `デッキ未提出` と `—`
- ⚠️ **チーム名は `trim()` して表示**（先頭空白のチームが実在する）
- **1位のチームブロックにだけ** 既存の `tr.top1` 相当の淡い背景を付ける
- 375px幅では既存の `@media (max-width:640px)` のグリッド組み替えに合わせる。
  ⚠️ **`メンバー情報なし` の行が右寄せにならないよう `grid-column:1/-1` を明示する**（モックで確認した唯一の崩れ）

### 6-3. 絞り込みの単位（⚠️ 行ではなくチームブロック）

- `data-search` は **`<tbody class="team-block">` に持たせる**（チーム名＋全メンバー名＋チャンピオン名の全文＋属性の英字コードと日本語名）

- 件数表示の分母は**チーム数**


- ⚠️ **`shared/js/card-i18n.js` の `FORMAT_JP` には足さない**（カードの使用可否表示の語彙を汚す）

## 8. 検証の手順（⚠️ 実データを取り込む唯一の経路）

### 8-1. なぜ手順が要るか

`#50528` は `category: regular` で**取り込み対象外**。現行の `scan()` は
**`index.scan.maxId + 1` から前へ進むだけ**で、過去のidを指定して取り込む方法が無い。

### 8-2. `--only <id>` を追加する（実装スコープに含む）

| 仕様 | 内容 |
|---|---|
| 形 | `node scripts/build-tournament-pages.mjs --only 50528`（カンマ区切りで複数可） |
| 動作 | 指定idだけを取得して `collectEvent()` を通し、`data/tournaments/events/<id>.json` を書く |
| ⭐ 例外 | **カテゴリ許可リストだけを無視する**（`canceled`・開催日・未確定の判定は通常どおり適用する） |
| やらないこと | 上端探索・pendingの再チェック・`index.scan` の更新（⚠️ **スキャン位置を汚さない**） |
| ⚠️ 注意 | **日次cronからは絶対に呼ばない**（許可リストを迂回するため）。用途はローカル検証のみ |

### 8-3. V9（フェイルセーフ）の作り方

⚠️ **テスト用の環境変数や一時的な細工をコードに入れない。** 代わりに**実データで再現できる経路**を使う:

- **`--only 51364`** … 完了済みのチーム戦だが **`decklists` が0件**（§2-2 の18件のうちの1つ）。
  §5-2 #3 の判定で **pending に落ち、ページが生成されない**ことを確認できる

⚠️ §5-2 の **#4（`/teams` が空）・#5（`standings` 行に `name` が無い）は実データで再現できない**。
この2つは**コードレビューでの確認**とし、**実装報告コメントに該当箇所を引用**すること。
