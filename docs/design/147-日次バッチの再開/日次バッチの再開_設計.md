## 1. 方針が変わった経緯

⭐ **停止の理由は GitHub から開示されていない**（示されたのは `flagged by our abuse-detection systems for manual review` と
`We've cleared the restrictions` の2文だけ）。そこで停止直前1か月の活動を実測した:

| 活動 | 主体 | 量 |
|---|---|---|
| push | 旧cron（`github-actions[bot]`） | **1日1回**（2回の日が2日） |
| push | 個人アカウント（人の手） | **1日 3〜15回** |
| issue コメント | 個人アカウント（**中身は Claude の各セッションが `gh` で投稿**） | **1か月 424件・最大 36件/日・平均 2,827字** |

- ⭐ **旧cronは「git scraping」と呼ばれる一般的な使い方の範囲**で、規約の Actions 節
  （`production, testing, deployment, or publication of the software project`）にも当たると読める（2026-10-17 に裏取り済み）
- ⚠️ ⭐ **目立つのは「人のアカウントから、自動化された長文コメントが毎日数十件」**という信号のほう（**推測**。確定はしていない）
- ⭐ よって **cron 側は小さく整えて再開し、自動化の名義を個人アカウントから外す**（＝D' ＋ A）

⭐ **再停止されたときの被害も前回より小さい**: GitLab ミラー（`backup`）で履歴は失われず、
`wrangler pages deploy`（経路②）で GitHub と無関係に公開できる。失うのは issue 運用と cron。

## 3. W1 — スキャン位置だけの日はコミットしない

### 3-1. 現状

旧cronの小さなコミットは **`data/tournaments/index.json` の `updatedAt` と `scan.maxId` の2行**だけだった
（実例 `ca7059f0`・`9e05aa38` など。8月の18件のうち **8件**）。⭐ **新しい大会が無い日も毎日 push していた**。

### 3-2. 規則

`git add`（8パス）の後、`git diff --cached` を見て次のとおり判定する:

| ステージされた差分 | 判定 |
|---|---|
| 何も無い | **コミットしない**（現状どおり） |
| ⭐ **`data/tournaments/index.json` だけ**で、その中の変化が **`updatedAt` と `scan`（`minId`/`maxId`）だけ** | ⭐ **原則コミットしない**。ただし **`HEAD` の `index.json` の `updatedAt` から 7日以上経っていればコミットする**（§3-3） |
| それ以外（`events` が変わった・`pending.json` が変わった・ページが変わった 等） | **コミットする**（現状どおり） |

- ⭐ **判定は JSON をパースして比べる**（行の差分を数えない）。`events` 配列は**深い比較**で同値を見る
- ⭐ **判定ロジックは `scripts/cron-commit-decision.mjs` に切り出し、ワークフローは結果（`commit` / `skip`）だけを使う**——
  **ローカルで fixture を与えて検証できるようにするため**（Actions は手元で回せない）
- ⚠️ **`HEAD` の版は `git show HEAD:data/tournaments/index.json` で読む**。⚠️ **`actions/checkout` は既定で履歴1件の浅いクローン**なので、
  **`git log` で「前回のコミット日」を引く実装は動かない**
- ⭐ **`pending.json` の変化はコミットする**——**`firstSeenAt` を持つ状態**なので、落とすと翌日に別の日付で再発見される
- ⚠️ ⭐ **判定が例外で落ちたら「コミットする」側に倒す**（fail-safe。旧来の挙動に戻るだけで、データは失われない）

### 3-3. なぜ「週1回だけ位置をコミット」するのか

コミットしないと、**翌日のスキャンは前回コミット済みの `scan.maxId + 1` からやり直しになる**（`build-tournament-pages.mjs` の `from`）。
世界全体で大会は**約115件/日**作られるので、**コミットしない日が続くほど1日あたりの取り直しが積み上がる**（7日で約800件）。
⭐ **7日で一度位置を進めれば、取り直しは最大でも約800リクエストで頭打ちになる**（旧cronの初回スキャンの規模と比べて十分小さい）。

### 3-4. 期待される効果（目安）

⭐ **新しい大会が収録された日・保留が増えた日・カード側に変化があった日だけ push する**。
⚠️ **頻度の実数は再開後に測る**（§8-3）。ここに予測値を書かない。

## 6. W4 — validate を回す（旧 Q5）

- ⭐ **ステップの位置は「コミット・push」と「IndexNow」の後＝ジョブの最後**
- ⭐ **`continue-on-error` は付けない**——**失敗したらジョブが赤くなり、GitHub がワークフローの所有者へメールで知らせる**（旧 Q3 はこれで足りる）

  `meta.sets` の抜けでその日の大会データごと止まる＝ CLAUDE.md が `continue-on-error` を付けている理由と同じ）
- ⭐ **得るもの**: **手で足す辞書（`meta.sets` / `meta.subtypes` / `meta.rarities`）の抜けが、新セット当日のメールで分かる**
  （#40 の「SP4 が約1か月絞り込めなかった」型の再発防止）
- ⚠️ ⭐ **赤の意味が増える**: いまは「IndexNow の既知403以外の何か」だったが、**「validate が落ちた」も赤になる**。
  ⭐ **赤を見たらどのステップが落ちたかを開く**（CLAUDE.md に追記する。§10）
- ⚠️ **`validate` は `tmp/api-cache/cards-snapshot.json` があれば実データ検査も走る**。Actions では前段の生成で取得済みなので**スキップされない**

### 6-1. 前段が失敗した日も validate を回す（1.1・ユーザー決定 Q-a・2026-11-17）

- ⭐ **validate ステップに `if: ${{ !cancelled() }}` を足す**。⚠️ **`continue-on-error` は付けないまま**
- **理由**: Actions は既定で **`if:` の無いステップに `success()` を暗黙に補う**ので、1.0 の形では
  **IndexNow やコミット・push のステップが落ちた日に validate が実行されない**（開発担当が報告・レビュー担当がワークフローを読んで確認）。
  ⭐ **辞書の抜けを知らせるのが W4 の目的**なので、**別の理由で赤くなった日にもその知らせを失わない**ほうを採った
  - ⭐ 公式の規則（GitHub Docs「Expressions」の Status check functions）: **`if:` の式に状態関数（`success()` / `always()` / `cancelled()` / `failure()`）が含まれると、暗黙の `success()` は付かない**。
    ⭐ **`always()` ではなく `!cancelled()`** にするのは、**手動キャンセル・タイムアウトの日まで validate を走らせない**ため（公式も `always()` より `!cancelled()` を推奨している）
- ⚠️ ⭐ **`if:` の書き方は `${{ !cancelled() }}` の形にする**（`${{ }}` で囲む）。⚠️ **`!` で始まる素の値は YAML のタグと解釈される**ので、
  囲まない `if: !cancelled()` は書かない（⭐ 囲んだ形は js-yaml 4.1.1 で `"${{ !cancelled() }}"` の文字列として読めることを設計担当が実測）
- ⭐ **赤の意味（1.1 での整理）**:

  | 落ちたステップ | 意味 | validate は |
  |---|---|---|
  | 生成3本のうち大会・カード（索引は `continue-on-error`） | API 障害等。**その日の公開は止まる** | ⭐ **走る**（途中まで生成された作業ツリーを検査する。⚠️ **赤が二重に出ても、原因は最初に落ちたステップ**） |
  | コミット・push | push 競合等。**公開は止まる** | ⭐ **走る** |
  | IndexNow | 既知403以外の失敗。**公開は済んでいる** | ⭐ **走る** |
  | **validate だけ** | ⭐ **手で足す辞書の抜け等**。公開は済んでいる | — |

  ⭐ **赤を見たら「最初に落ちたステップ」を開く**（CLAUDE.md へ反映するのは §10）。⚠️ **validate だけが赤の日が W4 の本来の知らせ**

## 7. W5 — マシンアカウント（単位2・ユーザー作業）

### 7-1. 何を分けるか

| 操作 | いま | 変更後 |
|---|---|---|
| Claude セッションの `gh issue create/comment/edit` | 個人アカウント（`dozyouneko`） | ⭐ **マシンアカウント** |
| `git push origin main` | 個人アカウント（ホストの VS Code 資格情報） | **変えない**（⭐ **公開は常に人の判断**なので人の名義のまま） |
| ローカルのコミットの author | `dozyouneko` | **変えない** |
| 日次cronのコミット・push | `github-actions[bot]` | **変えない** |

⭐ **`gh` と `git push` は資格情報の出どころが別**（実測: `gh` は `~/.config/gh/hosts.yml`、push は VS Code の credential helper）
なので、**`gh` だけを差し替えれば分かれる**。

### 7-2. 手順（ユーザーが行う）

1. **マシンアカウントを1つ作る**（例: `dozyouneko-bot`。⚠️ **規約上、個人が持てる無料アカウントは1つで、追加はマシン用途に限る**——このための用途なので該当する）
2. 本リポジトリの **Settings → Collaborators** でマシンアカウントを招待し、**Triage** 権限で承認する
   - ⭐ **Triage は issue の作成・コメント・ラベル操作・クローズができ、push はできない**
     ＝ ⭐ **「マシンアカウントが誤って公開する」経路が権限で塞がる**
3. マシンアカウント側で **Fine-grained PAT** を作る（対象リポジトリ: このリポジトリだけ／権限: **Issues: Read and write**・Metadata: Read）
4. コンテナで `gh auth login --with-token` に3のトークンを渡す（`gh auth status` の Active account がマシンアカウントになること）
   - ⚠️ **個人アカウントの `gh` ログインは残してよい**が、**Active をマシンアカウントにする**（`gh auth switch`）
   - ⚠️ **ワークフローの再有効化（§8）は個人アカウントで行う**（Triage では Actions を操作できない）。そのときだけ `gh auth switch` で戻す

### 7-3. 影響

- ⚠️ ⭐ **コンテナ再構築で `~/.config/gh/` が消えるのは変わらない**。再構築後は **4 をやり直す**（CLAUDE.md の該当行を更新する）
- ⭐ **`closes #<n>` による自動クローズは push した人（個人アカウント）の名義のまま**。これは人の操作なので問題ない
- ⚠️ **既存の issue・コメントの名義は変わらない**（遡って移さない）

**模擬器の要件**（`tmp/dev/147/` に置く。⚠️ **コミットしない**）:

- ⭐ **ワークフローを YAML としてパースし、各ステップの `if` を読む**（⚠️ **validate の判定を模擬器に書き込まない**——書くと何を変えても同じ結果になる）
- 評価規則は GitHub Docs の Status check functions に従う: **`if` が無い → `success()`**／**状態関数を含む → そのまま評価**／
  **状態関数を含まない式**（IndexNow の `steps.commit.outputs.committed == 'true'`）**→ `success() && <式>`**。`<式>` の真偽はシナリオで与える
- `success()` = それまでに**失敗したステップ（`continue-on-error` のものを除く）が無い**／`failure()` = その否定／`cancelled()` = シナリオの「キャンセル」／`always()` = 真
- ⚠️ ⭐ **知らない式に出会ったら例外で止める**（fail-closed。⚠️ 「走る」にも「走らない」にも倒さない）
- ジョブの結論 = **`continue-on-error` でないステップが1つでも失敗 → `failure`**／キャンセル → `cancelled`／それ以外 `success`

| シナリオ | 与える条件 | validate は（期待） |
|---|---|---|
| S1 | 全ステップ成功・`committed=true` | **走る**（IndexNow も走る） |
| S2 | 全ステップ成功・`committed=false` | **走る**（IndexNow は走らない） |
| S3 | ⭐ **IndexNow が失敗** | **走る** |
| S4 | ⭐ **コミット・push が失敗** | **走る**（IndexNow は走らない） |
| S5 | ⭐ **大会データのスキャンが失敗** | **走る**（カード・コミット・IndexNow は走らない。⭐ 索引は `continue-on-error` だが `if` が無いので**走らない**） |
| S6 | ⭐ **キャンセル**（コミット・push の途中で） | **走らない** |
| S7 | 前段すべて成功・validate だけ失敗 | 走る・**ジョブは `failure`**（V21） |

破壊試験（⭐ **ワークフローの複製に1点だけ当てる**。⚠️ 作業ツリーのワークフローは触らない。番号 B5 はレビュー担当が自前で使ったので飛ばす）:

| # | 壊し方 | 落ちるはずの項目 | ⭐ 識別力の根拠（設計担当の読み） |
|---|---|---|---|
| B6 | validate の **`if:` を外す**（＝1.0 に戻す） | **V19・S3・S4・S5**（3つとも「走らない」になる）。⚠️ **S1・S2・S6・S7 は通る** | 暗黙の `success()` が前段の失敗で偽になる |

- ⚠️ ⭐ **「落ちるはず」は設計担当がまだ実測していない**（模擬器が実装前のため）。**開発担当は B6〜B8 を実際に当て、上の「通る」側も通ることまで報告する**
  （⭐ **半分だけ落ちる**＝ #139 の6度目の型に当たったら、そのまま報告に書く）
