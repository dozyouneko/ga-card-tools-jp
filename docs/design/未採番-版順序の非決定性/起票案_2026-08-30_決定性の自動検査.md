## 本文（案）

### 何が問題か

未採番「版順序の非決定性」で `scripts/build-card-pages.mjs` に **`editionOrder()`（5段の全順序）** を入れ、
**公式APIの `editions` 配列順が変わっても生成物が変わらない**ようにした。

⚠️ **しかし、この性質を守っているのはコメント4行だけである。**

```js
// ⚠ 公式APIの editions 配列順は予告なく入れ替わる。第2キー以降を削ると出力が非決定的になり、
//   中身が変わらない日に日次cronがノイズコミットを作る(#71)。整形目的で簡略化しないこと。
```

⚠️ **将来この比較器が「整形目的で」簡略化されたとき、気づける経路は
「cronがノイズコミットを作り始めること」だけ**で、⚠️ **それはAPI由来のドリフトと区別が付かない**。

⭐ **それは今回の不具合が長く見過ごされたのとまったく同じ経路である**——
#71（2026-08-17）で「無関係な差分31ファイル」として観測されながら、
そのときは「API側のドリフト」で説明が付いてしまい、比較器の欠陥だと分かったのは
**2026-08-26のフレーバー表示経路のレビュー**（しかも別タスクのついで）だった。

### ⚠️ なぜコメントでは足りないか

CLAUDE.md には**同型の「外すと静かに壊れる対策」**が既にある
（スマホ幅の `overflow-x: clip` / `position: static` / `backdrop-filter: none` の3対策）。
⭐ **あちらは設計書に破壊試験を検証項目として書き、レビューが実際に外して壊れることを確認した**が、
それは**そのタスクの中だけの防御**であり、恒久的な自動検査ではない。

⭐ **今回は `npm run validate` に載せられる**（純粋な関数の性質なので、オフラインで判定できる）。

> | a | `main()` をエントリポイント判定で囲う | ⚠️ **cronが毎日叩く本番ビルドスクリプトの起動経路を変える** |
> | b | `editionOrder()` を `scripts/lib/` に切り出して両者が import する | 構造は綺麗だが**変更範囲が広がる** |
>
> ⚠️ **どちらでも `build-card-pages.mjs` に手が入る**ため、**V5（生成物が1ファイルも変わらないこと）の

### ⚠️ 実装時に判明している制約（設計担当が2026-08-30に確認）

- ⚠️ **`editionOrder()` は export されていない。** `scripts/build-card-pages.mjs` は
  `export` 文を1つも持たない（実測: `grep -n "^export" scripts/build-card-pages.mjs` は0件）。
  ⭐ **レビュー担当は検証時、スクリプトのコピーから `exposed.mjs` を作って import した**。
  → **`validate.mjs` から使うには export を1行足す必要がある**
  （⚠️ **`build-card-pages.mjs` に手が入る＝生成物が変わらないことを検証項目に入れる**）
- ⚠️ ⭐ **`build-card-pages.mjs` は import しただけでビルドが走らないか**を確認すること
  （トップレベルで `main()` を呼んでいると、validate がカードページを生成してしまう）
- ⭐ **反対称性（`sign(f(a,b)) === -sign(f(b,a))`）も併せて見る価値がある**。
  ⚠️ 反対称でない比較器は `Array.prototype.sort` の結果自体が実装依存になる
  （レビュー担当が本タスクで実測し、違反0を確認している）
- ⭐ **検出経路の整理**（CLAUDE.md の書き方に合わせる）:
  **`npm run validate` が exit 1 で人を止める**／⚠️ **cronは validate を実行しない**ので、
  cron 側で守れるものではない。⭐ **比較器を触るのは常に人**なので、
  #70（cron列挙のドリフト防止）と同じ理屈で**検出経路として成立する**
