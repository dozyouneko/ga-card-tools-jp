## 1. 原因

### 1-1. 該当行(`scripts/build-card-pages.mjs:150-157`)

```js
// 版を「所属セットの発売日が新しい順」に並べたカードのビューを返す。
// 代表画像・パンくず・収録一覧すべて最新版基準(指摘: 最古版だと旧セットの絵柄になる)。
function newestFirst(card) {
  const eds = [...(card.editions || card.result_editions || [])].sort((a, b) =>
    day(b.set && b.set.release_date).localeCompare(day(a.set && a.set.release_date))
  );
  return { ...card, editions: eds, result_editions: eds };
}
```

比較しているのは **所属セットの発売日だけ**で、同着時の第2キーが無い。
`Array.prototype.sort` は安定ソートなので、**同着の版は入力配列の順序をそのまま保つ**。
入力は公式APIの `editions` 配列で、⚠️ **この配列順は公式API側で予告なく入れ替わる**
(CLAUDE.md「`build:cards` — 手動実行すると、タスクと無関係な差分が混ざり得る」/ #71 実測)。

### 1-2. 何が変わるか(カードページ)

`newestFirst()` の戻り値の `editions[0]` が「代表の版」になり、次の4つを支配する:

| 出力 | 生成箇所 | 影響 |
|---|---|---|
| `og:image` / `twitter:image` / 本文の代表画像 | `cardPage()` の `imgs[0].url` | ⚠️ **SNSに貼ったときの絵柄が別の版に変わる** |
| イラスト切替サムネイル(`.cp-arts`)の並び | `CI.cardImages(card)` の返り順 | 並びと初期選択が変わる |
| 収録セット表(`収録セットと版`)の行順 | `eds.map(...)` | 表示上の並びが入れ替わる |
| 両面カードの裏面画像 | `CI.backFace()` → `flipEdition()` が **`find()` で最初の flip 版**を採る | 裏面の絵柄が別の版に変わりうる |

### 1-3. なぜ「静かに」問題になるのか

⚠️ **日次cronが毎日 `build:cards` を回して `cards/**` `sets/**` をコミットする**(#30)。
APIが配列を並べ替えるたびに**中身が1文字も変わっていないカードで差分が出て、そのまま自動publishされる**。
CLAUDE.md の「出力は決定的でなければならない(中身が変わらない日に差分が出ると、cronが毎日ノイズコミットを作る)」に反する。

⚠️ **「同じキャッシュで2回回してバイト一致」は決定性の証明にならない**(入力配列が同じなら同じ結果になるのは当然)。
**入力の並び順を変えても一致すること**まで見る必要がある(→ §6 V2)。

### 1-4. ⭐ 同じ経路がもう1箇所ある(セットページ)— 起票案の実測項目4への回答

**`sets/**` にも効いている。** ただし `newestFirst()` 経由ではなく、**生の配列順を直接使っている
第2の箇所**が原因(`scripts/build-card-pages.mjs`・`main()` のセット別グルーピング):

```js
  for (const card of cards) {
    const seen = new Set();
    for (const ed of card.editions || card.result_editions || []) {   // ← 生の配列順
      const prefix = ed.set && ed.set.prefix;
      if (!prefix || seen.has(prefix)) continue;                       // ← 同一セット内は先頭のみ採用
      seen.add(prefix);
      ...
```

**1枚のカードが同じセットに複数の版を持つ**とき(別絵柄 `#048A/B/C`・拡張アート版・
別カード番号での再録)、**配列の先頭に来た版が採用される**。セットページの
**カード番号・レアリティ・ホバー時のカード画像(`data-img`)**がこれで決まるため、
APIが並べ替えると**セットページも変わる**。

⚠️ **`newestFirst()` だけを直しても `sets/**` は非決定のまま残る。** 修正は2箇所必要(→ §4)。

## 3. 第2ソートキーの決定と根拠 — 起票案の実測項目2への回答

### 3-1. 要件は「決定性」だけではない

`newestFirst()` のコメント「代表画像・パンくず・収録一覧すべて**最新版基準**
(指摘: 最古版だと旧セットの絵柄になる)」は、**過去にユーザーから受けた指摘に基づく＝
代表画像の見た目そのものが要件**である。したがって第2キーは
**「決着すればなんでもよい」ではなく、「どの版の絵柄を代表にするか」を決める設計判断**になる。

実物の版を見ると、同着は3つの形で起きる:

| 同着の形 | 実例 | どれを代表にすべきか |
|---|---|---|
| **同一セット内の別絵柄**(番号に A/B/C が付く) | `break-apart` RDOPD **#048A / #048B / #048C**(すべてレア1) | ⭐ 通常版＝**A**(番号の自然順の先頭) |
| **同一セット内の特殊仕様**(番号は同じでレアリティ違い/拡張アート) | `pantheon-barrier` PP1 **#059**(PR) と **#059A〜D**(CPR)<br>`lorraine-spirit-ruler` RDOPD #009 の `-rdopd` と **`-rdopd-ext`** | ⭐ **通常版**(低レアリティ・無印slug) |
| **別セットが同じ発売日**(本編セットとスターターデッキ/イベントパック) | `aenean-frostlance` **PRD #141** と **PRDSD #041**(ともに 2026-08-21・レア2)<br>`spurn-to-ash` **RDOPD #149** と **RDOEVP #018**(ともに 2026-04-03・レア2) | ⭐ **本編セット側** |

⚠️ **3つ目が効くので「レアリティ→カード番号」だけでは足りない。**
`aenean-frostlance` はレアリティが同じで、カード番号は**スターターデッキ側が小さい**(#041 < #141)。
番号順だと**スターターデッキの絵柄が代表になる**。

### 3-2. 候補3案の実測比較

いずれも第1キーは既存どおり `release_date` 降順。第2キー以降だけを変えて、
**HEAD(`03ff53a5`)から `og:image` が変わるカード数**を測った:

| 案 | 第2キー以降 | `og:image` が HEAD から変わる |
|---|---|---:|
| C1 | レアリティ → カード番号 → 版slug | **209** |
| C2 | **セットprefixの辞書順** → レアリティ → カード番号 → 版slug | **16** |
| **C3(採用)** | **`meta.sets` の並び順** → レアリティ → カード番号 → 版slug | **16** |

- ⚠️ **素朴なC1は却下。** §3-1 の3つ目(本編セット vs スターターデッキ)を落とすため、
  **209枚で代表画像がスターターデッキ/プロモ側の絵柄に変わる**。
  ⭐ **「決定的になればどれでも同じ」ではないことが数字で出た**(C1とC2は代表版が **205枚**で食い違う)
- **C2 と C3 が食い違うのは 2枚だけ**(`gentle-respite` / `spurn-to-ash`。どちらも
  同日の **RDOPD**(パンテオンデッキ)と **RDOEVP**(イベントパック)の対決)。
  辞書順では `RDOEVP` < `RDOPD` で**イベントパックのプロモが代表になる**が、
  `meta.sets` は本編寄りの **RDOPD を先**に置いている。⭐ **どちらの実例でもC3のほうが妥当**なのでC3を採る

### 3-3. 採用する比較順(確定)

1. **所属セットの発売日 降順** — 既存の主キー。`day()` で `1970-01-01`(API未設定)を空文字に潰し、**末尾**に置く
2. **`meta.sets` の並び順 昇順**(`setOrder(prefix)`) — 同日なら**本編セット→1st Ed.→サプリメント→プロモ**の順。**未登録セットは 9999 で末尾**
3. **レアリティ 昇順** — 通常版を特殊仕様(PR/CSR/CUR/CPR)より優先。`null` は 99 として末尾
4. **カード番号 昇順**(`localeCompare(…, "en", { numeric: true })`) — 同一セット内が **#048A → #048B → #048C** の自然順になる
5. **版slug 昇順** — 最終決着キー

**なぜ `meta.sets` の順を使うのか(キー2の根拠)**

- ⭐ **同じ並びをこのファイルが既に使っている。** `setOrder()` は `cards/index.html` の
  エキスパンション索引・トップの静的セットリンク・セットページの並びの出所で、
  **「どのセットが先か」の唯一の宣言**になっている。ここで別の順序概念(prefixの辞書順)を
  作ると、**同じ問いに2つの答えがある**状態になる
- ⭐ **未登録セットでも壊れない。** `setOrder()` は未登録を 9999 に倒すので(#40 の登録漏れが起きても)
  比較は続行し、キー3〜5で決着する
- ⚠️ **`meta.sets` への追記は先頭(新しい順)なので、既存セットどうしの相対順は変わらない**
  ＝新セットを足しても既存カードの代表画像は動かない

**キー4とキー5の順序について**: 逆(slug先)にしても**代表版が変わるカードは0枚**、
並び順が変わるのは3枚だけだった。⭐ **収録セット表が番号の自然順に読める**利点を採ってカード番号を先にする。

### 3-4. 決着の保証

- 同一カード内で `edition.slug` は**一意**(実測: 2,495枚・4,940版で重複0)
- キー1〜5で**比較結果が0になる組は0**(全カードの全ペアで実測)

⚠️ **将来 `slug` が重複しうるようになったら、この保証は崩れる**。キー5を削らないこと。

## 4. 変更内容(実装待ち)

### 4-1. `editionOrder()` を新設する(`day()` と `newestFirst()` の間)

```js
// 版の正規順序。⚠ この比較器の出力順が、次の4つを支配する:
//   ① 代表画像(og:image / twitter:image / 本文の画像) ② イラスト切替サムネイルの並び
//   ③ 収録セット表の行順 ④ セットページが各セットで採る版(main() のグルーピング)
// ⚠ 公式APIの editions 配列順は予告なく入れ替わる。第2キー以降を削ると出力が非決定的になり、
//   中身が変わらない日に日次cronがノイズコミットを作る(#71)。整形目的で簡略化しないこと。
//   1. 所属セットの発売日 降順   … 代表は最新セットの版(既存の主キー。最古版だと旧セットの絵柄になる)
//   2. meta.sets の並び 昇順     … 同日なら本編セット→サプリメント→プロモ(未登録セットは 9999 で末尾)
//   3. レアリティ 昇順           … 通常版を特殊仕様(PR/CSR/CUR/CPR)より優先
//   4. カード番号 昇順(数値考慮) … 同一セット内が #048A → #048B → #048C の自然順になる
//   5. 版slug 昇順               … 最終決着キー(カード内で一意。実測: 4,940版で重複0)
function editionOrder(a, b) {
  const byDate = day(b.set && b.set.release_date).localeCompare(day(a.set && a.set.release_date));
  if (byDate) return byDate;
  const bySet = setOrder((a.set && a.set.prefix) || "") - setOrder((b.set && b.set.prefix) || "");
  if (bySet) return bySet;
  const byRarity = (a.rarity == null ? 99 : a.rarity) - (b.rarity == null ? 99 : b.rarity);
  if (byRarity) return byRarity;
  const byNumber = String(a.collector_number || "")
    .localeCompare(String(b.collector_number || ""), "en", { numeric: true });
  if (byNumber) return byNumber;
  return String(a.slug || "").localeCompare(String(b.slug || ""));
}
```

⚠️ `setOrder()` は同ファイルの先頭付近(`SET_LABELS` の直後)で定義済みなので、新規の依存は増えない。

### 4-3. セット別グルーピングを正規順序で回す(§1-4 の第2の経路)

`main()` のグルーピングループの1行を差し替える:

```js
  for (const card of cards) {
    const seen = new Set();
    // ⚠ 生の配列順で採ると「同じセットに複数の版を持つカード」でどの版を載せるかが
```
