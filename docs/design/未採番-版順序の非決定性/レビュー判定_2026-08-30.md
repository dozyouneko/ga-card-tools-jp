## 4. M5 静かな劣化の検査(破壊試験)

⚠️ **「動いたから合格」では、対策が効いているのか偶然そうなっているのか区別できない。**
そこで**わざと壊して検出できることを確認**した。

### 4-1. 比較器のキーが本当に効いているか(キー5の除去)

`sb-drop/` に**キー5(版slug)だけを `return 0` に潰した**変種を置き、
**正順入力と逆順入力で生成して比較**した:

```text
【破壊試験】キー5(版slug)を除去した比較器で 正順 vs 逆順 の出力差分: 7 ファイル
  cards: arisanna-astral-zenith / kongming-fel-eidolon / lorraine-spirit-ruler
         powercell / zander-blinding-steel
  sets : mrc / rdopd
```

⭐ **キー5は飾りではなく実際に7ファイルの決着を担っている**。
同時に、**V2 の置換テストが「旧コードほど派手でない劣化」も検出できる**ことが示された
(＝合格の根拠にした V2 の `0` は、単に鈍い検査が通っただけではない)。

### 4-2. キー2が黙って無効化されていないか

`setOrder()` は `SET_LABELS.has(prefix)` の**完全一致**で、外れると `9999` に倒れる。
⚠️ **もし prefix の表記が合っていなければ、キー2は例外も警告も出さずに全件 no-op になる**。

- 実測: スナップショット中の prefix は **63種**、`npm run validate` の
  `meta.sets covers all sets — 63件` と一致 ＝ **9999 に落ちる prefix は0**。キー2は全件で有効
- 実際に効いている証拠が `spurn-to-ash`(RDOEVP → RDOPD)として出力に現れている(§2)
- ⭐ **未登録セットが来ても壊れない**(fail-open): キー2が no-op になるだけで、
  キー3〜5が決着させるため**非決定には戻らない**。代表版の選び方が変わるだけ。
  しかも `validate` の `meta.sets covers all sets` が **exit 1 で人を止める**検出経路になっている

### 4-3. 検査の両辺が同源になっていないか

⚠️ CLAUDE.md の「検査の両辺が同源だと常に通る」に該当しないことを確認した。
V2 は **「同じ入力で2回回す」ではなく「入力の並び順を変えて出力を比べる」** 形であり、
V3(旧コードなら581ファイル動く)と 4-1(キー1つ抜けば7ファイル動く)の2つで**検出力を実証**している。

## 6. 推奨基準(S)— 合格を妨げないもの

- **S1(コード品質)**: `editionOrder()` は周囲の慣習(`day()` / `setOrder()` の再利用、
  コメント密度)に沿っており、設計書のコードブロックを逐語で採用している。指摘なし。
  `main()` のグルーピングで `newestFirst(card)` を呼ぶため**カードごとに版の整列が2回走る**が、
  総版数4,940・実測でビルド時間に体感差なし。**対応不要**と判断した
- **S3(fail-open)**: 未登録セット(9999)・`rarity: null`(99)・`collector_number` 空 のいずれでも
  比較は続行し、キー5で必ず決着する。実測で `rarity: null` 0件 / `collector_number` 空 0件だが、
  **来ても壊れない作りになっている**ことを確認した
- ⭐ **参考(合否に含めない・設計担当の判断を仰ぐもの)**: **決定性そのものを守る自動検査は無い。**
  将来この比較器が「整形目的で」簡略化されたとき、気づける経路は
  **cronがノイズコミットを作り始めること**だけで、⚠️ **それは今回の不具合が長く見過ごされたのと同じ経路**である
  (API由来のドリフトと区別が付かない)。`npm run validate` に
  「スナップショットの `editions` を置換しても代表版の選択が変わらない」検査を足せば構造で守れる。
  ⚠️ **レビュー担当は起票しない**ので、要否は設計担当の判断に委ねる
