⚠️ **これは「急がなくてよい」と矛盾しない。被害が増えないのは cron が止まっている間だけである。**

- 日次cronは **`cards` `sets` を `git add` する**（CLAUDE.md「cronがコミットする範囲」）。
  GitHub が復旧して cron が動き出すと、**旧コードの `build-card-pages.mjs` が
  `cards/**` `sets/**` を再生成して自動commit・pushする**
- そのとき本タスクの未pushコミット `81c4340e` は、**同じ76+8ファイルを別の内容で触っている**ため、
  `git pull --rebase origin main` が **76ファイル規模のコンフリクト**になる
- ⚠️ **コンフリクト解消は機械的にはできない**。どちらの側も「正しい生成物」に見えるうえ、
  cron 側の再生成には**その日のAPIドリフトが混ざっている**ため、手で選ぶ根拠が無い

⭐ **したがって順序は次のいずれかに限る**:

| # | 順序 | 可否 |
|---|---|:--:|
| A | **復旧前に経路②で公開しておく**（`CONFIRM=publish npm run deploy:prod`） | ⭕ ただし**gitとPagesが乖離する**ので、復旧後に**必ず push して追いつかせる**（CLAUDE.md「必ずHEADから作って乖離を生まない」） |
| B | **復旧直後・初回cronが走る前に push する**（`git pull --rebase` → `git push`） | ⭕ **最も安全**。⚠️ cronは **03:00 JST** なので、復旧に気づいた時点で**その日の03:00までに**出す |
| C | 初回cronを待ってから push | ❌ **やらない**（上記コンフリクト） |

## 7. ⭐ 今回の運用から得た知見（次に活かす）

| 知見 |
|---|
| ⭐ **「実装前のコード＋固定入力で親コミットとバイト一致するか」（V1）は、生成物タスクのドリフト検査の決定版である。** CLAUDE.md が警告する「内側に同居するドリフト」を、**ファイル名の集合ではなく全生成物の中身**で潰す。⚠️ 従来のひな形（対象ファイルからタスク由来の節を除去して比べる）は**タスクが変える節を書き下せる場合しか使えない**が、V1 は**変える節が何であっても効く**。⭐ **次の生成物タスクの設計書では V1 型を第1の検証項目にする** |
| ⭐ **「決定性」の検証は「同じ入力で2回」ではなく「入力の並び順を変えて1回ずつ」で書く。** 前者は**入力配列が同じなら同じ結果になるのは当然**で、検出力がゼロ。⭐ さらに**逆順は置換の1つに過ぎない**ので、**シャッフルを併用する**（今回は開発1種＋レビュー2種で計4種）。⚠️ **レビューが自前の置換スクリプトを書いた**のも正しい（開発担当の `tmp/dev/` を再利用すると両辺が同源になる） |
| ⭐ **設計時に「候補案を実測比較する」と、実装・レビューが同じ数字で会話できる。** 今回は素朴な「レアリティ優先」案が **og:image を209件**動かすと分かって却下し、採用案が **16件**に収まった。⚠️ **数字を出さずに案を選ぶと、影響の大小が実装後まで分からない** |
| ⚠️ **未pushの生成物コミットには「期限」がある。** cron が同じパスを再生成する以上、**cron が動き出す前に出す**必要がある。⭐ **`push待ち` に置いた時点で「いつまでに」を書く**——書かないと、`push待ち` は「いつでもよい」に読まれる |
| ⚠️ **「未調査」の派生は、起票する前に調査そのものを試みる。** 今回 §8-2 は grep 数回で**結果が空**と分かり、起票が不要になった。⭐ **着手できるだけの中身が無いissueを `着手可` で残すと、待ち行列の見通しが悪くなる** |
