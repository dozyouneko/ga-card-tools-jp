## 本文（案）

### 症状

**同じカードが、見る画面によって違うイラストで表示される。**

| 画面 | `break-apart` の代表画像 |
|---|---|
| トップの検索タイル / **カード詳細モーダル** / デッキ構築の検索結果 | **HVN #035**（`1nis8uaztx.jpg`） |
| **カード個別ページ** `/cards/break-apart/` | **RDOPD #048A**（`yd79dlDot4.jpg`） |

⭐ **レビュー担当が実駆動中に実物で観測した**（未採番・版順序の非決定性 レビュー判定 §7 参考2）。
詳細モーダルの版の並びは **HVN #035 / RDOPD #048B / #048A / #048C / P26 #014** で、
**個別ページの収録セット表（RDOPD #048A / #048B / #048C / HVN #035 / P26 #014）と順序が違う**。

- ⚠️ **食い違う枚数は 487枚**（2026-08-27 スナップショットでの実測）
- ⭐ **未採番「版順序の非決定性」が原因ではない**。**元から481枚食い違っており**、
  同タスクで**カードページ側だけが正しい順序を持った**結果 **+6枚**になった
- ⭐ **今後は「どちらが直っていないか」がはっきりした不具合になる**——
  カードページ側には `editionOrder()`（5段の全順序）があるが、**ブラウザ側は公式APIの配列順をそのまま使う**

### 原因（コードの所在）

`shared/js/card-i18n.js` の `firstEdition()` が **`editions[0]` をそのまま返す**。

```js
function firstEdition(card) {
  const eds = card.editions || card.result_editions || [];
  return eds[0] || null;        // ← 公式APIの配列順に完全依存
}
```

⚠️ **公式APIの `editions` 配列順は予告なく入れ替わる**（CLAUDE.md「`build:cards` — 手動実行すると、
タスクと無関係な差分が混ざり得る」／#71 実測）。⭐ **だからブラウザ側の代表画像は、
食い違うだけでなく「日によって変わる」**（生成物を持たないので差分としては見えない）。

### ⚠️ 影響を受ける箇所（**代表画像だけではない**・設計担当が2026-08-30に棚卸し）

| # | 箇所 | 使い方 | 配列順に依存するか |
|---|---|---|:--:|
| ① | `card-i18n.js` `firstEdition()` → `imageUrl()` | 代表画像 | ⚠️ **する**（本件の中心。トップのタイル・モーダル・デッキ構築が読む） |
| ② | `card-i18n.js` `cardImages()` | **イラスト切替の並び**（画像URLで重複排除しつつ順に積む） | ⚠️ **する**（並びが変わる。⭐ **重複排除が先頭優先なので、採用される版そのものも変わりうる**） |
| ③ | `card-detail.js` `renderEditions()` | 詳細モーダルの**収録一覧の行順** | ⚠️ **する**（個別ページの収録セット表と食い違う） |
| ④ | `card-i18n.js` `flipEdition()` | `configuration === "flip"` の**最初の**版を採る | ⚠️ **する可能性**（⭐ **flip版が複数あるカードで裏面画像が変わりうる。要実測**） |
| ⑤ | `card-search.js:670`（エキスパンション絞り込み） | `eds.some(...)` の集合判定 | ❌ **しない**（順序に意味なし） |

⭐ **①だけ直しても②③が残る**——「画面によって別の絵柄」は消えても「並びが違う」は残るため、
**4箇所をまとめて1つの順序に寄せるのが本筋**。

⚠️ **生成スクリプト側には残っていない**（設計担当が棚卸し済み・`承認_2026-08-30.md` §4-3）:
`gen-card-meta-index.mjs` は `sorted()` / `Math.min` で順序非依存、
`build-tournament-pages.mjs` は `editions` を1度も読まない。

### 方針の候補（⚠️ いずれも未検証・設計工程で決める）

1. ⭐ **`editionOrder()` 相当を `shared/js/card-i18n.js` へ移し、ビルド側と共用する**（本命）。
   ⭐ **`flavorOf()` と同じ「消費側を1関数に寄せる」形**で、前例がある
   （CLAUDE.md「新しい表示面を足すときは自前で `card.flavor` を読まず `flavorOf()` を呼ぶ」）
2. ブラウザ側は「決定的でありさえすればよい」として、**より単純な順序**（版slug昇順など）にする
   → ⚠️ **却下候補**。**カードページと食い違ったままになる**ので症状が消えない
3. 何もしない（仕様とする）→ ⚠️ **却下候補**。ユーザーに見える不整合が残る

#### ⚠️ 方針1で先に決めるべきこと

| # | 論点 | なぜ判断が要るか |
|---|---|---|
| **A** | **`meta.sets` の並び（キー2）をブラウザ側からどう参照するか** | ⚠️ `setOrder()` は **`scripts/build-card-pages.mjs` にしかない**。ブラウザ側は `data/translations.js` の `meta.sets` を持っているので**作れるはずだが、共用の形（`card-i18n.js` に置く／別モジュール）を決める必要がある** |
| **B** | ⚠️ **検索結果は `result_editions` を捨てている**（`card-search.js:726-729`・#44 の全件取得経路） | 順序付けに使うフィールド（`set.prefix` / `rarity` / `collector_number` / `slug`）が**その経路で残っているか**を実測する必要がある |
| **C** | **カードページ側の `editionOrder()` と一字一句同じにするか、共通ファイルに1本化するか** | ⚠️ **コピーすると必ず片方だけ直る日が来る**（本件がまさにそれ）。⭐ ただし `scripts/` は Node・`shared/js/` はブラウザで、**既存の共用実績は「移植して同一規則」というコメント運用**（`build-card-pages.mjs` の `matchedTerms()` 等）。1本化できるかは実測 |

### 規模（⚠️ `小タスク` を付けない理由）

- ⚠️ **`card-i18n.js` はブラウザ5面が共用する**（トップ・詳細モーダル・カードページのJS・
  デッキ構築のタイル・適合判定）。**触った瞬間に検証面が5つになる**
- ⚠️ **デッキ構築はDiscordログインが前提**でヘッドレスから素直に到達できない
  （CLAUDE.md の #51 の手順を使う。⭐ **デッキ内容に依存する表示は未検証として報告する**規約あり）
- ⭐ **本番配信物は `shared/js/card-i18n.js` 等のJSのみで、`cards/**` の再生成は不要**な見込み
  （⚠️ ただし方針1でビルド側も1本化するなら生成物が動く＝**設計時に確定させる**）
