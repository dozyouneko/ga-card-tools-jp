## タイトル（案）

```text
カードページの版の並び順が非決定的で、公式APIが editions を並べ替えるたびに og:image と収録セット表が変わる
```

## 本文（案）

### 症状

`scripts/build-card-pages.mjs:153` の `newestFirst()` が **`release_date` だけで比較しており、
同着時の第2ソートキーを持たない**。

```js
const eds = [...(card.editions || card.result_editions || [])].sort((a, b) =>
  day(b.set && b.set.release_date).localeCompare(day(a.set && a.set.release_date))
);
```

`Array.prototype.sort` は安定ソートなので、**同着の版は入力配列の順序をそのまま保つ**。
入力は公式APIの `editions` 配列で、⚠️ **この配列順は公式API側で入れ替わる**（CLAUDE.md・#71 実測）。

その結果、**中身が1文字も変わっていないカードで**次が変わる:

| 変わるもの | 影響 |
|---|---|
| ⚠️ **`og:image` / `twitter:image` / 本文の代表画像** | **SNSに貼ったときのカード絵柄が別の版に変わる** |
| 収録セット表の行順 | 表示上の並びが入れ替わる |

⚠️ **cronが毎日 `build:cards` を回して生成物をコミットする**ため、
**APIが並べ替えるたびにノイズコミットが発生する**（CLAUDE.md「出力は決定的でなければならない」に反する）。

**7件がこの原因**だった（レビュー担当・開発担当・設計担当が独立に確認）:

### ⚠️ これで全部は直らない（重要）

**同じ14ファイルのうち `prismspire-scepter` の1件は、この修正では消えない。**
収録セット表の **P25 #165 → #164** は**公式APIが `collector_number` を訂正した**もので、
⭐ **画像URLは同一・行順も不変**＝並び順に一切依存していない。
⚠️ **「これを直せばAPI由来の差分が全部無くなる」と書かないこと**（レビュー担当の明示的な申し送り）。

### 直し方の見当

`newestFirst()` に**第2キー**を足して同着を決着させる。既に**同型の問題を解いた先例**がある:
`shared/js/card-i18n.js` の `flavorOf()` は、**自前で昇順ソートし直し、同着を `edition.slug` の昇順で決着**させている
（未採番・フレーバー表示経路の §4-1）。

### ⚠️ 設計時に必ず実測すること（推測で進めない）

1. ⭐ **影響枚数を先に測る。** 第2キーを足すと、**同着の版を持つ全カードで代表画像・`og:image`・
   収録セット表の行順が現在の出力から変わりうる**。⚠️ **これは「14ファイル」では済まない可能性が高い**
   （`a7125896` に混ざった7件は、たまたまフレーバー修正と重なったページだけの数字）。
   **`build:cards` を新旧2通りで回して差分ファイル数と `og:image` の変化枚数を数えてから**、
   規模と push の扱いを決める
2. ⚠️ **どの版を先頭にするかは設計判断であって自明ではない。** `slug` 昇順だと `#048A` 系が先頭に来るが、
   「最新セットの**基本版**を代表にする」のが妥当かは**実物の絵柄を見て決める**
   （`newestFirst()` のコメントは「最古版だと旧セットの絵柄になる」という過去の指摘に基づく＝**代表画像の見た目が要件**）
3. ⭐ **決定性の検証は `flavorOf()` の V6 と同じ形にする**: `editions` を逆順にしたスナップショットで生成し、
   **出力がバイト一致すること**。⚠️ フレーバー側では `newestFirst()` のせいでこれが成立しなかったので、
   **本issueが直れば初めて「ページ全体のバイト一致」が期待値として成立する**
4. ⚠️ **`sets/**` にも同じ経路が効いていないかを確認する**（#71 ではセットページ6件にも差分が出ていた）
