# #52 カードスナップショットの鮮度チェック — 設計

## 改版履歴

| 版 | 日付 | 内容 | 状態 |
| --- | --- | --- | --- |
| 1.0 | 2026-08-08 | 初版。TTL方式を採用。実装指示・検証項目を確定 | 実装待ち |

## 1. 背景

`scripts/lib/cards-snapshot.mjs` の `loadCards()` は、スナップショットの**鮮度を一切見ない**。

```js
export async function loadCards(root, opts = {}) {
  const file = snapshotPath(root);
  if (opts.force || !existsSync(file)) return refresh(root);   // ← 存在するかどうかだけ
  const snap = JSON.parse(readFileSync(file, "utf8"));
  process.stderr.write(`スナップショット使用: ${snap.cards.length}枚 (取得: ${snap.fetched_at})\n`);
  return snap.cards;
}
```

#51 で実害が出た。7/27取得のキャッシュのまま `npm run build:cards` を回したところ、
**期待の33件を超える61件のカードページ＋無関係な8セットページ**に差分が出て、
`sets/prdevp/index.html` は**再生成すらされなかった**（stderr は `セット56ページ`／正しくは57）。
⚠️ **エラーは一切出ていない。** 差分は出るしログも正常に見えるため、
「cronの成果を古いデータで巻き戻すコミット」が普通に通ってしまう＝**静かな劣化**。

## 2. なぜ起きるのか（設計意図の取り違えではなく、環境差）

スナップショットは元々 **「1回のcron実行の中で3ステップがAPI取得を共有する」ための実行内キャッシュ**である。
ワークフローのコメントにも明記されている:

> 先行ステップが取得済みのスナップショット(tmp/)に相乗りするので追加は22リクエストのみ

| 環境 | `tmp/` | 実際の挙動 |
| --- | --- | --- |
| CI（cron） | 毎回空 | 1ステップ目が取得 → 2・3ステップ目が相乗り。**設計どおり** |
| ローカル | **日をまたいで残る** | ⚠️ 実行内キャッシュが**長期キャッシュに化ける**。TTLも警告も無い |

つまり不具合は「キャッシュを使うこと」ではなく、**ローカルでだけ寿命が無限になること**。

### 実測（2026-08-07 の cron・run 31208404147）

| ステップ | 所要 |
| --- | --- |
| 大会データをスキャンしてページ生成（ここでAPI取得） | 18:45:33 → 18:46:38（65秒） |
| カード・セットページと sitemap.xml を再生成（相乗り） | 18:46:38 → 18:46:40（2秒） |
| 日本語検索メタ索引を再生成（相乗り） | 18:46:40 → 18:46:48（8秒） |

⭐ **3ステップ全体で75秒**。この事実が採用案の根拠になる（§4）。

## 3. 影響範囲

`loadCards()` の利用側は4つ。⚠️ **`--refresh` で取り直せるのは `build-card-pages.mjs` だけ**：

| スクリプト | 呼び方 | 取り直す手段 | 古いと起きること |
| --- | --- | --- | --- |
| `build-card-pages.mjs` | `loadCards(ROOT, { force: REFRESH })` | ✅ `--refresh` | 新セット・新カードのページが作られない／既存ページが巻き戻る |
| `gen-card-meta-index.mjs` | `loadCards(ROOT)` | ❌ **無し** | ⚠️ **メタ索引が古くなる**。JPモードで候補から漏れる（取得後フィルタでは救えない） |
| `build-tournament-pages.mjs` | `loadCards(ROOT)` | ❌ **無し** | 大会ページのカード情報が古くなる |
| `gen-element-orbs.mjs` | `loadCards(ROOT)` | ❌ **無し** | 手動実行専用のため影響は小さい |

⚠️ **`build-tournament-pages.mjs --refresh` は別物**（収録済み**大会**の取り直し・79行目）。
同名フラグをスナップショット用に足すと**意味が衝突する**ので、フラグでの統一はしない（§4-2）。

## 4. 採用案 — TTL（有効期限）方式

`loadCards()` に**有効期限**を持たせ、期限切れなら自動で取り直す。

```text
取り直す条件 =  opts.force                      （既存。--refresh）
             || スナップショットが無い            （既存）
             || 経過時間 > 有効期限              （★今回追加）
```

### 4-1. なぜTTLか（他案を却下した理由）

| 案 | 却下/採用 | 理由 |
| --- | --- | --- |
| **A. TTL（採用）** | ⭐ 採用 | **人が何も覚えなくてよい**。CIは3ステップが75秒で終わるため60分TTLでも**相乗りが完全に維持され、ワークフローの変更が不要** |
| B. 警告を出すだけ | 却下 | **不具合の本質は「静かなこと」**。cronの長いログに1行足しても実質見えず、**悪いコミットを止められない**。#51 で気づけたのは設計書に期待ファイル数が書いてあったからで、警告のおかげではない |
| C. 既定を「常に取り直す」に反転 | 却下 | cronのカード取得が**75ページ×3回**になり、ワークフローに `--use-snapshot` を足す改修も要る。**実測で確認済みの相乗り設計を壊す** |

⭐ **判断の軸**: 元の failure mode は「**人が `--refresh` を思い出さないと壊れる**」こと。
B と C はその性質を残す（B は読む努力、C は設定を書く努力）。**A だけが人の記憶に依存しない。**

### 4-2. 取り直しの明示指定は環境変数で統一する

フラグは `build-tournament-pages.mjs` の `--refresh` と衝突するため使わない。
**環境変数 `GA_SNAPSHOT_MAX_AGE_MIN`** を新設し、4スクリプト共通で効かせる：

| 値 | 意味 |
| --- | --- |
| 未設定 | **60分**（既定） |
| `0` | **無期限**（＝常にキャッシュを使う）。⭐ **オフライン作業用の逃げ道** |
| 正の整数 | その分数 |

既存の `build-card-pages.mjs --refresh`（`opts.force`）は**互換のためそのまま残す**。

### 4-3. 有効期限を60分にする根拠

- CIの3ステップは**75秒**で完走（§2実測）→ 60分なら相乗りは確実に維持される（**48倍の余裕**）
- ローカルの反復作業（生成ロジックを直して回し直す等）は通常1時間以内に収まり、
  そのあいだ再取得は起きない → **開発体験を損なわない**
- 1日以上放置したキャッシュは確実に期限切れになる → **#51 の12日落ちは確実に防げる**

### 4-4. ⚠️ 残存リスク（設計として受け入れる）

**日次cron（03:00 JST）の直前に取ったスナップショットを、cron直後に使う**場合は
経過時間が60分未満のため取り直されない（例: 02:30取得 → 03:20使用）。
1日あたり最大1時間の窓で、しかも深夜帯に作業している場合に限る。

- ⭐ **cron時刻を定数として持ち込むことはしない。** ライブラリがワークフローの
  スケジュールに結合し、cron時刻を変えたときに**黙ってずれる**ほうが危険なため
- この窓に対する二重の防波堤は **「設計書に期待ファイル数を書く」**（#51 はこれで検出できた）。
  CLAUDE.md に記載済み

## 5. 変更内容

### 5-1. `scripts/lib/cards-snapshot.mjs`（主対象）

1. 有効期限の解決関数を追加（`GA_SNAPSHOT_MAX_AGE_MIN` を読む。既定60・`0`は無期限）
2. `loadCards()` に期限判定を追加
3. **相対年齢の表示**を追加（ISO文字列だけでは古さが読み取れない）

⚠️ **stderr の文言は検証項目で固定する。以下のとおり実装すること**（`{}` は埋め込み）：

| 場面 | 出力（1行） |
| --- | --- |
| 期限内で再利用 | `スナップショット使用: {N}枚 (取得: {ISO} / {相対})` |
| 期限切れで取り直す | `スナップショットが古いため取り直します ({相対} / 有効期限{M}分)` |
| 無期限指定で再利用 | `スナップショット使用: {N}枚 (取得: {ISO} / {相対} / 有効期限なし)` |

`{相対}` の形式: 60分未満は `{n}分前`、24時間未満は `{n}時間前`、それ以上は `{n}日前`（いずれも切り捨て）。

- ⚠️ **`fetched_at` が壊れている・欠けている場合は「期限切れ」とみなして取り直す**（fail-safe）。
  ここで例外を投げると4スクリプトすべてが止まる
- ⚠️ **取り直しに失敗したときに古いキャッシュへ黙って落ちないこと。** 現行どおり例外を投げる
  （黙って古いデータで生成するのが本issueの不具合そのもの）

### 5-2. `scripts/build-card-pages.mjs`（1行追加）

完走サマリに**どの時点のデータで生成したか**を出す。cronログにも手元にも痕跡が残る：

```text
生成完了: カード2240ページ(和訳あり…) / セット57ページ / … / sitemap.xml(2751URL)
データ取得時刻: {ISO}（{相対}）      ← 追加
```

### 5-3. やらないこと

- ワークフロー（`.github/workflows/build-tournaments.yml`）の変更 — **不要**（§4-1）
- `build-tournament-pages.mjs` への `--refresh` 追加 — **禁止**（既存フラグと衝突・§3）
- `CLAUDE.md` の更新 — **設計担当が行う**（`--refresh` 必須の記述を本修正後に見直す）
- 生成物（`cards/**` 等）の再生成 — **不要**。本修正で出力は1バイトも変わらない（V7で確認）

## 7. 検証項目

⚠️ **期待値は実際に出る文字列で書いてある。** 文言・相対表現まで一致させること。
⚠️ **スナップショットを直接書き換えて検証してよい**が、⚠️ **`tmp/` 配下の他セッションの作業物は消さないこと**。
検証前に現物を退避し、終わったら戻すこと。

| # | 手順 | 期待値（最終形） |
| --- | --- | --- |
| V1 | 取得直後（60分未満）のスナップショットで `node scripts/build-card-pages.mjs` | stderr に `スナップショット使用: 2240枚 (取得: … / {n}分前)`。⭐ **公式APIへのカード一覧リクエストが0件**（＝再取得していない） |
