## 2. ⭐ 実測: 公式APIはトークンの参照関係を**構造化して持っている**（2026-09-04 確認）

⚠️ **「APIがトークン情報をどう持っているか」は推測せず実測した。**
スナップショット（2026-08-31取得・2,495枚）と、公式APIへの直接アクセス（2026-09-04）の両方で確認した。

### 2-1. カードは `references` / `referenced_by` を持つ

```
GET https://api.gatcg.com/cards/aegis-of-dawn
  → references:    [{"kind":"SUMMON","name":"Automaton Drone","slug":"automaton-drone","direction":"TO"}]
     referenced_by: []

GET https://api.gatcg.com/cards/automaton-drone
  → types: ["TOKEN","ALLY"] / referenced_by 16件 / editions[0].image あり
```

⭐ **`/cards/:slug`（個別取得）の応答に含まれる**ことを実測済み。

### 2-2. `kind` は6種あり、⭐ **トークンを指すのは3種だけ**

スナップショット全体の集計（**参照 372件・参照を持つカード 257枚**）:

| `kind` | 件数 | 参照先が **TOKEN型** | 参照先が非TOKEN | 未収録 |
|---|---|---|---|---|
| `SUMMON` | 238 | ⭐ **238（100%）** | 0 | 0 |
| `MASTERY` | 76 | 0 | 71 | ⚠️ 5 |
| `GENERATE` | 18 | 0 | 18 | 0 |
| `REFERENCE` | 15 | **5** | 10 | 0 |
| `STATUS` | 13 | 0 | 13 | 0 |
| `BREW` | 12 | ⭐ **12（100%）** | 0 | 0 |

- ⭐ **TOKEN型を指す参照は `SUMMON` 238 ＋ `BREW` 12 ＋ `REFERENCE` 5 ＝ 255件**
- ⚠️ ⭐ **`kind` だけで判定してはいけない**。`REFERENCE` は TOKEN と非TOKEN が混ざる
  → **参照先カードの `types` に `TOKEN` が入っているか**で判定するのが確実
- ⚠️ **`direction` は全372件が `"TO"`**（`references` 側）。**方向で絞る意味は今のところ無い**

### 2-3. ⭐ TOKENカードは41枚あり、**和名も画像もそろっている**

| 項目 | 実測 |
|---|---|
| `types` に `TOKEN` を含むカード | **41枚** |
| うち `referenced_by` を持つ | **40枚**（⚠️ 残る1枚は `pantheon-barrier`） |
| ⭐ **和名（`data/tl-names.json`）がある** | ⭐ **41 / 41（全部）** |
| `editions` が空のもの | **0枚**（＝**全部に画像がある**） |
| カード個別ページ | ⭐ **生成済み**（`/cards/automaton-drone/` 等） |

### 2-4. ⭐ 追加のAPIリクエストは要らない見込み

デッキ構築ツールは既に **`GA_CARD_CACHE.getCard(slug)`（＝`/cards/:slug`）で
カードの完全な応答を取得している**（`tools/deck-builder/app.js` の `cardCache`）。
⭐ **`references` はその応答に含まれる**ので、**デッキ内のカードから参照を集めるだけなら
新たなAPIリクエストは発生しない見込み**。

⚠️ **ただしトークン自身の画像・和名を出すには、トークンのカード情報が要る。**
⭐ **スナップショット内では参照先255件すべてが収録済み**（未収録5件は `crystal-mastery`＝MASTERYでTOKENではない）
だったが、⚠️ **ブラウザは同じキャッシュを持たない**ので、
**トークン1枚につき `/cards/:slug` を1回叩く必要があるかどうかは設計工程で確かめる**
（⚠️ **公式APIは単発で約1.8秒。数が増えるなら並列度と進捗表示を考える**）。

## 3. ⭐ 既存の表示経路との関係（⚠️ **片方にしか無い**）

| 面 | トークン（＝関連カード）を表示するか |
|---|---|
| **静的カードページ**（`scripts/build-card-pages.mjs`） | ⭐ **する**。`references` と `referenced_by` を**混ぜて重複排除し**「関連カード」として**リンクのみ**列挙 |
| **カード詳細モーダル**（`shared/js/card-detail.js`） | ❌ **しない**（`references` を参照しているコードが無い） |
| **デッキ構築ツール** | ❌ **しない**（本件の要望） |

⚠️ ⭐ **これは `rule` フィールドで既に起きているのと同じ「表示経路が片方しかない」型**
（CLAUDE.md: 静的カードページは出すが**詳細モーダルは取得しているのに描画していない** → #74）。

- ⚠️ **静的カードページの「関連カード」は `kind` を区別せず、TOKEN以外も混ぜている**
  （マスタリー・ステータス等も同じ「関連カード」として並ぶ）
- ⭐ **本件で「トークンだけを取り出す規則」を作るなら、
  静的カードページ側と詳細モーダル側にも展開する価値がある**
  ——⚠️ **ただし要望はデッキ構築ツールに限定されているので、勝手に広げない**（→ §6 の確認事項2）

## 4. 設計工程で決めること

| # | 論点 | ⚠️ 注意 |
|---|---|---|
| **Q1** | ⭐ **どのゾーンを対象にするか** | ⚠️ **`maybe`（検討中）は常に判定対象外**という既存規約がある。⭐ **`material` / `main` / `side` / `pantheon` のどこまでを見るか**を決める |
| **Q2** | ⭐ **判定規則**（`kind` で見るか、参照先の `types` に `TOKEN` があるかで見るか） | ⭐ **§2-2 の実測から「参照先の `types`」を推す**が、⚠️ **`REFERENCE` の5件が「本当に用意すべきトークン」なのかは未確認** |
| **Q3** | 表示の置き場 | タブか、デッキ表示の下のブロックか、統計タブの中か。⚠️ **「検索結果のタブ化」が入るとタブ帯の空きが変わる** |
| **Q4** | ⭐ **どのカードが必要としているかを出すか** | 「オートマトン・ドローン ← 暁の盾 が生成」のように**出所を出す**と用意しやすい。⚠️ **1トークンを複数カードが参照する**（`automaton-drone` は `referenced_by` 16件）ので**行が伸びる** |
| **Q5** | 枚数の目安を出すか | ⚠️ ⭐ **公式APIは「何枚必要か」を持たない**（`references` は有無だけ）。⭐ **効果文から枚数を推定するのは裏が取れない**ので**やらない**ことを推奨する |
| **Q6** | トークンのカード情報の取得方法 | §2-4。⚠️ **追加リクエストが要るなら進捗表示の要否も決める** |
| **Q7** | 0件のときの見せ方 | ⚠️ **トークンを使わないデッキのほうが多い**（参照を持つカードは 2,495枚中 257枚）。⭐ **空の枠を常時出さない**ほうがよい |

## 7. 完了の目安（素案・⚠️ 正式な検証項目は設計書で起こす）

⚠️ **件数はスナップショット 2026-08-31 時点。設計書では実測し直して確定する。**

1. `aegis-of-dawn`（暁の盾）を入れたデッキで、**「オートマトン・ドローン」が和名と画像つきで出る**
2. トークンを1枚も使わないデッキでは **Q7 の決定どおり**（枠が出ない等）
3. 同じトークンを複数のカードが参照しても **重複して並ばない**
4. ⭐ **マスタリー・ステータスがトークンとして混ざらない**（`kind` が `MASTERY` / `STATUS` / `GENERATE` のもの）
5. **トークンが統計・フォーマット適合判定に影響しない**（R1）
6. `npm run validate` が exit 0
7. ⭐ **ユーザーがローカルサーバー（3000番）で実物を操作し、結論を出している**

⭐ **`小タスク` を付けてよいと考える。** データ源が既存の取得経路にあり（§2-4）、
判定規則も実測で確定していて、既存の判定・統計に触らないため。
⚠️ **ただし Q3（置き場）が「検索結果のタブ化」の結果に依存するので、そちらより後に着手するほうが手戻りが少ない。**
