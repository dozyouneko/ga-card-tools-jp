## 3. 事実確認（2026-08-13・設計担当が実測済み）

### 3-1. `_headers` は関与していない

```
git log --oneline --since=2026-07-25 -- _headers
b7b78c0d #56: 印刷ツールの _headers にも Web Analytics のCSP緩和を適用する
```

- 7/25 以降 `_headers` の変更は **#56 のCSP1件のみ**で、`Cache-Control` は触っていない
- ⭐ そもそも `_headers` に **ルート直下向けの `Cache-Control` 指定は存在しない**
  （`Cache-Control` を書いているのは `/shared/vendor/*` の1ブロックだけ）

→ **`s-maxage=604800` も `max-age=0, must-revalidate` も、どちらも Cloudflare Pages の既定。**
**自分たちの設定変更が原因ではないことが確定した**（issue本文の説明②「`_headers` のルールに当たるパスだった」は否定された）。

### 3-2. 本日の応答ヘッダ

| パス | HTTP | `cache-control` | `cf-cache-status` / `age` | `etag` |
|---|---|---|---|---|
| `/vercel.json` | **404** | `no-store` | 付かない | — |
| `/robots.txt` | 200 | `public, max-age=0, must-revalidate` | **付かない** | あり |
| `/sitemap.xml` | 200 | 同上 | **付かない** | あり |
| `/CLAUDE.md` | 200 | 同上 | **付かない** | あり |
| `/shared/css/element-orbs.css` | 200 | 同上 | **付かない** | あり |

- 8/12 の実測（6パス）と**同じ**。1日空けても再現する＝一過性の観測ミスではない
- ⚠️ **`/vercel.json` が404になっていること自体は、何の証拠にもならない。**
  #10 の削除は 8/4 で、記録上の残存目安は 8/11 頃。本日は 8/13 なので、
  **「7日待って消えた」でも「即座に消えていた」でも同じ404**になる

### 3-3. push を伴わない観測経路は無い

```
git log --diff-filter=D --since=2026-07-14 origin/main   → vercel.json の1件のみ
```

直近30日でリモートに入った削除は #10 の1件だけで、すでに7日を経過している。
→ **ダミーファイルによる実地観測以外に、削除挙動を確定させる手段は無い**（ユーザー承認済み・2026-08-13）。

## 4. 観測設計の要点

### 4-1. #10 と条件を揃える

比較のため、ダミーファイルは **#10 の `/vercel.json` と同じ条件**にする:

| 条件 | 揃える内容 |
|---|---|
| 置き場所 | **ルート直下**（サブディレクトリにしない） |
| 拡張子 | **`.json`**（Content-Type が変わると挙動が違いうる） |
| `_headers` のマッチ | `/*` のみに当たる（`Cache-Control` 指定なし＝Pages既定） |

⚠️ **`.html` にしない。** Pagesは `/foo.html` を `/foo` へ308でトリムするため、測定側が壊れる（CLAUDE.md 既知）。

### 4-2. ルート直下に置くことの影響

- ⚠️ ルート直下は**本番配信される**（#24 の対象）。観測中は検証用ファイル1つが公開される
- **中身は検証用の無害なテキストのみ**とし、秘匿情報・運用情報を一切書かない（§5-1）
- 検証終了後に削除する（削除そのものが観測の一部）

### 4-3. ⭐ 削除前に「キャッシュへ載せる」必要がある（issue本文に無い条件）

**#10 で残っていたのは、`age` が示すとおり削除前にキャッシュされたコピー**である。
`/vercel.json` は長期間存在していたファイルで、クローラや過去の検証でアクセスされていた。

→ ⚠️ **追加した直後に一度もアクセスせず削除すると、そもそもキャッシュに載っていないため404になって当然で、
#10 の再現にならない。** この状態で「404だった＝挙動が変わった」と結論すると**誤りになる**。

したがって手順に **「温め」フェーズ**（§5-3）を必ず挟む。
⚠️ 温めても `cf-cache-status` / `age` が付かない場合、**それ自体が観測結果**なので記録して先へ進む
（§6 の判定表がその場合も扱う）。

### 4-4. ⭐ 削除pushに「到達マーカー」を同梱する

削除後に素のURLが200を返したとき、原因は2つ考えられる:

1. **キャッシュが残っている**（本件で知りたいこと）
2. **デプロイがまだ届いていない**（単なる待ち時間不足）

これを区別できないと結論が出せない。
→ CLAUDE.md の既知（**新規追加ファイルはエッジに古いコピーが無いため 404→200 で到達を即確定できる**）を使い、
**削除pushと同じコミットに新規ファイルを1つ含める**。

- マーカーが 200 になった時点で「**デプロイは届いている**」が独立に確定する
- その時点でプローブが 200 なら、**キャッシュ残存が確定**する

⚠️ **マーカーはルート直下に置く**（ドットフォルダ配下は永久に404で到達判定にならない — CLAUDE.md 既知、#9 で5分空振りした実績あり）。

### 4-5. 日次cronと重ならない時刻に実施する

日次cron（03:00 JST）がpushすると**別のデプロイが挟まり**、観測中のデプロイとの切り分けが困難になる。
→ **測定中に 03:00 JST をまたがない時間帯**に実施する。

### 5-3. 反復測定の停止条件

⚠️ **7日間測り続けない。** 以下のいずれかで打ち切る:

| 停止条件 | 意味 |
|---|---|
| 素のURLが **404 を3回連続**（かつマーカーが200） | **即時消滅**が確定。終了 |
| **30分**（20秒×90回）経っても素のURLが200 | **残存する**が確定。終了し、**翌日1回・翌々日1回だけ追試**して残存時間の桁を記録 |
| マーカーが30分経っても404 | ⚠️ **デプロイが届いていない**＝測定不成立。中断してissueに報告する |

⭐ **30分に設定した理由**: #10 は8分（24回）で結論を出している。同じ条件で「8分では出なかった判定」を
取りこぼさないよう、余裕を持たせた。

## 6. 判定表（⭐ この4象限のどれに当たるかを報告する）

「温めでキャッシュに載ったか」×「削除後に残ったか」で結論と対処が変わる。**推測を混ぜず、観測どおりに分類する**:

| # | 温め（§5-2 手順4） | 削除後（同 手順7） | 結論 | CLAUDE.md の対処 |
|---|---|---|---|---|
| **A** | `cf-cache-status`/`age` が**付く** | **200が続く** | **#10 と同じ挙動が生きている** | 記録は正しい。**現行手順を維持**し、8/12・8/13 のヘッダ実測を「観測条件によっては出ない」と併記 |
| **B** | 付か**ない** | **すぐ404** | **挙動が変わった**（エッジキャッシュに載らなくなった） | ⭐ **記録を更新**。削除確認の手順を軽くできる（§7-B） |
| **C** | 付か**ない** | **200が続く** | ⭐ **最重要**: ヘッダに出ないだけでキャッシュは効いている | **記録は正しい**。加えて「**ヘッダでは判断できない**」を明記（§7-C） |
| **D** | **付く** | **すぐ404** | キャッシュはあるがデプロイで無効化される | **記録を更新**。「削除は即反映」＋「更新の伝播は別問題」 |

⚠️ **B と D は「記録を更新」だが、C は「記録を維持したうえで知見を足す」**。取り違えると手順が危険側に倒れる。

## 7. CLAUDE.md の更新方針（⚠️ 設計担当が行う）

対象は「git運用」節の **⚠️ ファイルを削除しても、素のURLは最大7日間200を返し続ける** 以下のブロック
（現在 #64 の注記が付いている箇所）。

- **A / C の場合** — 本文の手順は**変更しない**。`#64` の注記を「再検証の結果、記録は維持する」に書き換え、
  C なら **「ヘッダ（`cache-control` / `cf-cache-status`）では判断できない」**を追記する
  （⚠️ これは**新しい落とし穴**なので、注記ではなく本文に格上げする）
- **B / D の場合** — 本文を**実測に置き換える**。具体的には:
  - 「最大7日間200」→ 観測された実際の残存時間

  - ⚠️ **「更新の伝播はpush直後に新旧が入れ替わる」の記述は消さない。**
    これは #51・#52・#53/#54・#58/#59 で**4回別々に観測**されており、本件の削除挙動とは別事象

⚠️ **いずれの場合も、測定日（2026-08-13）と観測値を本文に残す。**
日付なしで書くと、次に食い違ったとき今回と同じ調査をやり直すことになる。

### 9-1. 測定コマンドの形（そのまま使ってよい）

```bash
URL=https://ga-card-tools-jp.pages.dev/cache-probe-20260813.json
for i in $(seq 1 90); do
  printf '%s #%02d ' "$(date -u +%H:%M:%S)" "$i"
  curl -sI "$URL" | grep -i -E '^HTTP|^cache-control|^cf-cache-status|^age:' | tr '\n' ' '
  echo
  sleep 20
done
```

⚠️ **`?cb=` 付きの測定では毎回値を変える**（`?cb=$(date +%s%N)`）。固定値だとそれ自体がキャッシュされる。

| 2 | 判定 A または C（残存する）だった場合の**正確な残存日数** | ⚠️ **確定させない**。追試は翌日・翌々日の2回のみで、**桁（時間単位か日単位か）が分かれば十分**。7日間の連続測定は費用対効果が合わない |
| 3 | カスタムドメイン移行後の挙動 | **#28 の範囲**。本件では扱わない |

## 12. ロールバック

- プローブ・マーカーとも**検証専用の無害なファイル**で、サイトの動作に一切関与しない
- 途中で中止する場合は、**マーカーとプローブを削除する1コミットをpush**すれば元の状態に戻る
- ⚠️ 中止した場合も、**どこまで観測したかを issue #64 にコメントで残す**（再開するのが同じセッションとは限らない）
