1. ⭕ **起票案の症状は実在する。実測で再現した**（§1）。`MULTI` に2つ目の版レベル項目を足すと、

## 1. ⚠️ 実測 — 起票案の主張の再現（2026-09-23・設計担当）

⭐ 起票案 §3 は自ら「**コード読解に基づく予測**であり、投函前に `MULTI` へダミーの版レベル項目を
1つ足して『選んでも1件も落ちない』ことを実測せよ」と指示している。
⚠️ **2026-09-21 の投函前コメントはコード読解の追認にとどまっており、この実測はまだ行われていなかった。**
本設計の冒頭で実施した。

### 1-1. 方法

⚠️ **作業ツリーは一切書き換えていない。** `shared/js/card-search.js` を**文字列として読み込み、
メモリ上で差し替えてから node の `vm` で実行**した（ハーネスはスクラッチパッドに置いた。リポジトリには残さない）。

- `window` / `GA_I18N` / `GA_CARD_I18N` を最小スタブで用意すると、**ブラウザ用の IIFE はそのまま node で動く**
  （⭐ この事実が §4 の検査の形を決めた）
- 差し替えは1箇所だけ: `MULTI` の末尾に **`["foil", "foil", null]`**（第3要素が `null` ＝版レベル）を追加
- フィクスチャ4枚 — `a`(rarity 3 / foil NONE) `b`(3 / COLD) `c`(8 / NONE) `d`(8 / COLD)。
  和名は `アルファ` `ブラボー` `チャーリー` `デルタ`
- 偽の公式APIは **`rarity` は解釈し、未知のパラメータ `foil` は無視する**（実際の api.gatcg.com と同じ振る舞い）

だが正常時も点くので「壊れている」の情報を一切持たない。** ⚠️ 起票案の

### 1-4. ⚠️ 起票案に無かった発見 — **「2つ目」でなくても壊れる**

⭐ `MULTI` の `rarity` を**別名に改名するだけ**（＝版レベル項目は1つのまま）でも同じ無言 fail-open になる。
第2段（`rarityMatchesIn()` / `matchesAndFilters()`）が **`vals("rarity")` / `els.rarity` / `isAnd("rarity")` と
キー名を名指し**しているためで、**個数ではなく「キー名が `rarity` であること」が条件**。

→ ⚠️ **検査の述語を「版レベル項目は1つまで」にしてはいけない。
「版レベル項目の集合が `{rarity}` と一致すること」で書く**（§4-2 でそうした）。

⚠️ **実測に使ったのはメモリ上の文字列差し替えのみ。** 測定後に `git status --short` が**空**であること、
`npm run validate` が **exit 0**（成功行17本）であることを確認済み。

## 2. 現状の構造（なぜ無言になるのか）

`shared/js/card-search.js` の `MULTI` は `[els のキー, APIのクエリ名, カードの配列プロパティ]` の表で、
**第3要素が `null` の項目＝版レベル**（`isIndexBlind()` の唯一の定義）。現在 `rarity` の1件だけ。

| 段 | 実装 | 版レベル項目への扱い |
|---|---|---|
| 一般ループ | `matchesActiveFilters()` / `matchesAndFilters()` / `metaMatches()` | `if (isIndexBlind(m)) continue;` で**読み飛ばす**（⭐ 正しく一般化されている） |
| 第2段 | `editionSetOf()` → `rarityMatchesIn()` | ⚠️ **`rarity` を名指し**。他のキーは**評価されない** |
| 保険 | `matchesMulti()` の `if (!field) return true;` | ⚠️ **fail-open で `true` に倒れる** ＝ **絞らない** |

⭐ **非対称はここ1箇所だけ**。`indexBlindActive()` と `metaMatches()` の読み飛ばしは
`isIndexBlind()` から導いており正しい。**手書きなのは第2段だけ**。

## 3. 案の比較と採否

### 3-1. A / B / C

| 案 | 内容 | 採否 |
|---|---|---|
| **A** | ⭐ **版レベル項目の集合が想定どおりかを検査し、ずれたら落とす** | ⭐ **採用** |
| B | 第2段を一般化し、版レベル項目ごとの判定関数を表に持たせる（`MULTI` の第4要素など） | ❌ **採らない**（下記） |
| C | 何もしない（コメントのみ＝現状） | ❌ **採らない**（§1-3 のとおり気づける経路が0本） |

⚠️ **案B を採らない理由**: 起票案が指摘するとおり **AND の意味が項目ごとに違う**。
レアリティの AND は「**版群の中で両方刷られている**」（同じ版では成立し得ない）のに対し、
たとえばフォイル種別の AND は同じ版で成立し得る。**契約が決まらないまま抽象化の器だけ作ると、
2つ目を足す人が器に嵌めて誤った判定を書く**——⚠️ **いまより静かに壊れる**。
⭐ **2つ目の版レベル項目を足す具体的な要件が現れた時点で、そのとき設計する**のが正しい順序。
**案A の検査は、そのとき必ず人を止める**ので、案B を先回りする必要が無い。

### 3-2. ⚠️ 「どこで落とすか」— **実測で決めた**

| 落とし方 | 実測・評価 | 採否 |
|---|---|---|
| **読み込み時に `throw`** | ⚠️ ⭐ **実測: IIFE が投げると `window.GA_CARD_SEARCH` が `undefined` になり、`app.js` 冒頭の `const { setPrefixes } = window.GA_CARD_SEARCH;` が `TypeError` で落ちる** → **トップもデッキ構築も丸ごと死ぬ** | ❌ **却下** |
| ブラウザで `console.error` | ⚠️ 人が開発者コンソールを見ないと気づかない。⭐ しかも `MULTI` を編集した人は**その場でレビューに出す**ので、`validate` のほうが確実に当たる。**同期先が1つ増える分だけ本件の病気が悪化する** | ❌ **置かない** |
| **`npm run validate` で exit 1** | ⭐ **人を止める**。レビューの必須基準 M3 が `validate` の exit 0 を要求するので、**工程を通る変更は必ず当たる** | ⭐ **採用（これ1本）** |

⚠️ ⭐ **fail-closed の線引き**: 「落とす」のは **`npm run validate` の中だけ**。
**ブラウザに配られるコードは、どんな状態でも例外を投げない**（`matchesMulti()` の
`if (!field) return true;` の fail-open は**そのまま残す**）。
⭐ 理由は上の実測 — `shared/js/card-search.js` は**トップとデッキ構築が共用する**ので、
ここで fail-closed にすると**症状が「絞り込みが効かない」から「サイトが開かない」に悪化する**。

⚠️ **cron は `validate` を実行しない**が、`MULTI` を編集するのは**常に人**なので検出経路として成立する
（#70 の `git add` 行の検査と同じ理屈）。

### 3-3. ⚠️ 字句検査にしない — **`vm` で本物を読む**

起票案 §5 は「`card-search.js` はブラウザ側なので `validate` からはそのまま読めない」として
**字句検査（正規表現で `MULTI` を読む）**を候補に挙げていた。
⭐ **§1-1 の実測でこの前提が偽だと分かった** — `window` / `GA_I18N` / `GA_CARD_I18N` の
最小スタブを置けば **node の `vm` でそのまま実行できる**。

⭐ したがって**字句検査は採らない**。起票案自身が警戒していた「**整形で壊れる**」（#70 の1行縛りの実績）を
そもそも背負わない。⭐ **#108（`editionOrder()` の全順序検査）が `scripts/lib/edition-order.mjs` を
import して比較器そのものを検査したのと同じ方針**——**実物を動かして測る**。

### 3-4. ⭐ 画面の挙動は変わらない

- **いま壊れている経路は無い**（版レベル項目は `rarity` の1件だけ）ので、**直す対象の症状が画面に出ていない**
- ブラウザ側の変更は **返却オブジェクトに `INDEX_BLIND_KEYS` を1つ足すだけ**（純増・既存の分岐に触れない）
- → ⚠️ **ユーザーの実物確認工程は挟まない**（進行役の申し送りどおり）。
  ⭐ **V3（§6）で「画面挙動が変わらないこと」を明示的に検証項目にしてある**

## 4. 変更内容

### 4-1. `shared/js/card-search.js` — 版レベル項目の一覧を**導出して**公開する

IIFE の返却オブジェクト（`SUBTYPE_TOP, ELEMENT_AND_MESSAGE,` の行）に**1行足す**:

```js
    // ⭐ 版レベル項目（isIndexBlind）の一覧。npm run validate が読んで、第2段
    //    （rarityMatchesIn）が名指ししているキーとずれていないかを検査する（#93）。
    // ⚠ ここに配列リテラルを書き写さないこと——MULTI から導くから検査が意味を持つ。
    INDEX_BLIND_KEYS: MULTI.filter(isIndexBlind).map(([k]) => k),
```

⚠️ ⭐ **必ず `MULTI` から導く**。手書きの配列にすると**二重定義**になり、
**片方だけ直したときに静かにずれる**——本件が塞ごうとしている型そのものになる。

⚠️ **既存の定数公開（`SUBTYPE_TOP` / `ELEMENT_AND_MESSAGE`）と同じ置き方にする**。
⚠️ **`matchesMulti()` の `if (!field) return true;` は触らない**（§3-2 の線引き）。

### 4-2. `scripts/validate.mjs` — 検査を1本足す

⭐ **置き場所**: UI規約の自動検査3本のブロックの**直後**、版の正規順序の検査（#108）の**直前**。
（成功行が `mobile band marker in sync` と `edition order is a total order` の間に出る）

⚠️ **トップレベル `await` を使う**（既存の #108 ブロックが `await import()` を使っているので前例あり）。

#### (a) モジュールの読み込み（`vm`）

```js
const sb = { console, setTimeout, clearTimeout, URLSearchParams, Promise, Set, Map };
sb.window = sb;
sb.GA_I18N = { meta: { sets: [] }, terms: {}, cards: /* フィクスチャの和名 */ };
sb.GA_CARD_I18N = {
  hasJapanese: (s) => /[ぁ-んァ-ヶ一-龠ー]/.test(String(s || "")),
  bannedFormats: () => [],
  loadEffects: () => Promise.resolve(),
};
sb.fetch = /* フィクスチャを返す偽API */;
vm.createContext(sb);
vm.runInContext(readFileSync(".../shared/js/card-search.js", "utf8"), sb, { filename: "card-search.js" });
```

⚠️ ⭐ **ネットワークは絶対に使わない**（`validate` はオフライン前提）。`fetch` は必ずスタブで塞ぐ。
⚠️ **読み込みに失敗したら `bad` に1行積んで exit 1**（素の例外でクラッシュさせない＝#108 と同じ作法）。

#### (b) 双方向の一致（許可リスト）

```js
// ⚠ 増やすときは第2段（rarityMatchesIn）の一般化とセット。表だけ増やすと無言で効かなくなる（#93）
const INDEX_BLIND_ALLOW = ["rarity"];
```

- `GA_CARD_SEARCH.INDEX_BLIND_KEYS` が**配列でない / 空**なら exit 1（**fail-closed**）
- 許可リストに**無いのに `MULTI` にある** → exit 1
- 許可リストに**あるのに `MULTI` に無い** → exit 1（⚠️ **片方向にしない**。§1-4 の改名も落とすため）

⭐ **両辺が別ファイル**（`shared/js/card-search.js` の実態 ↔ `scripts/validate.mjs` の許可リスト）＝
**人が2か所を意識して初めて通る**。`onRemoveOne` の配線検査と同じ作り。

#### (c) ⚠️ 空回り防止 — **行動フィクスチャ2組**

⚠️ **(b) だけでは穴が残る**（実測済み・§6 の V2-B2/B3）。
第2段の呼び出しを消しても `MULTI` は無傷なので **(b) は緑のまま**、絞り込みだけが無言で死ぬ。
⭐ そこで**許可リストの各キーについて「実際に絞れること」を本物の `create()` / `run()` で確かめる**。

`rarity` のフィクスチャ（**実測で期待値を確定済み**）— カード3枚
`a`(rarity 3) `b`(rarity 3) `c`(rarity 8)、和名 `アルファ` `ブラボー` `チャーリー`:

| 組 | 経路 | 条件 | 期待 |
|---|---|---|---|
| **F1** | `matchesActiveFilters()`（JPモード） | 名前「ー」+ `rarity=3`（OR）、`metaIndexUrl: null` | **`["b"]`**（候補は `b`,`c` の2枚。`c` が落ちる） |
| **F2** | `matchesAndFilters()`（ENモード AND） | `rarity=3,8`（AND）、偽APIは `rarity` を解釈 | **`[]`**（どのカードも両方は持たない） |

⚠️ ⭐ **許可リストにあるのにフィクスチャが無いキーは exit 1 にする**（fail-closed）。
⭐ こうしておくと、将来2つ目の版レベル項目を足した人は
**「検査がその項目の判定の仕方を知らない」と言われて必ず止まる**——本件の目的そのもの。

⚠️ `metaIndexUrl` は `null` にする（索引が無ければ候補は畳んだ全件＝fail-open で、**第2段だけを裸で測れる**）。

## 5. 成功時・失敗時に何が見えるか

### 5-1. 成功行（`npm run validate` に1行増える）

```text
index-blind filters in sync — 1項目（rarity）／行動フィクスチャ 2組
```

⭐ **数が出る**ので、赤くならない増減も目で追える（`card term highlights up to date` と同じ流儀）。

### 5-2. 失敗時（例）

```text
INDEX-BLIND FILTER WIRING (shared/js/card-search.js):
  - 許可リストに無い版レベル項目: foil — 第2段（rarityMatchesIn）は評価しないので無言で効かなくなります
  → 版レベル項目（MULTI の第3要素が null）を足すときは、第2段の判定も一般化してください。
    表だけ足すと「選んでも1件も落ちない」状態になり、警告も注記も出ません（#93）
```
