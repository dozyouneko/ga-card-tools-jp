## 1. 問題

トップページとデッキ構築ツールの並び替えで、**「レベル順」「パワー順」「ライフ順」を降順（▼）にすると、
その項目を持たないカードが先頭に大量に並び、目的のカードに到達できない。**

### 1.1 症状（本番APIで再実測・2026-08-02）

```
sort=level&order=DESC の先頭10件の level
  → —, —, —, —, —, —, —, —, —, —      ← すべて null
```

| 項目 | 値を持つ | **null** | 降順で先頭を埋める枚数 |
|---|---|---|---|
| `level` | 124枚（CHAMPION のみ） | 2,116枚 | **2,116** |
| `power` | 908枚 | 1,332枚 | **1,332** |
| `life` | 767枚 | 1,473枚 | **1,473** |
| `cost_memory` | 473枚 | （§3.5） | **1**（Xコストの `-1`） |

**「レベル順・降順」は 2,116枚を捲らないと1枚目のチャンピオンに届かない**＝事実上機能していない。

### 1.2 原因はAPI側の null 順序（サイトの実装ではない）

公式APIは **PostgreSQL 既定の null 順序**（`ASC` = NULLS LAST ／ `DESC` = NULLS FIRST）で返している。
サイトは `sort` / `order` をそのまま渡しているだけで、並べ替えの実装は持っていない。

## 2. ⚠️ 先に前提を1つ訂正する（#2 にも影響）

**#39・#2 のコメントとメモリに「`types` パラメータは無視される（全件が返る）」と記録していたのは誤り。**

サイトが実際に送っているのは **`type`（単数）** で（[`shared/js/card-search.js:274-279`](../../../shared/js/card-search.js#L274-L279) の `MULTI` 定義）、
**これは効く**。前回の実測は**レスポンス側のフィールド名 `types` をそのままクエリに使っていた**ため、
「無視される」という結論になっていた。

```
type=CHAMPION   → total_cards = 125    ✅ 効く
types=CHAMPION  → total_cards = 2240   ❌ 無視（＝存在しないパラメータ）
```

**数値項目が無視されるのは事実のまま**で、単数形でも複数形でも効かない:

| パラメータ | total_cards | 判定 |
|---|---|---|
| `type=CHAMPION` | **125** | ✅ **効く（訂正）** |
| `class=WARRIOR` | 299 | ✅ 効く |
| `level=4` / `levels=4` / `level=1-4` | 2240 | ❌ 無視 |
| `power=1-20` / `powers=1-20` | 2240 | ❌ 無視 |
| `life=1-30` / `lifes=1-30` | 2240 | ❌ 無視 |
| `cost_memory=2` / `cost_memories=2` | 2240 | ❌ 無視 |

⚠️ **判定に使う `page_size` は 2 以上にすること。** `page_size=1` のとき `total_cards` は
**常に 1 を返す**ため、「効いた」と誤判定する（§3.3）。

> **#2 への影響**: 「数値フィルタはサーバー側では実現できない」という結論は**変わらない**。
> ただし「タイプ絞り込みもクライアント側になる」という部分は**誤りだったので撤回**する。

## 3. 実測したAPIの挙動（すべて本番APIで裏取り済み・2026-08-02）

### 3.1 sort 別の挙動

| sort | total_cards | 昇順 | 降順 |
|---|---|---|---|
| `name` / `rarity` | 2,240 | ✅ 正常 | ✅ 正常 |
| `level` / `power` / `life` | 2,240 | **null が末尾** | ❌ **null が先頭** |
| `cost_memory` | ⚠️ **473** | `-1` が末尾 | ❌ `-1` が先頭 |

⚠️ **`sort=cost_memory` は方向によらず 473件しか返さない**（`level` 等は 2,240件返る）。
API側で null 行を落としているためで、**「コスト順」を選ぶと 1,767枚が黙って結果から消える**。
本設計のルール（§4.1）はこの挙動に合わせるので、**結果的にこの非一貫性も解消する**。

### 3.2 ⭐ 昇順では null が末尾にまとまる（本方式の土台）

`sort=level&order=ASC&page_size=50` の実測:

| ページ | 内容 |
|---|---|
| 1〜2 | すべて非null（level 0〜3） |
| **3** | **先頭24件が非null（… 3×22, 4×2）→ 25件目以降が null** |
| 4〜45 | すべて null |

→ **非nullは位置 0〜123 に連続し、124以降がすべて null。** 境界は1点だけ（ソートなので当然）。
非null件数 **N = 124** は、スナップショットの実測値（124枚）と一致する。

### 3.3 `page_size` の制約

| page_size | 返却件数 | total_cards | 位置指定 |
|---|---|---|---|
| **1** | 1 | ⚠️ **常に 1**（真の総数が取れない） | ✅ 正しい（`page=k` で k番目） |
| **2** | 2 | ✅ 2,240 | ✅ 正しい（`page=62` → 123,124番目） |
| 3〜50 | 指定どおり | ✅ 2,240 | ✅ 正しい |
| 100 / 200 / 500 / 1000 | **50** | 2,240 | — |

⭐ **`page_size` はサーバー側で 50 が上限**（超える指定は黙って 50 に丸められる）。
⭐ **`page_size=1` は位置指定には使えるが総数取得には使えない**（§4.2 でこの性質を使う）。

### 3.4 ⚠️⚠️ ソートは再現性はあるが、**同点行ではページ跨ぎで重複・欠落する**（第3版で訂正）

- ✅ **同一ページを2回取得すれば順序は完全一致**（再現性はある）
- ❌ **しかし異なるページを結合すると、同点行で重複と欠落が起きる**

```
sort=level&order=ASC の先頭124件
  page_size=50 … ユニーク120件（nameless-champion-tw/mr/rt/gm が2回ずつ）
  page_size=24 … ユニーク122件（nameless-champion-ar/mr が2回ずつ）
  ページ内の重複は0 ＝ 重複は必ずページ跨ぎで起きる
  page_size を変えると重複するカードも変わる
```

`Nameless Champion` は **`level=1` が15枚並ぶ同点行**で、そこが境界に当たると崩れる。
**APIのソートに同点時の第2ソートキーが無い**ためで、**サイト側では解決できない**
（`sort=power,name` のような複合指定は `collector_number` にフォールバックして無視される）。

> ⚠️ **第1版・第2版の「重複・欠落しない」は誤りだった。** 検証を **`level=3` の22枚並び（page 2+3）** で
> 行っており、**実際に崩れる `level=1` の15枚並びを踏んでいなかった**。
> ⭐ **教訓: 「同点で崩れないこと」を確かめるなら、最も長い同点行が境界に来る `page_size` で試す。**
> たまたま通った1ケースは反証になっていない。

### 3.4.1 本方式への影響 — **悪化はしないが、ズレが見えるようになる**

逆読みは**同じASCページの同じ位置を読む**ので、**降順の結果は昇順の完全な逆順**になる
（ASC全124件とDESC全124件で**集合・ユニーク数とも一致**することを設計・実装の双方が独立に実測）。
＝ **#39 の変更はこの問題を悪化させない。**

⚠️ ただし表示側は重複を弾く（トップは `shownSlugs`）ため、**「全 124 件」と出しながら 120 枚しか並ばない**
という形で**ズレが見えるようになる**（従来は総件数が 2,240 と出ていて誰も捲り切らなかったため隠れていた）。

→ **[#44](https://github.com/dozyouneko/ga-card-tools-jp/issues/44) として分離**。現時点の判断は**許容**
（124枚中4枚＝3%。根治にはAPI側の変更が要る）。

### 3.5 `cost_memory` の `-1`（Xコスト）は「null相当」

`-1` は**昇順では最終ページの末尾**（`… 9, 10, 12, -1`）、**降順では先頭**（`-1, 12, 10, 9 …`）。
数値として並んでいれば昇順の先頭に来るはずなので、**APIは `-1` を null と同じ扱いで並べている**。
該当は **1枚だけ**。→ §4.1 の `isNullish()` で `-1` を null と同一視すれば、他の3項目と同じ扱いで処理できる。

## 4. 採用する方式 — 降順は「昇順を逆から読む」

### 4.1 ルール（これ1つ）

> **数値項目（`level` / `power` / `life` / `cost_memory`）で並べ替えるときは、
> その項目を持たないカードを結果から除く。**
>
> - **N** = 現在の絞り込み下で、その項目が nullish でないカードの件数
> - **昇順**: APIの `ASC` をそのまま使い、**N件で打ち切る**
> - **降順**: APIには **`ASC` を送り**、位置 `N-1 → 0` を**逆順に読む**
> - 総件数の表示は **N**（2,240 ではない）

```js
const NUMERIC_SORTS = ["level", "power", "life", "cost_memory"];

// -1 は Xコストの表現で、APIはこれを null と同じ位置に並べる（§3.5）
function isNullish(field, card) {
  const v = card[field];
  return v == null || (field === "cost_memory" && v === -1);
}
```

⭐ **「レベル順なのにレベルを持たないカードが混ざる」ほうが不自然**なので、これは機能の削除ではなく
**意味を正す変更**。しかも **API自身が `cost_memory` で既にこの挙動をしている**（§3.1）ため、
サイト全体で挙動が揃う。

⚠️ **昇順も同じルールにする。** 降順だけ 124件・昇順は 2,240件、という非対称は説明できない。

### 4.2 N の求め方（reset ごとに1回）

**位置 k のカードが nullish かどうか**を `page_size=1` で1枚だけ引いて判定し、二分探索する。

```
手順:
 1. 総数 T を得る
      GET /cards/search?<絞り込み>&sort=<f>&order=ASC&page_size=2&page=1
      → T = total_cards
      ⚠️ page_size=1 は total_cards が常に 1 になるので使えない（§3.3）
      T === 0 なら N = 0 で終了

 2. probe(k): 位置 k（1始まり）のカードが nullish か
      GET /cards/search?<絞り込み>&sort=<f>&order=ASC&page_size=1&page=k
      → isNullish(f, data[0])

 3. 端を先に見る
      probe(T) が非nullish → N = T（null なし）で終了
      probe(1) が nullish  → N = 0（該当0件）で終了

 4. 二分探索で「非nullish である最大の k」を求める → N = k
      lo = 1, hi = T
      while (hi - lo > 1) { mid = (lo+hi)>>1; probe(mid) ? hi = mid : lo = mid; }
      N = lo
```

**リクエスト数（本番APIで実測・2026-08-02）**:

| sort | T（総数） | **N（非null）** | probe回数 |
|---|---|---|---|
| `level` | 2,240 | **124** | 14 |
| `power` | 2,240 | **908** | **15**（最大） |
| `life` | 2,240 | **767** | 14 |
| `cost_memory` | 473 | **472** | 12 |

→ **最大 15 リクエスト**（`ceil(log2(T)) + 3` が上限）。

⚠️ **`page_size=1` の応答は 1枚でも約 8 KB**（`effect_html`・`editions`・`references` を含むため）。
手順1の `page_size=2` が約 16 KB、以降が 8 KB ×最大14 で **合計約 130 KB**。
ページ本体の取得（`page_size=50` で約 442 KB／ページ）に比べれば軽いが、
**無視できる量ではない**ので §4.4 のキャッシュを必ず入れること。

✅ **この手順そのものを本番APIで実行し、4項目とも上表の N が得られることを確認済み**
（§8 の V2・V5・V6・V7 の期待値はこの実測値）。

### 4.3 降順ページの位置計算

`P` = `PAGE_SIZE`（⚠️ **トップは 50・デッキ構築は 24** と異なる。定数を直接使うこと）。

```
降順ページ k（1始まり）が表示すべき ASC 位置（0始まり）:
    from = N - 1 - (k-1)*P        // 降順の先頭（大きい位置）
    to   = max(N - k*P, 0)        // 排他的な下限
    必要な位置 = from, from-1, …, to

ASCページ番号 = floor(pos / P) + 1   → 高々 2ページ

取得した2ページを結合し、必要な位置を切り出して逆順に並べる。
    total   = N
    hasMore = to > 0
```

**検算（level・N=124・P=50）**: 降順1ページ目は `from=123, to=74` → ASC page 2・3 を取得。
実測で **`4,4,3,3,3,3,3,3,3,3,3,3 …`（null混入なし）** になることを確認済み（§8 V3）。

### 4.4 リクエストとバイト数（見積り）

| 場面 | 現状 | 本方式 | 増分 |
|---|---|---|---|
| 数値ソートで検索（reset）・1ページ目 | 1 req / 442 KB | 最大 15 + 2 req / 約 1,014 KB | **+16 req / +572 KB** |
| 2ページ目以降（loadMore） | 1 req / 442 KB | 2 req / 884 KB | **+1 req / +442 KB** |
| `name` / `rarity` ソート | 変更なし | 変更なし | — |

⚠️ **N は「絞り込みの組み合わせ」ごとに変わる**（`element=FIRE` を足せば N も減る）。
→ **`sort` × `order` を除いたクエリ文字列をキーにして、セッション中はメモリにキャッシュする**
（`card-cache.js` の `mem` と同じ方式）。同じ絞り込みのまま昇順⇄降順を切り替えても再探索しない。

⭐ **任意の最適化（実装判断でよい）**: 直前の N を種にした galloping search にすると、
絞り込みを少しずつ変える操作では反復が 11 → 4〜5 に減る。**まず素直な二分探索で作り、
遅ければ検討する**（早すぎる最適化を避ける）。

## 5. 既存機能との相互作用

### 5.1 AND 絞り込み（`anyAnd()`）

AND指定はAPIが上位集合しか返せないため、**取得したページ内でクライアントが間引いている**
（[`card-search.js:556-558`](../../../shared/js/card-search.js#L556-L558)）。
逆読みでも**位置の計算はAPIの並びに対して行う**ので、間引きは表示段階に効くだけで破綻しない。

⚠️ ただし **N は「AND を適用する前の件数」**になる。現状すでに AND 時は `approxTotal` で
総件数を出さない扱いなので、**数値ソート × AND のときも `approxTotal` を立てる**こと。

### 5.2 ⚠️ JPモードは本issueの対象外（別の問題が隠れている）

日本語テキスト検索（`isJpTextMode()`）では、`localJpSlugs()` が **slug の昇順**で候補を作り
（[`card-search.js:466`](../../../shared/js/card-search.js#L466) の `out.sort()`）、
その順に個別取得している。**`sort` / `order` の選択はJPモードでは一切効いていない。**

これは #39 の症状（該当しないカードが先頭に来る）とは別の欠陥なので、**本設計では触らない**。

## 6. 却下した案

| 案 | 内容 | 却下の理由 |
|---|---|---|
| **A** | `sort=level` のとき `type=CHAMPION` を足す | **level しか直らない**。level は `type=CHAMPION` で 125件中124件が有効（ノイズ1枚=`Lu Bu, Indomitable Titan`）と優秀だが、**power は全カバーに11タイプ必要で和集合 2,188枚**＝ほぼ絞れない。life も ALLY+CHAMPION で実測 787件中20件が null（Fatestone 群が混入） |
| **C** | 数値項目の降順を選べなくする | 「レベルの高いチャンピオンを見たい」という**本来の用途が昇順では満たせない**。症状は消えるがやりたいことはできないまま |
| **D** | メタ索引に数値を持たせてクライアント側ソート | 索引の拡張（#2 相当）が要り、**英語テキスト検索と併用できない**（索引は名前・効果の英語検索を再現できない）。さらに JPモードと同じ**1ページあたり24〜40回の個別取得**になり重い |

⚠️ **案Aのノイズが小さいのは level だけ**。`type=CHAMPION` が非CHAMPIONの `Lu Bu, Indomitable Titan`
（`types: ["UNIQUE","ALLY"]`）を返すことからも分かるとおり、**APIの `type` 絞り込みは
フリップ面・関連カードを拾って過剰一致する**。タイプ集合で「その項目を持つ」を表現するのは筋が悪い。

### 7.1 ✅ 修正済み（`f60986ef`）— N の二分探索が「探索中のUI変更」で汚染される

`probeNonNullCount()` の各 probe は `apiSearch()` → `buildQuery()` → **`filterParams()` / `sortField()` を
毎回その場で読み直す**（`card-search.js:565,570`）。二分探索は**最大15回の逐次リクエスト（数秒）**かかるため、
その間にユーザーが絞り込みや並び替えを変えると:

1. **探索の途中から別の条件で問い合わせる**ことになり、**N が誤った値になる**
2. その誤った N が、**呼び出し時点（＝変更前）の条件で作ったキー**で `nCache` に焼き付く
   （`countNonNull()` はキーを最初に1回だけ作る・`card-search.js:550`）
3. ⚠️ **並び替え項目を変えた場合はさらに悪い**: `isNullish(field, …)` は**呼び出し時に捕まえた `field`** を見るのに、
   `apiSearch` が送る `sort` は**現在値**なので、「power で並んだ列を level で null 判定する」状態になる

`mySeq` ガードは `await countNonNull()` の**後**にしか無いため、この汚染は防げない。
**症状は「後でその絞り込みに戻したときだけ件数がおかしい」**で、エラーも出ず気づけない。

**修正方針（どちらでもよい）**:

```js
// 案1: 探索開始時にクエリ文字列を固定し、probe はそれを使う（最小の変更）
async function probeNonNullCount(field) {
  const base = filterParams().toString();          // ← 1回だけ確定させる
  const url = (page, ps) => `${API}/cards/search?${base}&sort=${field}&order=ASC&page=${page}&page_size=${ps}`;
  …
}

// 案2: probe ごとに mySeq を渡して照合し、変わっていたら中断する
```

⭐ **案1を推奨**（キャッシュキーと探索条件が同じ文字列から作られるので、ズレが構造的に起きなくなる）。

### 7.2 ✅ 対応済み（`f60986ef`）— `numericSortNote` の呼び出しを防御的にする

`app.js` / `tools/deck-builder/app.js` は `GA_CARD_SEARCH.numericSortNote(...)` を**無条件で呼ぶ**。
Cloudflare Pages は**push直後に複数ファイルの伝播ラグがある**（#42・#37 で実測済み）ため、
**新しい `app.js` と古い `card-search.js` が組み合わさる数十秒の窓**で `TypeError` になる。

影響は限定的（`appendGrid()` は先に走るので**カードは出る**。ステータス行が「検索中…」のまま止まり、
「もっと見る」が無効のままになる）が、**`?.` を1つ足すだけで消える**:

```js
suffix += GA_CARD_SEARCH.numericSortNote?.(info.numericSort) || "";
```

### 8.1 ⚠️ V17 は「修正前でもPASSする」— 検証項目の当たり所に注意

**絞り込みを「広い→狭い」向きに変えると、fail-close が偶然この欠陥を打ち消す。**
`FIRE` を足すと対象が 2,240 → 297件に減るため、探索中の `probe(2240)` が**範囲外になって `data` が空**
→ §9-4 の fail-close で例外 → `countNonNull()` の `catch` が**キャッシュを削除**する。**自己修復してしまう。**

→ ⭐ **汚染を残すには「狭い→広い」向きが要る**（V17b は `FIRE` を**外す**）。
**この欠陥の検証は、探索対象が途中で「増える」向きで行うこと。**

⭐ **再現にはタイミングの固定が要る**（素直に操作すると `nCache` のヒットや probe の速さで割り込みの窓に入らない）。
実装検証では Playwright の `page.route` で **probe（`page_size=1|2`）の応答だけ 300ms 遅らせ**、
**APIリクエストが3件流れた時点で割り込む**方法を採った（**製品コードは無変更**）。同じ検証をするときはこの手を使う。

⚠️ **V5・V6 の期待値（908 / 767）は 2026-07-27 のスナップショット基準**。新セット追加後は増えるので、
**実行時に `sort=<f>&order=ASC` の境界を数え直して照合する**こと（数値の暗記に頼らない）。
