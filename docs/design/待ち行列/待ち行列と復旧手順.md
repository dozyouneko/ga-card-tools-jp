## 0. ⚠️ 最優先 — GitHub復旧後、**初回cron（03:00 JST）より前に push する**

⭐ **復旧してまず打つのはこれ。issueの起票より先。**

**なぜ**: cronは `origin/main`（GitHubが最後に受け取った位置）に対して走る。
未pushのまま初回cronが先に走ると、**停止期間中の修正（フレーバー・辞書・版順序・用語ハイライトほか）が
どれも入っていない旧コードで `cards/**` が再生成され、cronがそれをコミットする。**

⚠️ ⭐ **そうなると手で解消する根拠が無くなる。** 理由は2つ:

1. **どちらも「正しい生成物」に見える。** cronが作るページも、ローカルの未pushコミットが作ったページも、
   それぞれの時点のコードとしては正しい出力なので、**差分を見ても「どちらが正か」が判別できない**
2. ⚠️ **cron側に当日のAPIドリフトが混ざる。** cronは実行時点の公式API応答で再生成するため、
   タスク由来の差分と無関係なドリフトが**同じファイルの中に同居する**
   （CLAUDE.md「ドリフトの検査は変更ファイル数では不十分」＝内側に入るケース）

→ **復旧した日のうちに push の可否をユーザーに判断してもらう。**

### 手順

```bash
git status --short                                                   # 空であること
git diff --stat origin/main..HEAD -- . ':(exclude)docs/*' | tail -1  # 本番配信物の量を把握
git pull --rebase origin main                                        # ⚠️ 先に取り込む
npm run validate                                                     # rebase後に exit 0
git push origin main
```

### ⚠️ push前にユーザーへ伝えること — ⭐ **数字はその場で測る**（ここに書き写さない）

| 伝えること | 測り方 |
|---|---|
| ⭐ **本番の見た目が変わるか** | §3 ① で本番の位置 `P` を測り、`git diff --stat $P..HEAD -- . ':(exclude)docs/*'` を見る。⭐ **空なら「pushしても本番の見た目は変わらない」**（経路②で公開済みの内容が経路①で再デプロイされるだけ）。空でなければ、その差分が**pushで初めて公開される** |
| origin に載る本番配信物の量 | `git diff --stat origin/main..HEAD -- . ':(exclude)docs/*' \| tail -1` |
| ⚠️ **`CLAUDE.md` / `TRANSLATION.md` もルート直下＝配信物** | `docs/` だけを送る例外は使えない |
| ⭐ **pushすると #73 が自動クローズされる** | `git log --format='%h %s' --grep='closes #73' origin/main..HEAD`（`9b472a88` が出る） |

- ✅ **2026-09-03〜09-04 の公開保留（4タスクが揃うまで公開しない）は解けている。** 経緯は改版履歴の第6〜13版と git 履歴にある
- ⚠️ **「公開の可否は常にユーザーが判断する」は変わらない**——経路①（push）・経路②（`deploy:prod`）とも勝手に実行しない

## 4. ⭐ 「起票案が腐る」「索引が古くなる」ことへの対策

⚠️ **一覧を手で作るだけでは同じことが起きる**（一覧のほうが古くなる）。⭐ **2026-09-11（第24版）から、状態は1か所・一覧は生成・

### 4-1. 状態は**各起票案の1行目だけ**に書く（索引は生成する）

すべての `起票案*.md` / `派生起票案*.md` は、**1行目**を次の形にする:

```text
**状態: 生きている**（最終確認 2026-09-11）— 呼び名「検索結果のタブ化」。<ここから先は自由記述>
```

| 状態 | 意味 | 変える人・タイミング |
|---|---|---|
| `生きている` | 未着手（設計書なし）。GitHubなら `着手可` / `検討中` | 起票したとき |
| `設計中` | 設計担当が設計書・モックを作っている、またはユーザー判断待ち | 設計担当が着手したとき |
| `実装中` | 設計完了から承認まで（`実装待ち` / `レビュー待ち` / `設計確認待ち` を含む） | ⭐ **設計担当が `設計完了_` を書くコミットで** |
| `完了` | 承認済み（⚠️ **公開済みかどうかは状態に含めない**＝§3 で測る） | ⭐ **設計担当が `（→ 完了）` の記録を書くコミットで** |
| `取り下げ` | 前提が成立しなかった | 設計担当が `取り下げ_` を書くコミットで |

- ⭐ **呼び名がタスクの識別子**（→ §4-4）。**一意であること**を `validate` が確かめる
- ⭐ **`最終確認` は「その状態がまだ正しいと人が確かめた日」**。状態を変えなくても、確かめたら更新する
- ⚠️ ⭐ **手番（実装待ち／レビュー待ち／設計確認待ち）は状態語にしない**——往復のたびに書き換える値は必ず古くなる。
  書くなら1行目の自由記述に書く（**写しは作らない**）
- ⚠️ **状態を変えたら `node scripts/gen-queue-index.mjs` を打ち、同じコミットに入れる**

⭐ **起票案は「確定した事実」ではなく「投函前の下書き」である。**

  ⭐ **腐りを止めたのは索引でも検査でもなく「投函前に測り直したこと」**
- ⚠️ **`最終確認` が古い起票案ほど危ない。** 索引に日付を出しているのは、この判断を一目で

### 4-4. ⚠️ ⭐ タスクの呼び名 — **記号で呼ばない**（2026-09-04 ユーザー決定）

⚠️ ⭐ **英字・番号でタスクを呼ぶのをやめた。タスクは「名前」で呼ぶ。**
⚠️ **次のセッションが良かれと思って英字を振り直さないこと**——理由を以下に残す。

#### 何が起きたか — **記号の系列が3つ同時に走り、衝突していた**

ユーザーからの指摘は「**タスクの呼び名がごちゃごちゃで全貌が分からない**」。実際、次の3系列が並行していた:

| # | 系列 | 中身 | 衝突 |
|---|---|---|---|
| 1 | **§5 の英字 C〜J** | C・D・F・G・H・I は完了／生きているのは **E（大会データの週1更新）** と **J（腐った行番号参照）** | — |
| 2 | **§1 の新規5件に付けた英字 A〜E**（2026-09-04・設計担当） | 左ペイン化・タブ化・サイドボードプランメモ・フォーマット検索・トークン表示 | ⚠️ **C・D・E が系列1と衝突**。とくに ⭐ **E は両方とも「生きている」**（週1更新 vs トークン表示）で、**「Eをやって」が一意に通じない状態だった** |
| 3 | 進行役が説明のために付けた群番号 | — | ⭐ **破棄済み**（記録に残さない） |

#### ⭐ 決めたこと（案1）

- ⭐ **タスクは名前で呼ぶ。** §1・§5 の各表の**先頭列が「呼び名」**で、これが正
- ⚠️ ⭐ **`T-01` のような新しい通し番号は作らない。**
  **GitHub復旧後に `#n`（GitHubの採番）が付いたときに二重管理になる**ため。
  ⭐ **旧独自番号 `#11〜#17` で一度踏んだ型を繰り返さない**（CLAUDE.md「タスク管理」の「旧独自番号は別系列」）
- ⭐ **従来の英字は各表に「（旧 §5-F）」「（旧 新A）」の形で併記して残す。**
  ⚠️ **既存の設計書・承認記録・実装報告が英字で書かれている**ため、
  **対応が切れるとそれらが読めなくなる**（例: 承認記録が「タスクG」と書いている）

#### ⚠️ 紛らわしいので明記しておく

- **§2-②-A / §2-④ の ①〜⑪ は「その表の行番号」であって、タスクの識別子ではない。**
  ⭐ **2つの表で同じ番号が同じタスクを指す**ようにしてあるが、**表の外へ持ち出さない**
- ⚠️ **英字での呼び方を新しく作らない。** どうしても短く指したいときは**呼び名を短縮する**
  （例:「トークン表示」）。**新しい記号を発明しない**
