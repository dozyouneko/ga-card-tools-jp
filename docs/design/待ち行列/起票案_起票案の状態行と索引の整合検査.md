## 1. 症状（何が起きるか）

`docs/design/**` には**起票待ちのissue下書き（起票案）が11件**あり、状態は
**各ファイルの1行目**（`**状態: …**（最終確認 YYYY-MM-DD）…`）が正、
**索引** `docs/design/待ち行列/待ち行列と復旧手順.md` §1 がそれを一覧している。

⚠️ **この2つは人が手で書き写しており、ずれても何も起きない。**

| ずれ方 | 起きること |
|---|---|
| 起票案を新規に足して索引に載せ忘れる | **復旧後の起票で丸ごと漏れる**（issueが1件作られないまま消える） |
| 状態を片方だけ直す | **完了済み／取り下げ済みの案が「生きている」に見えて再起票される** |
| フォルダをリネームして索引のパスを直し忘れる | 索引のリンクが**全部404**（⚠️ 復旧後の §2 ③ で**必ず起きる**操作） |
| 見出しの「（**N件**）」を数え直さずに増減させる | 件数が**実態と合わない**まま一覧が読まれる |

⭐ **実害はすでに1回出ている。** 索引の前身（`73-PRD新カード和訳/issue反映待ち_2026-08-19.md`）は
**2日で実態と乖離**し、2026-08-30 に完了した2タスクが載らないまま残った。
その結果、状態を知るのに**10ファイルを開いて突き合わせる**必要が生じた。

⚠️ ⭐ **これはこのリポジトリが3回学んだ型そのもの**（#40 `meta.sets` / #43 索引の内部整合 / #70 cron列挙）:
**人が2箇所に書き写す運用は必ずドリフトし、しかも fail-open で緑のまま通る。**

## 2. やること（`scripts/validate.mjs` に検査を1つ足す）

⭐ **既存の #70（cron列挙のドリフト防止）と同じ形**。`scripts/validate.mjs` の末尾近く、
用語ハイライト検査の**前**に同期処理として足す（非同期にする必要はない）。

### 2-1. 集める

```js
// 対象: docs/design 配下の「起票案」ファイル（派生起票案 も含む）
//   glob 相当: docs/design/**/*起票案*.md
// ⚠ 索引ファイル自身（待ち行列と復旧手順.md）は対象外（名前に「起票案」を含まない）
```

各ファイルの**1行目**を次の正規表現で解釈する:

```js
const STATUS_RE = /^\*\*状態: (生きている|完了|取り下げ)\*\*（最終確認 (\d{4}-\d{2}-\d{2})）/;
```

- ⚠️ **1行目が一致しなければ exit 1**（メッセージ: `起票案の1行目に状態行がありません: <パス>`）。
  ⭐ **新しい起票案を状態行なしで作れなくする**のが、この検査のいちばんの効き目
- ⚠️ **日付の妥当性までは見ない**（`2026-13-45` を弾かない）。⭐ **正規表現で形だけ縛る**——
  値の正しさを機械が判定できない以上、厳しくしても嘘の安心が増えるだけ

### 2-2. 索引と突き合わせる（**2点だけ**）

正は `docs/design/待ち行列/待ち行列と復旧手順.md`。

| # | 検査 | 落とし方 |
|---|---|---|
| **A** | **収録漏れ**: 収集した各起票案のパスが、索引の本文に**Markdownリンクとして1回以上現れる**こと（`](…/<ファイル名>)` の部分一致でよい） | 現れないファイルがあれば **exit 1**。`索引に載っていない起票案: <パス>` |
| **B** | **件数の一致**: 索引の見出し `### 🟢 生きている（**N件**）` / `### ✅ 完了済み（**N件**）` / `### 🚫 取り下げ（**N件**）` と、`## 1. …（**全N件**）` の4つの数が、状態行から数えた実数と一致すること | 食い違えば **exit 1**。`索引の件数が実数と一致しません: 生きている 索引7 / 実数8` |

- ⭐ **AとBの組み合わせで、追加・削除・リネーム・状態変更のすべてが捕まる**
  （追加すればAかBが落ち、状態を片方だけ直せばBが落ち、リネームすればAが落ちる）
- ⚠️ **索引側の「どの表に載っているか」までは照合しない。** 表の構造をパースすると
  **索引の書き方を変えるたびに検査が壊れる**（#70 で「`git add` は1行で書く」の制約が生まれたのと同じ罠）。
  ⭐ **リンクの存在**と**見出しの数**という、書き方に鈍い2点だけを見る
- ⚠️ **索引ファイルが無い／見出しが見つからない場合は exit 1**（「一致」に倒さない。
  #40 の教訓: **抽出に失敗したときに「網羅できている」へ倒すと検査が嘘をつく**）

### 2-3. 成功時の出力

```text
issue drafts in sync — 起票案11件（生きている7 / 完了3 / 取り下げ1）
```

⭐ **他の検査と同じく、通ったことが1行で分かる形にする**（`meta.sets covers all sets — N件` の流儀）。

## 3. ⚠️ やらないこと（意図的に外した）

| 案 | なぜ外すか |
|---|---|
| ❌ **「最終確認から N日経過」で落とす**（鮮度の検査） | ⚠️ **その日の変更と無関係に、時計だけで赤くなる。** 直す手段がコミットに無いので
**無視される検査に育ち、他の検査ごと信用を失う**。`check-terminology.mjs` を exit code に載せなかったのと同じ判断 |
| ❌ **起票案の中身と実データを突き合わせる** | 起票案ごとに主張が違うので**一般化できない**。⭐ 腐りの手当ては運用側（索引 §4-2「投函前の再測定」）で行う |
| ❌ **索引の表の列（内容・ラベル案）まで照合する** | 索引の書き方に強く依存し、**索引を整形しただけで落ちる**。得られる安全より保守コストが勝る |

⚠️ ⭐ **「腐り」そのものはこの検査では防げない**（状態行と索引が**整合したまま**中身が古くなる型）。
**それを承知のうえで、整合だけを機械に持たせる**——という切り分けが本issueの要点。
