## 3. 実装仕様

⭐ **既存の #70（cron列挙のドリフト防止）と同じ形**。`scripts/validate.mjs` にブロックを1つ足すだけで、
**既存の検査・出力・exit code は一切変えない**。

### 3-0. 置き場所と定数

- 置き場所: ⭐ **`// --- cronの git add 対象とドキュメント列挙の一致（#70） ---` ブロックの直後、
  用語ハイライト検査（`if (loaded) { … }`）の直前**
  - 理由: 用語ハイライト検査は**トップレベル `await` を含む唯一のブロック**。その前に置くことで
    **本検査は同期処理のまま**でよく、出力順も決定的になる
- 定数: `const DRAFT_INDEX = "docs/design/待ち行列/待ち行列と復旧手順.md";`
  `const DRAFT_ROOT = "docs/design";`
- 既存の流儀に合わせる: ブロックは `{ … }` でスコープを切り、`const bad = [];` に問題を積み、
  最後に `if (bad.length) { problems++; console.error(…) }`

### 3-1. 集める（対象ファイル）

- `DRAFT_ROOT`（`docs/design`）を**再帰的に**走査し、次を満たすファイルを集める:
  - 拡張子が `.md`
  - **ファイル名（基名）が `/^(派生)?起票案/` に一致する**（D2・**前方一致**）
- 収集結果は**リポジトリ相対パス**に正規化し、**昇順にソートする**（出力を決定的にするため）
- ⚠️ **1件も集まらなければ exit 1**（D8）: `` 起票案が1件も見つかりません: docs/design ``
- 実測: **11件**（2026-09-02）。`docs/design` 配下の `.md` は97件なので走査コストは無視できる

⭐ **「含む」ではなく「前方一致」にする理由**: 「含む」だと将来
`大会の起票案テンプレート.md` のような文書まで拾う。実測では両者の結果は同じ（**11件**）。

#### ⚠️ ⭐ この検査が生む命名の制約（**実際に踏んだ**・§2-5）

> **`docs/design/**` に、`起票案` で始まる名前の `.md` を「起票案以外の目的」で置いてはいけない。**

- 設計書・解説文書・テンプレートは、**`起票案` 以外で始まる名前**にする
  （本設計書は当初 `起票案の整合検査_設計.md` で**この罠を踏み、`状態行と索引の整合検査_設計.md` に改名した**）
- ⭐ **破っても黙って通ることはない。** `起票案の1行目に状態行がありません: …` と
  `索引に載っていない起票案: …` が出て **exit 1** になる（＝**気づける失敗**）
- ⚠️ **除外リストで逃げないこと。** 「この1本だけ対象外」という規則を足すたびに、
  **本物の起票案を取りこぼす穴**が増える。**名前のほうを直す**

⚠️ **前方一致を `/^(派生)?起票案_/`（アンダースコアまで要求）に狭める案は採らなかった。**
実測では11件すべてが `起票案_` / `派生起票案_` の形なので**今は同じ結果**だが、
`起票案2026-09-05.md` のような命名を**黙って取りこぼす**（＝ fail-open）。
⭐ **うるさい誤検知（loud）と、静かな取りこぼし（silent）なら、前者を選ぶ。**

### 3-2. 状態行を読む

各ファイルの**1行目**を次で解釈する:

```js
const STATUS_RE = /^\*\*状態: (生きている|完了|取り下げ)\*\*（最終確認 (\d{4}-\d{2}-\d{2})）/;
```

- ⚠️ **一致しなければ問題として積む**（そのファイルは件数に数えない）:
  `` 起票案の1行目に状態行がありません: <リポジトリ相対パス> ``
  - ⭐ **これがこの検査のいちばんの効き目**——**状態行なしの起票案を新規に作れなくなる**
- ⚠️ **BOM に注意**。既存の翻訳検査と同様、先頭の `﻿` は除去してから照合する
  （BOM 付きで保存されると「1行目が無い」に見えて原因が分かりにくい）
- 日付は**形式だけ**見る（D5）。値の妥当性・鮮度は見ない（D4）

### 3-3. 索引を読む

- `DRAFT_INDEX` を読む。⚠️ **読めなければ exit 1**（D7）:
  `` 索引が見つかりません: docs/design/待ち行列/待ち行列と復旧手順.md ``
  → **この場合 A・B は実行しない**（「一致」に倒さない）
- 見出しから件数を取る。**4種それぞれ、ちょうど1回だけ**一致すること（D9）:

  | 状態 | 正規表現（`m` + `g` フラグ） | 実測値 |
  |---|---|---|
  | 全件 | `/^#{2,3} .*起票案の一覧（\*\*全(\d+)件\*\*/gm` | **11** |
  | 生きている | `/^#{2,3} .*生きている（\*\*(\d+)件\*\*/gm` | **7** |
  | 完了 | `/^#{2,3} .*完了済み（\*\*(\d+)件\*\*/gm` | **3** |
  | 取り下げ | `/^#{2,3} .*取り下げ（\*\*(\d+)件\*\*/gm` | **1** |

  - ⚠️ **索引の見出しの語は `完了済み`、状態行の語は `完了`**。**同じではない**ので、
    表示・比較のラベルは**状態行側の語（`完了`）に寄せる**
  - ⚠️ **閉じ括弧 `）` を要求しない**（§2-3。全件見出しは `**` の後ろが `・`）
  - 0回なら `` 索引に「<状態>」の件数見出しが見つかりません ``（exit 1・D7）
  - 2回以上なら `` 索引に「<状態>」の件数見出しが N個 あります（1個だけにしてください） ``（exit 1・D9）
- リンクを取る:

  ```js
  // ](path.md) と ](path.md#anchor) の両方を拾う
  const LINK_RE = /\]\(([^)\s#]+\.md)[)#]/g;
  ```

  - ⭐ **索引の位置を基準に解決してからリポジトリ相対に正規化する**（D1）:
    `path.normalize(path.join(path.dirname(DRAFT_INDEX), 捕獲したパス))`
    - ⭐ これで**同フォルダのスラッシュ無しリンク**（`](起票案_….md)`）も
      **`./` 付きのリンク**も**同じ1つのパス**に落ちる（§2-2 ①の誤検知が消える）
  - 実測: 索引の `.md` リンクは **15本**（重複除去後）、**すべて実在**

### 3-4. 検査A — 収録漏れ（起票案 → 索引）

- 収集した各起票案のパスが、**3-3 で解決したリンク集合に完全一致で含まれる**こと
- 含まれないものがあれば1件ずつ積む:
  `` 索引に載っていない起票案: <リポジトリ相対パス> ``
- ⚠️ **基名ではなくパスを出す**（§2-2 ②の重複があるため）

### 3-5. 検査B — 件数の一致（状態行 → 索引）

- 状態行から数えた実数（全件＝収集件数、状態別＝3種）と、索引の4つの数を突き合わせる
- 食い違うものを1件ずつ積む:
  `` 索引の件数が実数と一致しません: <ラベル> 索引<N> / 実数<M> ``
  - ラベルは **`全件` / `生きている` / `完了` / `取り下げ`**
- ⚠️ **状態行を読めなかった起票案が1件でもあれば、B は実行しない**（D6）。代わりに1行積む:
  `` 件数の比較を省略しました（状態行を読めない起票案が N件 あるため） ``

⭐ **A と B の組み合わせで、追加・削除・リネーム・状態変更のすべてが捕まる**
（追加すれば A か B が落ち、状態を片方だけ直せば B が落ち、リネームすれば A が落ちる）。

### 3-6. 出力

**成功時**（`bad` が空のとき、既存の流儀に合わせて `console.log` 1行）:

```text
issue drafts in sync — 起票案11件（生きている7 / 完了3 / 取り下げ1）
```

**失敗時**（既存の #70 ブロックに合わせる）:

```text

ISSUE DRAFT DRIFT (docs/design/待ち行列/待ち行列と復旧手順.md):
  - <積んだ問題を1行ずつ>
  → 状態の正は各起票案の1行目です。索引 §1 の一覧と見出しの件数を合わせてください
    （手順は docs/design/待ち行列/待ち行列と復旧手順.md §4）
  → 「起票案」で始まる名前の .md はすべて起票案として扱われます。設計書・解説文書には別の名前を付けてください
```

⚠️ ⭐ **2本目の誘導行を省かないこと。** §2-5 の事故（設計書自身が拾われる）は
**メッセージだけでは原因が分からない**——「状態行がありません」と言われた人が、
**そのファイルを起票案にしようとしてしまう**。

### 3-7. ⚠️ やらないこと（意図的に外した・再検討しないための記録）

| 案 | なぜ外すか |
|---|---|
| ❌ 「最終確認から N日経過」で落とす（鮮度の検査） | ⚠️ **その日の変更と無関係に、時計だけで赤くなる。** 直す手段がコミットに無いので**無視される検査に育ち、他の検査ごと信用を失う**（`check-terminology.mjs` を exit code に載せなかったのと同じ判断）。手当ては索引 §4-2 の**運用規約**で行う |
| ❌ 起票案の中身と実データを突き合わせる | 起票案ごとに主張が違うので**一般化できない** |
| ❌ 索引の**表の列**（内容・ラベル案）まで照合する | 索引の書き方に強く依存し、**索引を整形しただけで落ちる** |
| ❌ 索引の**どの表に載っているか**まで照合する | 同上。⭐ **リンクの存在**と**見出しの数**という、書き方に鈍い2点だけを見る |
| ❌ 索引の**リンク切れ**（索引 → 実ファイル）の検査 | ⭐ **A がほぼ同じ範囲を覆う**（フォルダをリネームすれば A が落ちる）。単独で必要になるのは「起票案を**削除**したのに索引のリンクだけ残した」場合だが、**運用は削除ではなく `状態: 取り下げ` を付ける**（索引 §4-2）ので起きない。検査を増やすぶんの保守コストが勝ると判断した |

⚠️ ⭐ **「腐り」そのものはこの検査では防げない**（状態行と索引が**整合したまま**中身が古くなる型）。
**それを承知のうえで、整合だけを機械に持たせる**——という切り分けが本タスクの要点。
腐りの手当ては索引 §4-2 の「**投函前の再測定**」（人の運用）が担う。

## 4. ⚠️ 索引が `npm run validate` の依存先になる（**消費側が1つ増える**）

⭐ **これは本タスクがリポジトリに持ち込む唯一の新しい依存関係**なので、明記して引き継ぐ。

これまで `docs/design/待ち行列/待ち行列と復旧手順.md` は**人だけが読むファイル**で、

### 4-1. ⚠️ 索引を壊したときに起きること（症状の表）

  移動と索引の修正は**同じコミットで行う**

- 起票案の1行目が状態行でない

⚠️ **「抽出に失敗したら一致に倒す」実装にしないこと。** #40 の教訓どおり、
**検査が壊れたまま黙って通るのが最悪の失敗**。
