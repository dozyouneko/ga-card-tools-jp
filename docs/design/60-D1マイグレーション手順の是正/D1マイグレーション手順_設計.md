## 1. 背景と目的

### 1-1. 何が壊れているか

`package.json` の `db:migrate:local` / `db:migrate:remote` は **`0001` から全マイグレーションを
`&&` で連結して流す**作りだが、`0001_init.sql` に `IF NOT EXISTS` が無いため、
**既にテーブルがあるDBでは1本目で必ず失敗する**。

実測（2026-08-15・適用済みのローカルD1）:

```text
$ npx wrangler d1 execute DB --local --file=migrations/0001_init.sql
✘ [ERROR] table users already exists at offset 13: SQLITE_ERROR
exit code = 1
```

⚠️ **壊れているのに、名前は「マイグレーションを実行するコマンド」のまま**である点が本質。

### 1-2. 影響度の評価（設計時に実測・結論）

| 観点 | 評価 | 根拠 |
|---|---|---|
| **データ喪失** | **なし** | `migrations/` 4本の中身は `CREATE TABLE` と `ALTER TABLE ADD COLUMN` のみ。**`DROP`/`DELETE`/`UPDATE` は1文も無い**（全文確認済み） |
| **部分適用（中途半端な状態）** | **なし** | wrangler が **exit 1** を返し `&&` 連鎖が1本目で止まる（実測） |
| **本番サービスへの影響** | **なし（直接には）** | 失敗するのは適用者の手元だけ。本番D1は無傷 |
| **発生頻度** | **低い** | マイグレーションは約1年で4本。当面スキーマ変更を伴う予定は `#5`（凍結中）のみ |
| **誤操作の誘発** | ⚠️ **これだけが実害** | 下記 |

⭐ **したがって本issueは「バグ修正」ではなく「誤解を招く道具と手順書の是正」である。**
急がないが、**次にスキーマを変更する前には必ず直っている必要がある**。

**是正すべき実害は3つ**（すべて設計時にファイルで確認済み）:

1. ⚠️ **`README.md:154` が壊れたコマンドを案内している** — 「スキーマ変更時は `npm run db:migrate:remote`
   を本番D1に適用」。CLAUDE.md には正しい注意書きがあるが、**READMEだけを読む経路はここに誘導される**
2. **`docs/dev-setup.md:417` が陳腐化** — 「マイグレーション0001〜0003を適用」で **`0004` が抜けている**
3. **唯一の破滅シナリオは人の誤操作** — `table users already exists` を「本番DBが壊れた」と読み違え、
   `DROP TABLE` で作り直そうとすると **users / decks 65件が消える**。
   バグ自体ではなく、**紛らわしいエラーが危険な操作を誘発する**経路

### 1-3. 目的

- **壊れたコマンドを叩けないようにし、代わりに正しい手順をその場に出す**
- **手順書（README・dev-setup.md）の記述を、将来のファイル追加で陳腐化しない書き方に直す**
- ⚠️ **本番D1には一切書き込まない**（軽量案の定義）

## 2. `wrangler d1 migrations apply` を採らない理由

### 2-1. どういう仕組みか（wrangler 4.86.0 で実測）

`d1_migrations` という管理テーブルに適用済みのファイル名を記録し、**未適用の分だけを流す**。
`migrations list` で未適用を一覧でき、失敗時は**そのマイグレーションをロールバックして
直前の成功状態を保つ**（`--help` に明記）。ファイル名の規約（`0001_init.sql` 形式）は
**現在の4本がすでに適合しており、改名は不要**（issue本文の「改名が要る可能性」は誤り）。

### 2-2. ⚠️ そのまま導入すると現状と同じ結末になる

**すでに 0001〜0004 が全部入っているローカルD1**での実測:

```text
$ npx wrangler d1 migrations list DB --local
Migrations to be applied:
  0001_init.sql / 0002_deck_card_art.sql / 0003_deck_thumb.sql / 0004_deck_format.sql

$ npx wrangler d1 execute DB --local --command "SELECT * FROM d1_migrations;"
"results": []      ← テーブルは作られるが記録は空
```

⭐ **適用済みの4本が「未適用」と表示される。** この状態で `apply` を打てば 0001 から流そうとし、
**`table users already exists` で落ちる**＝現状とまったく同じ。

### 2-3. 見送りの判断

移行するには、本番D1へ**適用済みであることを1回だけ手で記録する**ブートストラップが要る:

```sql
INSERT INTO d1_migrations (name) VALUES
  ('0001_init.sql'), ('0002_deck_card_art.sql'), ('0003_deck_thumb.sql'), ('0004_deck_format.sql');
```

⚠️ これは**本番D1への書き込み**であり、CLAUDE.md の「SELECT 以外を書かないこと」に対する例外となる。
当面スキーマ変更の予定が無い（`#5` は凍結中）以上、**いま本番DBに触るリスクを取る理由がない**。

⭐ **将来の再検討条件**: **次にスキーマ変更（0005）が必要になったとき**、その作業と同じ機会に
ユーザー立ち会いで移行する。そのとき本設計書の §2-2 の実測をそのまま前提として使える。

## 3. 変更内容

⚠️ **対象は3ファイル。`migrations/*.sql` は1文字も変更しない**（既存DBの状態と食い違うため）。

### 3-1. `package.json`（2行）

**変更前**（16〜17行）:

```json
    "db:migrate:local": "wrangler d1 execute DB --local --file=migrations/0001_init.sql && … 0004_deck_format.sql",
    "db:migrate:remote": "wrangler d1 execute DB --remote --file=migrations/0001_init.sql && … 0004_deck_format.sql"
```

**変更後**:

```json
    "db:migrate:local": "for f in migrations/*.sql; do echo \"-- $f\"; wrangler d1 execute DB --local --file=\"$f\" || exit 1; done",
    "db:migrate:remote": "echo '⚠️  本番D1へは一括適用できません（既存テーブルがあるため必ず失敗します）。' && echo '   追加した migrations/ のファイルだけを単体で実行してください:' && echo '     npx wrangler d1 execute DB --remote --file=migrations/000N_xxx.sql' && echo '   ⚠️ 必ず「本番D1へ適用 → push」の順。手順は README.md の「公開方法」節を参照。' && exit 1"
```

**設計意図**:

| 決定 | 理由 |
|---|---|
| `db:migrate:local` は **glob ループ**にする | ⭐ **ファイルを足すたびに `package.json` へ追記する手順が不要になる**（`#4` の設計書 396行が要求していた作業を1つ消す）。追記漏れは実際に `#4` で発生しかけた |
| ループに **`\|\| exit 1`** を付ける | ⚠️ **必須。** これが無いと `;` 区切りで**全4本が走って全部エラーになる**（実測: `table users already exists` に続き `duplicate column name: art_image` / `thumb_image` / `format` の**計4本**が出る）。現行の `&&` が持つ fail-fast を維持するため |
| `db:migrate:local` を**改名しない** | 用途は「初期化」だが、**ローカルは空DBなら正しく動き、失敗しても破壊しない**ため実害が小さい。改名すると README・dev-setup.md・利用者の記憶をすべて追随させる必要があり、軽量案の範囲を超える |
| `db:migrate:remote` を**削除せず案内に置き換える** | ⚠️ **削除案を実測で棄却した。** 存在しないスクリプトを叩くと `npm error Missing script: "…"` と出るだけで、**スクリプト一覧は表示されない**（「`npm run` を実行しろ」と案内するのみ）。**削除すると「では何を使うのか」がその場で分からない** |
| 案内の最後を **`exit 1`** にする | 何もしていないのに**成功したと誤解させない**ため |

### 3-2. `README.md`（2箇所）

**① 98行**

```diff
-npm run db:migrate:local # ローカルD1のマイグレーション
+npm run db:migrate:local # ローカルD1の初期化(migrations/ を順に適用。空のDB向け)
```

**② 153〜154行**

```diff
 - デッキ構築ツールのAPIは同一プロジェクトの **Pages Functions**（[functions/](functions/)）+ **D1** で動作。
-  スキーマ変更時は `npm run db:migrate:remote` を本番D1に適用
+  スキーマ変更時は **追加した `migrations/` のファイルだけ**を本番D1へ単体で適用する
+  （`npx wrangler d1 execute DB --remote --file=migrations/000N_xxx.sql`）。
+  ⚠️ **必ず「本番D1へ適用 → push」の順**。逆順にすると、コードだけが本番に出た数分間、
+  新しい列を読むクエリが `no such column` で落ちます（列の追加は既存クエリを壊さないため、先に適用しておくのは安全）
```

### 3-3. `docs/dev-setup.md`（1箇所・417行）

```diff
-2. `npm run db:migrate:local` — ローカルD1(`.wrangler/state`)にマイグレーション0001〜0003を適用
+2. `npm run db:migrate:local` — ローカルD1(`.wrangler/state`)に `migrations/` 配下を順に適用
+   (空のDB向け。⚠️ 適用済みのDBでは1本目の `table users already exists` で停止するが、これは正常)
```

⚠️ **「0001〜0004」と書き直さないこと。** 番号を書くと**次のファイル追加でまた陳腐化する**
（これが §1-2 の実害2の再発である）。**件数・番号を書かない表現に統一する。**
