## 5. 設計 — 単位1（AND系統・案E-1）

### 5-1. 変更の形

`run()` の経路は今 4本ある（JP → ENテキスト → 数値ソート → それ以外）。
⭐ **「数値ソート」の路を「数値ソート **または** AND」に広げ、並べ替えを `sortLocal()` に委ねる**だけでよい。

```
現在:  } else if (isNumericSort()) {            …… 全件路 + sortNumeric
       } else {                                 …… 1ページ取得 + ページ内で間引き
変更後: } else if (isNumericSort() || anyAnd()) { …… 全件路 + sortLocal
       } else {                                 …… 1ページ取得（⭐ anyAnd() が false なので間引きは起きない）
```

| 要素 | 扱い |
|---|---|
| 上位集合の取得 | ⭐ **既存の `fetchAll(filterParams().toString())` をそのまま使う**（`allCache` / `MAX_PAGES` / `ALL_CONCURRENCY` も既存のまま） |
| 進捗表示 | ⭐ **既存の `subscribeProgress([key], …)` → `opts.onProgress`**（両ページに配線済み）。⚠️ **必須**（CLAUDE.md「待ちが数秒を超えるなら進捗表示を出す」） |
| 数値項目を持たないカードの除外（#39） | ⚠️ **`isNumericSort()` のときだけ**にする（ENテキスト路と同じ形。⭐ 今は路が数値ソート専用だったので無条件だった） |
| 並べ替え | ⭐ **`sortLocal(pool)`**（#111 §5-5）。`isNumericSort()` なら `sortNumeric`、`rarity` なら `localRarityKey`、それ以外は `localNameKey` |
| AND の間引き | ⭐ **既存の `matchesAndFilters`**（意味は1ミリも変えない） |
| `fetchGap` | ⭐ **既存どおり `all.cards.length !== all.total` で立てる**（⚠️ **殺さない**。`MAX_PAGES` で切り落ちた場合もここに出る＝唯一の信号） |
| `elementAndBlocked()` | ⚠️ **触らない**。判定は今と同じ位置（全件路より前）に残す |
| `approxTotal` | ⭐ **`jpSlugs ? jpApprox : false`**（§5-3） |

⭐ **`localNameKey` の並びは公式APIの `sort=name` と一致する**ことを本件の17枚でも確認した（実測: 完全一致）。
⚠️ **Nameless Champion 18枚だけは同キーで API の内部順序と違う**（#111 N1 で受けた既知。本件で新しく増える話ではない）。

### 5-2. ⭐ 「1画面目に出そろう」の定義（issue §7-4 の論点を決着）

⚠️ **`PAGE_SIZE` はトップ 50・デッキ構築 24 で違う**ので、「全部が1画面に出る」とは言えない。**こう定義する**:

> ⭐ **検索の答えの件数 N が、1画面目を描く前に確定していること。** その帰結として:
> 1. 1画面目のタイル数 ＝ **`min(N, PAGE_SIZE)`**
> 2. 「もっと見る」が出るのは **N > PAGE_SIZE のときだけ**（＝「まだ分からない」ではなく「本当に続きがある」）
> 3. 件数表示が **N を言い切る**（`N 件を表示` または `PAGE_SIZE 件を表示 / 全 N 件`）

⭐ **A5/A6 は N=17 なので、トップ（50）でもデッキ構築（24）でも 1画面に全部出る。**
⭐ **N が `PAGE_SIZE` を超える AND でも「出そろう」は満たされる**（例: サブタイプ CLERIC＋SPELL は N=257 → `50 件を表示 / 全 257 件`）。

### 5-3. ⭐ 概算の注記を1つ撤去する（issue §7-3 の「出所は2つある」の片方）

単位1 のあと、**非JPモードで `approxTotal` が true になる経路は1本も残らない**:

|---|---|---|
| JPモード | 索引で取得前（+取得後の最終判断） | `jpApprox`（§6-2 で単位2 がさらに減らす） |

### 6-0. 索引の形式 — ⭐ `entry[7]` の意味を変える（トップレベルの別キーにはしない）

```
変更前: entry[7] = entry[4] と同じ並びの「そのセット内の最小レアリティ」          例: [1, 7]
変更後: entry[7] = entry[4] と同じ並びの「そのセット内のレアリティ集合（昇順）」   例: [[1, 8], [7]]
```

| 判断 | 内容 |
|---|---|
| **なぜ `entry[7]` の意味を変えるのか** | ⭐ **9要素目を足さない**規約（`sortKeyOf()` が `entry.length < 8` で旧形式を判定する）に抵触しない。⭐ **`entry[7].length === entry[4].length` という既存の不変条件がそのまま生きる**ので、`validate` の検査も構造を変えずに済む |

## 8. ⭐ 残る穴（承知のうえ）

### 8-1. ⚠️ 「`e.set` を持たない版」は索引から見えない

⭐ **実行時の `rarityMatchesIn()` は、エキスパンション絞り込みが無いとき `e.set` が無い版も E に入れる**が、
**索引は prefix ごとのスロットしか持たないので、その版のレアリティを表せない**。
→ ⚠️ ⭐ **そういう版のレアリティだけが選択値に一致するカードは、索引が候補から落とす**（**#27 の原則どおり、取得後フィルタでは救えない向き**）。

| 項目 | 内容 |
|---|---|
| 今日の件数 | ⭐ **0件**（版 4,941 件すべてが `e.set.prefix` を持つ。§2-6 で実測） |
| なぜ手当てしないか | ⭐ **0件のための分岐は誰も試せない**（＝このリポジトリが繰り返し刺されている型）。⚠️ **エキスパンション絞り込みのほうは今も同じ構造で、実行時も索引も同じ結論になる**ので、新しい種類の穴でもない |
| ⭐ **検出経路** | **生成スクリプトの完走サマリに `prefix の無い版: N件` を出す**（§6-1）。⚠️ **cron は `validate` を実行しない**ので、これが唯一の痕跡 |

### 8-2. ⚠️ `fetchGap` を消しても検証項目は1つも落ちない

今日 `unique !== total` は起きないので、**突き合わせを消しても画面も `validate` も変わらない**（破壊試験 B5）。
⭐ **守っているのは diff を読む人だけ**（#44 以来の性質で、本件で悪くなるわけではない）。

### 8-3. ⚠️ `localNameKey` の同キー18枚

**Nameless Champion 18枚**は `localNameKey` が同じで、公式APIの内部順序と並びが違う（#111 N1 で受けた既知）。
⭐ **単位1 で AND の並びがローカルになるので、この18枚が同時に AND の答えに入ると順序が API と違いうる**（⚠️ **件数は変わらない**）。

### 8-4. ⚠️ 索引の鮮度の責任は JPモードだけに留める（案E-2 を採らない）

⭐ **ユーザー決定（R3）**: **案E-2（ENモードでもメタ索引で先に絞る）は採らない。**

| | 案E-1（採用） | 案E-2（不採用） |
|---|---|---|
| エレメントAND（上位80・積17） | ⭐ **2 リクエスト** | 17 リクエスト |
| クラスAND（上位652・積61） | 14 リクエスト | 61 リクエスト |
| タイプAND（上位798・積 0） | 16 リクエスト | ⭐ **0 リクエスト** |
| ⚠️ **索引の鮮度** | ⭐ **関係ない**（公式APIが正） | ⚠️ **全モードが索引の鮮度に依存する** |

⚠️ ⭐ **採らない理由（将来の蒸し返し防止のために明記する）**:
**索引は手で再生成するコミット済みの静的データ**で、**候補から外れたカードは取得後フィルタでは救えない**（#27 の原則）。
⭐ **いま索引の腐りを被るのは JPモードだけ**で、**ENモードは公式APIが正**という単純な役割分担が成り立っている。
**案E-2 はこの分担を壊し、「索引を再生成し忘れた日に英語検索が静かに取りこぼす」という経路を新設する**。
⭐ **一方、案E-1 の代償は待ち時間だけで、進捗表示で可視化できる**（⚠️ **cron が止まっている今は、索引の鮮度の責任を広げる判断はとくに重い**）。
