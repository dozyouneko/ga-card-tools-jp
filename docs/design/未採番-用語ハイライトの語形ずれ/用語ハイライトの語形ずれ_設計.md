## 2. 現状と原因

### 2-1. 症状

**140枚のカードで、日本語効果文に用語がはっきり書かれているのにハイライトされず、用語解説にも出ない。**
⚠️ **fail-open なので画面は壊れない。黙って出ないだけ**（ユーザーからは「この語だけリンクが無い」に見える）。

⭐ **同じ語が出るカードでも、出るものと出ないものがある**のが決定的な症状:

| カード | 日本語効果文 | ハイライト |
|---|---|---|
| `astra-sight` | 「**グリンプス**中にこのカードを見ているとき…」 | ✅ 出る |
| `cometfall` | 「**グリンプス**中にこのカードを見ているとき…」（**同じ文面**） | ❌ 出ない |
| `aquamirage-whisper` | 「**ヒット時**：…」 | ✅ 出る |
| `crossroads-specter` | 「チャンピオン**ヒット時**：…」 | ❌ 出ない |

加えて、**用語が二色に割れて描画される**カードが15枚ある（型⑤）。

### 2-2. 現状の実装（変更対象の3関数）

`shared/js/card-detail.js`（ブラウザ）と `scripts/build-card-pages.mjs`（ビルド）に**同一規則で移植された**コードがある。

```text
matchedTerms(card)      … 英語効果文（"*" 除去・小文字化）に対し \b + terms のキー の前方一致
                          → 当たったキーの terms エントリを配列で返す（＝用語解説に出る集合）
highlightTerms(html, terms)
                        … terms の中核語（jp の「（」より前・2文字以上）を長い順に
                          1本の交替正規表現にして、日本語効果HTMLを <span class="term-hl"> で包む
jpEffectHtml(face, terms)
                        … renderEffect → highlightCardName
                          → applyOutsideSpans("card-name-hl", highlightTerms)
                          → applyOutsideSpans("card-name-hl", highlightSubtypes)
```

⚠️ **キーが英語に当たらなければ、訳文にどれだけ明確に用語が書かれていても何も起きない。**

### 2-3. 原因（3型）

| 型 | 原因 | 件数 / 枚数 |
|---|---|---|
| **①** | **英語の語形がずれてキーが当たらない** — ① 語中に別語が挿入される（キー `on hit` に対し実際は `On **Champion** Hit`）② 語尾の `e` が別字に変わる（`glimpse`→`glimpsing` / `materialize`→`materialization` / `reserve`→`reservable`） | **65 / 64** |
| ② | 用語解説は出るのにハイライトだけ出ない | ⭐ **0 / 0**（存在しない。§2-4） |
| **③** | **英語原文に該当語が無い** — 訳者が英語より手厚くリマインダーを補っている。**英語をゲートにする限り原理的に拾えない** | **90 / 78** |
| ④ | 用語解説には出るが訳文に中核語が無い | 11 / 11（**無害・D1で現状維持**） |
| **⑤** | `applyOutsideSpans()` の保護クラスが `card-name-hl` **だけ**なので、**すでに作った `term-hl` の内側にサブタイプのハイライトが入り込む** | — / **15** |

- ⭐ `\b` は正しく機能している（`champi|on hit` の誤マッチを防いでいる）。**キーの側が実態と合っていない**
- ⚠️ `banish→banished` のように語尾が伸びるだけの活用は当たるので、**「e が別字に変わる型」だけを取りこぼす**
- ①＋③ の合計 **155件 / 140枚**（`punishing-cartridge` と `tasershot` の2枚が①③の両方に該当）

### 2-4. ⚠️ 型②が0件であることの確認方法（実装時に必ず読むこと）

`elysian-aspirant` は `grep -c 'term-hl">エリュシオンオーラ'` が 0 になるが、**不具合ではない**。実物はこう:

```html
<span class="term-hl"><span class="subtype-hl">エリュシオン</span>オーラ</span>
```

**ハイライトは正しく掛かっている**（内側のサブタイプハイライトが文字列を割っているだけ）＝これが型⑤。

- ⚠️ ⭐ **教訓: `grep 'term-hl">核'` はこの実装の判定に使えない。**
  §5 の検出経路もこの理由で「タグを走査して `term-hl` の内側かを判定する」方式にしてある

### 2-5. 型⑤の対象15枚（実測・`b6feec6f` の生成物）

```text
aetheric-calibration bifurcating-fractal blazing-cindercharge elysian-aspirant elysian-orphan
elysian-test-subject embryonic-hemosynth lucia-reclaimed-blight magebane-lash manabolt-convergence
pure-cytosynth seekers-aetherwing thanatotic-hemosynth trivariate-dream venous-core
```

見た目の症状: `.term-hl` は青系・`.subtype-hl` は金系で、どちらも `color` + `background` + `padding: 0 2px` を
持つため、**1語の途中で色と背景が変わる**。

### 2-6. ⚠️ 案A / 案B を採らなかった理由（再検討しないための記録）

| 案 | 直る | 却下理由 |
|---|---|---|
| A: `terms` にキーを追加（`on champion hit` / `glimpsing` / `materialization` …） | 型①のみ 65件/64枚 | **型③90件は直らない**。⚠️ **対症療法**——新セットで語形が増えるたび再発し、更新の号令も無い（**#40 と同型の「気づけない辞書」を1つ増やす**） |
| B: 照合を語形に強くする（空白に単語挿入を許す＋語尾 `e` を任意に） | 型①のみ 65件/64枚 | ⚠️ ⭐ **過剰マッチが実測142件中73件**。内訳は `prepare`→`preparation` **70件** / `negate`→`negative` 2件 / `charge`→`Charging` 1件 |
| C（純・英語ゲートを**やめる**） | 155件/140枚 | ⚠️ **型④の11件（用語解説）が消える**。さらに**訳が無い15枚**で解説が空になる |

⚠️ ⭐ **`prepare`「プレパレーション（Prepare N）」と `preparation`「プレパレーションカウンター」は別の用語**。
キーワード `Prepare N` を使っていないカードの用語解説に「プレパレーション（Prepare N）」が並ぶのは**誤り**。
これは CLAUDE.md の「**`terms` に「無い」と判定するときは基語も見る**」の罠そのもので、
**語形を緩めると「キー同士が食い合う」問題が表に出る**。

**採用する案C′（英語ゲート ∪ 訳文駆動）は、この食い合いが構造的に起きない**——
追加されるのは「**その画面に実際に表示されている日本語の用語**」だけで、英語側の綴り一致に頼らないため。

## 3. 実装仕様

⚠️ ⭐ **変更1・2は `shared/js/card-detail.js` と `scripts/build-card-pages.mjs` の2箇所に同型で入れること。**
現状も同一規則で、**片方だけ直すと画面ごとに挙動が食い違う**（V13 がこの確認）。

### 3-1. 変更1 — `matchedTerms(card)` を C′ の規則にする

⚠️ **この3手順を、この順序どおりに実装すること。** 順序を変えると件数が変わる（§3-2 の感度表）。

```text
手順1. 英語ゲート（現行のまま・変更なし）
  英語効果文（card.effect から "*" を除去して小文字化）に対し、\b + キー の前方一致で
  当たったキーを「採用済み」とする。

手順2. 訳文ゲート（追加）
  照合対象の文字列 text を次のように作る:
    a. 和訳の効果文（CI.tr(face).effect / ブラウザ側は tr(face).effect）から "*" を除去する
    b. ⚠️ さらに自分のカード名（CI.jpName(face) / jpName(face)）の出現を
       「同じ長さの空白」で潰す（名前が2文字以上かつ日本語を含むときのみ）
       ⭐ 潰さないと「雪のフラクタル」→ fractal のような名前由来の誤検出が入る
          （highlightCardName() が先に保護する領域なので、ハイライトは出ないのに用語解説だけ増える）
    c. 和訳が無い面（effect が空）は手順2〜3をまるごと飛ばし、手順1の結果だけを返す（fail-open）
  手順1で採用されなかったキーのうち、中核語（terms[key].jp の「（」より前を trim・2文字以上）が
  text に出現するものを「候補」とする。

手順3. 占有判定（候補の絞り込み）
  ⚠️ 採用済み（手順1）と候補（手順2）を「中核語の長い順」に **混ぜて** 1本の列に並べる。
     （中核語が2文字未満のものは列から除く）
  text と同じ長さの「占有フラグ配列」を用意し、先頭から順に:
     その中核語が text に現れる位置を左から順に走査し、
     ⚠️ 「その出現の **全文字が未占有** であるとき」だけ、その範囲を占有済みにする。
     1文字でも占有済みなら、その出現は飛ばす（占有もしない）。
     どこか1箇所でも占有できたら、そのエントリは「出現した」とみなす。
  ・候補は「出現した」ときだけ採用する。
  ・採用済み（手順1）は占有だけ行い、**常に採用のまま**とする（手順1の結果は減らさない）。

戻り値
  「手順1の採用分（現行の並び）→ 手順3で採った候補」の順に terms エントリを並べた配列とする。
  ⭐ 既存ページの用語解説の並びを変えないため、この順序を守る。
```

- ⚠️ ⭐ **手順3で「採用済みを先に全部占有してから候補を見る」と実装しないこと。**
  `shadowstrike` で「プレパレーション」（採用済み・8文字）が
  「プレパレーションカウンター」（候補・13文字）を食い、**140枚から1枚落ちる**（実測 154件/139枚）。
  **長さ順に混ぜるのが正**（`highlightTerms()` が全中核語を長い順に置換するのと同じ考え方）
- ⚠️ **占有判定そのものを省くと、用語解説だけが無駄に増える**（実測 **288件/255枚**。
  「フローティングメモリー」に覆われた「メモリー」まで解説に並ぶ）

## 5. 検出経路の設計

⚠️ `scripts/check-terminology.mjs` は**この型を原理的に検出できない**
（「キーが英語に当たった」ものだけを対象にするため）。**`npm run validate` に検査を足して人を止める**（D3）。

### 5-1. 経路① `npm run validate`（exit 1・生成物を正とする・**片方向**）

| 項目 | 内容 |
|---|---|
| 正 | コミット済みの `cards/<slug>/index.html`（日次cronが毎日再生成する） |
| 走査対象 | `cards/` 直下の**ディレクトリ**（＝slug）の `index.html`。**2,495ページ** |
| 見るもの | 各ページの `<h2>効果（日本語）</h2><p class="cp-effect">…</p>` の中身（⚠️ **裏面にも同じ節が出るので、1ページに複数ある**。全部見る） |
| 判定 | `term-hl` / `card-name-hl` の span の**内側を取り除き、残りのタグも境界に潰した**テキストに、`terms` の中核語（2文字以上）が**1つも現れないこと** |
| 失敗時 | **exit 1**。件数と「該当slugの先頭いくつか」をメッセージに出す |
| 成功時 | `card term highlights up to date — 2495 ページ` の1行 |

**この検査が赤くなる原因**（＝止めたい事象）:

1. 照合規則の**回帰**（英語ゲートだけに戻す変更が入った）
2. ⭐ **`data/translations.js` に用語を足した／`data/tl/*.js` に訳を足したのに `build:cards` を回していない**
   （`data/tl-*.json` の陳腐化検査（#22フェーズ2）と同型の穴が、カードページ側にも開いている）
3. ハイライト実装のデグレ

⚠️ **片方向にする。** 「用語解説に出ているのに訳文に中核語が無い」（型④・現状11件）では**落とさない**。
辞書に先回りで用語を入れておくのは正当な運用で、ここで落とすとそれが止まる（`meta.subtypes` 検査と同じ方針）。

⚠️ **`validate.mjs` は現在すべて同期処理**。この検査は非同期（並列読み込み）で書くため、
**ESMのトップレベル `await`** を使い、既存の `problems++` / 末尾の `if (problems > 0) process.exit(1)`
の枠組みにそのまま乗せること。

### 5-2. ⚠️ 実装上の落とし穴（設計時に実測して踏んだもの）

| # | 落とし穴 | 正しいやり方 |
|---|---|---|
| P1 | ⭐ **`grep 'term-hl">核'` の形で判定しない** | `subtype-hl` が内側に入ると**型⑤で0件になる**（§2-4）。**タグを走査して `term-hl` の内側かどうかを判定する** |
| P2 | ⭐ **カード名（`card-name-hl`）の内側も除外する** | しないと「雪のフラクタル」「魂の装填」「メモライト・オベリス」などが**カード名由来で誤検出**される（`bifurcating-fractal` の罠） |
| P3 | **逐次 `readFileSync` は遅い** | 2,495ファイル＝**7.1秒**（`npm run validate` 全体が現状 **0.9秒**なので8倍以上になる）。⭐ **`node:fs/promises` の `readFile` を並列8** で回すと **1.2〜1.8秒**（並列16・32でも改善しない＝I/O律速） |
| P4 | ⚠️ ⭐ **`n += await readFile(...)` と書かない** | `+=` は await の**前**に左辺を読むため、並列実行すると集計が壊れる（設計時に実際に踏み、読み取りバイト数が **16.2MB → 2.0MB** に化けた）。⭐ `const s = await readFile(...); n += s.length;` と2行に分ける |

### 5-3. ⚠️ ⭐ この検査が拾えないもの（**実装前に必ず読むこと**）

**現状の生成物（`b6feec6f`）にこの検査を掛けると、引っかかるのは 140枚ではなく 139枚。**

- 落ちるのは **`shadowstrike` の1枚**。現在すでに「プレパレーション」が `term-hl` で包まれているため、
  span の内側を除いた残りテキストは「カウンター」だけになり、**中核語「プレパレーションカウンター」が現れない**
- ⭐ つまり **`validate` が緑になっても、§3-1 手順3の順序が正しい保証にはならない**。
  **検証項目 V6（`shadowstrike`）を独立の項目として残しているのはこのため**

⚠️ **「terms にまったく登録が無い新キーワード」**は、どちらの経路でも捕まらない
（中核語が存在しないので訳文からも引けない）。#40 と同型の問題で、派生issue候補（§1-3）。

### 5-4. 経路② `node scripts/check-terminology.mjs`（報告のみ・exit code 不変）

型④（用語解説に出るのに訳文に中核語が無い・現状11件）を一覧する既存の役割は**そのまま**。
⚠️ **赤くしない**（D4）。変更4のコメント修正のみ。
