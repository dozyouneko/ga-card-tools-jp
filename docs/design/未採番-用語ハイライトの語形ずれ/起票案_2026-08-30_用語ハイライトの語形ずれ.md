## 2. ⭐ 型②（解説は出るのにハイライトが出ない）は **0件** だった

リードが挙げた `elysian-aspirant` は、**grep の見かけ**であって不具合ではない。生成物の実物はこうなっている:

```html
<span class="term-hl"><span class="subtype-hl">エリュシオン</span>オーラ</span>
```

**ハイライトは正しく掛かっている。** `grep -c 'term-hl">エリュシオンオーラ'` が 0 になるのは、
サブタイプ `ELYSIAN`→「エリュシオン」のハイライトが**内側に入れ子になって文字列を割っている**ため。

- ⚠️ ⭐ **教訓: `grep 'term-hl">核'` はこの実装の判定に使えない。**
  タグを走査して「`term-hl` の内側かどうか」を**文字単位で**判定する必要がある（§6の検出経路もこの方式）
- 全2,495枚を上記の方式で走査した結果、**型②は0件**（`type2候補 0件 / uniq 0枚`）

### 型⑤（副次的に見つかった実在の不具合）— ハイライトの入れ子・**15枚**

`jpEffectHtml()` は `highlightTerms()` → `highlightSubtypes()` の順に適用するが、
`applyOutsideSpans()` に渡す保護クラスが **`card-name-hl` だけ**なので、
**すでに作った `term-hl` の内側にサブタイプのハイライトが入り込む**。

- 見た目の症状: 用語が**二色に割れる**（`.term-hl` は青系、`.subtype-hl` は金系。CSS は両方とも

## 4. 原因と、A/B/C の実測にもとづく評価

### 原因

`matchedTerms()` は **英語原文**に対して `\b` + キーの**前方一致**で判定し、
`highlightTerms()` は**日本語訳文**から中核語を探す。
⚠️ **キーが英語に当たらなければ、訳文にどれだけ明確に用語が書かれていても何も起きない。**

語形がずれる型が2つ、加えて英語に語が無い型が1つある:

1. **語中に別の語が挿入される** — キー `on hit` は連続した2語を要求するが、実際は `On **Champion** Hit`。
   ⭐ なお `champion hit` は文字列として `on hit` を含むが、`\b` が `champi|on hit` の誤マッチを正しく防いでいる。
   **`\b` は正しく、キーの側が実態と合っていない**
2. **語尾の `e` が別字に変わる/落ちる** — `glimpse`→`glimpsing`、`materialize`→`materialization`、
   `reserve`→`reservable`。⚠️ `banish→banished` のように語尾が伸びるだけの活用は当たるので、
   **この設計は「e が別字に変わる型」だけを取りこぼす**
3. **英語に語が無い**（型③・90件） — 訳文がリマインダーを補っている。**英語をゲートにする限り原理的に拾えない**

### 案の評価（すべて実測）

| 案 | 内容 | 直る | ⚠️ 実測した問題 |

### ⭐ 推奨: **案C′（英語ゲート ∪ 訳文駆動）**＋ 型⑤の入れ子修正

根拠:

1. **型①と型③を同時に、規則ひとつで解決する**（155件/140枚）。⭐ **新セットで新しい英語の語形が出ても、
   訳者が辞書どおりの中核語で訳す限り自動で追従する**＝ 案A のような「更新の号令が要る辞書」を増やさない
2. **失うものが無い**。型④の11件も、訳が無い15枚も、英語ゲートを残すので現状のまま
3. **過剰マッチが構造的に起きない**。追加されるのは「**その画面に実際に表示されている日本語の用語**」だけで、
   案B のような英語側の綴り一致に頼らない
4. **fail-open が保たれる**。`data/tl-effects.json` の取得に失敗すると訳文が空になり、
   **現行と同じ挙動に縮退する**（`shared/js/card-detail.js` の `open()` は `render()` の前に
   `loadEffects()` を待つので、通常経路では訳が揃っている）

#### 型③を含めるか（方針判断）→ ⭐ **含めることを推奨**

- **含める理由**: ここは日本語カードDBであり、**画面に日本語で書かれている用語が解説されないのは目的に反する**。
  90件すべて文脈を確認し、**誤検出は0**（すべて実在の用語がリマインダー文に書かれている）
- **ノイズにならない**: 追加は1枚あたり最大2件・平均1.1件
- **除外するほうが高くつく**: 「英語に無い語は採らない」を実装するには英語側の語幹判定が別途必要になり、
  結局 案A と同じ対症療法に戻る
- ⚠️ **許容する副作用**: 複合語の一部だけがハイライトされる箇所が**約19件**出る
  （「**レベル**アップ」10件、「**マテリアライズ**コスト」4件、「**リザーブ**コスト」5件）。
  既存の挙動と同型であり、意味は取れるので許容する

### 変更1 — `matchedTerms(card)` を C′ の規則にする

```text
1. 英語ゲート（現行のまま）
   英語効果文（"*" を除去して小文字化）に対し、\b + キー の前方一致で当たったキーを採用する。

2. 訳文ゲート（追加）
   判定対象の文字列は「訳文（card の和訳 effect）から "*" を除去し、
   ⚠️ さらに自分のカード名（CI.jpName(card)）の出現を潰したもの」。

        （highlightCardName() が先に保護する領域なので、ハイライトは出ないのに用語解説だけ増える）

   この文字列に出現するものを「候補」とする。

3. 占有判定（候補の絞り込み）
   ⚠️ 1の採用分と2の候補を「中核語の長い順」に**混ぜて**並べ、先頭から順に
   訳文中の出現位置を占有していく。すでに占有された位置としか重ならない候補は採らない。
   採用済み（1）は占有だけ行い、常に採用のままとする。
```

- ⭐ **手順3が無いと、用語解説だけが無駄に増える**（実測: 対象が **140枚 → 270枚** に膨らむ。

  「プレパレーションカウンター」（候補・13文字）を食ってしまう。**長さ順に混ぜるのが正**
  （`highlightTerms()` が全中核語を長い順に置換するのと同じ考え方）
- 戻り値の順序は「1の採用分（現行の並び）→ 3で採った候補」とする（既存ページの用語解説の並びを変えないため）
- ⚠️ **`data/translations.js` の `terms` に付いている注意書き
  「`jp` の「（」より前は既訳の字面と完全一致させること」は、C′ ではさらに重要**になる

## 6. ⭐ 検出経路の設計

⚠️ **`scripts/check-terminology.mjs` はこの型を原理的に検出できない**
（「キーが英語に当たった」ものだけを対象にするため）。#40・#43・「辞書の抜けと検出経路」と同じく、
**`npm run validate` に検査を足して人を止める**。

### 経路① `npm run validate`（**exit 1**・生成物を正とする・**片方向**）

| 項目 | 内容 |
|---|---|
| 正 | コミット済みの `cards/<slug>/index.html`（日次cronが毎日再生成する） |
| 見るもの | 各ページの `<h2>効果（日本語）</h2><p class="cp-effect">…</p>` の中身 |
| 判定 | `term-hl` / `card-name-hl` の span の**内側を除いた**残りテキストに、`terms` の中核語（2文字以上）が**1つも現れないこと** |
| 失敗時 | **exit 1**。メッセージに「該当slugの先頭いくつか」と件数を出す |
| 成功時 | `card term highlights up to date — N ページ` の1行 |

**これが赤くなる原因**（＝止めたい事象）:

1. 照合規則の**回帰**（英語ゲートだけに戻す変更が入った）
2. ⭐ **`data/translations.js` に用語を足した／`data/tl/*.js` に訳を足したのに `build:cards` を回していない**
   （＝ `data/tl-*.json` の陳腐化検査（#22フェーズ2）と同型の穴が、カードページ側にも開いている）
3. ハイライト実装のデグレ

⚠️ **片方向にする。** 「用語解説に出ているのに訳文に中核語が無い」（型④・現状11件）では**落とさない**。
辞書に先回りで用語を入れておくのは正当な運用で、ここで落とすとそれが止まる（`meta.subtypes` 検査と同じ方針）。

#### ⚠️ 実装上の落とし穴（設計時に実測して踏んだもの）

- ⚠️ ⭐ **`grep 'term-hl">核'` で判定しない。** `subtype-hl` が内側に入ると**0件になる**（§2）。
  **タグを走査して `term-hl` の内側かどうかを文字単位で判定する**
- ⚠️ ⭐ **カード名（`card-name-hl`）の内側も除外する。** しないと「雪のフラクタル」「魂の装填」
  「メモライト・オベリス」などが**カード名由来で誤検出**される（リードが `bifurcating-fractal` で踏んだ罠と同型）
- ⚠️ **逐次 `readFileSync` は遅い。** この環境の実測で **2,495ファイル＝7.1秒**
  （`npm run validate` 全体が現状 **0.9秒**なので、そのままだと8倍以上になる）。
  ⭐ **`node:fs/promises` の `readFile` を並列8で回すと 1.8秒**（実測。並列16・32でも改善しない＝I/O律速）
- ⚠️ ⭐ **`n += await readFile(...)` と書かない。** `+=` は await の**前**に左辺を読むため、
  並列実行すると集計が壊れる（設計時に実際に踏み、読み取りバイト数が 16.2MB→2.0MB に化けた）

### 経路② `node scripts/check-terminology.mjs`（**報告のみ**・exit code 不変）

型④（用語解説に出るのに訳文に中核語が無い）を一覧する既存の役割は**そのまま**。
⚠️ **赤くしない**（無害な11件で毎回止まると使われなくなる）。変更4のコメント修正のみ。

### この2経路で**まだ捕まらないもの**（正直に書く）

⚠️ **`terms` に**まったく**登録が無い新キーワード**は、どちらの経路でも捕まらない
（中核語が存在しないので訳文からも引けない）。これは #40 と同型の「気づけない辞書」の問題で、
**カウンター語については `check-terminology.mjs` が既に見ている**が、それ以外は依然として人の目に頼る。
→ 派生issueの候補（§8）。
