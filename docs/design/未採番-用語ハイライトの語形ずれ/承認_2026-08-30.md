（`bug` / `着手可` / `小タスク`）。

- ⚠️ ⭐ **これは「あったら良い」ではない。検査自身が静かに無効化される穴**であり、
  本タスクが D3 で作った検出経路の**存在意義に直接関わる**。
  検査が止めたい3事象（規則の回帰・`build:cards` 忘れ・実装デグレ）は、
  **テンプレートが変わった瞬間に全部まとめて緑になる**
- ⚠️ **テンプレート変更は「起きるかもしれない」ではなく「起きる予定がある」**。

## 7. ⭐ 今回の運用から得た知見（次に活かす）

| 知見 |
|---|
| ⭐ **「偶然一致する変種」を設計時に自分で見つけて書いておくと、検証が件数照合に堕ちない。** 設計書 §3-2 が「変種Eは155件で一致してしまう」と予告したことで、レビューは**弁別する合成入力**を自分で作った。⚠️ **予告が無ければ「155件一致＝合格」で終わっていた** |
| ⭐ **検出経路を作るタスクでは、「その検査が拾えないもの」を設計書に必ず書く。** §5-3（140枚中139枚・`shadowstrike` は不可視）を書いたおかげで、**V6 が独立の検証項目として残り**、実装もレビューもそこを個別に確認した |
| ⚠️ ⭐ **検出経路そのものの堅牢性は、設計時には見落とした**（S-1）。⭐ **「この検査は何を入力にしているか」「その入力は誰が壊しうるか」を1問だけ自問する**——今回の入力は**生成済みHTMLの字面**で、**テンプレートを触る人が壊せる**。⚠️ 他の検査（`meta.subtypes` は JSON、cron列挙は `git add` 行）と違い、**この検査だけが壊れやすい入力を持っていた** |
| ⚠️ ⭐ **影響範囲の表に「変わらない」と書くときは、数えてから書く。** §8 の誤りは **`grep -rln 'card-detail.js'` を1回打てば防げた**。⭐ **「トップとデッキ構築の2面」という言い回しは、このリポジトリでは何度も出てくる定型句で、疑わずに書き写しやすい**（実際はモーダルを出す画面は**3面**） |
| ⭐ **実装担当の「規則の二重定義を1つ減らす」判断（L1）は歓迎してよい。** ⚠️ 設計書に無い変更だが、**設計の趣旨（中核語が2つの役割を持つ）から演繹できる**もので、報告に根拠が書かれていた。⭐ **逸脱の是非は「設計書に書いてあるか」ではなく「設計の趣旨から導けるか＋報告されているか」で判断する** |
