## 1. 背景と目的

日次cron `build-tournaments` の最終ステップ（IndexNow通知・#38）が失敗し続けている。

⚠️ **これは新しい障害ではない。** 原因は #38 で 2026-07-30 から追跡中の既知事象で、
本命の仮説（`pages.dev` の構造的制約）の検証は **#28（独自ドメイン移行）の費用判断待ち**。
**本issueは原因を直すものではなく、cronの信号を回復させるためのもの。**

### 1-1. 実害はない（確認済み）

失敗するのは**pushの後段のステップだけ**で、大会データ取り込み・カード/セットページ生成・
索引再生成・commit/push は**全回成功**している。実害は「更新の即時通知が飛ばない」だけで、
Bing側の発見経路は**受理済みのサイトマップ（2.7K検出）による自律クロール**が生きている。

### 1-2. 直す理由: cronの赤/緑が診断能力を失った

⭐ **これが本issueの目的。** 直近12回（2026-07-30〜08-10）を全数調査した結果:

| 通知対象URL | 結果 | 回数 |
|---|---|---|
| **0件**（APIを呼んでいない） | 🟢 success | 5 |
| **1件以上** | 🔴 403 | 7 |

- 🟢 は「成功」ではなく「**送るものが無かった日**」。`data/tournaments/index.json` の
  `scan.maxId` しか動かない日は写像対象0件でAPIを呼ばず、そのまま緑になる
- ⭐ **IndexNow は導入以来一度も通知に成功していない。** 断続的な障害ではなく、
  **送るものがある日は100%失敗**する（2026-07-29〜08-10 で **88 URL** が未通知）
- ⚠️ **別のステップで本当の障害が起きても、実行一覧の見た目は今と同じ赤**になる。
  開いて中を読むまで区別が付かない＝**アラート疲れ**

### 1-3. 「赤のまま維持する」判断の前提が失効した

2026-07-30 にユーザー判断で「赤のまま維持する」と決めた。その根拠は #38 のコメントに残っている:

> 解除の見込み: BWTの所有権確認をBing独自の方法（XMLファイル）に切り替えることで解消する見込み。
> **それまでの数日は許容する**

- その切り替えは実施され、**候補①として否定された**（2026-07-31）
- 候補②（キーファイルの末尾改行）も否定された（2026-08-02）
- 残る候補③は **#28 の費用判断待ちで見込みが立たない**

→ **「数日」という前提が12日経って失効した**ため、判断を見直す。

## 2. 事実確認（2026-08-11 実測）

### 2-1. IndexNow APIの応答（本日、本番のホスト・キーで実測）

| 送ったもの | HTTP | `errorCode` |
|---|---|---|
| **正しいキー**（現行の本番設定そのまま） | **403** | **`UserForbiddedToAccessSite`** |
| 誤ったキー（1文字変更・その名のキーファイルは存在しない） | **202** | （本文なし） |
| URLが `host` に属さない（`https://example.com/`） | **422** | `InvalidRequestParameters` |

- POST（`api.indexnow.org`）・POST（`www.bing.com/indexnow`）・GET の3経路のうち、
  **POSTはどちらも403**、**GETは202**（＝キー検証が保留のまま受理）
- サイト側の前提はすべて正常: キーファイル **200**・`text/plain`・**32バイト**（末尾改行なし）・内容一致、
  `BingSiteAuth.xml` **200**、`robots.txt` は全許可、**bingbot UAでも両ファイル200**

### 2-2. ⚠️ #38 設計書の前提が2つ誤っていた

⭐ **本設計で最も重要な発見。** 案Bの安全性の根拠がここにある。

| #38 設計書の記述 | 実測 | 影響 |
|---|---|---|
| §2.3「**403** = key not valid（キーファイルが無い・中身が違う）」 | ❌ **誤り**。誤ったキーは **202** を返す | 403 は**サイトの認可**の問題であって、**キーの誤りの信号ではない** |
| §5 リスク表「キーファイルを消してしまう → 403 → **jobが赤くなって気づける**」 | ❌ **成り立たない** | **キーファイルが壊れても誰も気づけない**（現状も同じ） |
| §4「V10: 誤ったキーで送ると403になり exit 1 する」 | ❌ **再現不能**（202が返る） | この検証項目は現状では実行できない |

⭐ **したがって、403 を警告扱いにしても「キーの誤りの検出」は失われない**
——**もともと403では検出できていなかった**ため。案Bは既存の安全性を1つも削らない。

⚠️ **確度について正直に**: 上の「誤ったキー → 202」は、**サイトが認可されていない現状での測定**である。
健全なサイトで同じ挙動になるかは**確かめようがない**（我々は健全な状態を持っていない）。
断定できるのは「**現状の観測では403とキーの誤りが対応していない**」までで、
だからこそ §5-1 の抑制条件を狭く絞り、§5-2 の自前検査を足す。

## 5. 仕様

### 5-1. 既知403の警告化（案B本体）

`scripts/indexnow-submit.mjs` の応答分岐に、**429の直後**（400/403/422のまとめ処理より前）へ
1分岐を足す。

#### 抑制の条件 — ⚠️ **3つすべてを満たすときだけ**

| # | 条件 | 理由 |
|---|---|---|
| 1 | `res.status === 403` | |
| 2 | 応答本文がJSONとして解釈でき、`errorCode === "UserForbiddedToAccessSite"` | 他の403（将来の別要因）は握り潰さない |
| 3 | ⭐ **`HOST` が `.pages.dev` で終わる** | **独自ドメインへ移った瞬間に抑制が自動で解除される** |

- ⚠️ **1つでも満たさなければ、現行どおり `console.error` ＋ `process.exit(1)`**
- ⚠️ **本文がJSONとして壊れている403は抑制しない**（`try`/`catch` で解釈に失敗したら exit 1）。
  「読めなかったから握り潰す」を作らない
- ⭐ **条件3の意図**: この抑制は「`*.pages.dev` にいる間だけの暫定措置」である。
  #28 で独自ドメインへ移ると `HOST` の定数が変わり、**誰も覚えていなくても抑制が消える**。
  そこで再び403が出れば、それは**新しい情報**なので赤くなるのが正しい

#### 挙動

- **残りのチャンクを送らずに `return`**（＝ exit 0）。429と同じ扱い。
  ホストが認可されていない以上、後続のチャンクも同じ403になるため
- 送れなかったURLの件数を**必ず出す**（赤を消す代わりに、失った可視性をログで補う）

#### 出力（画面に出る最終形）

```
[1/1] ⚠ 403 UserForbiddedToAccessSite — 既知の未解決事象のため警告に留めます（issue #38）
      通知できなかったURL: 3 件（残り 0 リクエストを中止しました）
      ⚠ この抑制は host が *.pages.dev のときだけです。独自ドメイン(#28)へ移ると自動で解除されます
```

- 1行目の `[i/n]` は既存のラベルの形をそのまま使う
- ⚠️ **`console.warn` で出す**（`console.error` は使わない。Actionsのログで赤く見えるため）
- 「通知できなかったURL」は**残り全チャンクの合計**（当該チャンク以降の `part.length` の和）

### 5-2. キーファイルの自己検査（案Bに付随して必要と判断した追加）

⚠️ **これは案Bの依頼範囲を超える追加である。** 入れる理由を明記する:

§2-2 のとおり、**キーファイルが壊れても IndexNow の応答では検出できない**（202が返る）。
案Bで403が緑になると、このステップは**恒久的に緑**になり、
**キーファイルの健全性を見張るものが1つも無くなる**。#28 で独自ドメインへ移る日に、
キーファイルが壊れていることに初めて気づく事態を避けたい。

**IndexNowの応答に頼らず、自分で検査する**（1リクエストで済み、判定は完全に決定的）。

| 項目 | 仕様 |
|---|---|
| 実行タイミング | 送信の**直前**（`urls.length > 0` かつ `--dry-run` でないときだけ） |
| 取得先 | **`${KEY_FILE_URL}?cb=${Date.now()}`**（⚠️ **第2版で変更**。理由と正確な仕様は下の「#### 取得先とキャッシュ回避（第2版で変更）」） |
| ✅ 合格 | HTTP 200 かつ **本文を trim した文字列が `KEY` と完全一致** |
| ❌ 不合格 | 上記以外（404・本文不一致など）→ `console.error` ＋ **exit 1**。⭐ **送信はしない** |
| ⚠️ 判定不能 | fetch が例外（ネットワーク断など）→ **警告のみで送信へ進む**（1回だけ再試行する） |

- ⭐ **「壊れていることを証明できた」と「確かめられなかった」を区別する。**
  ネットワークの一時障害で赤くしない（false red を作らない）
- ⚠️ **`INDEXNOW_ENDPOINT` で差し替えているときは検査を飛ばす**。
  ダミーサーバーへ向けた検証中に本番のキーファイルを見に行っても意味がなく、
  オフラインでの検証を壊すため
- 出力（合格時）は**1行だけ**。冗長にしない:

  ```
  キーファイル: ✅ 200・内容一致（https://ga-card-tools-jp.pages.dev/c226706b28954362938a0297d5bc2b43.txt）
  ```

  不合格時:

  ```
  ❌ キーファイルが不正です（HTTP 404）— https://…/c226706b28954362938a0297d5bc2b43.txt
     IndexNowはキーの誤りを 202 で受理してしまうため、送信前にここで止めます（設計 §2-2）
  ```

#### 取得先とキャッシュ回避（⚠️ 第2版で変更）

**変更の理由**（レビュー担当の指摘・2026-08-12）:
初版は取得先を `${ORIGIN}/${KEY}.txt`（素のURL）と書いていた。しかし CLAUDE.md に記録のとおり
**Cloudflare Pages は削除したファイルの素のURLを最大7日間200で返し得る**（#10 の実測）ため、
**キーファイルを削除した当日は「200＋旧内容」で合格してしまう**。
§5-2 は「キーファイルが壊れたことに気づく唯一の経路」として足したものなので、
**その経路に7日の盲点があるのは設計の欠陥**と判断し、キャッシュ回避クエリを付ける。

**実装の形**（3点セット。⚠️ **①と②を取り違えると本番の通知が壊れる**）:

| # | 箇所 | 値 |
|---|---|---|
| ① | **定数を1つ作る**（`KEY` / `ORIGIN` の定義の直後） | `const KEY_FILE_URL = \`${ORIGIN}/${KEY}.txt\`;` |
| ② | `post()` の送信ペイロード `keyLocation` | **`KEY_FILE_URL` をそのまま**。⚠️ **クエリを付けない**（IndexNowに渡すのは実URL） |
| ③ | `verifyKeyFile()` の fetch 先 | **`${KEY_FILE_URL}?cb=${Date.now()}`** |

- ⭐ ①は推奨指摘 S1（同じURLが2箇所で別々に組み立てられている）への対処でもある。
  第2版では②と③で**値が意図的に異なる**ため、**定数を共有したうえで③だけクエリを足す**形にすると、
  「片方にだけクエリが付く」ことがコード上で1箇所に見える
- ⚠️ **ログに出すURLはクエリ**なし**（`KEY_FILE_URL`）のまま**にする。合格時・不合格時とも
  §5-2 の出力例の文言を変えない（毎回変わる値をログに出さない）
- ⚠️ 判定不能（fetch例外）時の再試行でも**クエリは毎回付け直す**（`Date.now()` を再評価する）

**裏取り**（2026-08-12・設計担当が本番で実測。推測ではない）:

| 測定 | 結果 |
|---|---|
| `https://ga-card-tools-jp.pages.dev/<KEY>.txt?cb=<epoch>` | **200**・**32バイト**・素のURLと**内容一致**（`cmp` で同一）→ クエリを付けても検査は通る |
| 存在しないキー `…/000…0.txt?cb=<epoch>` | **404** → 不合格判定が機能する |
| キーファイルの応答ヘッダ（素・クエリ付きとも） | `cache-control: public, max-age=0, must-revalidate`・**`cf-cache-status` は付かない** |

- ⚠️ **3行目は「7日キャッシュされない」ことの証明ではない**（削除して観測したわけではないため）。
  CLAUDE.md #10 の実測（削除後8分間200・`cf-cache-status: HIT`）と食い違って見えるが、
  **測ったのはヘッダだけ**なので本設計では**判断の根拠にしない**。
  ⭐ キャッシュ回避クエリは**追加コスト0（同じ1リクエスト）で盲点を潰せる**ため、
  どちらが正しくても**付けるほうが安全**という理由で採用する
- 📌 このヘッダの食い違いは **#10 の記録の再検証**という別論点。⚠️ **本issueでは追わない**
  （必要なら設計担当が別issueを起票する）

| # | 手順 | 期待値 |
|---|---|---|
| A-1 | 本番設定のまま実行（`node scripts/indexnow-submit.mjs <直近cronコミット>~1 <同>`） | **exit 0**。ログに `⚠ 403 UserForbiddedToAccessSite — 既知の未解決事象のため警告に留めます（issue #38）` と `通知できなかったURL: N 件` と `⚠ この抑制は host が *.pages.dev のときだけです…` の3行。⚠️ **`❌` で始まる行が無い**こと |
| A-2 | ダミーサーバーが `403` ＋ `{"errorCode":"SomethingElse"}` を返す | **exit 1**（`❌ HTTP 403 …`）。⚠️ **errorCodeが違えば抑制しない** |
| A-3 | ダミーサーバーが `403` ＋ **JSONでない本文**（例 `Forbidden`）を返す | **exit 1**。⚠️ **解釈できない本文を握り潰さない** |
| A-4 | ダミーサーバーが `403` ＋ 正しいerrorCode を返し、**`HOST` を `example.com` に差し替える** | **exit 1**。⚠️ **`.pages.dev` 以外では抑制が効かない**（自動解除の確認）。⭐ `HOST` は定数なので、検証は**一時的に書き換えて実行し、必ず元に戻す**（コミットしない） |
| A-5 | ダミーサーバーが `422` ＋ `InvalidRequestParameters` を返す | **exit 1**（従来どおり） |
| A-6 | ダミーサーバーが `429` を返す | **exit 0**・従来の `⚠ 429 Too Many Requests…` の文言が変わっていない（回帰） |
| A-7 | ダミーサーバーが `200` を返す | **exit 0**・従来の `✅ 200 受理されました（N URL）` が出る（回帰） |

⚠️ **A-2〜A-7 は複数チャンクでも試すこと**（`INDEXNOW_CHUNK_SIZE=1` と合成URL3件）。
A-1相当の抑制で **2チャンク目以降が送られないこと**と、`通知できなかったURL` が**残り全部の合計**になることを確認する。

### B. キーファイルの自己検査（§5-2）

| # | 手順 | 期待値 |
|---|---|---|
| B-1 | 本番設定のまま A-1 を実行 | 送信の**前**に `キーファイル: ✅ 200・内容一致（https://…/c226706b28954362938a0297d5bc2b43.txt）` が1行出る |
| B-2 | `INDEXNOW_KEY` に存在しないキー（`000…0`）を渡す | `❌ キーファイルが不正です（HTTP 404）— …` ＋ 2行目の説明が出て **exit 1**。⚠️ **IndexNow APIへの fetch が0件**であること — ⭐ **確認方法は「全fetchのURLを記録する保険を被せて数える」**（`node --import` 等）。⚠️ **ダミーサーバーのアクセスログでは観測できない**（下の注記） |
| B-3 | キーファイルは200だが**中身が違う**状況を作る（例: `INDEXNOW_KEY=robots` ＝ `/robots.txt` は200だが中身がキーと異なる。⚠️ **本番のキーファイルは壊さない**） | `❌ キーファイルが不正です（内容不一致）— https://…/robots.txt` で **exit 1**・送信なし |
| B-4 | `INDEXNOW_ENDPOINT` を差し替えて実行 | ⚠️ **キーファイル検査は実行されない**（`キーファイル:` 行が1回も出ない。オフラインで検証できる） |
| B-5 | `--dry-run` で実行 | 検査は**実行されない**・送信もしない（fetch **0件**・従来どおりURL一覧だけ） |
| B-6 | キーファイルの取得**だけ**が例外になる状況を作る（fail-open の確認） | `⚠ キーファイルを確認できませんでした（…）。1回だけ再試行します` → `⚠ キーファイルの健全性を判定できませんでした（…）。送信へ進みます` の順に出て、**送信へ進む**（exit 1 にしない）。⭐ 「壊れている」と「確かめられなかった」が分岐していること |
| **B-7**（第2版） | 本番設定のまま実行し、**キーファイル取得のURLを記録する** | ⭐ 取得したURLが **`https://ga-card-tools-jp.pages.dev/c226706b28954362938a0297d5bc2b43.txt?cb=<数字>`**（`?cb=` を含む）であること。⚠️ **ログの表示はクエリなしの `…c226706b….txt`** で、B-1 の文言が**変わっていない**こと |
| **B-8**（第2版） | ダミーサーバーに `200` を返させ（A-7 と同じ構成）、**受信した JSON ボディの `keyLocation` を確認する** | ⭐ `"keyLocation": "https://ga-card-tools-jp.pages.dev/c226706b28954362938a0297d5bc2b43.txt"` — ⚠️ **クエリが付いていないこと**。付いていたら**本番の通知が壊れる**ので不合格 |

⚠️ **B-2 の期待値は第2版で書き直した**（初版の「ダミーサーバーのアクセスログが0件」は**原理的に観測できない**）。
ダミーサーバーを使うには `INDEXNOW_ENDPOINT` が必要だが、そのとき §5-2 は**検査そのものを飛ばす**（B-4）ため、
「ダミーサーバー＋キーファイル検査」は**同時に成立しない**。⭐ **確認するのは「送信先のログ」ではなく「fetchが起きたかどうか」**。
（初版の手順のまま実施できなかった件は、開発担当・レビュー担当の双方から同じ指摘を受けている）

### C. 回帰・cron

| # | 手順 | 期待値 |
|---|---|---|
| C-1 | 差分0件の範囲で実行 | `通知対象がありません（送信しません）` で **exit 0**。⚠️ **キーファイル検査も走らない**（送るものが無いため） |
| C-2 | `--dry-run` で直近cronコミットの差分 | 従来どおりURL一覧が昇順で出る（#38 V1・V7 の回帰） |
| C-3 | `node --test` 等で `fileToUrl` / `filesToUrls` / `chunk` を import | **写像とチャンク分割の挙動が変わっていない**（#38 V2〜V4 の回帰） |
| C-4 | **翌朝のcron** | ⭐ **jobが緑**になる。実行ページに**黄色の警告注釈** `IndexNow未通知` が出る。IndexNow以外のステップはすべて成功 |

⚠️ **C-4 は翌朝まで結果が出ない。** それ以外の項目で合否を出し、**C-4だけ「翌朝確認」として報告に残す**こと
（レビュー担当も同じ扱いでよい）。

⚠️ **初版の「cronは 21:15 UTC 前後」は誤りだった**（第2版で訂正。開発担当・レビュー担当が独立に実測）:

| | 値 |
|---|---|
| スケジュール定義 | `cron: "0 18 * * *"`（＝**18:00 UTC** / 03:00 JST） |
| 直近8回の実際の開始時刻 | **18:27 / 18:30 / 18:45 / 18:47 / 18:53 / 19:20 / 19:22 UTC**、および外れ値 **23:52 UTC**（2026-08-06） |

- ⚠️ **Actions側の遅延は最大約6時間**の日がある。「18:20 UTC より後なら翌日」という言い方は**楽観的すぎる**
- ⭐ **確実にその日のcronに載せたいなら 18:00 UTC より前にpushする**、が安全な言い方
- ⚠️ **未pushのコミットは cron に載らない。** C-4 を判定できるのは **push後の最初のcron**である
  （#38 で「次のcronが判定」と書いて2回踏んでいる。**push済みかどうかを必ず先に確認する**）

## 8. やらないこと（今回のスコープ外）

- **IndexNowの403そのものを解決すること** — #38 の本題で、**#28（独自ドメイン）の判断待ち**。本issueは信号の回復だけ
- **ワークフローに `continue-on-error` を付けること** — #38 §2.3 の判断を維持する（他のエラーは赤にする）
- **通知ステップを停止すること**（案C） — 不採用
- **未通知URLの再送キュー** — 403が解けた日にまとめて送る仕組み。⚠️ **作らない**。
  Bing側はサイトマップ（2.7K検出）で自律クロールしており、
  403が解けた時点で**その後の更新だけ通知すれば足りる**（過去分の一括送信は #38 §「やらないこと」で
  429リスクを理由に既に不採用と決めている）
- **`npm run dashboard` の運用ヘルスに「IndexNow未通知」を出すこと** — 検出経路としては筋が良いが、
  ダッシュボードはローカル専用でcronの監視には使えない。⭐ **#61 でダッシュボードを触るときの候補として記録するに留める**
- **`data/tournaments/index.json` の `scan.maxId` しか動かない日にコミットを作らないようにすること** —
  §1-2 の「0件の日が緑になる」の根本だが、cronの自動コミットの仕様変更は影響範囲が広い（#30）
