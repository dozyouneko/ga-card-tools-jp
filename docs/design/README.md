# docs/design/ の構成

設計成果物は**対処内容(タスク)ごとのサブフォルダ**で管理する。

```text
docs/design/
├── <issue番号>-<タスク名>/   ← タスクごとの設計書・モック
│   ├── ○○_設計.md            (改版履歴表つき。実装済み/実装待ちを明記)
│   └── ○○_モック.html        (必要な場合のみ。自己完結HTML)
└── リリース確認/              ← リリース時の確認資料(日付プレフィックスつき)
    └── YYYY-MM-DD_○○.md
```

### `リリース確認/` の使い方

- **本番配信物をpushする前**に、ロールバック手順書を作って**別ワークツリーで実際に戻せることを検証**しておく(`2026-07-26_#22フェーズ2_...` / `..._#31...` が雛形)
- **実行しなかった場合も「ロールバックは不要でした」と追記して残す**(次回の雛形になる)

## 運用メモ

- 設計はVSCode拡張側セッション、実装はターミナル側セッションが担当(詳細はリポジトリ直下のCLAUDE.md)
- `docs/` 配下は本番配信対象外(`functions/docs/[[path]].js` が全パス404を返す)。
  そのため **`docs/` だけの変更はpush承認が不要**(2026-07-23〜)。⚠️ ただし**pushは未push分を全部送る**ので、
  実行前に `git diff --stat origin/main..HEAD -- . ':(exclude)docs/*'` が**空**であることを必ず確認する
- `tmp/` はgitignoreのため設計成果物を置かない
- 設計書には**改版履歴表**を付け、実装済み/実装待ちを明記する。完了時は「完了」の行を追記して締める
- ⚠️ **小さすぎるタスクに設計書は起こさない**。コメント修正・デッドコード削除のような数行の変更は
  **issueコメントを受け渡し仕様とする**(例: #32・#33)。設計判断がコメントに収まるかが線引き
