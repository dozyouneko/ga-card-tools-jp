# docs/design/ の構成

設計成果物は**対処内容(タスク)ごとのサブフォルダ**で管理する。

```text
docs/design/
├── <issue番号>-<タスク名>/   ← タスクごとの設計書・モック
│   ├── ○○_設計.md            (改版履歴表つき。実装済み/実装待ちを明記)
│   └── ○○_モック.html        (必要な場合のみ。自己完結HTML)
└── リリース確認/              ← リリース時の確認資料(日付プレフィックスつき)
    └── YYYY-MM-DD_○○.md
```

### `リリース確認/` の使い方

- **本番配信物をpushする前**に、ロールバック手順書を作って**別ワークツリーで実際に戻せることを検証**しておく(`2026-07-26_#22フェーズ2_...` / `..._#31...` が雛形)
- **実行しなかった場合も「ロールバックは不要でした」と追記して残す**(次回の雛形になる)

  実行前に `git diff --stat origin/main..HEAD -- . ':(exclude)docs/*'` が**空**であることを必ず確認する
- `tmp/` はgitignoreのため設計成果物を置かない
- 設計書には**改版履歴表**を付け、実装済み/実装待ちを明記する。完了時は「完了」の行を追記して締める
- ⚠️ **小さすぎるタスクに設計書は起こさない**。コメント修正・デッドコード削除のような数行の変更は
  **issueコメントを受け渡し仕様とする**(例: #32・#33・#40・#41)。設計判断がコメントに収まるかが線引き
  - ⚠️⚠️ **「issueに書いた」と「仕様になっている」は別**。起票時に書くのは*診断*(症状・原因・対処の候補)で、
    そこには**裏を取っていない推測が混ざる**(実例: #40 の起票コメントに書いた「cronが赤くなる懸念」は、
    調べたら cron が `validate` を実行しないので**成立しなかった**)。
    渡す前に**推測を全部つぶして仕様に書き換える**こと
  - 渡す仕様に必ず入れる: **変更箇所(file:line)** / **その値にした根拠(実測)** / **影響範囲の実数** /
    **変更しないものの明示** / **検証項目** / **pushの扱い**
  - ⭐ **「心配しなくてよいと確認できた点」を表で書く**。開発担当が同じ不安を再調査する時間が消える
    (#40 では 共有URL・カードページのパンくず・`gen-tl-json.mjs` の要否 の3つ)
  - ⭐ 検証項目には **「入れた検査が本当に落ちるか」**を入れる(#40 の V2/V3 = わざと壊して
    `validate` が exit 1・`build:cards` が exit 0 で完走することを確認した)
