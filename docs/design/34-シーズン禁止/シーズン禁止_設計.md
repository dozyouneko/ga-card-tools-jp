## 目的

公式が導入した **Seasonal Banlist**（1シーズン限りの一時的な禁止）を当サイトで扱えるようにする。当面の最重要目的は2つ:

1. **2026-08-21 以降、デッキ構築ツールが誤情報を出さないようにする**（現状は季節禁止カード入りのスタンダードデッキを「適合」と表示してしまう）
2. **発効前から「8/21でシーズン禁止になる」ことを利用者に見せる**（初心者が知らずにデッキを組むのを防ぐ・ユーザー必須要件）

## 前提（調査で確定・2026-07-27）

### 公式仕様

| 項目 | 内容 |
|---|---|
| 性質 | 恒久禁止（B&R）の**置き換えではない補助的リスト**。混同してはいけない |
| 期間 | ちょうど1シーズン（メインセット発売〜次のメインセット発売）で**自動解除** |
| 連続禁止 | 同じカードが2シーズン連続で載ることはない |
| 規模 | 初回3枚。**0枚のシーズンもあり得る** |
| 期中変更 | シーズン途中の追加あり。シーズン終了で失効 |
| 告知 | 各メインセット発売の**1週間前** |
| 適用フォーマット | **Standard Constructed**（ユーザー判断で確定） |
| 初回 | PRDシーズン／`baleful-oblation`・`fabled-azurite-fatestone`・`spirit-blade-ascension`／**発効 2026-08-21** |

### 公式APIは季節禁止を持っていない（実測）

- 対象3枚とも `GET /cards/<slug>` の **`legality` が `null`**
- `/formats`・`/banlist`・`/legality` は**すべて404**
- 既存 `legality` は `{"STANDARD":{"limit":0}}` 形式で **STANDARD / DRAFT / PANTHEON の3種のみ**（limit0: 122 / 44 / 64枚）
- ⚠️ `legality_format` に**未知の値を渡すとエラーではなく全2,240枚が返る**。フォーマット名を推測で先回りしてはいけない
- 一方、**恒久禁止はAPIに反映されている**（公式トーナメントルールのStandard禁止10枚のうち**9枚**が `STANDARD limit0`。`Baby Gray Slime` のみ `legality: {}` で未反映）
  → APIは禁止情報を追随する仕組みを持っているので、**将来 季節禁止も載る可能性はある**。ただし時期も形式も不明

→ **自前データを持つ以外に手段が無い。**

| PTM（5prefix） | 2025-12-05 | 2025-11-24 | **11日前** |

## データ設計

### `data/seasonal-banlist.json`（新規・コミットする）

```json
{
  "seasons": [
    {
      "id": "PRD",
      "name": ".asphodel/paradise",
      "nameJp": "PRDシーズン",
      "format": "STANDARD",
      "announcedAt": "2026-07-25",
      "effectiveFrom": "2026-08-21",
      "effectiveTo": null,
      "sourceUrl": "https://www.gatcg.com/article/introducing-seasonal-banlists",
      "slugs": ["baleful-oblation", "fabled-azurite-fatestone", "spirit-blade-ascension"]
    }
  ]
}
```

| フィールド | 意味 |
|---|---|
| `effectiveFrom` | 発効日（**この日から禁止**）。JSTの暦日 |
| `effectiveTo` | 終了日（**この日まで禁止**）。**次のメインセット発売日が未確定の間は `null`** |
| `format` | 適用フォーマット。当面は `STANDARD` 固定だが、将来 他フォーマットに広がっても持てるようにする |
| `slugs` | 対象カードのslug。**0件の配列も正常**（0枚のシーズンがあり得る） |

- **配列で履歴を持つ**（過去シーズンを消さない）。過去シーズンは `effectiveTo` を過ぎているので自動的に表示されなくなる
- シーズン更新時の作業は**このファイルに1ブロック追記し、前シーズンの `effectiveTo` を埋めるだけ**

⚠️ `effectiveTo: null` の扱い: **「終了日未定＝まだ有効」** と解釈する。次シーズンの告知（発売1週間前）で前シーズンの `effectiveTo` を埋める運用。

### ⚠️ 運用リスク: `effectiveTo` の埋め忘れ（実装レビューで追記・2026-07-27）

**埋め忘れるとそのシーズンの禁止が永久に残る**（設計担当の実測: `effectiveTo: null` のまま 2027-06-01 でも `active`）。

通常は「次シーズンの新ブロックを追記する際に前シーズンの `effectiveTo` を埋める」1操作で拾えるが、
⚠️ **次シーズンの禁止が0枚だった場合、追記するブロックが無いため更新の機会そのものが来ない**。
公式は「0枚のシーズンもあり得る」と明言している。

- **失敗の向きとしては安全側**である。古い禁止が残る＝「使えるカードを使えないと表示する」であり、
  逆方向（禁止を見落として使えると表示する）は**大会での失格**につながる。
  → **`null` を「まだ有効」と解釈する現在の設計は正しい**。fail-open にしてはいけない唯一の箇所
- 対策はコードではなく**運用**で行う: **次のメインセットの発売日が判明した時点で
  `effectiveTo`（＝発売日の前日）を埋める**。禁止0枚のシーズンでも必ず作業が発生するようにする。
  この運用メモは CLAUDE.md にも記載する

## 判定ロジック

### 置き場所: `shared/js/card-i18n.js`

このファイルは**ブラウザとビルドの両方から使われる**（`build-card-pages.mjs` が `CI.` として利用）。**1つの実装で5面すべてを賄える**ため、ここに追加する。

```js
// 追加する公開API（イメージ）
function setSeasonalBanlist(data)      // 読み込んだJSONを保持する
function seasonalBanState(card, today) // → null | { state, season }
```

`state` は3値:

| state | 条件 | 意味 |
|---|---|---|
| `"announced"` | `today < effectiveFrom` | **予告**（まだ使える） |
| `"active"` | `effectiveFrom <= today` かつ（`effectiveTo` が `null` または `today <= effectiveTo`） | **禁止中** |
| （null を返す） | `effectiveTo` を過ぎている / 対象外カード | 表示なし（自動失効） |

### ⚠️ 日付は「JSTの暦日」を文字列比較する

`new Date()` はブラウザのローカルタイムゾーン、CIはUTCで動くため、**素直に書くと環境で境界がずれる**（CIは 03:00 JST = 前日18:00 UTC に動く）。

```js
// YYYY-MM-DD をJSTで得る。以降は文字列比較のみで判定する（Dateのパースを挟まない）
const todayJst = () => new Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Tokyo" }).format(new Date());
```

- `"2026-08-20" < "2026-08-21"` のような**辞書順比較**で判定する。タイムゾーン・夏時間・パース差異の影響を受けない
- ブラウザ・ビルドの**両方でこの1つの関数を使う**

### データの読み込み経路

| 面 | 経路 |
|---|---|
| S1・S2・S4（ブラウザ） | `data/seasonal-banlist.json` を **fetch**。`card-search.js` の `metaIndex()`（[card-search.js:381-390](../../../shared/js/card-search.js#L381)）と同じ「Promiseを保持して再利用」方式 |
| S3（ビルド） | `build-card-pages.mjs` が `readFileSync` で直接読む |

⚠️ **描画とのレースを作らないこと。** 予告バッジが「たまに出ない」状態は要件を満たさない。
検索結果を描画する前に**このPromiseを `await` する**（300バイト程度のローカルJSONなので待ち時間は無視できる）。
`translationsReady()` のような「準備できるまで出さない」方式は**採らない**。

## やらないこと（記録）

| 項目 | 理由 |
|---|---|
| 検索の「シーズン禁止」絞り込み | フォーマット絞り込みはサーバー側 `legality_format` で処理しており自前データを送れない。クライアント側で間引くと [#27](https://github.com/dozyouneko/ga-card-tools-jp/issues/27) と同じ「件数が概算・該当が埋もれる」問題が再発する。対象3枚では利用場面も乏しい |
| メタ索引（`data/card-meta-index.json`）への季節禁止の追加 | 上記の絞り込みをやらないため不要 |
| 公式APIが季節禁止に対応した場合の移行 | 形式が不明。載ったときに再検討する（検知手段は下記） |
| `Baby Gray Slime` のAPI未反映（恒久禁止なのに `legality: {}`） | 本issueの範囲外。別途 issue 化を検討 |

### APIが季節禁止に対応したことに気づく手段（追加コードなし）

`data/card-meta-index.json` は **cronが毎日再生成してコミットする**（#29）。対象3枚は索引に収録済みで、`bannedFormats` 相当の値を持つ。
→ **公式APIがこの3枚を `STANDARD limit0` にした日、索引の日次コミットに差分が出る**。
つまり**既存の仕組みでそのまま検知できる**ため、専用の監視は作らない。差分に気づいたら本設計を畳む検討に入る。

## ロールバック手順

| 事象 | 手順 |
|---|---|
| 表示が壊れた／誤った情報を出した | **`data/seasonal-banlist.json` の `seasons` を `[]` にして push**。判定は全カードで `null` を返し、**季節禁止関連の表示・判定がすべて消える**（既存機能は無傷）。コード修正より速い |
| それでも問題がある | 該当コミットを `git revert` → カード個別ページは翌朝のcronで自動的に戻る（#30） |

⚠️ **開発担当は「`seasons: []` で全表示が消え、既存の恒久禁止表示が無傷であること」を実際に確認する**（検証6）。これがロールバック手順の実地検証を兼ねる。
