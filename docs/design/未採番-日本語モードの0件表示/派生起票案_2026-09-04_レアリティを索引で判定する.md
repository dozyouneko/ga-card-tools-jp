# 派生issueの起票案 — 索引がレアリティを判定できないため、確実に0件と分かる組み合わせでも「もっと見る」を3回押させる

⭐ **由来**: **ユーザーの指摘**（2026-09-04・[`日本語モードの0件表示`](日本語モードの0件表示_設計.md) の実物確認の場）。

> 「RDOPD 全141件の中にプロモであるカードはないんですよね？ ないのであれば『もっと見る』のボタンの表示もいらず、
> "検索条件に当てはまるカードはありません" のような文言を表示するべきです」

⚠️ ⭐ **これは案Y（自動追従）の蒸し返しではない。** → §5。

## 1. 症状

`/?q=の&set=RDOPD&rarity=6`（日本語で「の」＋エキスパンション RDOPD ＋レアリティ **プロモ**）:

| 画面 | タイル | もっと見る | 文言（⭐ **`5ebf817c` 適用後**） |
|---|---|---|---|
| 1 | 0 | **表示** | 候補 141 件のうち **40** 件を確認しましたが、絞り込み条件に合うカードはまだありません。… |
| 2 | 0 | **表示** | 同・**80** 件 |
| 3 | 0 | **表示** | 同・**120** 件 |
| 4 | 0 | 非表示 | 日本語テキストには一致しましたが、絞り込み条件に合うカードはありませんでした（絞り込みを外すと表示できます）。 |

⚠️ **`5ebf817c` で「嘘の文言」は解消した**（G1）が、
⭐ **ユーザーの指摘は残った症状②のほう**——**答えが最初から確定しているのに3回押させる**。

⭐ **しかも `/cards/:slug` を 141 回叩いてから捨てている**（実測・[設計書 §3-1](日本語モードの0件表示_設計.md)）。
**押させるだけでなく、外部APIへの141リクエストが丸ごと無駄**である。

## 2. ⭐ ユーザーの前提の裏取り（**2つの独立な出所で確認・前提は正しい**）

⚠️ **起票前に実測した**（CLAUDE.md「起票案が主張する症状を必ず実測して再現させる」）。

### 2-1. スナップショット（`tmp/api-cache/cards-snapshot.json`・2026-08-31 取得・2,495枚）

| 項目 | 実測 |
|---|---|
| RDOPD のカード数 | **238**（版 258） |
| 版のレアリティ内訳 | コモン(1) **105** / アンコモン(2) **77** / レア(3) **49** / スーパーレア(4) **27** |
| ⭐ **プロモ(6)** | ⭐ **0件** |

### 2-2. 公式API（2026-09-04・**直接叩いて確認**）

```text
GET /cards/search?prefix=RDOPD&rarity=6&page=1&page_size=50
  → data: 0 / paginated_cards_count: 0 / total_cards: 0 / total_pages: 0
GET /cards/search?prefix=RDOPD&page=1&page_size=50
  → total_cards: 238   （⭐ §2-1 と一致）
GET /cards/search?prefix=RDOPD&rarity=4&page=1&page_size=50
  → 1件以上（⭐ 対照。「rarity を付けると常に0」ではない）
```

⭐ **ユーザーの前提は正しい。RDOPD にプロモは1枚も無い。**

- ⚠️ **「141」はセットの全数ではなく、`q=の` に日本語一致した候補数**である。
  **RDOPD の全数は 238**。⭐ **どちらであっても「プロモ0件」は変わらない**
- ⚠️ ⭐ **`page_size=1` で件数を読んではいけない**（2026-09-04 に実測して発見した罠）。
  `prefix=RDOPD&page_size=1` は **`total_cards: 1` / `total_pages: 1`** を返す（正しくは 238 / 48）。
  **`page_size>=5` では正しい値が返る。** → **§4 案C を検討するなら必ずここを踏まえる**

## 3. 原因 — ⭐ **索引がレアリティを「そのセット内の最小値」しか持っていない**

- JPモードは `data/card-meta-index.json` で**取得前に候補を絞る**（#27）。
  ⚠️ **索引が判定できない項目は絞れない**（`shared/js/card-search.js` の `isIndexBlind()`＝`MULTI` の第3要素が `null`）。
  ⭐ **現在該当するのはレアリティ 1つだけ**
- ⚠️ ⭐ **索引にレアリティが「無い」のではない。** `entry[7]` が
  **`entry[4]`（セットprefix）と同じ並びの「そのセット内の最小レアリティ」**を持っている（#43 の並び替え用）。
  ⚠️ **最小値では「プロモが存在しないこと」を判定できない**（RDOPD の最小は 1＝コモン）。
  だから `metaMatches()` は**レアリティを読み飛ばす**（コード中のコメントもそう明記している）

⭐ **結果、アプリは「その時点で0件だと知らない」ので `もっと見る` を出す。**
これは**実装の抜けではなく、索引の情報量が足りていない**という構造の問題である。

## 4. 実現の道（⚠️ **どれも未検証の案。設計時に必ず裏を取ること**）

### ⭐ 案A（本命）— 索引に**レアリティの完全な列挙**を持たせる

`entry[7]` を「そのセット内の**最小**レアリティ」から「そのセット内の**レアリティ集合**」に変える。

| 項目 | 2026-09-04 の実測 / 見積り |
|---|---|
| 索引のサイズ | **207,667 → 約 217,514 バイト（+9,847・+4.7%）**（⚠️ スナップショット2,495枚で試算。**設計時に実物で測り直すこと**） |
| セットprefixのスロット数 | **4,790**（2,516エントリ） |
| ⭐ **うちレアリティが2種以上のスロット** | ⭐ **119（2.5%）**。**1スロットの最大は 2種** |

⭐ **`entry[7]` の意味を変えるので、9要素目は増えない**——
CLAUDE.md の ⚠️ **「`m` のエントリに9要素目を足さないこと（`sortKeyOf()` が `entry.length < 8` で旧形式を判定する）」**に抵触しない。
（トップレベルの別キー（`f` と同じ形）にする案もある。⭐ **設計時に両方を比べて決める**）

⚠️ **同時に直すもの**（⭐ **どれも黙って通らない**）:

| 箇所 | 何が要るか |
|---|---|
| `scripts/gen-card-meta-index.mjs` の `metaOf()` | `Math.min(...)` → 集合。⚠️ **`prefixes` を先にソートしてから作る規約は維持**（並びが対応の根拠） |
| `shared/js/card-search.js` の `sortKeyOf()` | `entry[7]` から **`Math.min(...)` で最小を取り直す**（#43 の並び順を1ミリも変えない） |
| `shared/js/card-search.js` の `metaMatches()` | ⭐ **レアリティを読み飛ばすのをやめる**。⚠️ **判定規則は `rarityMatchesIn()` と同じにする**（OR＝`∃`／AND＝`∀r ∃e`。**意味統一の設計書 §4 の2段階評価**） |
| `scripts/validate.mjs` | ⚠️ **今の検査は `entry[7]` の要素が「1〜9の整数か null」であることを要求する**。⭐ **配列にした瞬間 exit 1 になる＝直し忘れが黙って通らない**（良い性質。**緩める方向に直さないこと**） |

### 案B（⚠️ **不採用の再確認**）— 自動追従（案Y）

⚠️ ⭐ **2026-09-04 にユーザーが明示的に見送った**（[設計書 §8](日本語モードの0件表示_設計.md)）。**蒸し返さない。** → §5。

### 案C（比較用）— 公式APIに**先に1回だけ**問い合わせて0件を知る

絞り込みだけの検索を1回投げ、`total_cards === 0` なら候補を引かずに終わる。

- ⭕ 索引を変えずに済む。⭐ **意味統一の設計書が「OR＝公式APIの `prefix`+`rarity` と完全一致」を全数427通りで実証済み**なので、判定は信用できる
- ⚠️ **APIリクエストが1回増える**（0件でない普通の検索でも毎回）。⚠️ **単発約1.8秒**
- ⚠️ **ANDモードでは使えない**（APIはANDに非対応）
- ⚠️ ⭐ **`page_size=1` で問い合わせると `total_cards` が嘘をつく**（→ §2-2）
- ⚠️ **英語モードの結果件数であって、日本語一致との積集合ではない**。
  ⭐ **0 なら 0 と言い切れる**（上位集合なので）が、**0 でないときは何も分からない**

## 7. ⚠️ 設計時に必ず確かめること（⭐ **推測のまま設計書に書かない**）

1. ⚠️ **索引サイズの実測**（§4 の +4.7% は**スナップショット試算**。**生成スクリプトを実際に走らせて測る**）
2. ⚠️ ⭐ **`rarity == null` の版の扱い。** 生成側は `e.rarity != null` で落としているが、
   実行時の `rarityMatchesIn()` は `String(e.rarity)`＝**`"null"` という文字列として集合に入る**。
   **両者が同じ判定になることを確かめる**
3. ⚠️ **スナップショット未収録のフリップ面22件**（索引は `/cards/:slug` で個別取得している）で
   レアリティが取れるか
4. ⚠️ ⭐ **ANDモードの規則が索引でも同じになるか。**
   `editionSetOf()`（エキスパンションで版の候補集合 E を作る）→ `rarityMatchesIn()`（E の中で判定）という
   **2段階評価**（意味統一 §4）を、**索引側でも同じ順序で再現する**。
   ⚠️ **項目ごとに独立に判定すると、427通り中351通り（82.2%）で英語モードと食い違う**——**同じ罠を踏み直さない**
5. ⚠️ **cron が止まっている間は索引の再生成が手動である。**
   実装時に `node scripts/gen-card-meta-index.mjs` を回して**生成物もコミットする**
6. ⭐ **索引の消費側はすべて fail-open という既存方針を維持する**（旧形式・未収録でも落ちない）。
   ⚠️ **`entry[7]` が数値のままの旧索引を読んだときに壊れないこと**を検証項目にする
