## 1. 背景と目的

現行は **ターミナルを2つ**使い分けている:

- `cc-design`（設計セッション）… ユーザーが要件を相談し、設計書を書かせる
- `cc-sprint`（スプリント進行役）… dev / review をサブエージェントとして交互に呼び、実装〜レビューを回す

これを **「ユーザーが会話するのはリードセッション1つだけ」** にまとめたい、というのが本構想。
リードが `design` / `dev` / `review` の3サブエージェントを直接呼び、
`設計 → 開発 → レビュー` のループを1つの窓口で回す。

```text
ユーザー ── リードセッション（唯一の窓口・進行と監視のみ）
                ├─ Agent(design)  … 設計書を作成       ─関所→ 実装待ち
                ├─ Agent(dev)     … 実装・コミット・報告 ─関所→ レビュー待ち
                ├─ Agent(review)  … 操作して合否判定    ─関所→ 設計確認待ち / 実装待ち
                └─ 最終承認はユーザー（push判断も同じ）
```

- ⭐ **サブエージェント同士は直接つながらない。** 成果物は必ずリードを経由する
- ⭐ **どの工程からでも、判断が要ればユーザーへ戻って停止する**（§6）

## 2. 実現性

**技術的には可能で、3工程のうち2つ（dev↔review）は `.claude/agents/sprint.md` に実装済み。**
追加で必要なのは「設計のサブエージェント化」と「窓口の一本化」の2点だけ。

## 3. 決まったこと

| # | 決定 | 理由 |

| D1 | `sprint.md` を拡張せず **`.claude/agents/lead.md` を新設**する。`.claude/aliases.sh` に `cc-lead` を追加し、既存の `cc-design` / `cc-sprint` は残す | sprint は「実装〜レビュー専用」という単機能が明確で、設計を混ぜると責務が濁る |

| D3 | 要件ヒアリングは**リードがユーザーと直接**行い、確定後に design へブリーフとして渡す。design にやらせるのは設計書の執筆（API調査・検証項目・モックHTML）だけ | サブエージェントは**呼び出し中に質問できず**、対話が「1往復＝1回の呼び出し」に分断されるため |
| D4 | ⭐ **関所（工程間のリードの承認）は「進行確認」まで。合否判定は review が行う**（§5） | リードが合否まで決めると**レビューの独立性が消え、リードが合格と思ったものを誰も再チェックしない** |
| D5 | ⭐ **最終承認はユーザーが行う。** design サブエージェントに承認させない | 起票者と承認者が同じになり、`設計確認待ち` に溜めて人が見るという安全弁が消える |

## 5. 関所でリードが見るもの（D4の内訳）

| リードが**確認する**（進行確認） | リードが**やらない** |
| --- | --- |
| 工程の記録が**実際に残ったか**（issueコメント・設計書・コミットハッシュ） | コードの**良し悪しを判定する**（review の仕事） |
| ラベルが次の工程へ**付け替わったか** | 自分で**実装する・修正する**（dev の仕事） |
| 指示した範囲から**はみ出していないか** | **仕様を決める**（ユーザーと design の仕事） |
| **ストップ条件に当たっていないか**（§6） | issueコメントを**代筆する** |

- できていなければ**肩代わりせず担当サブエージェントにやり直させる**
- ⚠️ リードが代筆すると、**次の周回でサブエージェントが読む前提が崩れる**
  （現行 `sprint.md` の規約と同じ）

## 6. ストップ条件（点線の経路）

リードは勝手に判断せず、状況をissueに残してから止まる。

| 条件 | リードの動き |
| --- | --- |
| push が必要になった | 停止。本番公開の可否は**常にユーザーの判断** |
| 仕様の判断が要る | `設計確認待ち` に付け替えて停止 |
| 設計書が無い / 不十分 | 停止。**推測で実装させない** |
| 差し戻しが2往復を超えた | 停止。基準の解釈違いか仕様の曖昧さが原因 |
| スコープ外・破壊的な操作が要る | 停止。設計書に無いことはやらない |
| 同じ失敗を2回繰り返した | 停止。3回目を試す前に状況を記録 |
| 着手できるissueが無い | 停止。**新しい作業を自分で作らない** |

⭐ **この表は初期値。実際に回しながら増やして調整する方針**（2026-08-19・ユーザー合意）。
現行 `CLAUDE.md`「自律スプリント運用」のストップ条件をそのまま引き継いでいる。

## 7. 設計をループに入れるときの注意（開発↔レビューとは難易度が違う）

1. **設計は本質的に対話工程** — dev/review は「issueを読んで作業して報告」で完結するが、
   設計は途中で仕様判断が必ず出る → §3 D3 で回避する
2. **起票者＝承認者になる** — §3 D5 で回避する
3. **リードのコンテキストが溜まる** — 記録の正は issueコメントと `docs/design/` に置いたまま、
   リードは「どのissueがどのラベルか」だけを持つ。サブエージェントの戻り値を要約して次に渡さない
   （思い込みの混入防止という現行ルールがそのまま効く）
