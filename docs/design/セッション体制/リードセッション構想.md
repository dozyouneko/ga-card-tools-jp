## 1. 背景と目的

現行は **ターミナルを2つ**使い分けている:

- `cc-design`（設計セッション）… ユーザーが要件を相談し、設計書を書かせる
- `cc-sprint`（スプリント進行役）… dev / review をサブエージェントとして交互に呼び、実装〜レビューを回す

これを **「ユーザーが会話するのはリードセッション1つだけ」** にまとめたい、というのが本構想。
リードが `design` / `dev` / `review` の3サブエージェントを直接呼び、
`設計 → 開発 → レビュー` のループを1つの窓口で回す。

```text
ユーザー ── リードセッション（唯一の窓口・進行と監視のみ）
                ├─ Agent(design)  … 設計書を作成       ─関所→ 実装待ち
                ├─ Agent(dev)     … 実装・コミット・報告 ─関所→ レビュー待ち
                ├─ Agent(review)  … 操作して合否判定    ─関所→ 設計確認待ち / 実装待ち
                └─ 最終承認はユーザー（push判断も同じ）
```

- ⭐ **サブエージェント同士は直接つながらない。** 成果物は必ずリードを経由する
- ⭐ **どの工程からでも、判断が要ればユーザーへ戻って停止する**（§6）

## 2. 実現性

**技術的には可能で、3工程のうち2つ（dev↔review）は `.claude/agents/sprint.md` に実装済み。**
追加で必要なのは「設計のサブエージェント化」と「窓口の一本化」の2点だけ。

| D5 | ⭐ **最終承認はユーザーが行う。** design サブエージェントに承認させない | 起票者と承認者が同じになり、`設計確認待ち` に溜めて人が見るという安全弁が消える |

## 5. 関所でリードが見るもの（D4の内訳）

| リードが**確認する**（進行確認） | リードが**やらない** |
| --- | --- |
| 工程の記録が**実際に残ったか**（issueコメント・設計書・コミットハッシュ） | コードの**良し悪しを判定する**（review の仕事） |
| ラベルが次の工程へ**付け替わったか** | 自分で**実装する・修正する**（dev の仕事） |
| 指示した範囲から**はみ出していないか** | **仕様を決める**（ユーザーと design の仕事） |
| **ストップ条件に当たっていないか**（§6） | issueコメントを**代筆する** |

- できていなければ**肩代わりせず担当サブエージェントにやり直させる**
- ⚠️ リードが代筆すると、**次の周回でサブエージェントが読む前提が崩れる**
  （現行 `sprint.md` の規約と同じ）

## 6. ストップ条件（点線の経路）

リードは勝手に判断せず、状況をissueに残してから止まる。

| 条件 | リードの動き |
| --- | --- |
| push が必要になった | 停止。本番公開の可否は**常にユーザーの判断** |
| 仕様の判断が要る | `設計確認待ち` に付け替えて停止 |
| 設計書が無い / 不十分 | 停止。**推測で実装させない** |
| 差し戻しが2往復を超えた | 停止。基準の解釈違いか仕様の曖昧さが原因 |
| スコープ外・破壊的な操作が要る | 停止。設計書に無いことはやらない |
| 同じ失敗を2回繰り返した | 停止。3回目を試す前に状況を記録 |
| 着手できるissueが無い | 停止。**新しい作業を自分で作らない** |

⭐ **この表は初期値。実際に回しながら増やして調整する方針**（2026-08-19・ユーザー合意）。
現行 `CLAUDE.md`「自律スプリント運用」のストップ条件をそのまま引き継いでいる。

## 7. 設計をループに入れるときの注意（開発↔レビューとは難易度が違う）

1. **設計は本質的に対話工程** — dev/review は「issueを読んで作業して報告」で完結するが、
   設計は途中で仕様判断が必ず出る → §3 D3 で回避する
2. **起票者＝承認者になる** — §3 D5 で回避する
3. **リードのコンテキストが溜まる** — 記録の正は issueコメントと `docs/design/` に置いたまま、
   リードは「どのissueがどのラベルか」だけを持つ。サブエージェントの戻り値を要約して次に渡さない
   （思い込みの混入防止という現行ルールがそのまま効く）

## 10. 使えるskill / コマンドの調査（2026-08-19）

⚠️ **`/code-review` と `/security-review` は「skill」ではなく実体はコマンド。**
定義形式が違い、**起動条件が違う**ため `lead.md` の書き方に影響する。

| | コマンド | スキル |
| --- | --- | --- |
| 置き場所 | `commands/<name>.md`（ファイル1枚） | `skills/<name>/SKILL.md`（ディレクトリ） |
| frontmatter | `allowed-tools:` / `description:` / `disable-model-invocation:` | `name:` / `description:` |
| 中身 | 手順書（「①〜⑧の順に実行せよ」） | 知識・方針（「こう考えて設計せよ」） |
| 起動 | ⭐ **`/name` で明示的に呼ばないと動かない** | 内容が状況に合致すればモデルが自動で読む |
| 例 | `code-review` / `security-review` | `frontend-design` / `artifact-design` |

⭐ **役割定義に書かないとコマンドは使われない。** スキルは書かなくても効く。

### 10-1. `/code-review`（組み込み）

- 対象: **現在の差分 / ブランチ / パス / PR**。効果レベル `low`〜`max`（無指定は前回値）
- 構造: 8〜10観点の並列候補出し → 1票検証（CONFIRMED / PLAUSIBLE / REFUTED・REFUTEDのみ落とす）
  → 抜け探し（最大8件追加）。**失敗シナリオを書けない指摘は落とす**
- フラグ: `--comment`（PRへ）/ `--fix`（作業ツリーに適用）/ `ultra`（クラウド多エージェント・課金）
- ⚠️ **`--fix` は作業ツリーを変えるので dev 専用。** レビュー担当が使うと
  「レビュー担当はコードを直さない」（CLAUDE.md 役割をまたぐときのルール4）に違反する
- ⚠️ **無指定だと作業ツリーの差分を見る。** この運用は
  **dev がコミットしてから review へ渡す**（同ルール3）ため、**無指定では差分が空になる**。
  → **review担当には対象コミット範囲を明示して渡させる**

### 10-2. `/security-review`（組み込み）

- 対象: **`git diff origin/HEAD...`** ＝ ブランチが origin から進めた分**すべて**
- 読み取り専用（`allowed-tools` が git系 + Read/Glob/Grep/LS/Task に限定。「bashを使うな・書くな」と明示）
- 検査: 入力検証（SQLi・コマンドインジェクション・パストラバーサル等）/ 認証・認可 / 暗号・秘密情報 /
  コード実行（**XSS含む**）/ データ露出。**80%以上の確度で悪用可能なものだけ**
- ⚠️ **除外**: DoS・レート制限・**ハードニング不足全般（＝CSPの緩さは出ない）**・
  **markdownドキュメント内の指摘**・古い依存・理論上のレース
- ⚠️ **「クライアント側JSの権限チェック欠如は脆弱性ではない」という前提**があるため、
  `app.js` / `shared/js/` の差分では**ほぼ何も出ない**。
  ⭐ **価値は `functions/api/`（Discord OAuth・セッション・D1のSQL）と `migrations/` に集中する**
  （バニラJSなので `innerHTML` 系のXSSは対象に入る。React/Angularの除外規定は当たらない）
- ⚠️ **未pushが溜まっていると「タスクの差分」ではなく「未push全部」を見る**
  （2026-08-19時点で236ファイル）。**push前提の運用と相性が悪い点に注意**

### 10-3. マーケットプレイス版 `code-review` プラグイン（別物・導入しない）

同名だが中身が違い、**PR前提（`gh` 必須）**なので main 直接コミットの本リポジトリでは使えない。
⭐ ただし観点の作りは参考になる: **CLAUDE.md準拠チェック / git blame・履歴 / 過去PRのコメント /
コード内コメント**を独立した観点として持つ。
→ **プラグインを入れるのではなく、`lead.md` のレビュー指示に「CLAUDE.md準拠」の観点を1つ足す**
