## 1. 要望（ユーザー・2026-09-04）

> よりユーザーが欲しい情報を見れるように整理する。リストを以下のように改修
> スタンダード使用可 ／ スタンダード禁止（シーズンバンと通常の禁止のサマリー・パンテオン限定やドラフト限定を含めない）／
> パンテオン使用可 ／ パンテオン限定 ／ パンテオン禁止（スタンダード限定やドラフト限定を含めない）／
> ドラフト使用可 ／ ドラフト限定 ／ ドラフト禁止（スタンダード限定やパンテオン限定を含めない）

現状の選択肢は **5種**（#16）:
スタンダード／パンテオン／ドラフトで使用可、スタンダード禁止、パンテオン禁止。

⭐ **要望の核心は「禁止」の中身が混ざっていること。**
いまの「スタンダード禁止」には、**本当に禁止されたカード**と、
**そもそもパンテオン用・ドラフト用でスタンダードには最初から入らないカード**が同居している。

## 2. ⭐ 実測（2026-09-04・スナップショット 2026-08-31 取得・**2,495枚**／一部は公式APIで当日再確認）

⚠️ **公式APIの `legality` は、実際には4つの形しか取らない**:

| `legality` の形 | 枚数 | 意味 |
|---|---|---|
| `null` | **2,346** | どこでも制限なし |
| `{"DRAFT":0,"STANDARD":0}` | **64** | パンテオンでのみ使える＝**パンテオン限定** |
| `{"PANTHEON":0,"STANDARD":0}` | **54** | ドラフトでのみ使える＝**ドラフト限定** |
| `{"STANDARD":0}` | **31** | パンテオン・ドラフトでは使える＝**スタンダードだけ禁止** |

（`{}`＝空オブジェクトも「制限なし」だが、本スナップショットには出現しなかった）

これを要望のリストに当てはめると:

| 要望の項目 | ⭐ **実測の件数** | 備考 |

| **スタンダード禁止**（限定を除く） | **31** | ⚠️ **うち14枚は Boon**（→ §3） |
| パンテオン使用可 | **2,410** | `null` ＋ パンテオン限定64 |
| パンテオン限定 | **64** | |
| **パンテオン禁止**（限定を除く） | ⚠️ ⭐ **0件** | |
| ドラフト使用可 | **2,400** | `null` ＋ ドラフト限定54 |
| ドラフト限定 | **54** | |
| **ドラフト禁止**（限定を除く） | ⚠️ ⭐ **0件** | |

### ⚠️ ⭐ 要望どおりに作ると、選択肢が2つ**常に0件**になる

**「パンテオン禁止（スタンダード限定やドラフト限定を含めない）」と
「ドラフト禁止（スタンダード限定やパンテオン限定を含めない）」は、いまのデータでは定義上0件になる。**
パンテオンで禁止されている54枚は**全部ドラフト限定**、
ドラフトで禁止されている64枚は**全部パンテオン限定**だからである。

⭐ **これは要望が間違っているのではなく、「対称に並べると空欄が2つできる」というだけ**。

## 3. ⚠️ ⭐ 見つかった問題1: Boonカード14枚が「スタンダード禁止」に混ざる

**Boon（`LESSER BOON` / `GREATER BOON`）は61枚あり、パンテオン専用のカード**なのに、
**公式APIの `legality` が2通りに割れている**:

| Boon の `legality` | 枚数 | 分類のされ方 |
|---|---|---|
| `{"DRAFT":0,"STANDARD":0}` | **47** | ✅ パンテオン限定（正しい） |
| `{"STANDARD":0}` | ⚠️ **14** | ❌ **「スタンダード禁止」に落ちる**（ドラフトでは使える扱い） |

⭐ **つまり「スタンダード禁止 31枚」の内訳は Boon 14枚 ＋ 非Boon 17枚**で、
**ユーザーが「含めないでほしい」と言った種類のカードが、規則どおりに作っても14枚残る。**

- ⚠️ **公式APIのデータ不整合なのか、ドラフトでBoonが使えるという意図的な仕様なのかは未確認**
  （公式ルールの裏取りが要る）
- ⭐ **`legality` の形だけで「限定」を判定すると、この14枚は取りこぼす。**
  **`types` に `LESSER BOON` / `GREATER BOON` を含むかも併せて見る**という選択肢がある
  （⚠️ **どちらが正しいかは仕様判断＝設計工程でユーザーに確認する**）

## 4. ⚠️ ⭐ 見つかった問題2: シーズン禁止が公式APIに入っている（**CLAUDE.md の記述と食い違う**）

⭐ **`legality` は `null` ではなくなっている。** `data/seasonal-banlist.json` の
`effectiveFrom` は **2026-08-21** で、**その日以降に公式APIが追随した可能性が高い**。

- ⚠️ ⭐ **ただし「APIがシーズン禁止を取り込んだ」と断定はできない**（**未確認**）。

## 5. ⭐ 実装の見通し（設計工程で確かめること）

### 5-1. #16 が「専用カード絞り込み」を見送った理由は、**弱まっている**

[`フォーマット検索_設計.md`](../16-フォーマット検索/フォーマット検索_設計.md) より:

> 「専用カード」絞り込みは**見送り**（サーバー側で表現不可＝クライアント後処理になり
> ページング件数が不正確化。検索結果の専用バッジ `formatBadgeHtml()` で実用上カバー済み）

⚠️ **「限定」はサーバー側で表現できない**（`legality_format` は1つしか指定できない）ので、
その指摘自体は今も正しい。⭐ **だが 2026-08-06 の #44 以降、
「安定キーで全件取ってからローカルで絞る」は既に本番で動いている確立した手法**である
（数値ソートが `sort=collector_number` で全件取得してローカル処理している）。

### 5-2. ⭐ 「限定」も「禁止」も、**サーバー1回・149件の取得で全部作れる見込み**

⭐ **いま存在する「限定」は パンテオン限定・ドラフト限定の2つだけで、
どちらも `legality.STANDARD.limit === 0` を含む。**
したがって **`legality_format=STANDARD&legality_state=RESTRICTED`（実測 149件）を取れば、
禁止・限定に関する全カテゴリの母集合がそろう**。

- ⚠️ ⭐ **例外は「スタンダード限定」**（パンテオンとドラフトの両方で禁止）で、
  これは STANDARD-RESTRICTED に含まれない。**ただし現在0件**
- ⚠️ **つまり「いまは0件だから成り立つ」設計になる。** ⭐ **将来スタンダード限定のカードが出たら
  黙って漏れる**ので、**そうなったことに気づける経路を設計に含める**
  （＝ `npm run validate` か、件数の突き合わせ注記）。⚠️ **fail-open のまま放置しない**
- ⚠️ **149件という数字はスナップショット時点のもの**。禁止改定で動く

### 5-3. 影響範囲

- ⭐ **選択肢の定数は `shared/js/card-search.js` の `FORMAT_FILTERS` 1箇所**（#16 の設計）
  ＝ **トップとデッキ構築の両方に一括で効く**
- ⚠️ **日本語検索モード（`matchesActiveFilters`）にも同じ意味論を入れる必要がある**（#16 と同じ）
- ⚠️ **既存の共有URL（`#f-format` の値）が壊れないかを見る**。
  現在の値は `"<FORMAT>:<STATE>"` 形式。⭐ **選択肢を作り替えると、
  過去に共有されたURLが無効な値を指しうる**——**無効値のときの挙動を決める**
