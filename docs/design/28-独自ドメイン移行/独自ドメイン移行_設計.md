## 1. 背景 — なぜ独自ドメインが選択肢に上がったか

`#28` の実測で、**Googleの発見経路が2本とも死んでいる**ことが確定している:

| 経路 | 状態 |
|---|---|
| サイトマップ | ❌ 2026-07-23 の送信から**一度も取得されていない**（再送信しても同じ） |
| リンク | ❌ `/cards/` はインデックス済みなのに、そこからリンクする `/sets/rdo/` は「URLが認識されていません」 |

一方、**打てる手はすべて打ち終わっている**:

| 施策 | 状態 |
|---|---|
| 入口の軽量化（#22） | ✅ 完了（114.2 KB / 15リクエスト） |
| 内部リンクの拡充（#37） | ✅ 完了。**`/` → 56セット → カード2,240枚。未リンク0・リンク切れ0で完備**（2026-07-30 全数実測） |
| サーバー側の疑いの排除 | ✅ Googlebot UAで10/10が200・BOM無し・`X-Robots-Tag` 無し・リダイレクト無し・TTFB 83ms |
| 同一ファイルの他社での受理 | ✅ **Bingは即日「成功」・2.7K検出** → sitemap.xml とその配信は無実 |

→ **原因は内部構造の外**にある。残る候補は **(a) 外部からの被リンクが皆無** **(b) `pages.dev` という
ホストそのものの制約** の2つで、本設計は (b) に対処する。

### 1.1 (b) を疑う根拠と、その限界

- **同症状の報告がCloudflare Pagesで多数**あり、解消手段として「独自ドメインを接続する」が挙げられている
  （出典は #28 のコメントに記録）
- ⚠️ **ただし原典はすべてユーザー投稿で、Google公式の確認ではない。因果は断定できない**
- ⭐ **断定できる構造的不利が1つある**: GSCの回避策として一般に挙がる
  **「プロパティをドメイン型に変更する」は DNS の TXTレコードによる所有権確認が必須**で、
  `*.pages.dev` は**DNSを我々が管理していないため原理的に選べない**
- #38 の IndexNow 403（`UserForbiddedToAccessSite`）も、同じ「ドメインの所有権を示せない」制約の
  表れである可能性がある（未検証）→ **独自ドメインは2問題に同時に効く可能性がある**

⚠️ **効果は保証されない。** 本移行は「原因候補を1つ潰し、同時に打てる手を増やす」施策である。
効かなかった場合は (a) 外部被リンクへ移る。

## 2. 前提の裏取り結果（2026-07-30 実測・公式ドキュメント確認）

推測で設計しないため、判断に効く前提はすべて確認した。

| # | 前提 | 結果 | 根拠 |
|---|---|---|---|
| P1 | `_headers` は**ホスト名で条件を書ける** | ⭐ **書ける** | 公式ドキュメントに `https://:project.pages.dev/*` の記法と、`X-Robots-Tag: noindex` を `*.pages.dev` にだけ付ける例が明記されている。「絶対URLは `https` 始まり・ポート指定は不可」 |
| P2 | `_headers` のルール数上限 | **100ブロック**（1行2,000文字） | 現在**5ブロック**。余裕あり |
| P3 | `_redirects` は**ホスト間リダイレクトができる**か | ❌ **できない** | 公式に「Domain-level redirects ❌」と明記。ホスト条件・別ホストへの301は不可 |
| P4 | CSPにホスト名のハードコードがあるか | ⭐ **無い＝変更不要** | `_headers` と各HTMLの `<meta>` CSPはすべて `'self'` と外部API（`api.gatcg.com` 等）のみ。`'self'` は文書のオリジンに追従する |
| P5 | Discord OAuth の `redirect_uri` がホスト固定か | ⭐ **コード変更不要** | `authorize.js:11` と `callback.js:44` が `${url.origin}/api/auth/discord/callback` と**リクエストのOriginから組み立てている** |
| P6 | D1バインディングにホスト依存があるか | **無い** | `wrangler.toml` は `binding`/`database_id` のみ |
| P7 | `sitemap.xml` は何が書くか | `build-card-pages.mjs:788` | `SITE` 定数由来（→ 定数1つで全URLが変わる） |

⚠️ **P5 の落とし穴**: コードは変更不要だが、**Discord Developer Portal の
「Redirects」許可リストに新ドメインのコールバックURLを追加する必要がある**（§5-B2）。
忘れると**ログインが `invalid_redirect_uri` で失敗する**。コードだけ見ていると気づけない。

## 4. ⚠️ 最大のリスク — 旧ホストを早く切ると**Bingの成果を捨てる**

現在 **Bingだけが唯一機能している経路**である（サイトマップ「成功」・2.7K検出）。
これは `pages.dev` に対して積み上がった実績で、**新ドメインには引き継がれない**。

→ ⭐ **旧ホストの `noindex` 化・リダイレクトは、新ドメインが両エンジンに受理されたことを
確認した後にしか行わない。** 順序を誤ると「どこにも載っていない」状態になる。

これを守るため §5 は**3フェーズに分ける**。

## 5. 実施手順

### フェーズA — 新ドメインを並走させる（旧ホストは無傷のまま）

| # | 作業 | 担当 |
|---|---|---|
| A1 | ドメインを取得する。⭐ **Cloudflare Registrar 推奨**（卸値・更新料の上乗せ無し、かつ**ゾーンがCloudflareに載るので §1.1 のDNS TXT確認が可能になる**＝移行の主目的の1つ） | ユーザー |
| A2 | Cloudflare Pages のプロジェクトに **Custom domain を追加**（ダッシュボード） | ユーザー |
| A3 | 新ドメインで `curl -sI` 確認（`/` `/sitemap.xml` `/cards/` `/sets/rdo/` `/BingSiteAuth.xml` `/<key>.txt`）。⚠️ **キャッシュ回避必須**（`-H 'Cache-Control: no-cache'` + `?cb=$RANDOM`） | 設計担当 |
| A4 | §3.1 の定数3+ファイル6を変更 → `build:cards` と `build:tournaments -- --no-scan` を実行 → 生成物込みでコミット | 開発担当 |
| A5 | ⚠️ **`--no-scan` は `data/tournaments/index.json` の `updatedAt` だけを書き換える**ので、その差分はコミットに含めない（`git checkout -- data/tournaments/index.json`） | 開発担当 |
| A6 | push（**本番公開＝ユーザーの明示指示が必要**） | ユーザー判断 |

⚠️ **A4 の時点で、旧ホストで配信されるHTMLの `canonical` は新ドメインを指す。**
これは意図的（正規化を新ドメインへ寄せる）だが、**旧ホストのBing実績は徐々に新ドメインへ移る**。
`noindex` は付けないので、移行に失敗しても旧ホストは検索対象のまま残る。

### フェーズB — 新ドメインを各サービスに登録

| # | 作業 | 担当 | ⚠️ |
|---|---|---|---|
| B1 | **GSC**: 新ドメインを ⭐ **「ドメイン」プロパティ**で追加（DNS TXT確認）→ サイトマップ送信 | ユーザー | **これが本移行の主目的**。`pages.dev` では選べなかった経路 |
| B2 | ⭐ **Discord Developer Portal** → OAuth2 → Redirects に `https://<新ドメイン>/api/auth/discord/callback` を**追加**（旧も残す） | ユーザー | 忘れると**デッキ構築のログインが壊れる**（P5） |
| B3 | **BWT**: 新ドメインをサイト追加 → `BingSiteAuth.xml` で所有権確認 → サイトマップ送信 | ユーザー | ファイルは既に配信済み（§3.3） |
| B4 | **IndexNow**: 新ドメインでキーファイルが200を返すことを確認 → cronの通知が通るか確認 | 設計担当 | ⭐ **403が解消すれば §1.1 の仮説が裏付けられる**（#38 の判定材料） |
| B5 | 新ドメインで**実ログインしてデッキ構築の絞り込み・保存**を確認 | ユーザー | B2の検証 |

### フェーズC — 旧ホストを畳む（⚠️ **B1・B3が「成功」になってから**）

`_redirects` ではホスト間リダイレクトができない（P3）ため、選択肢は2つ。

#### 案C-1: `_headers` で `*.pages.dev` にだけ `noindex`（⭐ 推奨）

```
https://:project.pages.dev/*
  X-Robots-Tag: noindex

https://:version.:project.pages.dev/*
  X-Robots-Tag: noindex
```

- ✅ **公式ドキュメントに載っている記法**（P1）。コード追加ゼロ・ルール2ブロック増（上限100に対し7）
- ✅ プレビューデプロイ（`<version>.<project>.pages.dev`）も同時に塞げる
- ⚠️ `noindex` と「別ホストを指す `canonical`」は**Googleにとって矛盾した指示**になり得る。
  → **`canonical` を打ち消す恐れがあるため、C-1を入れる前に新ドメインがインデックス済みであることを確認する**
- ⚠️ **旧URLの被リンク（もしあれば）の評価は新ドメインへ渡らない**（301と違い転送されない）

#### 案C-2: `functions/_middleware.js` で Host を見て 301

- ✅ 正規化としては教科書的に正しい（重複解消・シグナル統合）
- ❌ **全リクエストがWorkerを通る**（静的アセットも）。レイテンシとコストが増える
- ❌ `/api/*` も301すると **Discord OAuthのコールバックが壊れる**（除外設計が必要＝複雑）
- ❌ `pages.dev` を使ったローカル/プレビュー確認ができなくなる

**→ C-1 を推奨。** 被リンクが現状ほぼ皆無（§1 の (a)）なので、301で救う評価が無く、C-2 の代償だけが残る。
⚠️ **ただし B3 でBingの実績が新ドメインに移り切る前にC-1を入れると、Bingの2.7Kを失う**（§4）。

## 6. ロールバック手順

| フェーズ | 戻し方 |
|---|---|
| A | `git revert <移行コミット>` → `build:cards` / `build:tournaments --no-scan` を再実行して生成物を旧ホストに戻す。**Custom domain は消さない**（並走のままで害が無い） |
| B | GSC/BWTのプロパティを削除するだけ（サイトに影響しない） |
| C | `_headers` の2ブロックを削除して push。⚠️ **`noindex` は再クロールされるまで解除が反映されない**（数日かかり得る）＝ **Cが最も戻しにくい。だから最後に、確認後にやる** |

⚠️ [[rollback-ready-release]] の方針に従い、**Aの revert は別ワークツリーで実際に適用して確かめる**
（生成物2,740ファイルの revert が正しく戻るかは、手順書だけでは信用しない）。
